# 3.1 杀死一只单例

SINGLETON 模式简单得异乎寻常。
它的意图是：

> 确保一个类只有一个实例，并提供一个访问它的全局点。

它还很灵活。
在文件系统设计里，SINGLETON 帮我们封装了 `User` 对象的创建，`User` 对象赋予文件系统用户访问自家文件的权限，别家的文件一概碰不到。
客户端程序要取得一个 `User` 对象，调用的是静态的 `User::logIn` 操作：

```cpp
static const User* User::logIn(
    const string& loginName, const string& password
);
```

你大概还记得，这不过是 SINGLETON 那个静态 `Instance` 操作的花哨改装版。
在模式的原味实现里，`Instance` 把你严格限制在 Singleton 类（此处即 `User` 类）的**一个**实例上。
但模式的一个效果是：你可以**控制**实例的数目，而不是一刀切地禁止多于一个。
我们用的正是这个选项——禁止每个用户拥有多于一个 `User` 实例。
这样一来，只要应用要同时伺候多个用户，它就可以自由地创建多个实例。

我另外还提到一点：模式在 "销毁" 这件事上沉默得震耳欲聋。
Singleton 实例由谁销毁？
怎么销毁？
什么时候销毁？
"删除" 和 "析构" 这两个词在模式里从未出现过。
是诚实的疏忽？
是刻意的省略？
还是干脆在躲一个难题？
我希望能说服你：后两者都不是。
我们还会看到一批关于这个小模式的种种新观察——它可真是丰富得出人意料。

<p align="center">❖ ❖ ❖</p>

任何有自尊的类都该定义析构函数，Singleton 类也不例外。
如果 Singleton 要被继承，析构函数就该声明为虚函数。
这些全是 C++ 入门课的内容。
棘手的地方这才来：这个析构函数该是 public、private，还是 protected？

"这有什么可纠结的？" 你也许会问， "设成 public，接着往下写就是了。"
这种说法的言外之意是：单例的销毁是**显式的**——也就是说，销毁是客户端的责任。

但这话有个站得住脚的反驳。
SINGLETON 模式把对象的**创建**责任整个儿压在 Singleton 类身上。
客户端到这个类来取一个 Singleton 实例。
倘若客户端把实例删掉，而 Singleton 类毫不知情，那么从那一刻起，这个类发出的全是 "悬垂引用"，指向一个早已不存在的对象。
Singleton 的职责意味着它**拥有**自己创建的那个实例；而拥有，归根到底就意味着负责销毁。
这一点与 ABSTRACT FACTORY、FACTORY METHOD 等其他创建型模式不同——那些模式并不保留所创建实例的所有权。

话虽如此，只要下面两条成立，public 析构函数也不是不能用：

1. 析构函数删除实例，并清理它自己指向那个静态实例的引用。
这样后续调用 `Instance` 操作时，一切都能像第一次那样正常工作。
2. 客户端不保留指向 Singleton 对象的引用。
否则它们手里剩下的就是悬垂引用。

这两条限制足够苛刻，足以让显式销毁成为例外而非惯例。

举例来说，在我们的文件系统设计里，必须考虑 `User` 对象怎样销毁、何时销毁。
假设我们让客户端用普通的 `delete` 运算符显式删除 `User` 对象。
我们甚至可以更显式一些，提供一个静态 `logOut` 操作，与 `logIn` 对称（无所谓了，销毁接口其实无关紧要）。
然而目前 `User` 类没法知道哪些客户端持有指向 `User` 对象的引用。
所以一旦某个 `User` 被删掉，客户端手里可能就落下悬垂引用——这完全不能接受。

我们大概确实需要一套让用户注销的机制，比如用来记账，但悬垂引用的隐患使销毁没资格充当注销机制。
换句话说，别把 "注销" 和 "删除 `User` 对象" 混为一谈。
无论我们为注销用户选哪种接口，它都不能涉及显式销毁 `User` 对象。

我讲这些，是为了说明为什么该否决 public 析构函数。
否决**private** 析构函数要容易得多——前提是我们想允许 Singleton 类被继承。
在我们的文件系统例子里，这个前提恰好不成立；但一般而言，你确实会希望允许 Singleton 的子类。
那就只剩一个选择——protected 析构函数。

现在回到原点：单例到底怎么被删掉？

Singleton 对象通常是（即便不是天生就是）长寿的。
它们往往与程序同寿。
删除它们，与其说是为了回收空间，不如说是为了有序地谢幕。
你要关文件、解锁资源、断开网络连接等等，而且不能让外界看着像突然终止（也就是 "崩溃"）。
如果你的 Singleton 对象确实需要做这类清理，它们多半得等到程序即将终止前的那一刻。
这是个好性质，因为这意味着 C++ 也许能替我们**隐式**完成销毁。

C++ 在程序终止时自动删除静态对象。
语言保证它们的析构函数会被调用、空间会被回收，尽管不保证调用顺序。
眼下我们不妨假设顺序无关紧要：程序里只有一个单例，或者即便有好几个，它们的销毁也不依赖顺序。
这意味着我们可以这样定义 Singleton 类：

```cpp
class Singleton {
public:
    static Singleton* instance();

protected:
    Singleton();
    Singleton(const Singleton&);

    friend class SingletonDestroyer;
    virtual ~Singleton() { }

private:
    static Singleton* _instance;
    static SingletonDestroyer _destroyer;
};

Singleton* Singleton::_instance = 0;
SingletonDestroyer Singleton::_destroyer;

Singleton* Singleton::instance () {
    if (!_instance) {
        _instance = new Singleton;
        _destroyer.setSingleton(_instance);
    }
    return _instance;
}
```

`SingletonDestroyer` 是个类，它唯一的目的就是销毁某个特定的 Singleton 对象：

```cpp
class SingletonDestroyer {
public:
    SingletonDestroyer(Singleton* = 0);
    ~SingletonDestroyer();

    void setSingleton(Singleton* s);
    Singleton* getSingleton();

private:
    Singleton* _singleton;
};

SingletonDestroyer::SingletonDestroyer (Singleton* s) {
    _singleton = s;
}

SingletonDestroyer::~SingletonDestroyer () {
    delete _singleton;
}

void SingletonDestroyer::setSingleton (Singleton* s) {
    _singleton = s;
}

Singleton* SingletonDestroyer::getSingleton () {
    return _singleton;
}
```

Singleton 类声明了一个静态的 `SingletonDestroyer` 成员，它在程序启动时自动创建。
等到用户第一次调用 `Singleton::instance` 时，不但 Singleton 对象会被创建出来，`instance` 还会把这个对象交给那个静态的 `SingletonDestroyer` 对象——所有权就此移交给 `SingletonDestroyer`。
程序退出时，`SingletonDestroyer` 神奇地自动销毁，Singleton 对象也随之而去。
单例的销毁如今是隐式的了。

简单——差不多吧。
注意 Singleton 类声明里的那个 `friend`。
它的用处是让销毁器有权限访问 Singleton 的 protected 析构函数。
如果你讨厌 `friend` 关键字，这写法不好看；但鉴于前面那些反对 public 析构函数的理由，它是必需的。
它同时也示范了 `friend` 或许最站得住脚的一种用法——用来另设一级保护，而不是给糟糕的设计打补丁。

为了尽量复用，尤其是当你的程序里有好几种单例时，你也许可以少敲些字，定义一个模板化的 `Destroyer` 类：¹

¹：关注标准制定进程的人会认出，这就是标准库里的 `auto_ptr` 类模板，它即将驾临你身边的某个编程环境。

```cpp
template <class DOOMED>
class Destroyer {
public:
    Destroyer(DOOMED* = 0);
    ~Destroyer();

    void setDoomed(DOOMED*);
    DOOMED* getDoomed();

private:
    // 防止用户复制 Destroyer，以免重复删除：
    Destroyer(const Destroyer<DOOMED>&);
    void operator=(const Destroyer<DOOMED>&);

private:
    DOOMED* _doomed;
};

template <class DOOMED>
Destroyer<DOOMED>::Destroyer (DOOMED* d) {
    _doomed = d;
}

template <class DOOMED>
Destroyer<DOOMED>::~Destroyer () {
    delete _doomed;
}

template <class DOOMED>
void Destroyer<DOOMED>::setDoomed (DOOMED* d) {
    _doomed = d;
}

template <class DOOMED>
DOOMED* Destroyer<DOOMED>::getDoomed () {
    return _doomed;
}
```

这样我们就可以这样定义 Singleton：

```cpp
class Singleton {
public:
    static Singleton* instance();

protected:
    Singleton();
    Singleton(const Singleton&);

    friend class Destroyer<Singleton>;
    virtual ~Singleton() { }

private:
    static Destroyer<Singleton> _destroyer;
};

Destroyer<Singleton> Singleton::_destroyer;

Singleton* Singleton::instance () {
    if (!_instance) {
        _instance = new Singleton;
        _destroyer.setDoomed(_instance);
    }
    return _instance;
}
```

> 译注：这一版清单漏掉了 `static Singleton* _instance;` 的声明（前面第一版清单里有），但下文 `instance` 仍在给 `_instance` 赋值。照抄会编译不过，读时请自行补上。

隐式销毁有两个潜在问题。
第一，如果你需要在程序结束**之前**删掉单例，它帮不上忙。
那种情形下，很难想象有什么办法不需要显式销毁。
再者，你要么得加上某种机制（比如引用计数）把悬垂引用问题压到最小，要么得强迫客户端只通过 `Singleton::instance` 操作来访问 Singleton 实例。

要做到后者，办法之一是：(1) 让 `instance` 返回 Singleton 的引用；(2) 把赋值运算符和复制构造函数声明为 private，从而禁止复制与初始化：

```cpp
class Singleton {
public:
    static Singleton& instance();

protected:
    // ...

private:
    Singleton(const Singleton&);
    Singleton& operator=(const Singleton&);
    // ...
};
```

遗憾的是，这个办法并非万无一失：客户端随时可以取 `instance` 返回值的地址，也可以把这一层层设防整个儿强转掉。
不过这个问题不太可能成为拦路虎。
如我先前所说，SINGLETON 模式偏爱长寿对象，所以显式销毁大概不会是个常见问题。

第二个问题更棘手，它出现在你的程序里存在多个 Singleton 对象、且它们彼此依赖的时候。
那种情况下，销毁顺序可能大有讲究。

回想我们的文件系统设计——SINGLETON 模式我们用了两次。
第一次用来控制 `User` 对象的数目，于是有了单例的 `User` 类。
第二次的应用保证只有一个 `Grouping` 对象，它定义了用户与其所属组之间的映射。
`Grouping` 对象让我们可以针对用户**组**、而非仅针对个人来定义保护。
因为同时存在多个生效的组映射既不合理（事实上相当危险），我们把 `Grouping` 类做成了 Singleton。

`Grouping` 对象同时持有指向 `User` 对象和 `Group` 对象的引用。
它不拥有那些 `User` 对象，但可以设想它拥有那些 `Group` 对象。
无论如何，在我看来，最好在 `User` 对象**之前**先删掉 `Grouping` 对象——我这个死硬的个人主义者就是这么想的。
诚然，否则会产生的悬垂引用大概不会造成麻烦，因为 `Grouping` 在销毁过程中本不该解引用其中的任何一个。
可话说回来，谁说得准呢。

我的意思很简单：销毁器这套做法建立在语言实现中未作规定的机制之上，一旦销毁顺序要紧，它就开始散架了。
如果你的应用需要多个相互依赖的单例，那你可能就得退回到显式销毁。
有一件事是肯定的：如果各个 Singleton 的析构函数互相依赖，你就不能用多于一个销毁器。

另一条路是干脆放弃销毁器，改用标准草案里的 `atexit()` 函数，这是 Tim Peierls 向我建议的 [Peierls96](../biblio.md#peierls96)：

> 我坚持认为，在 C++ 里，当你确实想要与程序同寿、不可替换的单一实例时，`atexit()` 是清理单例的好办法。
> 标准草案许下了一大堆承诺：
> <br/><br/>
> §3.6.3 第 1 段：来自 `<cstdlib>` 的函数 `atexit()` 可用来指定一个在退出时被调用的函数。
> 如果 `atexit()` 将被调用，则在 `atexit()` 调用中指定的函数被调用之前，实现不得销毁在 `atexit()` 调用之前初始化的对象。

据我看，这套东西唯一可能失灵的情形是：某个静态初始化的对象，其析构函数依赖某个 Singleton 实例，
而它又是在该 Singleton 实例构造之后才被初始化——也就是说，它是由另一处静态初始化带出来的。
这提示我们：带有静态实例的类在销毁期间应当避免依赖单例。
（或者至少应当让这类类有办法在销毁期间查一探 Singleton 是否存在。）

即便这条路免掉了销毁器，真正的问题——删除相互依赖的单例——依然在。
谁来上垃圾回收？

<p align="center">❖ ❖ ❖</p>

很久很久以前，在一个遥远的星系里，Scott Meyers 提出了如下方案 [Meyers95](../biblio.md#meyers95)：

> 我[这版 SINGLETON]和你的很像，但我不用类静态成员让 `instance` 返回指针，而是用函数内的静态变量并返回引用：
>
> ```cpp
> Singleton& Singleton::instance () {
> static Singleton s;
> return s;
> }
> ```
>
> 这似乎具备你那套方案的全部好处（从不使用时就不构造、不依赖编译单元之间的初始化顺序等等），而且还让用户可以享用对象语法而不是指针语法。
> 此外，我这套方案让调用者因为误以为要防内存泄漏而顺手把单例删掉的可能性小得多。
> <br/><br/>
> 我是不是漏掉了什么理由，非得返回指向类静态成员的指针、而不是指向函数静态变量的引用？

我在这里能看到的唯一缺点是：函数静态变量使 Singleton 难以通过继承来扩展，因为 `instance` 总是创建 `Singleton` 类型的对象。
（关于扩展 Singleton 类的更多内容，见《Design Patterns》第 130 页开始的讨论。）
无论如何，只要析构函数不是 public，就不必操心删除 Singleton 实例。
后来我确实渐渐偏向返回引用，但归根结底，这似乎没多大差别——我指的是在单线程应用里。

后来，Erich Gamma 注意到 Scott 的方案有个更根本的难处 [Gamma95](../biblio.md#gamma95)：

> 事实证明，如果多个线程都可能调用 `instance`，[Scott 的做法]就没法做成线程安全的。
> 问题在于[某些 C++ 编译器]生成的内部数据结构无法用锁保护。
> 这种情况下你只好在调用点加锁——相当难看。

没错。
而没过多久，Doug Schmidt 就被一个相关、也更根本的缺陷咬了一口 [Schmidt96b](../biblio.md#schmidt96b)：

> [Double-Checked Locking] 模式 [SH98](../biblio.md#sh98) 是在我校对 John Vlissides 1996 年 4 月那期 Pattern Hatching 专栏时浮现出来的。
> 在那期专栏里，John 在多用户文件系统的保护这一语境下谈 SINGLETON。
> 讽刺的是，我们最近正好在多处理器上跑多线程版 ACE 时遇到了一些莫名其妙的内存泄漏问题。
> <br/><br/>
> 读 John 那篇专栏时，我突然想到：问题正是竞态条件导致 Singleton 被多次初始化造成的。
> 一旦看清这两个问题之间的联系，再把关键的作用力算进去（例如单例的日常使用不该有加锁开销），解法就自己蹦出来了。

大约一个月后，Doug 给我发来一封后续邮件 [Schmidt96c](../biblio.md#schmidt96c)：

> 我的一个研究生（Tim Harrison）最近实现了一个名为 `Singleton` 的 C++ 库类，它基本上就是把现有的类改造成 "Singleton"。
> 我们现在就在 ACE 里用它，它算是 "半有用" 吧。
> 它的好处是自动实现了 [Double-Checked locking 模式]，还让 LOCK 策略容易参数化。
> 我把它附在下面，纯属好玩。
>
> ```cpp
> template <class TYPE, class LOCK>
> class Singleton {
> public:
>    static TYPE* instance();
> 
> protected:
>    static TYPE* _instance;
>    static LOCK _lock;
> };
>
> template <class TYPE, class LOCK>
> TYPE* Singleton<TYPE, LOCK>::instance () {
>     // 执行 Double-Check 模式……
>     if (_instance == 0) {
>         Guard<LOCK> monitor(_lock);
>         if (_instance == 0) _instance = new TYPE;
>     }
>     return _instance;
> }
> ```

我很好奇，尤其是 "半有用" 那部分。
我问他，是不是因为这个做法并不能真正阻止创建基类型的多个对象（想必那个类型在别处是作为非单例定义的）。
他的回答既让人开眼，又有点让人不安 [Schmidt96d](../biblio.md#schmidt96d)：

> 对，正是如此。
> 另一个问题是，很多 C++ 编译器（例如 g++）不实现模板里的静态数据成员。
> 这种情况下，你得这样实现静态 `instance` 方法：
>
> ```cpp
> template <class TYPE, class LOCK>
> TYPE* Singleton<TYPE, LOCK>::instance () {
> static TYPE* _instance = 0;
> static LOCK _lock;
>
> if (_instance == 0)
> // ...
>
> return _instance;
> }
> ```
>
> 啊，跨平台 C++ 可移植性的乐趣！;-)

这一下又点亮了我几个休眠的神经元。
我回信说：如果你真想让某个类天生就是 Singleton，可以让它从这个模板继承，把子类作为模板参数传进去（又是 Cope 那个奇妙的循环模板模式 [Coplien95](../biblio.md#coplien95)——我很喜欢它！）。
例如：

```cpp
class User : public Singleton<User, Mutex> { ... }
```

这样你就能保住 Singleton 的语义，而不必把模式连同它那套多线程的 "血腥" 细节重抄一遍。

> 译注：原文此处写作 "in all its multithreaded gory (sic)"， "gory" （血腥的）应是 "glory" （荣光）之误，作者自己标了 *(sic)* 表示 "原文如此"。

*提醒*：这个变体我自己没试过，也没机会用上。
我只是觉得它漂亮，无论从美学上看，还是从我们抵达它的路径上看。
我以前觉得 SINGLETON 是我们那些模式里比较琐碎的一个，简直不配和 COMPOSITE、VISITOR 之类称兄道弟；也许正是这种态度，解释了它在某些问题上的沉默。
老天，我错得离谱。
