# 3.6 多谢内存泄漏

好吧，我把 `cursor()` 的实现称作这个设计的 "最后一笔"，那是撒了谎。
如果我们在一种带垃圾回收的语言里实现这个做法，我说的倒会是实话。
可在 C++ 的语境里，我把删除 `cursor()` 所创建的那个游标的责任推给了客户端——于是内存泄漏的机会大大的有。
返回 `Cursor*` 而不是 `Cursor&`，也使得我们把堆分配的游标传给 `first`、`more` 这类操作时，得多写些难看的解引用。

用上 Dijkstra 的万灵药——增加一层间接——就能同时绕开这两个问题。
具体地说，我们来实现 Cope 的 Handle-Body 惯用法的一个变体 [Coplien92](../biblio.md#coplien92)。
我们不让 `Cursor` 充当那个抽象 Memento 基类，而是定义一个 "body" 类 `CursorImp` 来顶替它：

```cpp
class CursorImp {
public:
    virtual ~CursorImp () { }
    void ref ()  { ++_count; }
    void unref () { if (--_count == 0) delete this; }

protected:
    CursorImp () { _count = 0; }
    CursorImp (const Cursor&);

private:
    int _count;
};
```

和 Handle-Body 惯用法里大多数 "body" 一样，`CursorImp` 对象是带引用计数的。
`CursorImp` 的具体子类就是 ConcreteMemento；也就是说，它们定义了享有特权的接口。
于是我们那个 `ListCursor` 例子变成了

```cpp
class ListCursorImp : public CursorImp {
public:
    ListCursorImp () { _current = 0; }

    ListElem* getCurrent () const { return _current; }
    void setCurrent (ListElem* e) { _current = e; }
    // 与之前相同的特权操作

private:
    ListElem* _current;
};
```

接下来是这个做法与原方案的关键差别：客户端并不直接和 `CursorImp` 对象打交道。
我们改为引入一个具体的 `Cursor` 类，让它充当 `CursorImp` 这个 body 的 "handle"：

```cpp
class Cursor {
public:
    Cursor (CursorImp* i) { _imp = i; _imp->ref(); }

    Cursor (Cursor& c) {
        _imp = c.imp();
        _imp->ref();
    }

    ~Cursor ()            { _imp->unref(); }
    CursorImp* imp ()     { return _imp; }

private:
    static void* operator new (size_t)  { return 0; }
    static void operator delete (void *) { }

    Cursor& operator = (Cursor& c)      { return c; }
    // 为求简单、并防止常见的失误，
    // 禁止堆分配与赋值

private:
    CursorImp* _imp;
};
```

作为 handle，`Cursor` 聚合了一个 `CursorImp` 子类的实例。
`Cursor` 还负责照看这个实例的引用计数是否正确。
Originator 用这些类返回一个看上去纯属栈分配的 `Cursor` 对象：

```cpp
class Structure {
public:
    // ...

    virtual Cursor cursor () {
        return Cursor(new ListCursorImp);
    }
    // ...
};
```

`cursor()` 返回的是一个 `Cursor`，而不是指向它的引用，从而确保客户端会去调用复制构造函数：

```cpp
Structure s;
Cursor c = s.cursor();  // 对第 105 页原示例的唯一改动

for (s.first(c); s.more(c); s.next(c)) {
    Element e = s.element(c);
    // 使用 Element e
}
```

注意这里不必再去解引用 `c`——而在原先那个返回指针的 `cursor()` 版本里是必须的。

我们需要的其他改动，只在于那段做动态转换、以取回 ConcreteMemento 的代码：

```cpp
class Structure {
    // ...

    virtual void first (Cursor& c) {
        ListCursorImp* imp;

        if (imp = dynamic_cast<ListCursorImp*>(c.imp())) {
            imp->setCurrent(_head);
        }
    }
    // ...
};
```

当然，对 Memento 的实现者来说，这比不带引用计数的版本稍微复杂一点。
但它让基于类型洗白的版本对客户端来说，用起来和基于 `friend` 的版本一样轻松——而后者本身也有自己那套实现上的曲折。

话虽如此，我倒从来不怎么热衷于倒垃圾。;-)

Michael McCosker 来信说 [McCosker97](../biblio.md#mccosker97)：

> 你提到用纯虚析构函数来迫使子类定义自己的析构函数。
> 按我对 C++ 的理解，*所有*析构函数都会被调用。
> 在我工作的环境（PC 上的 Win32）里，到地址零去调用析构函数会引发页面出错。
> 这是该环境独有的问题，还是说人们压根儿就不该用纯虚析构函数？

我在 C++ 里让一个类变成抽象类的首选做法，是把构造函数设为 protected，而不是把至少一个成员函数设为纯虚。
类型洗白的例子，在某种程度上就是为了展示我这个偏好的好处。
这里再把那个类列一遍：

```cpp
class Cursor {
public:
    virtual ~Cursor () { }

protected:
    Cursor();
    Cursor(const Cursor&);
};
```

另一个让 `Cursor` 变成抽象类的办法，是把析构函数设为纯虚。
可 "纯虚析构函数" 到底是什么意思？
析构函数本身并不被继承；它们全都会依次被调用。
因此，纯虚析构函数必须被定义。
这做得到吗？

那还用说。
看看 C++ 标准草案里的这段话 [ASC96](../biblio.md#asc96)：

> §10.4 第 2 段：纯虚函数只在以*限定标识符*（qualified-id）语法被显式调用时才需要定义。
> ……注意：一个函数声明不能同时提供*纯虚指示符*和定义。

由于纯虚析构函数在销毁过程中确实会被显式调用，这一节意味着它*必须*被定义——不是在声明里，而是在一个单独的定义里：

```cpp
class Cursor {
public:
    virtual ~Cursor () = 0;
};

Cursor::~Cursor () { }
```

我看这两种做法归根到底也没多大差别。
一种是你得把每个构造函数都设为 protected；另一种是你得定义一个纯虚析构函数。
反正*总得有点什么事*。
