# 2.2 孤儿、收养与替身

现在让我们再深入一点，看看 COMPOSITE 在这个应用里的含义。
我们要考察 `Node` 类接口设计中的一项重要权衡，然后再试着给这个雏形设计添点新功能。

我们已经用 COMPOSITE 搭起了这个应用的骨架。
它向我们展示了如何用面向对象的说法，表达层次化文件系统的根本特征。
该模式通过继承与组合，把它的关键参与者——Component、Composite 和 Leaf 三个类——关联起来，从而支持任意大小、任意复杂度的文件系统结构。
它也让客户端能一视同仁地对待文件、目录，以及里面可能出现的别的什么东西。

如你所见，一视同仁的关键在于文件系统各对象之间有一个公共接口。
到目前为止，设计里有三个类：`Node`、`File` 和 `Directory`。
我已经解释过，那些对文件和目录都有明确意义的操作，需要声明在 `Node` 基类里。
读取和设置节点名字、保护权限的操作就属于这一类。
我也解释了为什么要把访问子节点的操作（`getChild`）放进公共接口，尽管乍看之下它对 `File` 对象并不合适。
现在我们要考虑另一些操作，它们 "公共" 得更加不明显。

<p align="center">❖ ❖ ❖</p>

冒着像个早熟的五岁小孩的风险，我得问一句：子节点到底是从哪儿来的？
（我想，放在任何语境下这都是个合理的问题。）
在我们指望一个 `Directory` 对象能枚举它的子节点之前，它总得先以某种方式得到子节点。
可从哪儿得到呢？

显然不是从它自己。
目录不可能负责创造它今后可能容纳的每一个子节点——文件系统的用户掌控着这类事。
合理的期待是：文件系统的客户端创建文件和目录，然后把它们放到想放的地方。
这意味着 `Directory` 对象（尤其是它）会*收养*子节点，而不是创建子节点。
因此 `Directory` 需要一个收养子节点的接口。差不多像这样就行：

```cpp
virtual void adopt(Node* child);
```

当客户端对一个目录调用 `adopt` 时，它是在明确地把对给定子节点的责任移交给这个目录。
责任意味着所有权：目录被删除时，子节点也随之被删除。
这正是 `Directory` 与 `Node` 两个类之间聚合关系（即 [图 2.1](1.md#fig-2-1) 中那个菱形）的要义。

那么，既然客户端能叫一个目录承担起对某个子节点的责任，那反过来的、*放弃*这份责任的调用也就顺理成章了。于是：

```cpp
virtual void orphan(Node* child);
```

这里的 "orphan" 并不意味着父目录会死掉……呃，会被删除。
它只是说，这个目录不再是该子节点的父节点了。
子节点也还活着，也许很快会被别的节点收养，也许就要……被删除。

<p align="center">❖ ❖ ❖</p>

那这跟一视同仁有什么关系？
为什么我们不能只在 `Directory` 上定义这些操作、别处一概不定义？

好吧，假定我们就那么干。
现在考虑客户端如何实现改动文件系统结构的操作。
这类客户端的一个例子，是创建新目录的用户级命令。
这个命令的用户界面无关紧要；我们就假定它是个命令行界面，跟 UNIX 的 `mkdir` 命令一样。
`mkdir` 把待建目录的名字当作参数，像这样：

```shell
mkdir newsubdir
```

其实用户还可以在名字前面接上任何合法的路径：

```shell
mkdir subdirA/subdirB/newsubdir
```

只要 `subdirA` 和 `subdirB` 存在、并且是目录而不是文件，这就该管用。
更一般地说，`subdirA` 和 `subdirB` 应当是能够拥有子节点的 `Node` 子类的实例。
如果不是这样，用户就该收到一条错误消息。

`mkdir` 怎么实现？
首先，假定 `mkdir` 能弄清楚当前目录是哪个；也就是说，它能取得一个引用，指向与用户所选当前目录相对应的 `Directory` 对象。¹
往当前目录里加一个新目录，不过就是创建一个新的 `Directory` 实例，然后对当前目录调用 `adopt`，把新目录作为参数传进去：

```cpp
Directory* current;
// ...
current->adopt(new Directory("newsubdir"));
```

¹：客户端可以从某个众所周知的地方取得当前目录对象，比如 `Node` 类上的一个静态操作。访问众所周知的资源，是 SINGLETON 设计模式的活儿。我们后面会看到它的实战。

简单。可是，如果 `mkdir` 拿到的是一个不简单的路径，一般情形又该怎么办？

这里就开始棘手了。`mkdir` 必须：

1. 找到 `subdirA` 对象（若不存在则报错）。
2. 找到 `subdirB` 对象（若不存在则报错）。
3. 让 `subdirB` 对象收养 `newsubdir` 对象。

第 1、2 步都要遍历当前目录的子节点、以及 `subdirA` 的子节点（如果它存在），去找一个代表 `subdirB` 的节点。

`mkdir` 实现的核心，可能就是一个以路径为参数的递归函数：

```cpp
void Client::mkdir (
    Directory* current, const string& path
) {
    string subpath = subpath(path);

    if (subpath.empty()) {
        current->adopt(new Directory(path));

    } else {
        string name = head(path);
        Node* child = find(name, current);

        if (child) {
            mkdir(child, subpath);
        } else {
            cerr << name << " nonexistent." << endl;
        }
    }
}
```

其中 `head` 和 `subpath` 是字符串处理例程。`head` 返回路径里的头一个名字；`subpath` 返回其余部分。
`find` 操作则在一个目录里查找指定名字的子节点：

```cpp
Node* Client::find (
    const string& name, Directory* current
) {
    Node* child = 0;

    for (int i = 0; child = current->getChild(i); ++i) {
        if (name == child->getName()) {
            return child;
        }
    }
    return 0;
}
```

注意 `find` 必须返回 `Node*`，因为 `getChild` 返回的就是这个。
这没什么不合理的，因为一个子节点既可能是目录，也可能是文件。
但如果你一直在留心，就会发现这个小细节实际上把 `Client::mkdir` 给弄沉了——它根本编译不过。

再看一眼那个对 `mkdir` 的递归调用：传给它的类型是 `Node*`，而它需要的是 `Directory*`。
问题在于：当我们一路往下遍历层次结构时，分不清某个子节点是文件还是目录。
一般说来这是件好事——只要客户端不在乎这个区别。
但在这个例子里，我们好像还真在乎，因为只有 `Directory` 定义了收养与弃养子节点的接口。

可是我们*真的*在乎吗？更切题地说，客户端（`mkdir` 命令）需要在乎吗？
其实不必。它的职责不过是：要么创建一个新目录，要么向用户报告失败。
那么，姑且——只是姑且——假定我们对各个 `Node` 类一视同仁地对待 `adopt` 和 `orphan`。

我知道，我知道。你在想："天哪！这些操作对 `File` 这样的叶组件毫无意义。"
可这个假设有多站得住脚？
万一将来有人在路上定义了新的一种叶组件，比如一个垃圾桶（说得更准确些，回收站），它会把收养来的东西统统消灭掉呢？
万一收养进一个叶节点意味着 "产生一条错误消息" 呢？
要证明 `adopt` 对叶节点绝无意义，是很难的。`orphan` 也一样。

换个角度，也许可以论证：压根就不需要把 `File` 和 `Directory` 分成两个类——*一切*都该是 `Directory`。
但实现上的问题会给出相反的答案。
`Directory` 对象往往拖着一堆大多数文件都用不着的包袱：用来存放子节点的数据结构、为提升性能而缓存子节点信息，诸如此类。
经验表明，在许多应用里，叶节点往往比内部节点多得多。
这也是 COMPOSITE 规定要分出 Leaf 和 Composite 两个类的原因之一。

下面看看：如果我们把 `adopt` 和 `orphan` 定义在*所有* `Node` 上，而不是只定义在 `Directory` 类上，会怎样。
我们让这些操作默认产生错误消息：

```cpp
virtual void Node::adopt (Node*) {
    cerr << getName() << " is not a directory." << endl;
}

virtual void Node::orphan (Node* child) {
    cerr << child->getName() << " not found." << endl;
}
```

这些未必是最好的错误消息，但意思到了。
换个做法，这些操作也可以抛异常，或者干脆什么都不做——可能性多得很。
无论如何，`Client::mkdir` 现在跑得漂亮极了。²
还要注意：这个做法没有对 `File` 类做任何改动。
当然，我们得把 `Client::mkdir` 改成接收 `Node*` 而不是 `Directory*`：

```cpp
void Client::mkdir (Node* current, const string& path) {
    // ...
}
```

²：嗯，*差不多*漂亮极了。我承认这个例子里我忽略了内存管理问题。具体说来，当 `adopt` 被调用在一个叶节点上时，会有一处潜在的内存泄漏，因为客户端把所有权交给了一个不肯接受所有权的节点。这是 `adopt` 的普遍问题，因为即使对象是 `Directory`，它也可能失败（比如客户端权限不够）。当 `Node` 采用引用计数、并且 `adopt` 在失败时递减（或者不递增）引用计数时，这个问题就消失了。

要点在于：尽管 `adopt` 和 `orphan` 看起来不像我们该一视同仁对待的操作，但这么做确有实实在在的好处，至少在这个应用里是这样。
最可能的替代方案，是引入某种向下强制转换，让客户端辨认出节点的类型：

```cpp
void Client::mkdir (
    Directory* current, const string& path
) {
    string subpath = subpath(path);

    if (subpath.empty()) {
        current->adopt(new Directory(path));

    } else {
        string name = head(path);
        Node* node = find(name, current);

        if (node) {
            Directory* child =
                dynamic_cast<Directory*>(node);

            if (child) {
                mkdir(child, subpath);
            } else {
                cerr << getName()
                     << " is not a directory."
                     << endl;
            }
        } else {
            cerr << name << " nonexistent." << endl;
        }
    }
}
```

看见 `dynamic_cast` 如何引出了多余的控制路径吧？
它是为了处理这种情况：用户在路径里某处指定了一个不合法的目录名。
这就说明，不统一会让客户端变得更复杂。

这并不是说，不统一就从来没有好理由。
在某些应用里，让编译器揪出任何在叶节点上调用子节点操作的企图，可能是必须的。
那种情况下，`adopt`、`orphan` 以及诸如此类的操作就不能声明在基类里。
但在没有什么严重后果需要防范的场合，统一通常会在简单性与可扩展性上给你回报，这一点我们马上就会看到。
