# 2.6 单用户保护

凡是长时间用过计算机的人，都能讲出一段惨痛经历：因为一个不走运的语法错误、一次手滑的鼠标点击，或者只是深夜里那么一次脑子短路，就丢了要命的数据。
在恰恰最不合适的时刻删掉文件，是常见的一类灾难。
另一类是误编辑——改了一个本来不该随手改的文件。
真正先进的文件系统会有撤销功能，用来应对这类意外，预防通常胜过补救。
遗憾的是，大多数文件系统给你的是另一种选择：要么预防，要么后悔。

眼下我先专注于保护文件系统对象（也就是节点）不被删除、不被改动。
我要考虑的是保护与编程接口的关系，而不是它与用户界面的关系。
这个区别其实不必让我们操心，因为我们的编程抽象与用户级抽象贴得很近。
此外，我假定我们处理的是单用户的文件系统，就像经典的非联网个人计算机上那样（而不是 UNIX 那样的多用户系统）。
这一开始能让事情简单些。多用户保护的含义，我后面再考虑。

文件系统的所有元素（包括文件、目录和符号链接）都遵循 `Node` 接口，该接口目前包含下列操作：⁴

```cpp
const string& getName();
const Protection& getProtection();

void setName(const string&);
void setProtection(const Protection&);

void streamIn(istream&);
void streamOut(ostream&);

Node* getChild(int);

void adopt(Node*);
void orphan(Node*);
```

⁴：注意，我为 `getName` 和 `getProtection` 补上了相应的 `set...` 操作。它们做的事跟你想的一样。

这些操作里，除了 `getProtection`，每个我都讲过些实质内容。
表面上它是取回节点的保护信息，可那到底是什么意思，还不清楚。
我们说的 "保护"，是哪一种保护？

如果我们是想保护节点不被误改、误删，那我们需要的只是写保护——节点要么可写，要么不可写。
如果我们进一步规定节点还该防住窥探的眼睛，那我们也应当能让它不可读。
当然，这只能防住那些既爱窥探、又*无知*的眼睛——不知道怎样改动节点保护设置的那种。
读保护对于防着配偶、甚至防着孩子翻你的东西，也许管用，但它算不上不可或缺。
在多用户环境里，它会变得重要得多。

回顾一下：我们知道节点可以是可读的或不可读的，可写的或不可写的。
多数文件系统还有别的保护模式，管着可执行、自动归档之类的事情。
这些保护模式，我们可以用差不多同样的方式处理，就像可读性与可写性那样。
为了把要点讲清楚，我只限于讨论这两种模式。

不可读与不可写对节点的行为有什么影响？
显然，不可读的文件不该泄露内容，这就意味着它不该响应 `streamOut` 请求。
也许不那么显然的是：客户端也不该访问不可读节点的子节点——如果它有子节点的话。
所以对不可读的节点，`getChild` 应当不起作用。
至于不可写：不可写的节点应当既不许你改它的属性，也不许你改它的结构；因此 `setName`、`streamIn`、`adopt` 和 `orphan` 也都该失效。
（在这方面，`setProtection` 必须小心处理。等我们讲到多用户保护时，我会再多说几句。）

防止不可写的节点被删除，会带来一些有趣的语言层面的挑战。
比如，客户端没法像删除别的对象那样显式删除一个节点。
C++ 编译器可以替我们抓住这样的企图，但不是靠把节点声明为 `const`——人们容易想到这个办法。
毕竟，节点的保护设置在运行期是可能变的。

我们换一种做法：*把析构函数保护起来*。
与通常的公有析构函数不同，受保护的析构函数使得 `Node` 类层次之外的类无法显式删除节点。⁵
保护析构函数还有一个好处：不许创建局部的 `Node` 对象，也就是创建在栈上的节点。
它防止一个不可写的节点在作用域结束时被自动删除——那种前后不一致，可能正是某个 bug 的征兆。

⁵：把析构函数设为私有不是一个选项，因为那会禁止子类化。

既然析构函数受保护了，你现在怎么（试图）删除一个节点呢？
有一点似乎可以肯定：到头来，我们会用一个以被删节点为参数的操作。
火烧眉毛的问题是：谁来定义这个操作？有三种可能：

1. `Node` 类（可能由子类重新定义）
2. `Node` 类层次之外的某个类
3. 全局函数

第三种可以立刻排除：比起定义在既有类上的静态成员函数，它几乎没什么额外好处。
把删除操作放在 `Node` 层次之外也同样不讨人喜欢，因为它迫使定义该操作的那个类成为 `Node` 的友元。
为什么？因为如果这个节点恰好可写、因而可删，那就总得有人去调用它那个受保护的析构函数。
要在 `Node` 类层次之外做到这一点，唯一的办法就是把那个执行删除的类设为 `Node` 的友元。
这有个倒霉的副作用：暴露的不只是 `Node` 的析构函数，还有它封装的其他一切。

我们来看第一种可能：在 `Node` 基类上定义一个 `destroy` 操作。
如果让 `destroy` 成为静态操作，那它就必须接收一个 `Node` 实例作参数；如果它不是静态的，那它可以没有参数，因为 `this` 参数是隐含的。
在静态、虚和非虚成员函数之间做选择，归根到底是在可扩展性与观感之间做选择。

虚成员函数可以通过子类化来扩展。
但有些人觉得这样的语法

```cpp
node->destroy();
```

有点让人不安。
我不确定这是为什么，但我敢打赌：人们看到

```cpp
delete this;
```

之所以皱眉，也是同一个理由。也许是因为太像自杀了。
静态成员函数可以绕开这块绊脚石……

```cpp
Node::destroy(node);
```

……但这样又不便于在子类里修改。
而非虚成员函数，则把两边的坏处都占了。

那就看看我们能不能把蛋糕留下又吃掉——既享受静态成员函数在语法上的好处，又允许在子类里扩展。

撇开子类可能想怎么扩展不论，我们 `destroy` 操作的职责究竟是什么？
有两件事看来是不变的：`destroy` 必须检查传给它的节点是否可写；如果可写，就删掉它。
子类也许想扩展删除的判定条件，或者想改变删除的做法。
但那些不变的部分，还是不变。
我们只需要一点帮助，好以一种可扩展的方式把它们实现出来。

进入 TEMPLATE METHOD 设计模式，它的意图是这样说的：

> 在一个操作中定义一个算法的骨架，将某些步骤延迟到子类中实现。
> TEMPLATE METHOD 让子类重新定义算法的某些步骤，而不改变算法的结构。

按照该模式 "适用性" 一节的第一条，只要你想把算法中不变的部分实现一次、把可变的行为留给子类去实现，就适用 TEMPLATE METHOD。
一个模板方法大致是这样的：

```cpp
void BaseClass::templateMethod () {
    // an invariant part goes here
    doSomething();       // a part subclasses can vary
    // another invariant part goes here
    doSomethingElse();   // another variable part
    // and so forth
}
```

`BaseClass` 定义 `doSomething` 和 `doSomethingElse` 两个操作来实现默认行为，子类则特化它们去做不同的事。
模式把这类操作叫做*原语操作*（primitive operation），因为模板方法实际上是在组合它们，从而造出一个更高阶的操作。

原语操作应当声明为 `virtual`，因为子类必须能多态地重新定义它们。
模式建议我们在名字前面加上 "do-"，以显式地标出原语操作。
我们还应当把它们声明为 `protected`，免得客户端直接调用——在模板方法的语境之外，调用它们未必讲得通。

至于模板方法本身，模式建议把它声明为非虚（在 Java 里是 `final`），以确保那些不变的部分保持不变。
在我们的例子里，我们又多走了一步：我们那个模板方法的候选者 `destroy`，不仅是非虚的——它是静态的。
这并不意味着我们不能应用这个模式，但它确实让我们对模式的实现添了一层曲折。

不过在敲定 `destroy` 之前，先来设计我们的原语操作。
我们已经确定了操作中不变的部分，也就是判断该节点是否可写、若可写就删除它。
从这里到下面这个结构，只差一小步：

```cpp
void Node::destroy (Node* node) {
    if (node->isWritable()) {
        delete node;

    } else {
        cerr << node->getName() << " cannot be deleted."
             << endl;
    }
}
```

`isWritable` 是一个原语操作 ⁶，子类可以重新定义它，以改变保护判定条件。
基类既可以给出 `isWritable` 的默认实现，也可以把它声明为纯虚，从而强制子类去实现它：

```cpp
class Node {
public:
    static void destroy(Node*);
    // ...

protected:
    virtual ~Node();
    virtual bool isWritable() = 0;
    // ...
};
```

⁶：好吧，我承认我在破规矩。可 "doIsWritable" 实在太过了。

纯虚声明避免了把与保护相关的状态存进抽象基类，但同时也让这些状态无法在子类里复用。

虽然 `destroy` 是静态的而不是非虚的，它在这种情况下仍然能充当模板方法。
这是因为：它不需要引用 `this`，只是把活儿委托给它收到的那个 `Node` 实例。
又因为 `destroy` 是 `Node` 基类的成员，它能在 `Node` 实例上调用受保护的操作（比如 `isWritable` 和 `delete`），而不破坏封装。

眼下 `destroy` 只用一个原语操作（析构函数不算）。
我们还该再加一个原语，让子类能改变错误消息，而不是把它硬编在基类里：

```cpp
void Node::destroy (Node* node) {
    if (node->isWritable()) {
        delete node;

    } else {
        node->doWarning(undeletableWarning);
    }
}
```

`doWarning` 把节点如何向用户警告*任何*问题的做法抽象出来，而不只是警告删不掉。
它可以是任意复杂的：从打印一个字符串到抛出一个异常，什么都行。
这就避免了为每一种想得到的情形都定义一个原语操作（比如 `doUndeletableWarning`、`doUnwritableWarning`、`doThisThatOrTheOtherWarning`，没完没了）。

我们还可以把 TEMPLATE METHOD 用到 `Node` 的其他操作上，而它们恰好不是静态的。
这样做时，我们会引入新的原语操作：

```cpp
void Node::streamOut (ostream& out) {
    if (isReadable()) {
        doStreamOut(out);

    } else {
        doWarning(unreadableWarning);
    }
}
```

`streamOut` 与 `destroy` 这两个模板方法的主要区别在于：`streamOut` 能直接调用 `Node` 的操作。
`destroy` 做不到这一点，因为它是静态的，不能引用 `this`。
因此必须把待删的节点传给 `destroy`，由它把原语操作委托给这个节点。
还要记住：`streamOut` 在升格为模板方法时，变成了*非虚*的。

<p align="center">❖ ❖ ❖</p>

[TEMPLATE METHOD](../../design-patterns/ch5/10.md) 模式引出的控制反转，被称为*好莱坞原则*（Hollywood Principle），
也就是 "别给我们打电话，我们会打给你"。
子类可以扩展或重新实现算法中可变的部分，但它们不能改变模板方法的控制流以及其他不变的部分。
因此，当你定义 `Node` 的一个新子类时，你不能按控制流的思路去想，而要按*职责*去想：哪些操作是你*必须*覆写的 (override)，哪些是你*可以*覆写的，还有哪些是你*绝不能*覆写的。
把操作组织成模板方法，能让这些职责更明确。

好莱坞原则特别有意思，因为它是理解框架的关键。
它让框架能够捕获那些并不变化的架构与实现构件，而把可变的部分推迟到应用特定的子类里。

控制反转正是框架编程让某些人觉得不自在的部分原因。
按过程式方式编程时，人会非常在意控制流。
很难想象在不知道程序七拐八拐走了哪些路的情况下，你怎么能读懂一个过程式程序——哪怕它的功能分解无可挑剔。
而好的框架会把控制流的细节抽象掉。
你最终专注于对象，与控制流比起来，对象既可能显得更实在，也可能显得更不着边际。
你必须按对象的职责与协作去思考。
这是一种更高层、也略微更声明式的世界观，能带来大得多的杠杆效应与灵活性。
TEMPLATE METHOD 以比框架更小的尺度实现了这些好处——在操作这个层面，而不是在对象这个层面。
