# 2.5 VISITOR 的告诫

在你应用 VISITOR 模式之前，有几件事要考虑。

<ins>第一，问问自己：我要访问的这套类层次稳定吗？</ins>
在我们的情形里，我们是不断地定义新的 `Node` 子类，还是很少这么做？
新增一种 `Node`，可能迫使我们改动 Visitor 层次中的每一个类，只为添上对应的一个 `visit` 操作。

如果你的 visitor 没有一个在乎这个新子类，而且你已经定义了相当于 `visitNode` 的操作、提供了合理的默认行为，那就不成问题。
可只要有那么一种 visitor 在乎，你至少得改它和 Visitor 基类这两处。
话又说回来，在这种情形下，多处改动也许本来就免不了。
如果你不用 VISITOR，而是把功能一古脑塞进 `Node` 层次里，你大概也少不了要在那儿做好几处改动。

<ins>要意识到的第二件事是：VISITOR 在 `Visitor` 与 `Node` 两套类层次之间造成了循环依赖。</ins>
因此，改动任何一边的基类接口，都可能引发两边一起重新编译。
这大概也不比改动一个臃肿的基类糟多少。
但一般而言，这种依赖能免则免。

> 译注：ADP（Acyclic Dependencies Principle，无环依赖原则）是 Robert C. Martin 提出的包设计原则：组件（包、发布单元）之间的依赖图不允许有环。原文的 "循环依赖" 只发生在 Visitor 与 Node 两类层次之间；只要把 Visitor 抽象与 Node 层次放进同一个组件（GoF 的通常做法），环就留在组件内部，不算违反 ADP。若必须分包，可让 Element 层次与 Visitor 抽象同居 "稳定核心" 组件，具体 Visitor 的实现另置上层组件并单向依赖核心——Element 只依赖 Visitor 抽象，依赖方向便不再成环；C++ 里再用前向声明，还能降低编译期耦合。

<p align="center">❖ ❖ ❖</p>

Kevlin Henney 有一番相关的见解 [Henney96](../biblio.md#henney96)：

<a id="example-2-5-1"></a>
> C++ 的重载并不要求你必须重载 `visit` 的所有版本，也不要求你放弃对 `visit` 成员使用重载。
> 除了支持命名空间的概念之外，`using` 声明还允许你把基类里的名字注入当前类，以便参与重载：
>
> ```cpp
> class NewVisitor : public Visitor {
> public:
>     using Visitor::visit;  // pull in all visit
>                            // functions for overloading
>
>     virtual void visit(Node*);  // override Node* variant
> };
> ```
>
> 这样既保持了重载带来的规整性，也不具侵入性：用户不必去记 `visit` 函数该用什么名字或什么约定；同时，较新发布的 Visitor 也可以纳入改动而不影响客户端代码。

<p align="center">❖ ❖ ❖</p>

我们已经看过了用于定义文件系统结构的模式（COMPOSITE 和 PROXY），也看过用于非侵入式引入新能力的模式（VISITOR）——所谓非侵入式，就是靠 *添加* 代码，而不是 *改动* 代码。
这里又碰到一条好的面向对象设计的陈词滥调：<ins>当你的系统能在不碰已有代码的前提下被修改时，灵活性与可维护性就达到最大。</ins>
如果别人用了你的软件之后还能这么说，那就恭喜了——你已兑现了对象技术所允诺的大部分好处！

不过话说远了。

2. 在硬件与软件出错时维持系统的完整性。
