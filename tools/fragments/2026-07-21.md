# 片段：7月21日

Martin Fowler：2026年7月21日

---

通过这篇文章，我将结束对第二次 [软件开发未来 Retreat](https://martinfowler.com/bliki/FutureOfSoftwareDevelopment.html) 的笔记。
但在结束之前，我应该指出，[Thoughtworks 关于这次 retreat 的完整报告现已发布](https://www.thoughtworks.com/content/dam/thoughtworks/documents/report/tw_future_of_software_engineering_europe_2026.pdf) 。
他们有五个主要发现：

> 1. 代码生成不再是瓶颈 —— 验证才是。
> 2. “Harness 工程” 正在成为一个独特的、可拥有的学科。
> 3. 组织正面临真正的学徒危机。
> 4. 高管/工程师的期望差距是比任何技术限制都更大的风险。
> 5. 遗留系统现代化是最清晰、最可辩护的近期价值池。

❄　❄

一个会议围绕使用 LLM 的工程师与呼吁使用它的高管和董事会之间观点不匹配而召集。
担忧在于董事会正盯着承诺的生产力提升，而对风险（尤其是安全风险）关注不足。

一个故事说明了这一点：一家公司使用 ML 训练的软件来优化其现场设备空气过滤器的更换。
他们很高兴地发现能够减少更换空气过滤器的频率，节省了 5000 万美元。
但问题是 ML 模型是在沙漠中使用的设备上训练的，而他们的设备是在北极使用的。
沙漠中的空气过滤器处理的是灰尘，但在北极需要去除的是蚊子。
这里有一个重要的区别，蚊子会腐烂，足够多的腐烂蚊子会带来严重的火灾风险。
由于不频繁更换空气过滤器，这类因死蚊子引发的火灾给公司造成了 1000 亿美元的损失。

这样的故事在没有 AI 介入的许多情况下也可能发生。
许多人类情境在新环境中应用解决方案时也出过问题（这就是为什么上下文是模式写作者中如此关键的一个词）。
但这个故事确实提醒我们要警惕 AI 的建议，并始终思考如何构建传感器以提供快速反馈。

工程师特别担心公民开发者开始进行 “氛围编码” 时的风险。
当然，从很多方面来说，这并不新鲜。
IT 人员经常担心有多少重要的商业决策是基于电子表格的，而这些电子表格几乎没有控制、测试或数据质量评估。
氛围编码放大了这些担忧，因此公司需要一系列控制措施来防范安全漏洞。
一些人已经主动在董事会层面提出这些问题，与董事会成员一起进行威胁建模会议，向他们介绍风险。
氛围编码的应用程序需要放在独立的基础设施中，通过确定性的数据访问控制来遏制致命的三重威胁。
一家公司鼓励公民开发者广泛进行氛围编码，但后来对出现的巨大影子 IT 问题感到退缩 —— 他们现在正在寻求建立一个平台来帮助控制这项工作，同时不扼杀已生成的有用工具。

这里的问题部分可能在于对 LLM 的简单经验。
许多管理层发现 LLM 在准备管理报告方面做得不错。
或者总结由其他 LLM 准备的管理报告。
鉴于此，他们自然认为 LLM 在编程方面也应该做得不错。
我反管理的自我不得不提到 Kelsey Hightower 的观察：

> 你越少做琐碎工作，这些 AI 工具的吸引力就越小。

一个可能的解药：让法律部门参与进来。
他们看到 LLM 做得不好，并欣赏所涉及的风险。

❄　❄

我在 retreat 内外交谈过的大多数人都认识到我们正处于某种泡沫之中。
像这样的技术进步几乎总是伴随着经济泡沫，在未来，我们都会回首往事，摇头说我们知道当时有太多的泡沫。
但虽然很容易看到有泡沫，却很难看到它会持续多久，或者泡沫破裂后会出现什么。
毕竟，互联网泡沫在 1995 年就被清楚地认识到了。
我们可以愉快地指出那些失败的公司（Webvan、pets.com），但需要同时承认那些幸存下来的公司（Amazon）。

retreat 中的大多数人年纪都够大，经历过互联网泡沫和崩溃，但一位老资历人士指出了一个有趣的区别。
那时，我们对未来将带来的东西感到兴奋，我们看到了许多新东西正在被构建。
这一次，这种情况要少得多。
[大多数人对](https://poll.qu.edu/poll-release?releaseid=3955) AI 泡沫正在创造的东西持谨慎态度。
部分原因可能源于互联网希望之后的现实。
社交媒体可能无处不在，但我们是否认为它实际上显著改善了我们的生活，即使（特别是如果？）我们使用了这么多？

我们听到了很多关于我们可以用 [智能体编程](https://martinfowler.com/bliki/AgenticProgramming.html) 做的令人难以置信的高效事情，但有没有人注意到用它构建的精彩应用程序的洪流？
或者我们是否注意到来自大型 AI 推动者（如 Google 或 Microsoft）的常见应用程序有显著改进？

这可能是董事会与工程师之间分歧的另一个因素。
目前推动 AI 采用的大部分是成本削减，而主要是董事会对成本削减感到兴奋。
也许 [对 token 成本日益增长](https://martinfowler.com/fragments/2026-07-06.html#token-costs) 的担忧会缓和这种热情。

❄　❄

人们发现 LLM 在运维方面很有帮助：通过可观测性工具的良好事件流，智能体能更快地发现异常。
公民开发者应用程序的一个问题是，它们通常不提供良好的可观测性，因为公民开发者不会想到去要求它。
智能体查看事件流的能力确实引发了治理问题，因为这类事件流通常包含大量敏感信息。

强化了我在犹他州听到的观点，更多人同意 LLM 对运维人员理解代码做什么很有价值。
交叉匹配代码和事件跟踪有助于他们帮助人类在出问题时找到发生了什么。
智能体在处理重复事件时特别有用，因为它们可以从不同案例中整理大量信息并呈现给人类团队。

让智能体进行自动修复将我们带到下一个能力和关注级别。
至关重要的是，智能体在进行修复时仔细记录它们的所有操作。
我们还需要确保有反馈给开发团队，以便他们能够学习。
智能体不学习，它们能做的最好的事情是更新上下文。

有一种感觉是，许多人高估了智能体处理事件的能力。
这些人认为事件解决是一个简单的线性过程。
但它很少如此，相反，有很多意外和需要的适应。
人类擅长这个，但 LLM 不擅长。

智能体开发代码的隐患之一是它们习惯插入从未被要求的功能。
一个团队花了三天时间试图弄清楚这样一个未请求的功能，试图找出是谁请求了它以及是否有人想保留它。

❄　❄　❄　❄　❄

一组法学教授进行了一项有趣的实验，以评估 [LLM 为学生问题提供简短答案的能力](https://law.stanford.edu/publications/law-professors-prefer-ai-over-peer-answers/) 。
他们创建了四十个合同法问题，并要求教授们以及几个 LLM 提供答案。
为了评估 LLM 的答案，他们向教授们展示了一对答案 ——一个来自人类，一个来自 LLM—— 并问他们更愿意向学生提供哪个回答。

> 教授们对 LLM 的评价远高于对他们的同行（平均胜率为 75.33%），模型的表现与最佳讲师相似。
LLM 的响应也很少被标记为有害（3.53%，而教授为 12.06%）。

这让我想起了我在最近的一篇片段中提到的 [互动型专长和贡献型专长](https://backofmind.substack.com/p/faking-versus-making) 之间的区别。

❄　❄　❄　❄　❄

几天前，Unmesh Joshi 在这里发表了一篇文章，讲述了他 [使用 DSL 来实现更可靠地使用 LLM](https://martinfowler.com/articles/llm-and-dsls.html) 的经验。
对此的回应包括指向 Spender Nelson 一篇文章的链接，[该文章表达了类似的看法](https://blog.firetiger.com/custom-programming-languages-make-agents-really-really-smart/) 。

> 像这样的 DSL 对 LLM 来说有很多优势。
你可以使它们在 token 方面极其高效，并强制执行硬性安全边界。
你可以将高层次的 LLM 意图转化为大量确定性代码，在（自定义）编译器级别确保良好行为和护栏。
>
> 而大型语言模型非常擅长学习和使用 DSL。
也许这不应该令人惊讶；毕竟它们是语言模型。
一小段文档通常就足以让它们启动和运行，而合理的错误信息让它们即使在出错时也能纠正方向。

他描述了它们使用中的几个例子：一个考虑了安全和授权问题的数据湖查询语言，以及一个用于更轻松创建安全 SQL where 子句的小表达式语言。

使用 DSL 的最大障碍之一，特别是外部 DSL，是构建解析器和工具。
LLM 使这变得容易得多。
也就是说，我的感觉是，支撑 DSL 的语义模型才是真正重要的，而 DSL 是该模型的一个投影。
LLM 可能帮助我们探索以有趣的方式投影该模型的其他方法。

❄　❄　❄　❄　❄

最近几周，我越来越注意到 LLM 用语的气味。
不仅仅是常见的特征，而是一种弥漫在散文中的 LLM 瘴气感。
我注意到它越来越引起一种本能反应，在几段之后，我就只想完全放弃整篇文章。
对于其中一些，我有必要捏着鼻子通读全文，但那是带着一种智力上的恶心感，模糊了内容，甚至增加了我想沉溺于查看社交媒体这种糟糕的分散注意力的事情的欲望。

我想知道 —— 是我一个人对 LLM 用语有如此负面的反应吗？
还是其他人也有一种反应，导致他们扔掉任何触发他们 LLM 警报的散文？

一个表明不只是我一个人的指标是 Jason Koebler 几个月前的一篇文章，我 highlighted 过，他 [观察到 AI 如何破坏他的大脑](https://www.404media.co/your-ai-use-is-breaking-my-brain/) ：

> 人们认为假的是真的，真的是假的。
关于 “AI 精神病” 已经写了很多，这是一个非特定的、非科学的诊断，给予那些迷失在 AI 中的人。
关于其他人的 AI 使用对我们其他人造成的认知负荷，以及不得不应对一个懒惰的 AI 已经渗透到一切的互联网和世界的阴险性质，讨论得较少。
我们的大脑现在每天进行着数不清的计算：这是 AI 吗？
我在乎它是 AI 吗？
为什么这听起来或看起来或读起来如此奇怪？
这个人就是这样写的吗？
这到底是一个人吗？

一段时间前，我曾认为，对于那些不像我这样致力于写作的人来说，使用 AI 来润色他们的文章是合理的。
现在我转向鼓励作者拒绝它。
那种无处不在的 LLM 声音现在太常见了，我的感觉是，它在读者有机会试图理解所说内容之前，就已经使文章失去可信度。
我认为要求 LLM 写初稿然后调整是不够好的。
我不确定作者一旦 LLM 风格进入文章后，是否还能将其编辑掉。
我甚至担心要求 LLM 提出改进建议，我认为太容易接受 LLM 的建议，并在此过程中触发读者的 LLM 抗体。

当然，像大多数问题一样，这也是一个机会。
那些能够获得独特人类声音的人将获得更多的可见性和可信度。
但问题仍然存在，我们如何指导人们将他们的真实个性释放到写作中。
学术和企业写作都倾向于扼杀引人入胜的散文，LLM 是很好的放大器，它们会放大这种扼杀。
对于那些以英语为第二语言（或者对许多同事来说是第三或第四语言）的人来说，这是一个更大的挑战。
我太容易忽视一个我从未能够面对的困难了。

我能给出的最直接建议是我多年前学到并在去年分享的东西 —— [朗读你的文字](https://martinfowler.com/bliki/SayYourWriting.html) 。

> 一旦你有了一个合理的草稿，大声朗读它。
通过这样做，你会发现听起来不对劲的地方，并需要修复。

我一直建议这样做，以帮助人们摆脱呆板的散文，特别是如果他们花太多时间在学术或企业写作上。
但现在我认为，为了对抗 AI 的阴险影响，朗读你的文字的需求变得更加重要。
对大多数人来说，他们的说话模式更接近他们真实的自我，所以将写作口头化是对抗那些试图抹去作者个性力量的方式。
