# 片段：7月13日

Martin Fowler：2026年7月13日

--- 
来自 [Thoughtworks 软件开发未来 Retreat](https://martinfowler.com/bliki/FutureOfSoftwareDevelopment.html) 的更多笔记。

当我们今年早些时候在犹他州举行第一次 retreat 时，没有人听说过 [Harness Engineering](../harness-engineering.md) 。
这次我们有一个完整的会议讨论它。

当涉及到 harness 的指导方面时，大部分讨论是关于上下文管理的。
虽然上下文窗口随着模型变得更复杂而增大了尺寸，但这并不意味着模型会正确地关注正确的部分。
模型通常只将注意力集中在上下文的一部分上，为了获得最佳行为，我们需要管理这种关注。
一位参会者将他们的上下文保持得很小，将 agents.md 文件限制在 200 行以下。

在传感器方面，我们看到对计算传感器的关注更多。
一位参与者提出的两种模式是转向具有更强控制力的语言（例如 Rust 而不是 Python），以及 “升级” 验证方法，使用更多基于属性的测试和形式化方法中的技术。
一位评论说，虽然他们不够聪明，无法用形式化规范语言编写规范，但他们足够聪明，可以阅读它并检查它是否适合他们的领域。

关于 harness 的关注是否能持续到我们下一次 retreat？
模型会不会变得如此优秀，以至于 harness 变得不再必要？
那些对 LLM 有某种机械同理心的人似乎认为不会 —— 但他们是否过度耦合于当前的技术状态？
我发现这种推测往往不会带来任何有用的结果，我过去没有看到多少成功预测未来的例子，而在像这样激进的技术面前，我也不认为它会变得更容易。
因此，就目前而言，对 harness 的关注是值得的。
我们发现它可以减少 token 使用，并且还能让较弱的模型变得有用，支持诸如开源权重模型的本地托管等事情。

❄　❄

这自然引出了关于自托管模型的会议。
不断增长的 token 成本使得托管开源权重模型更具吸引力，特别是由于开源权重模型追赶前沿模型的时间在缩短。
然而，成本并不是唯一的因素，许多人发现对独立于前沿模型公司的渴望才是驱动力。
毕竟，我们已经看到美国政府干预以拒绝访问模型，这增加了对更大模型主权的渴望。
信息安全也是需要考虑的因素，一些参会者就是无法将必要的数据交给模型来完成关键工作。
即使没有这个因素，如果其他人托管模型，那么是他们的模型在学习，而不是你的模型。
尽管最近的事件增加了兴趣，但几位参与者曾在已经自托管长达一两年的公司工作过。

这是否是在重蹈自托管云的覆辙，导致许多人将过多资金花费在半吊子的私有云上？
答案取决于托管模型是否最终比托管云更简单，也许是因为更简单的交互协议。
其中的难点可能是高效使用 GPU 所需的人才，目前管理推理数据中心还不是一项广泛可用的技能。
即使是自托管模型也有运营成本，包括 GPU 的资本成本和持续的电力成本。
数据中心的物理设计会影响最优使用率。
这里存在着专业服务公司帮助企业管理这一点的机会。

成本控制还包括教人们为工作选择正确的模型。
我们能否教工程师，或者实际上是其他用户，选择一个能力较弱的模型？
当然，这可能是模型本身的工作，充当经纪人，决定哪个模型是处理某些工作的最佳选择。

自托管可能导致更多使用微调。
目前这还是一种小众活动，但随着时间的推移，我们很可能会发现，
针对特定领域进行微调的模型需要更少的推理，消耗更少的 token，因此运营成本更低。
我们正在看到专门为支持编程而训练的模型。

与任何具有这种不确定性的主题一样，最大的胜利不是找到正确的答案，
而是制定一个能够应对不可避免且不可预测的变化的策略。

❄　❄

在这样的活动之后，很多人会来找我，让我做一个宏大的总结。
我讨厌这样，因为我很少带着某种宏大叙事离开这类活动。
即使在事后仔细思考（在写上面的笔记时）之后，我通常仍然没有一个，并且不信任一个形成的叙事，因为我的怀疑主义包括试图对一个自然相当混乱的事件做出连贯叙事的尝试。

然而，这次我的缺点无关紧要，因为 Kief Morris 已经整理了这样一个叙事，[而且它是一个令人信服的叙事](https://infrastructure-as-code.com/posts/fose-july-2026.html) ，即使对像我这样的叙事否认者来说也是如此。

> 这些会议有不同的标题和不同的人员组成，表面上它们是关于不同的问题。
>
> 但事实并非如此。它们几乎每一个都是同一个论点的不同方面。
我们让智能体决定多少，以及我们如何对自己所做的事情保持信心？

他审视了代码审查，质疑它是否重要，但看到许多人与之相关的严谨性转移到了其他形式。
他描述了关于我们应该在多大程度上信任智能体来识别和修复生产事件的分歧。
他看到团队给予智能体多少回旋余地的对比取决于他们所处的上下文。

> 在这些会议背后，无论是关于操作的辩论、宽泛范围的团队、暗工厂频谱，还是关于谁被允许引导模型的争论，人们都在一遍又一遍地对同一件事做出相同的少数选择：他们准备交给智能体的工作单元。
它有多大。
它覆盖了多少工作。
你做什么来准备它以便交接。
你如何检查返回的内容。
你在智能体周围放置什么以使其保持在界限内。
不同的会议室对这些设置不同，但他们设置的却是相同的控制。

❄　❄

Sam Ruby 召集了一个名为 “给我一块石头” 的会议。
这个名字让人联想到一种特定的管理功能障碍。
管理者告诉下属给他带一块石头，然后开始拒绝结果而不解释原因（ “不，不是那个”，“不，不是那个” ），直到最终有一块石头符合未说明的期望。

> 它命名了一位管理者，他用连续拒绝代替了说出他们想要什么的工作，并让你一块石头一块石头地为他们的未完成思考付出代价。

Sam 已经写过为什么他认为有了 LLM， [这从一个侮辱变成了一种可辩护的工作方式](https://intertwingly.net/blog/2026/06/27/Bring-Me-a-Rock.html) 。
当它是一群不知疲倦的机器，拥有无限的耐心，能在几分钟而不是几天内返回新的石头时，那么像这样的方法（使用 [头脑风暴模式](https://martinfowler.com/fragments/2026-06-16.html#registers) ）就成为了一种可辩护的工作方式。

Sam [描述了讨论内容](https://intertwingly.net/blog/2026/07/01/What-Survived-Contact.html) ：

> 房间把讨论拉到了一个比我框架更窄的地方，而这个更窄的地方更有趣：不是关于如何通过排除法进行探索，而是关于谁应该被允许这样做。
产品经理，越来越多的人事经理，正在直接使用这些模型，而有经验的工程师使用它们得到的结果比未经训练的人明显更好 —— 于是担忧随之而来。
如果专业能力是区分好结果和劣质结果的关键，那么非工程师是否应该被允许引导模型呢？
>
>
> 这是一个合理的问题，但我认为这是个错误的问题，因为它误解了这种行为。
当一个经理选择使用 LLM，而不是将工作分配给汇报给他们的团队时，他们并不是拿起了一个工具 —— 他们做了一个雇佣决定。
而管理自己的团队并不需要请求许可；
一个经理决定某件工作更适合交给一个新的参与者而不是现有的团队成员，这是在做一个管理者最平常的事情。
从这个角度来看，许可问题就消解为一个更古老、更被理解的问题 —— 德鲁克在 1959 年提出的那个问题：当工人比经理更了解具体情况时，你通过目标来管理，而不是通过方法。
非工程师引导智能体正是那个经理，被他们所指导的东西所超越，而房间所担心的劣质结果，正是当你应该通过目标管理时却通过方法管理的古老危险。
问题不是他们可以雇佣吗？
而是他们知道如何通过目标管理吗？
—— 这是你可以教的、可以雇佣的、可以要求人们做到的，而不需要任何人先成为工程师。

Sam 的文章探讨了通过目标来管理 LLM，给它一个目标而不是一个任务。
而 Kief 之前关于讨论本质的观点仍然成立：我们对其做了正确的事情有多大信心？
我们可以外包许多事情，但不能外包验收标准，在某个点上有一个人类的请求和一个人类对该请求是否被正确执行的判断。
但危险在于重要的未明确目标，未明确也许是因为它们甚至没有被想象到。

围绕所需功能陈述目标很容易。
给我一个应用程序，它将检查我的电子邮件并为我今天的待办事项列表。
但在这简单陈述的背后，是一堆未明确的假设。
我们倾向于假设精灵不会包含任何不需要的功能，也许删除它认为不值得关注的电子邮件。
我们假设它不会让一封电子邮件告诉它将私人信息发送给 villain@evil.com。
我们在这方面有一些希望 —— 我们听到更多的经验表明，最近的模型可以在发现（并希望修复）安全漏洞方面做得非常出色。
机器的谨慎精确超越了软体中如果富有想象力的思维的草率。
也许我们可以假设精灵能够处理我们一些未明确的目标。
一致性测试（传感器）比规范（指导）更有价值，但很难想象所有需要说明不应该发生什么的一致性测试。

此外，构建软件是关于探索的，找出工作流如何随着机器嵌入过程而演变。
对于人类来说，要指导这个过程，我们需要对它有一些理解。
我的感觉是，模型构建仍然很重要，虽然我同意精灵可以在这种构建中发挥积极作用，但我不认为人类可以完全外包它。
即使精灵自己构建模型，它也需要教会我们这个模型，因为模型帮助我们想象和沟通目标，那些我们给予机器的目标。

> 发现某个人 ——他是 Electron 的高级维护者—— 领导了 Slack、Notion 以及现在的 Claude 桌面客户端的团队，就像发现是某个人 ——他的家族企业是一家酿酒厂—— 掌舵了泰坦尼克号、驾驶了兴登堡号，然后担任了 Amelia Earhart 的空中交通管制员。

有很多证据表明，编码智能体在多种语言和平台生态系统中构建相同的东西方面做得非常出色。
这应该意味着最低公分母的跨平台 UI 的日子已经屈指可数了 —— 而且这个数字很小。

Dan Davies 试图 [区分互动型专长和贡献型专长](https://backofmind.substack.com/p/faking-versus-making) 。
贡献型专长属于那些从事工作以推进研究领域的人，而互动型专长则属于那些花时间与贡献型专家交谈、自己积累了相当知识储备，但并未深入日常工作的人。

> 在我看来，这里有一个重要的区别，即使这条分界线可能难以通过经验确立，或者即使这条线最终位于与我们猜测不同的位置，这个区别的重要性也不会降低。
除了难以判断的灰色地带，我认为我们也能想到一些情况，在这些情况下，互动型专长和贡献型专长之间的区别会突然变得非常清晰和重要 —— 那些假装拥有专长的人被 “发现” 的情况。
>
> 因此，我认为相当重要的问题是：机器通过工业化消费和与比任何人类能吸收的都要大得多的文献语料库进行交互所获得的专长，与能够应用于该文献之外的全新情境的真正贡献型专长之间，
是否存在类似的区别？

作为人类，我愿意认为自己更像一个贡献者而不是互动者（尤其是考虑到我日益增长的内向性格），因此相对安全，不会被硅基力量迫使过时。
但我也意识到，我的职业生涯缺乏任何原创思想，我的技能仅仅是一个擅长选择和解释他人思想的人的技能。
（正如 Brian Foote 更令人难忘地说的那样：“一个对腐肉有好品味的智力型豺狼。”）但做一个好豺狼也是一种技能 —— 而我们还不知道 LLM 的真正边界将位于何处。
