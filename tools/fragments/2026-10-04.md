针对我 [上一篇片段](2026-09-29.md)（大概是关于我们担心 LLM 是否有意识，而我们真正该思考的是它们为什么没有意识那部分），[“Metalanguage” 回复道](https://x.com/metalanguage_os/status/2104934457333707058)：

> 我们交付了本我，却忘了超我。经典的软件生命周期。

我不知道他们当时在想什么，但他们的帖子立刻让我想起了 1956 年的经典电影 Forbidden Planet。
大量科幻作品及其他文学都探讨过人类创造的技术产生意外行为，至少可以追溯到 Mary Shelly。
但那部电影对科幻电影制作的影响尤为深远 ，其故事核心正是当我们培育一台会思考的机器时会发生什么。

我这里用 “培育” 一词是刻意的。
我们谈论构建软件，但构建意味着某种程度的确定性。
当我们建造一座桥或一台机车时，我们期望它以受控且充分理解的方式运行。
这与我们在花园里栽培植物或养育幼儿有着程度上的不同。
与这些系统打交道的一个挑战，就是理解从构建一个计算系统到培育一个推理系统这一转变中发生了什么变化，以及我们的流程需要如何相应改变。

确定性的构建也会带来意外行为：有些桥倒塌了，我们的计算系统也常常有漏洞。
但一个区别是，当我们在计算系统中发现漏洞时，通常可以修复它。
即使不能，我们通常也可以禁用某个组件，使漏洞不再造成进一步伤害。
然而对于推理型 LLM，并没有这样简单的修复或禁用方法，这可能会让我们走向 Krell 人的命运。

（如果你没看过 Forbidden Planet，很值得一看。是的，它显示出制作于 20 世纪 50 年代 —— 带着那个年代的特效、音乐、表演和观念。
但故事很扎实，其关键主题与我们用生成式 AI 构建的未来非常相关。
只是不要提前去读相关内容，最好不带剧透地沉浸在故事里 —— 尽管我对那段经历的记忆自然已经模糊了。）

DDD Europe 发布了 Gien Verschatse 在 6 月会议上采访 Eric Evans 和我的 [视频](https://www.youtube.com/watch?v=fndU_B5rmPE) 。
我们首先谈到 20 世纪 90 年代末我们是如何因概念建模而结下友谊的。
对话很快转向 AI，我们指出，无法预测如此巨大的变化会如何发展。
我们确实预计它会促使我们以不同方式思考自己的工作，但这种变化很可能具有解放性，它重新点燃了 Eric 对编程的热爱。

> 人们很可能会对 [这种思考软件的新方式\] 感到非常沮丧……但当你挺过那个阶段，就会有一种奇妙的感觉，仿佛我的大脑被松开了。

我们在敏捷规划方面的背景有助于应对不确定性，因为我们习惯于小步前进并关注反馈。
我们思索写作与思考之间的相互作用，无论是散文还是代码，以及它多么像是一个探索与精炼的迭代过程 —— 当我们与 LLM 聊天时也是如此。

不要错过 Eric 重要的最后一条建议。

关于阅读代码是否会在软件开发者的未来中发挥作用，猜测仍在继续。[Geoffrey Huntley 说](https://ghuntley.com/readable/?ref=geoffrey-huntley-newsletter) ：

> 人们仍然在大声疾呼，代码应当可读，以便人类能够理解它。我不再认为那是目标。

有趣的是，他的例子让 LLM 通过把一段 Haskell 函数定义翻译成 Python 来解释它……
这对我来说表明代码仍有其作用——只是 LLM 不必以它呈现给读者的同一形式来存储代码。
这本质上与 [投影编辑](https://www.martinfowler.com/bliki/ProjectionalEditing.html) 是同一理念，后者主张软件的可编辑表示不必与其存储表示相同。

Sam Ruby [在思考 Rails World 主题演讲](https://www.martinfowler.com/bliki/ProjectionalEditing.html) 时谈到了这一点。他引用 DHH 的话说：

> Rust 目前是一个不错的小提示词编译目标，但 C++ 也是。
> 很快汇编语言也是。然后是微码 (microcode)。
认为我们会阻止智能体钻头直到它抵达计算基岩，是短视的。

他回应道：

> 不过，这篇文章留下了一个未被提出的问题：钻头顶端是什么？我们保留、编辑并信任什么作为真相之源？

他做了一次实验，查看某个 Rails 软件。
用 Ruby/Rails 表示，大约 60,000 个 token。
把它编译成 C，就变成 4,000,000 个 token。
token 规模的这种增长会妨碍 LLM，因为它仍然必须把它放进上下文窗口，而且即使放得进去，也得弄清楚该把注意力集中在哪里。
Sam 指出了为什么即使没有人阅读它，用更高层语言表示程序也是合理的。

> 当智能体编写代码时，Rails 会变成什么：一个 Web 应用最紧凑、最精确、最符合惯例的规格说明，无论它最终被编译成什么。
>
> 让钻头尽可能往深处钻。只要把记法保持在顶端就好。

这一切让我想起 [Unmesh Joshi 的论点](https://martinfowler.com/articles/what-is-code.html#CognitiveDebt) ：代码服务于 “两个不同但交织的目的”：给机器的指令，以及问题领域的概念模型。
在探讨这些目的如何随 LLM 变化之后，他总结道：

> 编码的角色并没有消失。但它在改变。
>
> 随着 LLM 让代码生成变得更便宜，编写指令的机械行为变得不那么核心。
变得更重要的是让概念模型显式化，发现正确的词汇，并通过迭代、领域专业知识和反馈来精炼那套词汇。
这也是为什么编程语言仍然深深重要。
我们不该成为生成代码的被动审查者。
写代码这一行为本身就是我们思考的一部分。
>
> 代码仍然是给机器的指令。
但它也是一种理解的模型。
在 LLM 时代，第二种角色变得更加重要。
编码的未来不只是更快地写更多代码。
它是在构建更好的概念模型、更好的词汇，以及更好的基础，让人类和 LLM 都能在其上工作。
