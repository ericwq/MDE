# 整洁代码精炼器

## 这将产出什么

- **输出**：`.lattice/standards/clean-code.md`（或来自 `.lattice/config.yaml` → `paths.clean_code` 的自定义路径）
- **两种模式**：
  - **叠加（Overlay）**（`mode: overlay`）：一份精简文档，仅包含与默认值不同的章节。整洁代码原子首先读取其嵌入的默认值，然后将本文档的章节叠加在上面。这是预期的常见情况。
  - **覆盖（Override）**（`mode: override`）：一份全面的独立文档，完全替换原子嵌入的默认值。适用于有根本不同编码标准的团队。
- **默认模式**：叠加——仅产出用户想要更改的内容
- **配置键**：`.lattice/config.yaml` 中的 `paths.clean_code`
- **模板**：读取 `./assets/template.md` 获取完整的文档结构、默认内容和访谈指导注释

## 范围澄清

此技能定义*代码工艺规则*——单个函数、类和模块应该如何编写。它不定义架构（那是 architecture-refiner）或领域建模（那是 ddd-refiner）。边界：

- **整洁代码**——函数大小、命名、复杂度、错误处理、可测试性、抽象纪律
- **整洁架构**——层级、依赖方向、命令/查询流程、结构位置
- **DDD**——聚合、实体、值对象、领域事件、仓库模式

## 开始之前

### 检查现有文档

在开始访谈之前，检查是否已经存在自定义文档：

1. 读取 `.lattice/config.yaml`——`paths.clean_code` 是否指向一个文件？
2. 如果是，读取该文件。询问用户：
   - "你已有一份自定义整洁代码文档。你想要**修订**它（更新特定章节）、**重新开始**（新访谈），还是**添加**（添加新章节）？"
   - 修订：加载现有文档，仅浏览用户想要更改的章节，原地更新。
   - 重新开始：继续下面的完整访谈流程。
   - 添加：跳到访谈的"新章节"部分。
3. 如果没有配置或没有现有文档，继续完整访谈流程。

### 扫描仓库

寻找能指导对话的信号：

- **Linter 配置**：ESLint、Pylint、Rubocop 等——已经强制执行了哪些规则？配置了什么复杂度阈值？
- **格式化工具配置**：Prettier、Black、gofmt——哪些格式化决策已经自动化？
- **现有代码风格**：函数普遍短还是长？命令式还是函数式？注释多还是少？
- **测试模式**：什么测试框架？同目录还是分开？模拟模式？
- **语言**：TypeScript、Python、Go、Java 等——语言惯用法影响命名约定和错误处理模式。

在开始时与用户分享相关发现："我注意到你的项目配置了 ESLint，max-complexity: 15，并使用 Prettier 进行格式化。我将使用它作为上下文。"

如果项目是全新的，没有代码，则将纯默认值作为起点。

## 选择模式

对话中的第一个决策。呈现三个选项：

"你想如何定义你的整洁代码原则？

1. **自定义特定章节**（叠加）——保留默认值，只更改与你项目不同的部分。这生成一份精简文档。大多数团队选择此项。
2. **从头定义一切**（覆盖）——浏览所有章节，生成一份全面的独立文档。
3. **仅添加项目特定章节**（叠加并添加）——保持所有默认值不变，为团队特定规则添加新章节。

默认值很好地覆盖了标准整洁代码实践。除非你的编码标准有根本性的不同，推荐选项 1。"

映射选择：
- 选项 1 和 3 → `mode: overlay`
- 选项 2 → `mode: override`

## 引导方法

### 对话风格

- **一次一章。** 不要一次性抛出所有问题。按顺序浏览模板。
- **默认值优先。** 对于每个章节，简要总结默认值，然后询问是否匹配。不要逐字读出整个默认值——总结关键点并询问。
- **记录决策，而非讨论。** 输出文档读起来像规范，不是会议笔记。
- **追问，而非审问。** 使用模板指导注释中的追问问题作为用户回答模糊时的后续问题，而不是作为清单。

### 对于叠加模式

这应该很快。许多章节将是"保持原样"。

1. 简要呈现每个章节的默认值（2-3 句总结，不是完整内容）。
2. 询问："这与你的项目匹配吗，还是你想更改？"
3. 如果用户说匹配 → 跳过（该章节不会出现在输出中）。
4. 如果用户想更改 → 深入该章节，讨论具体内容，记录更改。
5. 最后，询问："是否有不在默认值中但你想添加的章节？"（例如，语言特定惯用法、框架模式）。
6. 只有用户更改或添加的章节出现在输出文档中。

### 对于覆盖模式

这是彻底的。每个章节都会得到关注并出现在输出中。

1. 完整详细地浏览每个章节。
2. 用户确认、修改或替换每个章节。
3. 所有章节出现在输出中——未更改的使用默认值，更改的使用用户版本。

### 常见场景

- **"我同意一切"** → 不需要自定义文档。告诉用户："嵌入的默认值已激活并匹配你的偏好。不需要自定义文档——整洁代码原子将自动使用默认值。"
- **"我只同意除一个章节外的全部"** → 叠加模式，仅访谈那一个章节。
- **"我们使用更短的函数"** → 叠加 §2（阈值从约 20 改为团队偏好的任何值）。
- **"我们使用 Result 类型而非异常"** → 叠加 §8（错误处理模式根本改变）。
- **"我们是函数式团队——没有类"** → 叠加 §1（移除类内聚指导）、§5（函数式风格的参数模式）、§9（函数式模式强调）。
- **"我们想要更严格的复杂度限制"** → 叠加 §3（调整阈值，例如最大复杂度 5 而非 10）。
- **"我们有语言特定的惯用法"** → 叠加并添加，例如 §11 Go 特定模式、§12 Python 特定模式。

## 逐章访谈指南

读取 `./assets/template.md` 并遵循每个章节的 `<!-- 访谈指导： -->` 注释。这些注释包含要问的具体问题、追问问题以及什么是可自定义的、什么是固定的。

### 跨章节依赖表

早期章节的决策会影响后续章节。当用户更改早期章节时，标记依赖的章节：

| 决策位置 | 影响 | 如何影响 |
|-------------|---------|-----|
| §1 — 单一职责范围（类 vs 仅函数） | §2（提取目标）、§10（清单） | 函数式代码库仅提取为函数；基于类的代码库也提取为类 |
| §2 — 函数大小阈值 | §3（复杂度阈值）、§10（清单） | 更短的函数意味着更低的复杂度预算 |
| §3 — 复杂度阈值 | §2（函数大小） | 更低的复杂度限制可能需要更严格的函数大小 |
| §4 — 命名约定 | §7（注释必要性） | 更好的命名减少对"是什么"注释的需求 |
| §5 — 参数设计 | §1（单一职责信号） | 长参数列表通常表示单一职责违规 |
| §8 — 错误处理策略 | §9（可测试性模式） | Result 类型 vs 异常改变了错误路径的测试方式 |

当触发依赖时，告知用户："既然你更改了 [X]，我们也应该审查 [Y]——它受该决策影响。"

### 叠加模式特定的章节流程

对于 10 个默认章节中的每一个：

1. 用 2-3 句话总结该章节的关键点。
2. 询问："这与你的项目匹配吗？"
3. **是** → 移到下一章。该章节将不会出现在输出中。
4. **否** → 使用模板指导深入章节细节。生成用户版本。
5. 完成全部 10 章后，询问新增章节。

### 覆盖模式特定的章节流程

对于 10 个默认章节中的每一个：

1. 呈现该章节的完整内容。
2. 询问："这样可以吗，还是你想修改？"
3. **可以** → 将默认内容原样包含在输出中。
4. **修改** → 讨论更改，生成修改版本。
5. 完成全部 10 章后，询问新增章节。
6. 所有章节都进入输出。

## 输出组装

### 对于叠加模式

1. YAML 前置元数据：`mode: overlay`
2. 叠加引言文本（来自模板）
3. 仅列出包含章节的目录
4. 仅包含用户更改或添加的章节
5. 每个章节必须自包含——它是默认值中该章节的完整替换。不要写差异或部分章节。
6. 章节标题必须与 `defaults.md` 精确匹配（原子通过标题匹配章节）
7. 新章节（§11+）包含在默认章节之后
8. 页脚包含项目名称、日期、模式

### 对于覆盖模式

1. YAML 前置元数据：`mode: override`
2. 覆盖引言文本（来自模板）
3. 完整目录（全部 10+ 章节）
4. 所有章节：未更改的使用默认值，更改的使用用户版本，新章节在末尾
5. 页脚包含项目名称、日期、模式

### 对于两种模式

从输出中剥离所有 `<!-- 访谈指导： -->` 注释。最终文档是一份干净的规范。

**确定输出路径：**
1. 如果 `.lattice/config.yaml` 存在且有 `paths.clean_code`，使用该路径。
2. 否则，默认为 `.lattice/standards/clean-code.md`。

**写入文档：**
1. 如果 `.lattice/standards/` 目录（和 `.lattice/` 父目录）不存在则创建。
2. 将文档写入确定的路径。

**更新配置：**
1. 如果 `.lattice/config.yaml` 不存在，创建它并包含：
   ```yaml
   paths:
     clean_code: .lattice/standards/clean-code.md
   ```
2. 如果 `.lattice/config.yaml` 存在但没有 `paths.clean_code`，添加该键。保留所有现有内容。
3. 如果 `.lattice/config.yaml` 存在且已有该键，不需要配置更改。

**向用户确认：**
"你的整洁代码文档已写入 `[PATH]`，以 **[叠加|覆盖]** 模式。整洁代码原子现在将 [在默认值之上 | 代替默认值] 使用它。"

## 文档质量检查

在编写最终文档之前，验证：

### 叠加模式检查

- [ ] 每个包含的章节是自包含和完整的（不是差异或部分章节）
- [ ] 章节标题与 `defaults.md` 精确匹配（用于原子按章节匹配）
- [ ] 没有残留的 `<!-- 访谈指导： -->` 注释
- [ ] 前置元数据包含 `mode: overlay`
- [ ] 仅包含更改/添加的章节——未更改的章节被省略

### 覆盖模式检查

- [ ] 模板的每个章节都存在（§1 到 §10，加上任何新章节）
- [ ] 各章节的阈值一致（函数大小与复杂度限制对齐）
- [ ] 代码示例使用伪代码（语言无关，与 defaults.md 风格相同）
- [ ] 验证清单（§10）与 §1 到 §9 中定义的原则一致
- [ ] 没有残留的 `<!-- 访谈指导： -->` 注释
- [ ] 前置元数据包含 `mode: override`
- [ ] 文档可作为独立规范阅读

### 两种模式

- [ ] 前置元数据是有效的 YAML，具有正确的模式值
- [ ] 文档是格式良好的 Markdown
- [ ] 配置文件（`.lattice/config.yaml`）已正确更新
- [ ] 输出路径存在且可写入
