# 安全编码

## 配置解析

技能支持项目自定义。顺序：

1. 在仓库根目录查找 `.lattice/config.yaml`
2. 如果找到，检查 `paths.secure_coding` 是否存在自定义文档路径
3. 如果自定义路径存在，读取文档，检查 YAML 前置元数据中的 `mode`：
   - **`mode: override`**：使用自定义文档而非嵌入默认值
   - **`mode: overlay`**：先读取嵌入默认值，然后叠加自定义章节
4. 如果没有配置，读取 `./references/defaults.md`
5. **语言适配**：如果配置中存在 `paths.language_idioms`，读取"错误处理"章节，将 §1 错误消息模式适配到语言惯用法。

## 自检清单

在生成每个组件后**停止**。逐一验证所有检查项：

1. **信任边界**：受信任代码在哪里接触不受信任数据？所有边界是否明确识别？
2. **输入验证**：每个外部输入是否在边界处用允许列表验证后才到达业务逻辑？
3. **查询安全**：所有数据库查询是否参数化？查询构建中是否有字符串拼接？
4. **命令安全**：是否有 shell/命令执行？如果有，输入是否严格做允许列表限制？
5. **密钥**：代码中是否有 API 密钥、密码、令牌、连接字符串？如果有 → 移到环境变量或密钥管理器。
6. **输出编码**：输出是否根据渲染上下文（HTML、JSON、URL）进行适当编码？
7. **授权**：授权是否在服务层验证，而不仅是控制器？每个端点是否强制执行最小权限？
8. **错误消息**：暴露给用户的错误消息是否避免泄露内部细节（堆栈跟踪、SQL 查询、文件路径）？
9. **依赖**：新的第三方包是否必要？版本是否锁定或约束？是否添加了已知有漏洞的包？

## 主动反模式扫描

- [ ] **信任所有输入**、**SQL 字符串拼接**、**硬编码密钥**、**缺少授权**、**过于宽泛的权限**、**未验证的重定向**、**详细错误消息**、**记录敏感数据**

## 歧义信号与核心原则

安全编码管理生成代码的安全态势。与 clean-code 的边界：clean-code 管理错误消息的工艺；此技能管理错误消息不得泄露什么。与 architecture 的边界：architecture 定义检查的*位置*；此技能定义*检查什么*。

参见 `./references/defaults.md`。
