# Bug 修复

## 所需技能

根据 bug 范围加载这些技能（何时加载见步骤 2 和 5）：

1. `framework:knowledge-priming` -- （始终使用）
2. `framework:context-anchoring` -- （始终使用）
3. `framework:learning-harvest` -- （始终使用）
4. `framework:collaborative-judgment` -- （始终使用）
5. `framework:clean-code` -- （始终使用）
6. `framework:test-quality` -- （始终使用）
7. `framework:architecture` -- （条件使用）
8. `framework:domain-driven-design` -- （条件使用）
9. `framework:secure-coding` -- （条件使用）

## 工作流程

### 步骤 1：建立 Bug 上下文

从故障开始，而非从提议的修复开始。

- 收集**观察到的行为**、**预期行为**、**重现路径**，以及任何证据：失败的测试、错误消息、堆栈跟踪、日志摘录、请求载荷、最近的变更。
- 使用 `framework:learning-harvest` 加载行为。关注提示："bug 调查——关注：可靠性、质量信号"。
- 使用 `framework:context-anchoring` 的文档发现，检查受影响功能/模块的现有上下文文档。
  - **如果找到** → 加载它（context-anchoring 加载行为）。在诊断期间尊重已记录的决策 + 约束作为活动承诺。
  - **如果未找到** → 从 bug 报告 + 当前代码继续。不要因缺少上下文而阻塞诊断。

结束此步骤，用一句话总结 bug：

> "观察到 X，预期 Y，可通过 Z 重现。"

**停止：** 如果尚不能清晰陈述 bug，在提议代码更改之前收集更多证据。

### 步骤 2：重现和定位

**首要纪律**：不要为尚未重现的 bug 提出修复方案。

使用可用的最强证据重现故障，按此顺序：

1. **现有的失败自动化测试** -- 最佳情况；作为回归防护使用
2. **新的失败自动化测试** -- 当尚无测试时的首选
3. **可执行的重现路径** -- 当尚无法自动化时，命令、请求序列、确定性的手动流程

在编辑之前定位问题：

- **哪个层级可能是源头？** 使用 `framework:architecture` 的层级定义来识别缺陷起源于哪个架构层级
- **生产 bug 还是测试 bug？** 有时代码正确，测试/夹具错误
- **故障症状还是根本原因？** 崩溃行通常位于真实缺陷的下游
- **Bug 跨越信任边界？** 如果是，计划加载 `framework:secure-coding`
- **涉及领域不变量或聚合行为？** 如果是，计划加载 `framework:domain-driven-design`
- **修复可能触及多个层级或依赖流？** 如果是，计划加载 `framework:architecture`

如果仍存在多个可能的根本原因，使用 `framework:collaborative-judgment` 呈现主要假设 + 哪些证据可以区分。

在编写回归测试之前，明确陈述根本原因假设，使用 `framework:collaborative-judgment` 呈现：

> "Bug 由 [X] 引起。当 [C 成立] 时，正确结果应为 [P]。
>  通过编写在修复前为红、修复后为绿的测试来确认这一点。"

如果用户发现假设中的缺陷，在编写测试之前修订。

结束步骤时给出明确的 bug 契约：

> **C（bug 条件）：** [触发 bug 的确切输入/状态]
> **P（修复后置条件）：** [当 C 成立时正确行为的样子]
> **保留：** [对于 C 之外的所有输入，什么必须保持相同]

**停止：** 如果无法陈述全部三项，在编写测试之前继续定位。

**可选的持久化检查**：现在 bug 已重现 + 定位，决定是否持久化调查：

- 如果调查复杂，涉及多个假设，可能跨越多个会话，询问用户是否想持久化诊断 + 修复决策
- 如果存在相关上下文文档 → 计划在步骤 7 中丰富它
- 如果不存在 + 用户想要持久化 → 提议创建一个，按 `framework:context-anchoring` 确认文档名称，作为真相来源使用
- 如果用户不想要持久化或 bug 狭窄 + 局部 → 继续非持久化模式。修复工作流仍然适用；决策保留在会话中

### 步骤 3：首先添加回归保护

**阶段 A — Bug 条件测试（必须以 RED 开始）**

- 编写在 C 成立时触发的最小失败测试
- 优先使用在重现真实故障时不丢失信号的最低级别测试
- 以破坏的行为命名测试，而非实现细节
- 断言正确的预期结果（后置条件 P），而不仅仅是没有故障
- 内联应用 `framework:test-quality`
- 在未修复的代码上运行，确认 RED
  - 如果修复前即为绿，bug 条件假设错误——停止，重新定位

**停止规则**：

- **停止：** 如果无法创建稳定的失败自动化测试，在进行代码更改之前解释原因。
- 记录你最接近的可执行重现。
- 除非用户明确接受限制，否则不要将推测性修复作为"完成的"呈现，如果没有自动化重现器的话。
- 如果由于紧密耦合/深度集成而无法直接测试 bug，引入使测试成为可能所需的最小结构接缝（方法提取、参数注入、接口边界）。不是重构——是回归保护的前提条件。内联应用 `framework:clean-code`，保持接缝最小。

**阶段 B — 保留基线（必须保持 GREEN）**

- 识别覆盖 C 之外行为的现有测试
- 如果重要的相邻行为没有测试覆盖，最多添加 2-3 个针对性的特征测试
- 在应用修复之前确认所有保留基线测试为绿
- 这些测试必须在步骤 5 的每次更改中保持绿色——任何从绿变红意味着修复有副作用；停止，缩小范围

### 步骤 4：选择最小安全修复

将**修复策略**与代码更改本身分离。

在编辑之前，决定：

- **根本原因**是什么？
- 纠正它的**最小安全更改**是什么？
- 修复的正确层级（**正确修复位置**）是什么？
- 问题需要**局部补丁**还是**小的结构修正**？

默认选择恢复正确行为的最小安全修复，**不出现架构倒退**。

护栏：

- 在选择修复位置时应用 `framework:architecture` 分层规则——不要在外层打补丁，当规则属于内层时
- 不要将任务扩展为无关的清理
- 不要仅仅为了使测试套件变绿而删除/削弱失败测试
- 如果真正的修复需要超出狭窄修复范围的契约/设计更改，停止，明确讨论范围
- 不要为 C 之外的输入添加 guard 子句、null 检查、防御性处理——正确输入的代码路径必须在修复前后逐字节相同。

如果存在多个有效的修复策略且具有有意义的权衡，在继续之前使用 `framework:collaborative-judgment` 呈现。

### 步骤 5：实施修复

始终应用：

- `framework:clean-code` -- 保持变更聚焦、可读、易于推理
- `framework:test-quality` -- 维护回归测试 + 任何附近的支撑测试

根据定位的根本原因条件应用：

- **如果修复改变了层级职责、依赖方向、架构流程** → 应用 `framework:architecture`
- **如果修复改变了领域行为、不变量、聚合边界、值对象** → 应用 `framework:domain-driven-design`
- **如果修复触及输入验证、授权、查询、外部边界、敏感数据** → 应用 `framework:secure-coding`

实施修复后，在呈现之前：

1. 重新运行回归测试，确认现在为绿
2. 对更改的代码运行适用的原子自检清单
3. 运行适用的反模式扫描
4. 在呈现结果之前修复任何违规

### 步骤 6：验证无回归

在三个层面验证修复：

1. **修复证明** -- 修复前为红、修复后为绿的回归测试。断言正确的结果，而不仅仅是原始故障的消除。
2. **保留证明** -- 覆盖 bug 相邻行为的测试仍然通过。如果步骤 3 中添加了保留基线测试，必须保持绿色。任何从绿变红意味着修复有副作用——停止，在继续之前缩小范围。
3. **结构信心** -- 修复没有引入错误层级的变通方案、依赖违规、削弱的安全态势

报告完成时，明确验证范围：

- 重新运行了什么
- 现在什么通过了
- 什么未验证 + 为什么

如果修复狭窄 + 信心高，简要说明。如果验证不完整，清楚说明。

### 步骤 7：捕获根本原因并闭环

使用 `framework:context-anchoring` 丰富行为，持久化修复的重要部分：

- Bug 摘要：观察到的 vs 预期的行为
- 根本原因：实际什么失败了 + 在哪里
- 修复决策：为什么选择此修复而非替代方案
- 添加的保护：现在保护行为的回归测试或可执行重现器
- 更改的关键文件：路径 + 目的

如果没有上下文文档 + 修复暴露了非平凡的设计/领域教训，建议创建一个。

**收获经验。** 使用 `framework:learning-harvest` 收获行为。会话上下文："bug 调查——根本原因诊断和修复"。综合并提出本次会话的横切模式——根本原因类别、可能在其他地方重现的故障模式、边界条件缺口。用户确认哪些内容进入文档。**停止：在下面推荐 `/review` 之前运行此步骤。**

修复完成后，当更改满足以下条件时推荐 `/review`：

- 触及多个层级
- 更改安全敏感的代码
- 更改领域行为
- 引入了非平凡的结构修正
