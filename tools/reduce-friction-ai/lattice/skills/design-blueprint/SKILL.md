# 设计蓝图

## 所需技能

按顺序读取并应用技能：

1. `framework:knowledge-priming` -- 加载项目上下文（技术栈、架构、约定），让决策立足于真实项目
2. `framework:context-anchoring` -- 创建或加载功能上下文锚定文档
3. `framework:learning-harvest` -- 加载先前的操作经验指导设计；在会话结束时收获新模式（始终使用）
4. `framework:collaborative-judgment` -- 用结构化选项呈现真正的设计判断决策，而非默默假设（始终使用）
5. `framework:design-first` -- 遍历 5 个递进设计层级
6. `framework:architecture` -- 在组件和交互层级应用结构规则
7. `framework:domain-driven-design` -- 在组件、交互、契约层级应用领域建模

## 工作流程

### 步骤 1：建立上下文

使用 `framework:learning-harvest` 加载行为。关注提示："设计会话——关注：设计模式、可靠性、结构健康"。

使用 `framework:context-anchoring` 建立功能活文档。

- **文档发现**：检查是否存在功能的现有上下文锚定文档（扫描上下文基础目录，按功能名称或前置元数据匹配）。
- **如果存在** → 加载（context-anchoring 加载行为）。呈现结构化确认——功能名称、状态、决策数量、未决问题、约束。从文档中记录的最后一个设计检查点恢复。
- **如果不存在** → 创建（context-anchoring 创建行为）。从模板创建新功能文档。在创建前与用户确认功能名称、摘要和需求文档链接。

**加载需求约束**：从上下文文档前置元数据中读取 `requirement_doc`。
- 为 null/缺失 → 跳过。
- 本地路径 → 读取它。提取 `## 技术约束`。视为不可协商的——与架构规则具有同等权威。在 Level 1 之前向用户呈现。
- 外部引用（URL、工单 ID 或其他非本地路径标识符）→ 如果连接的 MCP 工具可以解析它，获取并以同样方式提取约束。如果没有连接 MCP 工具或获取返回空，要求用户直接粘贴当前约束——这是预期行为，不是错误。
- 设计过程中出现冲突 → 通过 `framework:collaborative-judgment` 呈现。用户决策；如果是本地文件，在需求文档的 `## 技术约束` 中记录任何变更。如果是外部引用，改为在上下文文档的决策日志中记录变更——本分子绝不向外部系统写入。

**写入反向链接**：如果 `requirement_doc` 解析为 `.lattice/requirements/features/{功能名称}.md` 的可读本地文件，则在其 `## Links` 章节中写入：`- Design: [{功能名称}.md](../../context/{功能名称}.md)`。离散的文件编辑，只做一次——如果链接已存在则跳过。

### 步骤 2：遍历设计层级

如果关键用例或成功标准现在不清晰，使用 `framework:collaborative-judgment` 呈现在开始 Level 1 之前需要回答的内容。

按顺序驱动 `framework:design-first` 的 5 个层级。每个层级，呈现设计输出，获得用户批准，然后**在推进前将批准的输出持久化到上下文锚定文档中**。

丰富规则和架构原子应用详见完整版 SKILL.md。包括零实现规则、范围扩展、设计摘要、状态设置为 `approved`、以及经验收获。

### 步骤 3：最终确定蓝图

Level 4（契约）批准并持久化后，验证完整性、检查需求规范偏差、写入设计摘要、设置 `status: approved`、记录完成决策、收获经验，并建议用户准备就绪时调用 `/code-forge`。
