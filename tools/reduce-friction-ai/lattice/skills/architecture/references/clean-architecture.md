# 整洁架构执行规则

这些是整洁架构模式的执行指令。定义了架构原子在 `architecture_mode` 为 `clean`（默认）时应用的自检清单、反模式扫描、歧义信号和结构原则。

详细内容（层级职责表、各层级规则、命令/查询流程示例、违规/修复对照）在 `./clean-architecture-defaults.md` 或团队的叠加/覆盖文档中。

## 自检清单

在生成每个组件后停止。逐一验证所有项目后再继续。如果某项检查失败，先修复代码再呈现。如果存在具有多种有效方法的判断决策（参见下文的歧义信号），则标记它——呈现选项和推理，而不是默默选择。

1. **操作类型**：状态变更（命令）还是读取（查询）？首先确定——决定整个流程。
2. **命令流程**：状态变更操作——数据在持久化前是否经过领域并通过仓库？领域不变量是否在持久化前得到执行？
3. **查询流程**：读操作——是否使用提供者（而非仓库）？在不需要执行不变量时是否避免了领域对象？
4. **依赖方向**：所有源代码依赖是否指向内部？领域层是否对外层零导入？
5. **层级位置**：每个类是否在正确的层级中？控制器仅做转换，应用服务编排，领域执行规则，基础设施实现接口。
6. **边界数据**：跨层边界的数据是否使用简单结构（DTO、纯对象）？没有框架特定类型或实体向外泄露。
7. **接口归属**：仓库接口是否定义在领域层中？提供者契约是否不在领域层中？
8. **单一层级**：每个类是否恰好属于一个架构层级？没有类同时涵盖 HTTP 解析、业务逻辑和数据库访问。

## 主动反模式扫描

在验证上述清单后，扫描输出中是否存在这些反模式。如果发现任何反模式，先修复再呈现代码。

- [ ] **控制器中的业务逻辑**：控制器做出超出转换范围的业务决策 → 提取到领域或用例中
- [ ] **领域依赖基础设施**：领域导入数据库客户端、HTTP 库或外部服务 → 在领域定义接口，在基础设施实现
- [ ] **上帝类**：单个类要为各种需求变更 → 按层级分解为专注的类
- [ ] **贫血架构**：层级在文件夹中存在但依赖规则未被强制执行 → 验证导入，添加接口
- [ ] **数据格式泄露**：数据库模式变更破坏 API 契约 → 在每个边界处映射 DAO、领域对象和响应 DTO
- [ ] **循环依赖**：两个层级相互导入（例如应用层导入基础设施类型，基础设施导入应用类型）→ 在内层引入接口
- [ ] **臃肿应用服务**：业务规则或领域逻辑堆积在编排层 → 将决策移入领域实体或领域服务
- [ ] **实体泄露**：领域对象直接从控制器返回而非映射为响应 DTO → 添加边界映射步骤

## 歧义信号

这些检查通常有多种有效结果。遇到时，呈现选项而非默默选择。

- **层级位置**：协调领域对象但也包含业务规则的逻辑，可以是领域服务或应用服务。区分：逻辑本身是业务规则，还是在编排业务规则？
- **查询复杂性**：读操作需要在返回数据前执行业务规则，这模糊了提供者和仓库的边界。
- **DTO 粒度**：每个端点一个 DTO 还是相关端点间共享 DTO——类型安全和重复之间的权衡。

## 核心原则

整洁架构关乎**结构**——代码位于何处，存在哪些层级，依赖流向何方。区别于 DDD，DDD 关乎在领域层*内部*精心制作领域逻辑。此技能处理结构外壳；DDD 处理其内部的领域制作。

结构约束：业务规则可独立测试，不与框架、UI、数据库或外部机构耦合。任何外层组件都可以在不触及领域逻辑的情况下进行替换。

## 依赖规则

使架构生效的单一规则：**源代码依赖只能指向内部。**

内层没有任何东西知道外层。外层声明的任何名称——函数、类、变量、数据格式——不能被内层代码提及。

原因：隔离。当内层对外层无知时，可以替换、重写或删除任何外层，而不会向内产生级联变更。

当控制流必须向外（例如，用例需要调用仓库），使用**依赖反转**：内层定义接口，外层实现它。源代码依赖指向内部，即使运行时调用指向外部。跨边界的数据应为简单结构——DTO、纯对象、基本类型——绝不能是框架特定类型。

关于层级职责表、各层级规则、命令/查询流程示例和违规/修复对照，参见 `./clean-architecture-defaults.md`。
