# 领域驱动设计

## 配置解析

技能支持项目自定义。解析：

1. 在仓库根目录查找 `.lattice/config.yaml`
2. 如果找到，检查 `paths.ddd_principles` 自定义文档路径
3. 如果自定义路径存在，读取文档，检查 YAML 前置元数据中的 `mode`：
   - **`mode: override`**（或没有模式）：自定义文档完全优先。使用它而非嵌入默认值。必须全面——作为唯一参考。
   - **`mode: overlay`**：先读取嵌入的 `./references/defaults.md`，然后将自定义文档的章节叠加在上面。自定义章节替换默认值中匹配的章节（按标题匹配）。新章节追加在默认值之后。
4. 如果没有配置、没有路径或路径未找到，读取 `./references/defaults.md`
5. **语言适配**：如果配置中存在 `paths.language_idioms`，读取 **"类型系统与对象模型"** 章节，将实体、值对象和聚合实现模式适配到语言结构（例如 struct vs class、trait vs interface、data class vs record）。语言惯用法优先于伪代码默认值。

## 自检清单

在生成每个组件后**停止**。在继续之前逐一验证所有项。**停止：** 如果任何检查失败，在呈现之前修复。如果检查是判断决策且存在多种有效方法（见歧义信号），则标记——呈现选项和推理而非默默选择。

1. **实体 vs 值对象**：每个领域对象——业务是否需要随时间跟踪单个实例？是 → 具有标识的实体。否 → 不可变且自验证的值对象。
2. **聚合边界**：事务性不变量是否要求此对象在聚合内部？如果不是 → 通过 ID 引用分离的聚合。
3. **丰富行为**：实体是否有强制执行业务规则、守卫状态转换、触发事件的方法？如果实体只是数据容器 → 将逻辑从服务移入实体。
4. **值对象覆盖率**：扫描应为值对象的基本类型——字符串 email、数字金额、原始 UUID 作为标识符 → 包装为带验证的值对象。
5. **聚合内聚**：列出根强制执行的业务规则。每个内部实体是否参与至少一个不变量？如果不是 → 属于它自己的聚合。
6. **领域事件**：是否为其他聚合需要响应、变更触发通知、审计/合规需求的状态转换触发领域事件？不为无响应的内部变更触发事件。
7. **领域服务**：跨多个实体的无状态逻辑是否放在领域服务而非应用服务中？是否避免 I/O 和基础设施调用？
8. **工厂**：复杂聚合创建是否封装在工厂方法（`Order.create(...)`）或独立工厂类中？初始创建和从持久化重建是否分开处理？

## 主动反模式扫描

- [ ] **贫血领域模型**：实体只是数据容器只有 getter/setter；所有逻辑在服务中 → 将业务规则移入实体和值对象
- [ ] **基本类型偏执**：原始字符串表示 email、数字表示金额、UUID 表示 ID → 包装为带验证和行为的值对象
- [ ] **上帝聚合**：聚合有很多实体、加载慢、高争用 → 分解，仅保留共享事务不变量的
- [ ] **跨聚合事务**：服务在一个事务中更新两个聚合 → 使用领域事件实现最终一致性
- [ ] **领域逻辑泄露**：业务规则在控制器、应用服务或基础设施中 → 提取到领域对象或领域服务
- [ ] **实体/值对象误判**：没有生命周期的实体，或有标识跟踪的值对象 → 应用标识测试

## 歧义信号

- **聚合边界大小**：小聚合（更多事件、最终一致性）vs 大聚合（简单事务、即时一致性）。没有固有的对错——取决于争用模式和不变量范围。
- **实体 vs 值对象**：某些概念（如 `Address` 或 `Money`）可能需要也可能不需要标识，取决于领域复杂性。应用标识测试，但在临界情况时承认。
- **领域服务 vs 实体方法**：跨多个实体的逻辑可以放在领域服务中，也可以作为主要实体的方法。选择取决于哪个实体"拥有"不变量。
- **对象创建模式**：聚合根上的工厂方法、独立工厂类、构建器模式或普通构造函数——取决于组装复杂性和团队约定。不规定模式；询问团队偏好哪种方法。

## 范围声明

技能在单个仓库、单个限界上下文内操作（例如，一个 API——订单、用户、定价）。仅覆盖战术 DDD 模式——不包括战略 DDD（无上下文映射、无微服务拓扑、无限界上下文集成）。

关于聚合设计规则、实体/值对象/领域服务/领域事件/仓库/创建模式及代码示例、内联反模式警告和分解指南，参见 `./references/defaults.md`。
