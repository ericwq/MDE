# 架构精炼器

## 步骤 0：风格选择

在任何事情之前，询问用户他们团队使用哪种架构风格：

"你的团队使用哪种架构风格？

1. **整洁架构**（默认）——层级（领域、应用、接口、基础设施），依赖反转，命令/查询分离
2. **六边形 / 端口与适配器**——核心领域被端口包围，适配器在外围
3. **模块化单体**——垂直切片，每个模块拥有自己的层级
4. **自定义 / 从头定义**——你来描述层级和规则"

**分支：**

- **选项 1** → 进入下面的整洁架构流程（现有访谈）。模板：`./assets/template-clean-arch.md`。输出：`.lattice/standards/architecture.md`。配置键：`paths.architecture`。不需要 `architecture_mode` 键（默认为 `clean`）。
- **选项 2–4** → 进入通用架构流程。模板：`./assets/template-generic.md`。输出：`.lattice/standards/architecture.md`。配置键：`paths.architecture`。另外，在 `.lattice/config.yaml` 中设置 `architecture_mode: custom`。

本文档的其余部分描述**整洁架构流程**（选项 1）。对于**通用流程**（选项 2–4），读取 `./assets/template-generic.md` 并遵循其中的 `<!-- 访谈指导： -->` 注释。下面的引导方法、对话风格、输出组装和文档质量检查适用于两种流程——替换相应的模板、输出路径和配置键。

## 这将产出什么

**对于整洁架构（选项 1）：**

- **输出**：`.lattice/standards/architecture.md`（或来自 `.lattice/config.yaml` → `paths.architecture` 的自定义路径）
- **两种模式**：
  - **叠加（Overlay）**（`mode: overlay`）：一份精简文档，仅包含与默认值不同的章节。架构原子首先读取其嵌入的整洁架构默认值，然后将本文档的章节叠加在上面。这是预期的常见情况。
  - **覆盖（Override）**（`mode: override`）：一份全面的独立文档，完全替换原子嵌入的默认值。适用于想从头定义整洁架构的团队。
- **默认模式**：叠加——仅产出用户想要更改的内容
- **配置键**：`.lattice/config.yaml` 中的 `paths.architecture`
- **模板**：读取 `./assets/template-clean-arch.md` 获取完整的文档结构、默认内容和访谈指导注释

**对于其他风格（选项 2–4）：**

- **输出**：`.lattice/standards/architecture.md`（或来自 `.lattice/config.yaml` → `paths.architecture` 的自定义路径）
- **模式**：始终为 `override`——对于非整洁架构风格没有嵌入默认值可供叠加
- **配置键**：`.lattice/config.yaml` 中的 `paths.architecture`
- **额外配置**：在 `.lattice/config.yaml` 中设置 `architecture_mode: custom`
- **模板**：读取 `./assets/template-generic.md` 获取文档结构和访谈指导注释

## 开始之前

### 检查现有文档

在开始访谈之前，检查是否已经存在自定义文档：

1. 读取 `.lattice/config.yaml`——检查 `paths.architecture`。
2. 如果相关路径存在（基于步骤 0 中选择的风格），读取该文件。询问用户：
   - "你已有一份自定义架构文档。你想要**修订**它（更新特定章节）、**重新开始**（新访谈），还是**添加**（添加新章节）？"
   - 修订：加载现有文档，仅浏览用户想要更改的章节，原地更新。
   - 重新开始：继续下面的完整访谈流程。
   - 添加：跳到访谈的"新章节"部分。
3. 如果没有配置或没有现有文档，继续完整访谈流程。

### 扫描仓库

寻找能指导对话的信号：

- **目录结构**：`src/`（或等效目录）是否已有层级？它们叫什么名字？
- **现有模式**：是否有现有的控制器、服务、仓库、提供者？使用什么命名约定？
- **依赖注入模式**：是否有 DI 容器、手动注入或框架提供的注入？
- **架构文档**：任何现有的架构文档（ADR、README 章节）？
- **框架**：使用什么框架？（NestJS、Spring、Django 等）这会影响命名约定和常见模式。

在开始时与用户分享相关发现："我注意到你的项目已经有 [X 结构]。我将使用它作为上下文。"

如果项目是全新的，没有代码，则将纯默认值作为起点。

## 选择模式

对话中的第一个决策。呈现三个选项：

"你想如何定义你的架构原则？

1. **自定义特定章节**（叠加）——保留默认值，只更改与你项目不同的部分。这生成一份精简文档。大多数团队选择此项。
2. **从头定义一切**（覆盖）——浏览所有章节，生成一份全面的独立文档。
3. **仅添加项目特定章节**（叠加并添加）——保持所有默认值不变，为团队特定规则添加新章节。

默认值很好地覆盖了标准整洁架构。除非你的架构有根本性的不同，推荐选项 1。"

映射选择：
- 选项 1 和 3 → `mode: overlay`
- 选项 2 → `mode: override`

## 引导方法

### 对话风格

- **一次一章。** 不要一次性抛出所有问题。按顺序浏览模板。
- **默认值优先。** 对于每个章节，简要总结默认值，然后询问是否匹配。不要逐字读出整个默认值——总结关键点并询问。
- **记录决策，而非讨论。** 输出文档读起来像规范，不是会议笔记。"我们讨论了 X 并决定 Y"是错的。"Y"是对的。
- **追问，而非审问。** 使用模板指导注释中的追问问题作为用户回答模糊时的后续问题，而不是作为清单。

### 对于叠加模式

这应该很快。许多章节将是"保持原样"。

1. 简要呈现每个章节的默认值（2-3 句总结，不是完整内容）。
2. 询问："这与你的项目匹配吗，还是你想更改？"
3. 如果用户说匹配 → 跳过（该章节不会出现在输出中）。
4. 如果用户想更改 → 深入该章节，讨论具体内容，记录更改。
5. 最后，询问："是否有不在默认值中但你想添加的章节？"（例如，命名约定、框架特定规则）。
6. 只有用户更改或添加的章节出现在输出文档中。

### 对于覆盖模式

这是彻底的。每个章节都会得到关注并出现在输出中。

1. 完整详细地浏览每个章节。
2. 用户确认、修改或替换每个章节。
3. 所有章节出现在输出中——未更改的使用默认值，更改的使用用户版本。

### 常见场景

- **"我同意一切"** → 不需要自定义文档。告诉用户："嵌入的默认值已激活并匹配你的偏好。不需要自定义文档——架构原子将自动使用整洁架构默认值。"
- **"我只同意除一个章节外的全部"** → 叠加模式，仅访谈那一个章节。
- **"我们使用 CQRS"** → 叠加 §3.2 + §4（它们是耦合的——CQRS 改变了服务模式，进而改变两种流程）。
- **"我们不使用 Provider"** → 叠加 §3.4 + §4.2 + §4.3 + §6（Provider 移除会波及查询流程和验证）。
- **"我们有额外的层级"** → 叠加 §1 + §2 + §3（新层级需要职责、依赖位置和各层级规则）。

## 逐章访谈指南

读取 `./assets/template-clean-arch.md`（用于整洁架构）或 `./assets/template-generic.md`（用于其他风格），并遵循每个章节的 `<!-- 访谈指导： -->` 注释。这些注释包含要问的具体问题、追问问题以及什么是可自定义的、什么是固定的。

### 跨章节依赖表

早期章节的决策会影响后续章节。当用户更改早期章节时，标记依赖的章节：

| 决策位置 | 影响 | 如何影响 |
|-------------|---------|-----|
| §1 — 层级名称 | 所有章节 | 名称必须到处一致 |
| §1 — 额外层级 | §2（图表）、§3（各层级规则） | 新层级需要依赖位置和规则 |
| §3.2 — 服务模式（统一 vs CQRS） | §4.1、§4.2 | CQRS 使用分离的处理器而非统一服务 |
| §3.4 — 提供者模式（是/否） | §4.2、§4.3、§6 | 无提供者 → 读操作通过仓库；比较表和清单改变 |

当触发依赖时，告知用户："既然你更改了 [X]，我们也应该审查 [Y]——它受该决策影响。"

### 叠加模式特定的章节流程

对于 6 个默认章节中的每一个：

1. 用 2-3 句话总结该章节的关键点。
2. 询问："这与你的项目匹配吗？"
3. **是** → 移到下一章。该章节将不会出现在输出中。
4. **否** → 使用模板指导深入章节细节。生成用户版本。
5. 完成全部 6 章后，询问新增章节。

### 覆盖模式特定的章节流程

对于 6 个默认章节中的每一个：

1. 呈现该章节的完整内容。
2. 询问："这样可以吗，还是你想修改？"
3. **可以** → 将默认内容原样包含在输出中。
4. **修改** → 讨论更改，生成修改版本。
5. 完成全部 6 章后，询问新增章节。
6. 所有章节都进入输出。

## 输出组装

### 对于叠加模式

1. YAML 前置元数据：`mode: overlay`
2. 叠加引言文本（来自模板）
3. 仅列出包含章节的目录
4. 仅包含用户更改或添加的章节
5. 每个章节必须自包含——它是默认值中该章节的完整替换。不要写差异或部分章节。
6. 章节标题必须与 `clean-architecture-defaults.md` 精确匹配（原子通过标题匹配章节）
7. 新章节（§7+）包含在默认章节之后
8. 页脚包含项目名称、日期、模式

### 对于覆盖模式

1. YAML 前置元数据：`mode: override`
2. 覆盖引言文本（来自模板）
3. 完整目录（全部 6+ 章节）
4. 所有章节：未更改的使用默认值，更改的使用用户版本，新章节在末尾
5. 页脚包含项目名称、日期、模式

### 对于两种模式

从输出中剥离所有 `<!-- 访谈指导： -->` 注释。最终文档是一份干净的规范。

**确定输出路径：**

1. 如果 `.lattice/config.yaml` 存在且有 `paths.architecture`，使用该路径。
2. 否则，默认为 `.lattice/standards/architecture.md`。

这对所有风格都一样——整洁架构自定义和其他风格都写入 `paths.architecture`。

**写入文档：**
1. 如果 `.lattice/standards/` 目录（和 `.lattice/` 父目录）不存在则创建。
2. 将文档写入确定的路径。

**更新配置：**

对于整洁架构（选项 1）：
1. 如果 `.lattice/config.yaml` 不存在，创建它并包含：
   ```yaml
   paths:
     architecture: .lattice/standards/architecture.md
   ```
2. 如果 `.lattice/config.yaml` 存在但没有 `paths.architecture`，添加该键。保留所有现有内容。
3. 如果 `.lattice/config.yaml` 存在且已有该键，不需要配置更改。

对于其他风格（选项 2–4）：
1. 如果 `.lattice/config.yaml` 不存在，创建它并包含：
   ```yaml
   paths:
     architecture: .lattice/standards/architecture.md
   architecture_mode: custom
   ```
2. 如果 `.lattice/config.yaml` 存在，添加或更新：
   - `paths.architecture` 指向输出路径
   - `architecture_mode: custom`
   - 保留所有现有内容。

**向用户确认：**

对于整洁架构：
"你的架构文档已写入 `[PATH]`，以 **[叠加|覆盖]** 模式。架构原子现在将 [在整洁架构默认值之上 | 代替整洁架构默认值] 使用它。"

对于其他风格：
"你的架构文档已写入 `[PATH]`，已设置 `architecture_mode: custom`。架构原子将使用它作为你项目的唯一架构标准。"

## 文档质量检查

在编写最终文档之前，验证：

### 叠加模式检查

- [ ] 每个包含的章节是自包含和完整的（不是差异或部分章节）
- [ ] 章节标题与 `defaults.md` 精确匹配（用于原子按章节匹配）
- [ ] 没有残留的 `<!-- 访谈指导： -->` 注释
- [ ] 前置元数据包含 `mode: overlay`
- [ ] 仅包含更改/添加的章节——未更改的章节被省略

### 覆盖模式检查

- [ ] 模板的每个章节都存在（§1 到 §6，加上任何新章节）
- [ ] 层级名称在所有章节中一致
- [ ] 依赖图（§2）匹配层级表（§1）
- [ ] 代码示例使用伪代码（语言无关，与 defaults.md 风格相同）
- [ ] 验证清单（§6）与 §3 和 §4 中定义的规则一致
- [ ] 没有残留的 `<!-- 访谈指导： -->` 注释
- [ ] 前置元数据包含 `mode: override`
- [ ] 文档可作为独立规范阅读

### 通用流程检查（选项 2–4）

- [ ] 文档前置元数据包含 `mode: override`
- [ ] §1 到 §7 章节存在（§8 歧义信号是可选的，加上任何新章节）
- [ ] 层级名称在所有章节中一致
- [ ] 依赖图（§2）匹配层级表（§1）
- [ ] §6（验证清单）至少包含 3 个具体、可验证的检查项
- [ ] §7（反模式）至少包含 3 个反模式及其症状和修复方法
- [ ] 没有残留的 `<!-- 访谈指导： -->` 注释
- [ ] 文档可作为独立规范阅读
- [ ] 配置已设置 `architecture_mode: custom`

### 两种模式（所有流程）

- [ ] 前置元数据是有效的 YAML，具有正确的模式值
- [ ] 文档是格式良好的 Markdown
- [ ] 配置文件（`.lattice/config.yaml`）已正确更新
- [ ] 输出路径存在且可写入
