# 整洁代码

## 配置解析

技能支持项目自定义。顺序：

1. 在仓库根目录查找 `.lattice/config.yaml`
2. 如果找到，检查 `paths.clean_code` 是否存在自定义文档路径
3. 如果自定义路径存在，读取文档并检查 YAML 前置元数据中的 `mode`：
   - **`mode: override`**（或没有模式）：自定义文档完全优先。使用它而不是嵌入默认值。必须全面——作为唯一参考。
   - **`mode: overlay`**：先读取嵌入的 `./references/defaults.md`，然后将自定义文档的章节叠加在上面。自定义章节替换默认值中匹配的章节（按标题匹配）。新章节追加在默认值之后。
4. 如果没有配置/路径/文件，读取 `./references/defaults.md`
5. **语言适配**：如果配置中存在 `paths.language_idioms`，读取该文档并使用以下章节适配默认值：
   - **"错误处理"** → 将 §8（错误处理）模式适配到语言惯用法。语言惯用法优先于伪代码默认值。
   - **"类型系统与对象模型"** → 将 §1（单一职责）内聚指导适配到语言结构（例如 struct vs class）。
   - **"命名约定"** → 将 §4（有意义的命名）模式适配到语言约定。
   - **"参数与函数设计"** → 将 §2（小而专注的函数）和 §5（参数设计）适配到语言能力。
   - **"依赖管理"** → 将 §9（可测试代码）依赖注入模式适配到语言惯用法。

## 自检清单

在每个组件之后**停止**。逐一验证所有项目。在呈现之前修复任何失败的检查。判断决策 → 标记并附选项（见歧义信号）。

1. **单一职责**：描述每个函数时不需要用"和"？如果不行 → 提取为单独的函数。
2. **大小**：每个函数是否在已加载文档的大小阈值（默认约 20 行）以下？如果不行 → 将子操作提取为命名函数。
3. **复杂性**：圈复杂度是否在已加载文档的阈值（默认约 10）以下？如果不行 → 用 guard 子句简化、提取分支。
4. **抽象层级**：每个函数是否在一个层级上操作？如果高层级与低层级混合 → 提取细节。
5. **命名**：函数/变量名是否无需上下文就揭示意图？如果不行 → 重命名为自说明。
6. **参数**：参数数量是否在已加载文档的阈值（默认 4 个）以下？如果不行 → 分组为对象。
7. **基本类型偏执**：String/number/boolean 用命名类型更清晰？如果是 → 引入参数对象或类型包装器。
8. **错误处理**：每个可能失败的操作是否有带可操作信息的显式处理？是否在正确的层级处理？

**项目特定检查：** 如果已加载文档（来自配置解析）包含验证清单章节（§10），在以上清单之后将这些检查作为额外的项目特定验证来应用。

## 主动反模式扫描

在清单之后，扫描以下内容。如果发现，在呈现之前修复。

- [ ] **上帝函数**：函数超过约 30 行做多件事；描述需要"和"→ 提取专注的函数
- [ ] **深层嵌套**：三级以上缩进 → 用提前返回/guard 子句扁平化
- [ ] **晦涩命名**：变量如 `d`、`tmp2`、`processData` → 重命名揭示意图
- [ ] **长参数列表**：五个以上参数 → 分组为对象或拆分函数
- [ ] **过早抽象**：只有两个相似块就提取的工具函数 → 保持内联，直到有相同变更原因的第三个实例
- [ ] **吞没错误**：空 catch、通用的"出了点问题"、默默返回 null → 显式处理
- [ ] **注释作为除臭剂**：注释解释绕来绕去的代码而不是重构 → 重命名为自说明；只保留"为什么"注释，删除"是什么"
- [ ] **隐藏副作用**：命名为 `getX` 的函数还写入缓存/发送通知 → 重命名或分离
- [ ] **死代码**：注释掉的代码块、未使用的导入、不可达分支 → 删除（版本控制会保留）
- [ ] **不可测试逻辑**：副作用与业务逻辑纠缠；单元测试需要模拟 I/O → 将副作用推到边界，提取纯函数，注入依赖

## 歧义信号

多种有效结果。呈现选项而非默默选择。关于以下每个信号的解决方案指导见 `./references/defaults.md`。

- **单一职责**：两个紧密耦合的顺序操作可能是一个职责（管道），而非两个。"和"测试会捕获真正的违规和假阳性。
- **函数大小**：接近阈值（20-30 行）但有一个明确目的——提取可能产生五个不清晰的小函数。呈现权衡。
- **DRY vs 过早抽象**：两个相同的代码块可能服务于不同的目的并且之后会分化。在有相同变更原因的第三个实例之前，真正存在歧义。
- **错误处理策略**：异常 vs Result 类型 vs 错误码取决于语言惯用法和团队约定，而非通用的。
