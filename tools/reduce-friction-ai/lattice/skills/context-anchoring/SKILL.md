# 上下文锚定

## 范围

> 仅限功能级别——在功能从设计 → 实现 → bug 修复 → 重构的流转中锚定决策。

## 配置解析

技能管理每个功能上下文文档的目录。解析顺序：

1. 在仓库根目录查找 `.lattice/config.yaml`
2. 如果找到，检查 `paths.context_base` 是否存在自定义目录路径
3. 如果自定义路径存在，使用该目录存放上下文文档
4. 如果没有配置/路径/路径未找到，使用默认 `.lattice/context/`

每个功能在 `<context_base>/<feature-name>.md` 有一个文档。没有默认原则，没有叠加模式，没有覆盖文件——只有精简的模板和通过丰富不断增长的每功能文档。

## 问题

AI 没有持久记忆。上下文衰减是真实的：到消息 30+ 时，早期决策被矛盾、命名不一致、"为什么"蒸发。损害累积——遗忘的决策成为潜在的矛盾，丢失的约束成为违规，未解决的问题成为沉默的假设。

上下文锚定文档解决：

- **功能绑定**——每个功能一个文档，仅限范围的决策
- **决策聚焦**——为每个选择捕获什么、为什么、还考虑了什么
- **仅追加**——决策永不删除/重写，仅按时间顺序添加
- **跨会话**——文档比对话更持久，将上下文向前传递
- **Git 原生**——存在于仓库中，与代码一起版本化

每个功能两份文档：**需求文档**（静态，事先编写，不由本技能管理）和**上下文锚定文档**（活的、演进的，由本技能管理）。需求文档定义*构建什么*。上下文锚定文档捕获*如何*和*为什么*——在开发过程中涌现的决策、约束和推理。

需求文档可能存在于本仓库中，或团队已有的任何跟踪需求的系统（Jira、Linear、wiki）中——无论它在何处，本原子绝不向其写入。

## 文档生命周期

三种行为管理上下文锚定文档的生命周期。每种行为可被动触发（用户要求）或主动触发（AI 建议）。两种情况下，AI **始终在行动前确认**——提议，用户决定。

| 行为 | 目的 | 被动触发 | 主动触发 |
|----------|---------|-----------------|-------------------|
| **创建** | 开始新上下文文档 | 用户要求创建一个 | AI 检测到功能工作开始但没有文档 |
| **加载** | 从现有文档恢复上下文 | 用户要求加载/恢复 | AI 检测到现有文档并建议加载 |
| **丰富** | 添加新决策、约束、解决方案 | 用户要求捕获某些内容 | AI 检测到对话中做出了决策 |

## 状态生命周期

每个上下文文档携带一个 `status` 前置元数据字段。永远不要从正文文本推断状态。

| 值 | 设置者 |
|---|---|
| `draft` | `context-anchoring` 创建——设计尚未完成 |
| `approved` | `design-blueprint` 步骤 3——L1–L4 完成，设计已审查 |
| `complete` | `code-forge` 步骤 5——实现完成 |

**停止：在对上下文文档采取行动前检查此字段。** `draft` ≠ 已批准。`approved` ≠ 完成。偏离已批准设计：更新文档并重新批准——没有新的状态值。

## 创建行为

创建前始终确认。

**步骤**：

1. **识别功能名称。** 从功能名称推导 kebab-case 文件名（例如，"用户认证" → `user-authentication.md`）。与用户确认名称。
2. **询问需求文档。** 如果用户有需求文档，为 `requirement_doc` 前置元数据字段捕获它——本地文件路径，或外部引用（URL、工单 ID，或可通过连接的 MCP 工具解析的其他标识符）。如果没有，留 `null`。
3. **创建目录**——如果 `<context_base>/` 尚不存在则创建。
4. **从模板生成。** 读取 `./assets/feature-doc-template.md` 并填入：
   - 前置元数据：`feature`、`requirement_doc`、`created`（今天日期）、`status: draft`
   - H1 标题：功能名称
   - 摘要：单行描述（询问用户或从上下文推导）
   - 如果模板文件未找到，使用以下最小结构生成文档：
     ```
     ---
     feature: <功能名称>
     requirement_doc: <本地路径、外部引用或 null>
     created: <今天的日期>
     status: draft
     ---
     # <功能名称>
     <单行摘要>
     ## 决策日志
     | 日期 | 决策 | 推理 | 考虑过的替代方案 |
     |------|----------|-----------|------------------------|
     ## 未决问题
     无。
     ## 约束
     无。
     ## 关键文件
     | 路径 | 角色 |
     ```
5. **确认创建。** 向用户展示提议的路径和内容摘要。

## 加载行为

加载前始终确认。

**步骤**：

1. **读取上下文文档。** 解析前置元数据和所有章节。
2. **解析链接的需求文档**——如果 `requirement_doc` 不为 null。本地路径 → 直接读取。外部引用（URL、工单 ID 或其他标识符）且连接的 MCP 工具可以解析它 → 尝试获取。两者都不适用 → 要求用户直接粘贴当前需求约束——这是预期行为，不是错误。使用解析到的任何内容来理解功能目标和范围，但不修改。
3. **呈现结构化确认**（见下面的输出格式）：
   - 功能名称和摘要
   - **状态**（来自前置元数据 `status` 字段——显式呈现）
   - 需求文档状态（已链接或未链接）
   - 决策数量和最新决策
   - 未决问题（如有）
   - 约束（如有）
4. **尊重所有已记录的决策。** 日志中的每个决策被视为活动承诺。未经明确讨论和解释变更的新决策条目，绝不能与已记录决策矛盾。
5. **尊重约束为不可协商的。** 约束比决策更硬——代表未经有意的、有记录的覆盖不能跨越的边界。
6. **当工作触及未决问题时标记。** 如果当前任务涉及存在未解决问题的领域，立即呈现。不默默假设答案。

## 丰富行为

写入前始终确认。

**在决策日志中捕获什么**：

- **日期**——决策做出的时间
- **决策**——决定了什么，清晰简明地陈述
- **推理**——为什么做出此选择，关键因素
- **考虑过的替代方案**——还评估了什么以及为什么拒绝

**规则**：

1. **仅追加。** 新条目放在决策日志表的底部。绝不修改或删除现有条目。
2. **按时间顺序。** 条目反映决策做出的顺序，不按主题分组。
3. **简明但完整。** 每个条目无需重新阅读整个会话即可独立理解。
4. **仅功能绑定。** 仅捕获与此特定功能相关的决策。横切关注点、项目范围的约定、通用偏好归于其他地方。
5. **明确解决未决问题。** 当未决问题被回答时，将答案作为决策添加到日志中，并从未决问题列表中移除该问题。
6. **约束不可协商。** 一旦约束被记录，它即具有约束力。更改约束需要新的决策条目来解释为什么约束正在被修订。
7. **约束覆盖协议。** 如果用户明确表示覆盖约束（例如，"忘掉那个约束，我们已经改变方向了"），不要默默删除。改为：(a) 要求用户明确确认覆盖，(b) 在约束章节中划掉约束（以 `~~` 前缀），以及 (c) 在决策日志中添加决策条目记录覆盖和推理。约束历史得以保留；约束状态被撤销。
8. **关键文件去重。** 添加到关键文件表时，检查路径是否已存在于表中。如果存在——跳过。
9. **横切检查。** 丰富后，应用 learning-harvest 的横切测试：(1) 它是否命名了一种模式或方法，而非功能特定的事实？(2) 开发另一个功能的开发者能否在不知道此功能上下文的情况下应用它？如果两项都通过——静默添加到 learning-harvest 队列。此处不提示用户。

## 文档发现

当用户要求加载或恢复但未指定哪个功能时：

1. **扫描上下文基础目录**中的 `.md` 文件。
2. **按前置元数据** `feature` 字段或按文件名匹配。
3. **如果存在多个文档**，呈现带功能名称、创建日期和决策数量的编号列表。让用户选择。
4. **如果只有一个文档存在**，建议加载它。在继续之前确认。
5. **如果没有文档存在**，通知用户并建议创建一个。
6. **模糊匹配**：如果用户术语部分匹配多个文档（例如，"auth" 匹配 `user-authentication.md` 和 `oauth-authentication.md`），显示所有部分匹配及其完整文件名，让用户选择。绝不猜测。

当用户在对话中提到功能名称时，检查是否存在匹配的上下文文档。如果存在且在此会话中未加载，建议加载它。

## 输出格式

**加载**：显示功能名称、**状态**（来自前置元数据）、需求文档状态、决策数量、未决问题、约束、最新决策。以以下内容结束："所有已记录的决策是活动的。约束是不可协商的。当工作触及未决问题时我会标记。"

**丰富**：显示确切将被添加的内容（决策、推理、考虑过的替代方案）。在写入前等待确认。

**创建**：显示提议的路径、功能名称、需求文档链接。在创建前等待确认。

## 与其他技能的集成

此原子由编排功能工作流的分子组合使用：

- **`design-blueprint`**——在步骤 1（建立上下文）中调用**创建**或**加载**，然后在每个设计层级检查点调用**丰富**以捕获涌现的决策。
- **`code-forge`**——在步骤 1（建立实现上下文）中调用**加载**以加载蓝图，然后在步骤 3-5 中调用**丰富**以捕获实现决策、关键文件、已解决问题。

当上下文文档活动时（在当前会话中加载），**丰富**持续运行——AI 监控对话中值得捕获的决策，并在出现时建议丰富。不限于加载文档的分子；任何产生决策的技能都可以触发丰富建议。
