# 架构指南针

## 所需技能

读取并应用：

1. `framework:knowledge-priming` -- 加载代码库上下文：语言、框架、结构、约定（始终使用）
2. `framework:architecture` -- 架构审计视角和推荐方向护栏（始终使用）
3. `framework:domain-driven-design` -- 仅限战略 DDD：限界上下文、领域接缝（条件使用：仅当领域复杂性值得时才应用）
4. `framework:collaborative-judgment` -- 在共同设计轮次中呈现判断决策（始终使用）

## 工作流程

### 步骤 1：加载现有上下文

**首先检查是否已有洞察文档。** 如果 `.lattice/insights/architecture.md` 已存在：
- 读取它。使用以下三种状态检查会话状态表：
  - `pending` — 行存在，尚未写入内容
  - `in-progress` — 章节中有内容但未记录达成一致的日期
  - `✅ agreed` — 内容存在且已记录日期
- 从最早的 `pending` 或 `in-progress` 阶段恢复。对于 `in-progress` 阶段：呈现现有内容以供重新确认，而非重新生成。
- **进行中但无内容：** 如果当前架构是 `in-progress` 但文档中没有当前架构内容（上次会话的扫描上下文已丢失），在呈现之前重新运行步骤 2 扫描。
- **过期检查：** 如果会话状态表中最近一次 `✅ agreed` 的日期超过 30 天，运行轻量重新扫描（仅步骤 2.1 和 2.6——目录树 + 导入）。如果检测到重大结构变化，呈现这些变化并询问当前架构是否需要修订后再继续。
- 如果当前架构已经是 `✅ agreed` 且过期检查通过，则不要重新扫描。
- 告诉用户发现了什么，以及会话从哪个阶段恢复。

如果没有现有文档：从步骤 2 开始。

检查 `.lattice/config.yaml`。加载 `.lattice/standards/` 中的 `knowledge-base.md` 和 `architecture.md`（如果存在）——这塑造了审计视角和推荐方向提案。

如果没有 `.lattice/` 配置，提议首先运行 `lattice-init`。如果被拒绝，则从扫描中推断默认值。

### 步骤 2：静默扫描——架构信号提取

在此阶段不要提问。先扫描，形成假设，然后只问代码无法揭示的问题。

**扫描前确认范围。** 如果工作目录是单体仓库或包含多个独立服务/模块，询问：*"本次评估应聚焦于哪个服务或模块？"* 不要扫描整个单体仓库根目录——一次评估一个有限范围。如果用户要求评估整个单体仓库：解释单个洞察文档无法有意义地捕捉多个独立架构。提供选项：(1) 将共享基础设施/平台层作为一个范围评估，(2) 生成所有服务的轻量索引并附上一行架构分类，然后深入评估 2-3 个最痛的服务。如果用户仍然坚持，按每个服务降低深度进行扫描（每个服务执行步骤 2.1 + 2.6）。

这是信号提取，不是完整读取。**目标：15-25 次文件读取**（查看/打开操作）。grep、glob 和目录列表不计入此预算——它们是结构侦察，不是深度读取。一旦明确模块的职责、依赖和层级适配就停止读取。

**扫描协议——按顺序执行：**

1. **目录树**（3 层深度）——预期组织、层级结构、命名约定。在任何文件打开之前执行此操作。

2. **依赖清单**——`package.json`、`pom.xml`、`go.mod`、`requirements.txt`。语言、框架、关键外部依赖。

3. **架构文档**——`README.md`、`ARCHITECTURE.md`、`docs/`、ADR 目录。预期架构通常在这里——意图与现实之间的差距本身就是一个发现。

4. **考古学**——在分析流程之前，缩小范围：
   - 死代码（无调用者）——删除候选，但首先验证无副作用：静态初始化器、定时任务、事件监听器和框架钩子在调用图分析中不可见
   - 重复功能——同一概念的两个实现，必须在任何变更前协调
   - 隐式耦合——共享可变状态、全局变量、环境上下文、线程局部变量
   - 隐藏的集成点——在意外位置的外部系统出站调用

5. **接缝识别与可行性**——一方可以变更而另一方不知情的自然边界：
   - 领域接缝（不同的业务概念）、技术接缝（I/O 与业务逻辑）、团队接缝、时间接缝
   - 对每个接缝：评估可行性——有多少调用者跨越它？低成本的接缝成为首选行动。

6. **导入和依赖模式**——对所有源文件进行 grep 导入语句。不要打开完整主体。低成本揭示依赖方向、承重模块、层级违规。

7. **入口点**——3-5 个文件：路由、控制器、CLI 处理器、事件消费者。揭示最外层。

8. **接口和契约文件**——接口、抽象类、端口。揭示预期边界，无论是否被遵循。

9. **每个顶级模块一个代表性文件**——确认职责，捕获导入 grep 遗漏的内容。

10. **停止。形成假设：**
    - 架构实际是什么 vs 它预期是什么
    - **偏差还是错配？** 偏差 = 初衷合理，逐渐退化 → 恢复。错配 = 对领域而言错误的模式 → 替换。这塑造了推荐方向。
    - 哪些接缝是可行的（低利用成本）
    - 最显著的违规，附具体命名证据
    - 在任何结构工作之前可以清理的死代码和重复项

    如果步骤 9 之后某个模块仍然不清晰，从该模块再读一个文件。这是唯一允许的扫描扩展。

    **如果扫描没有产生有意义的架构信号**——少于 3 个不同模块，没有依赖违规，没有接缝，或代码库明显处于早期阶段（新仓库，大部分是生成代码，扁平结构）——在访谈前提出："*此代码库没有需要评估的架构复杂性——少于 3 个模块，没有依赖违规，也没有可识别的接缝。这要么是早期阶段，要么是有意简单。如果您正在从头建立架构，`/design-blueprint` 可能更合适。仍然继续评估吗？*" 如果用户确认，继续。如果不确认，结束会话。

**完全跳过：** 完整方法实现、测试文件、生成代码、vendor 目录、迁移文件、静态资源。

---

### 步骤 3：四幕访谈

读取 `references/interview-guide.md`。应用该文档中的四幕弧线、每幕问题库、答案解读表、对话原则和红旗信号。

**如果用户明确拒绝访谈**（"只分析代码就好"、"不要问我问题"）：*"推荐方向将仅基于代码信号，没有团队上下文。它可能遗漏交付约束、团队拓扑或未声明的目标。继续吗？"* 如果确认，跳到步骤 4。在洞察文档中将团队愿景章节标记为"推断，未经确认"。

**停止：** 第三幕的答案是架构输入，不是软上下文。步骤 5 的推荐方向必须可见地回应团队在第三幕中所说的内容。在形成推荐之前查阅 `references/interview-guide.md` 中的答案解读表。

---

### 步骤 4：当前架构达成一致（第 1 轮）

呈现扫描得出的架构快照。目标：共享的、准确的地图——不是批评。

呈现：
- 偏差或错配的判定及其理由
- 当前层级结构（或缺失）及具体文件/目录证据
- 模块清单：每个模块实际拥有什么以及不应该拥有什么
- 依赖流向——使用**此代码库的实际模块和层级名称**的 Mermaid 图。以下结构仅为模板——在实际输出中将每个节点标签替换为扫描中发现的真实名称。绝不在实际输出中呈现像"Services"或"DB"这样的通用标签。

```mermaid
graph TD
  [实际入口层] --> [实际服务层]
  [实际服务层] --> [实际数据层]
  [实际服务层] --> [实际领域层]
  [实际领域层] --> [实际数据层]
  style [实际数据层] fill:#f96
```

- 识别的接缝及其可行性
- 考古发现——死代码、重复项、快速胜利
- 关键违规——具体且指名，不通用

如果扫描发现和访谈答案相互矛盾——例如，扫描显示没有层级但团队描述有整洁架构——在要求确认前明确呈现两者：*"扫描显示 [X]。您描述了 [Y]。是意图和当前实现之间存在差距，还是我误读了某些内容？"* 在推进前解决矛盾。

具体询问：*"这张地图是否准确反映了代码库当前的结构？哪些是缺失的、错误的，或者我标记为违规但实际是有意的？"*

如果在 3 轮修正后地图仍未收敛，使用 `framework:collaborative-judgment` 呈现特定的未解决点，让用户做出决策而不是继续迭代。

**停止：** 在用户明确确认当前架构地图之前，不要推进到步骤 5。

对当前状态解读中的真正歧义使用 `framework:collaborative-judgment`。

---

### 步骤 5：推荐方向（第 2 轮）

提出一个为此代码库量身定制的推荐架构方向——不是通用模板。

**将偏差/错配传导下来：**
- **偏差** → 恢复原始意图。目标应该感觉像"这本来就该有的样子。"
- **错配** → 从领域向上全新设计。不要恢复——替换。

**最小可行方向：** 提出能解决所述痛点的最简单结构。测试：团队能在本周内采取第一步行动吗？一个只能在六个月工作后才见效的方向是错误的。

**愿景-护栏张力：** 如果团队的愿景（第三幕）与某个护栏（第四幕）在结构上不兼容，在提议前明确呈现这种张力：*"您的目标 [X] 需要变更 [Y]，但您已将 [Y] 标记为禁区。推荐方向将绕行此约束——以下是具体方式以及它在愿景方面的代价。"* 不要默默妥协——明确指出权衡。

**应用 `framework:architecture` 护栏。** 不可协商的规则：领域对基础设施零依赖——基础设施依赖领域。

**应用 `framework:domain-driven-design`**（仅战略层面）当：存在多个不同的业务能力、不同部分以不同速率变化、或不同团队负责不同领域时。当以上都不适用时，跳过 DDD。

提案涵盖：
- 架构风格和理由——针对此代码库的特定说明，不是教科书示例
- 层级定义——每层拥有什么，绝不能拥有什么
- 依赖方向规则——明确的，领域/基础设施反转作为硬性规则
- 模块和文件夹结构——与此代码库的语言和框架约定匹配的名称
- 限界上下文边界（当 DDD 适用时）

呈现：
- 推荐方向 Mermaid 图——使用**此代码库的实际提议层级名称**，不是通用标签。以下结构仅为模板——将每个节点替换为反映此代码库语言、框架和领域的名称。

```mermaid
graph TD
  [实际API层] --> [实际应用层]
  [实际应用层] --> [实际领域层]
  [实际基础设施层] --> [实际领域层]
  [实际API层] --> [实际基础设施层]
  style [实际领域层] fill:#6f9
```

- 带注解的目标文件夹树——层级作为目录，每层代表性文件附单行角色注解。应用 `framework:knowledge-priming` 和 `.lattice/standards/language-idioms.md`（如果存在）确保层级名称和文件命名约定匹配此代码库的语言和框架——不是通用 OOP 模板。不必详尽——足以使结构无歧义。
- 限界上下文图（当 DDD 适用时）

询问：*"这个方向是否解决了您描述的痛点？是否有约束或偏好应该改变此提案？"*

**停止：** 在用户明确确认推荐方向之前，不要推进到步骤 6。

如果在 3 轮修订后方向仍未收敛，使用 `framework:collaborative-judgment` 呈现特定的未解决张力（例如，愿景 vs. 约束、简单性 vs. 完整性），让用户做出决策而不是继续迭代。

此步骤是一个有效的停止点。如果团队只需要当前架构和推荐方向达成一致，会话可以在此结束。在此情况下，**立即运行步骤 7** 以持久化已达成的共识。尚未触及的章节必须在会话状态表中显示为 `pending`——不要遗漏它们。差距评估和首选行动可以在后续会话中完成。

### 步骤 6：差距评估与首选行动

**差距评估——仅限结构项：**
- 必须变更——达到推荐方向所需的结构性变更
- 应该变更——在工作过程中值得处理的违规
- 明确推迟——目前不在范围内的命名项（不是忘记）
- 保持原样——依赖方向已匹配推荐方向且扫描中未发现违规的模块或层级。明确命名以保护其免受不必要变更。

不包括战术项（命名、测试覆盖率、代码风格）——执行关注点由 `code-forge` 和 `refactor-safely` 处理。

**首选行动**——不是完整待办列表。接下来要做的 2-3 个最重要的结构决策。

合适的粒度：引入一个层级，隔离一个接缝，反转一个依赖。不是"改进领域层"（太宽）。不是"重命名这个方法"（太窄）。

对每个首选行动：
- 要做什么结构变更
- 为什么首先做这个——它解除什么阻塞
- 使用哪个分子：
  - 结构变动（现有代码改变位置或职责）→ `/refactor-safely`
  - 新结构（尚不存在的层级、接口或模块）→ `/design-blueprint` → `/code-forge`
- **受影响的模块：** 来自当前架构扫描的具体文件/目录
- **依赖：** `[行动 N]` 或 `无`——使排序明确
- **完成标志：** 结构成功标准——例如，"domain/ 对 infrastructure/ 零导入"、"所有数据库调用通过仓库接口"、"routes/ 不包含业务逻辑"

询问：*"这些首选行动是否匹配团队的容量和您想首先解决的内容？"*

**停止：** 在用户确认差距评估和首选行动之前，不要推进到步骤 7。

### 步骤 7：编写洞察文档

生成 `.lattice/insights/architecture.md`。如果 `.lattice/insights/` 目录不存在则创建。

**必需结构：**

```markdown
# 架构指南针 — [仓库名称]

## 会话状态
| 阶段 | 状态 | 已达成一致 |
|---|---|---|
| 扫描 + 访谈 | 完成 | — |
| 当前架构 | ✅ agreed | [日期] |
| 推荐方向 | ✅ agreed | [日期] |
| 差距评估 | ✅ agreed | [日期] |
| 首选行动 | ✅ agreed | [日期] |

## 仓库身份
语言、框架、规模、范围边界、交付约束、团队上下文。

## 我们为什么做这个
燃烧的平台——来自访谈。今天什么正在崩溃。
之前的尝试以及什么阻止了它们。

## 团队愿景与护栏
团队想要实现什么（第三幕答案——逐字记录 + 架构解读）。
约束和禁区（第四幕答案）。
这些是直接塑造推荐方向的架构输入。

## 考古发现
死代码候选。需要协调的重复项。
隐式耦合。隐藏的集成点。快速胜利。

## 领域地图
核心领域。自然接缝。限界上下文（如适用）。

## 当前架构
偏差或错配——附理由。
层级结构。模块清单。
[Mermaid 图 — 层级和违规]
关键违规——具体且指名。

## 推荐方向
架构风格和理由。
层级定义和依赖规则。
[Mermaid 图 — 整洁目标]
[带注解的目标文件夹树]
[限界上下文图 — 如适用]

## 差距评估
必须变更 / 应该变更 / 明确推迟 / 保持原样。

## 首选行动

[行动 2] — 什么、为什么首先、哪个分子、受影响模块、依赖、完成标志
[行动 3] — 什么、为什么首先、哪个分子、受影响模块、依赖、完成标志（如适用）

## 进度日志
[每次后续会话追加：YYYY-MM-DD — 阶段回顾、变更内容、新发现]
```

在会话状态表中出现 `[日期]` 的地方使用今天的日期，格式为 YYYY-MM-DD。

在恢复此文档的后续会话中，在关闭前向进度日志追加一条记录：日期、回顾了哪个阶段、变更了什么、出现的任何新发现。
