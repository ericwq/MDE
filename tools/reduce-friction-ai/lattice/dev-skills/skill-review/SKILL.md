# Skill Review

**核心职责：** 通过三个独立角色审查 Lattice skill 来发现真实的行为缺口。每个角色以不同的视角看待 skill，关心不同的事物，可能发现不同的缺口。综合的发现应该比任何单一审查更实用、更完整。

**输入：** 一个 skill 路径或 skill 名称。

**输出：** 统一的发现报告——仅保留来自三个角色的高置信度、实用缺口，合并、去重、修剪，按严重程度排序——附修复建议。

**审查标准：** 倾向于省略而非推测。仅报告你高度确信会在正常使用中浮现、属于此 skill 职责范围、修复后会实质性改善结果的发现。一次有效的审查可以得出没有实质性实用缺口仍然存在的结论。

**如何验证此 skill 已完成工作：**
- 每个报告的发现都基于真实场景，并与 skill 中的具体证据挂钩
- 如果没有高置信度的实用缺口，零发现是可以接受的
- 每个缺口都有具体的修复建议，而不仅仅是标记
- 来自多个角色的重叠发现合并为一个条目，并注明多个视角达成一致
- 多个角色一致仅在发现通过实用性过滤器后才提高置信度
- 最终报告排序：关键缺口在前，警告次之，观察最后——或明确说明未发现实质性实用缺口
- 修复应用后，对同一 skill 文件再次运行此 skill 应显示没有高置信度实用缺口

---

## Step 1：读取 skill

读取完整的 SKILL.md 和所有引用的文件（defaults.md、template.md、references/）。

形成清晰的理解：
- Skill 声称做什么，谁使用它
- 它产生什么（文档、报告、代码、更改）
- 它的输入是什么，这些输入可能处于什么状态
- 它在 Lattice 管道中的位置（上游/下游连接）

如果 skill 被 molecule 组合、消费 refiner 输出或依赖其他 skill，同时读取相关的上游/下游文件。针对实际运行时使用进行审查，而非想象中的独立用例。

---

## Step 2：提出 3 个审查角色

根据 skill 的功能和服务对象，提出 3 个角色，其视角会浮现出最有用的缺口。

**角色选择逻辑：**

| 如果 skill... | 考虑这样的角色... |
|---|---|
| 是产品/BA 人员使用的 molecule | 高级 PM、业务分析师、消费输出的首席开发者 |
| 是执行代码质量的 atom | 代码审查者、遵循规则的初级开发者、检查结构缺口的架构师 |
| 是配置标准的 refiner | 设定标准的团队负责人、新团队成员上线、消费标准文档的 AI 助手 |
| 是开发工具 skill（forge、validator、sync） | Lattice 维护者、首次创建 skill 的人、刚接触 Lattice 的有经验开发者 |
| 横跨产品和技术受众 | 一个产品角色、一个实践者角色、一个技术角色 |

提出 3 个角色并附一行理由：

*"对于 [skill-name]，我将从以下三个视角审查：*
*1. [角色 A]——因为 [此 skill 对他们为什么重要/他们会寻找什么]*
*2. [角色 B]——因为 [此角色带来的不同角度]*
*3. [角色 C]——因为 [第三个角度，最好是 skill 输出的消费者]*

*想使用这些角色、替换其中任何一个，还是添加自己的角色？"*

等待用户确认或调整后再继续。

**STOP：在角色达成一致之前不要进入 Step 3。**

---

## Step 3：角色分析（独立运行三个角色）

按顺序进行每个角色的分析。在一个角色中时，完全沉浸在当前视角中，忘记其他角色。

### 对每个角色，运行此分析：

**3a — 场景生成**

生成对该 skill 进行压力测试所需的最小真实场景集（通常 4-6 个；不要强行填充所有场景类型）。考虑：
- 理想情况（一切如 skill 所预期）
- 首次使用（没有现有设置，没有先验知识）
- 恢复中断的工作（某些输出已存在）
- 最小输入（用户提供尽可能少的信息）
- 最大/复杂输入（大量范围、多个项目、混乱的材料）
- “错误”的输入（粒度错误、格式错误、概念误解）
- 拒绝推荐路径（用户跳过建议，想采取不同方式）
- 冲突输入（两个来源给出不同信息）

仅使用真正适用于此 skill 的场景。跳过不适用的任何情况。4 个有真实发现的相关场景比 8 个带有推测发现的强制场景更好。

对每个选择的场景，按 skill 指令字面操作。仅在以下所有条件都满足时才将静默视为缺口：
- 场景在正常使用中是现实的
- 决策属于此 skill 而非其他 skill 或管道阶段
- 缺失的指导很可能导致真正的失败、困惑或漂移

**STOP：如果上述任何条件为 false，不要记录发现。**

**3b — 角色特定关注点**

将这些用作注意力提示，而非发现配额。它们帮助你注意到问题的类别；不保证存在真实的发现。

每个角色都有自己关心但其他人可能忽略的事项：

- **实践者或用户角色**问："这个 skill 在每个决策点都告诉我该做什么吗？还是我在猜测？" 可能发现：决策指导的缺口、缺失的错误处理、模糊的指令。
- **质量或标准角色**问："这里的规则可执行吗？我能区分通过和失败吗？" 可能发现：模糊的标准、缺失的边界条件、相互矛盾的规则。
- **技术或架构角色**问："这个组合正确吗？它是否守住了自己的边界？" 可能发现：缺失的交叉引用、范围溢出、破损的上游/下游交接、缺失的恢复逻辑。
- **产品或输出角色**问："它产生的东西真的有用吗？" 可能发现：不完整的输出、缺失到下一个管道步骤的连接、未解释的结果。
- **新用户角色**问："我能在不阅读整个框架的情况下知道该做什么吗？" 可能发现：假设的知识、缺失的上下文、没有定义的行话。
- **维护者角色**问："随着 Lattice 发展，这个 skill 会漂移或损坏吗？" 可能发现：将变得过时的硬编码列表、缺失的动态清单读取、紧耦合的假设。

**3c — 记录此角色的发现**

在记录任何发现之前，运行此过滤器：

1. **证据**——你能指出导致问题的确切行、节或指令吗？
2. **实用性**——这在真实的会话中会与真实用户发生吗？
3. **归属**——被审查的 skill 是否真的负责防止或处理它？
4. **实质性**——修复它会实质性改善结果吗？
5. **置信度**——你至少有 90% 置信度这是一个真正的缺口吗？

如果任何答案为“否”，放弃该发现。单纯的可能性是不够的。

格式化每个发现：
```
[角色：{name}]
场景：{浮现此发现的真实场景}
证据：{支持该缺口的确切行/节/指令}
类型：CRITICAL | WARNING | OBSERVATION
缺口：{skill 未涉及或处理不正确的内容——具体}
修复：{对 SKILL.md 的具体添加或更改——足够精确以编写}
置信度：{90%+ 及原因}
```

## Step 4：合并与去重

在所有三个角色完成分析后：

1. **收集**三个角色的所有发现
2. **合并**从不同角度描述同一缺口的发现——合并为一个条目，注明哪些角色达成一致：`(发现者：角色 A、角色 C)`
3. **去重**——如果两个发现关于同一问题，保留最具体的并注明重叠
4. **修剪**使用此过滤器：
   - **实用性**：这会在正常使用中发生吗？
   - **可预测性**：它是否足够可能复发，而非一系列不可能事件的堆叠？
   - **归属**：被审查的 skill 是否真的负责？
   - **实质性**：修复它会实质性改善结果吗？
   - 单纯的可能性不足够——丢弃纯理论的发现
5. **重新评估置信度**——多个角色一致仅在修剪后才提高置信度；一致本身不能使发现变为真实
6. **按严重程度排序**：CRITICAL 在前，WARNING 次之，OBSERVATION 最后
7. **计数**总数：保留了多少关键缺口、警告、观察；有多少得到了多个角色的佐证

---

## Step 5：呈现统一报告

严重程度定义：
- **CRITICAL**——可能在正常使用中发生，且实质性阻止、误导或使 skill 的预期结果无效
- **WARNING**——实用问题，可能导致困惑、不一致、漂移或降级输出
- **OBSERVATION**——真实但影响较低的改进；如果是推测性、琐碎或不太可能发生的则省略

**STOP：不要强制每个严重程度桶都非空。** 报告零观察、零警告或没有发现都是有效的。

```
## Skill Review — {skill-name}
角色：{角色 A} | {角色 B} | {角色 C}

如果修剪后没有保留的发现：未发现实质性实用缺口。

否则呈现：

### 关键缺口（使用前必须修复）

GAP-1：{缺口标题}
发现者：{角色 A、角色 C}
场景：{浮现该缺口的场景}
证据：{确切的行/节/指令}
问题：{skill 未涉及或处理不正确的内容}
修复：{具体更改}
置信度：{90%+ 及原因}

GAP-2：...

### 警告（应该修复——会导致困惑或不一致）

WARN-1：...

### 观察（考虑——不阻塞）

OBS-1：...

---
摘要：{N} 个关键，{M} 个警告，{P} 个观察
最高置信度发现（修剪和佐证后）：GAP-1、WARN-2
推荐修复顺序：[有序列表]
```

如果有发现，询问：*"我应该修复哪些发现？建议从关键缺口开始——特别是那些既实用又得到佐证的。"*

如果没有发现，声明不推荐修复并停止。

---

## Step 6：应用已确认的修复

对每个已确认的修复：
- 进行解决该缺口的最小更改。**STOP：不要重写周围内容。**
- 每次编辑后，声明：更改了什么、关闭了哪个缺口、由哪个（哪些）角色提出
- **STOP：除非用户明确要求，不要修复警告或观察。**

所有修复后：呈现简短的关闭摘要——关闭的缺口、推迟的缺口、再次运行此 skill 可能会发现的结论。
