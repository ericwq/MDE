<img src="../imgs/fig-ch19-4.png" width="75%"/><br/>
*Fig 19-4 新增员工的动态模型*

Listing 19-5 和 19-6 显示了AddEmployeeTransaction 类中 TEMPLATE METHOD 模式的实现。
该类实现了 Execute() 方法，调用两个将由派生类实现的纯虚函数。
这些函数 GetSchedule() 和 GetClassification() 返回新创建的 Employee 所需的 PaymentSchedule 和 PaymentClassification 对象。
然 后Execute()方法将这些对象绑定到 Employee，并将 Employee 保存到 PayrollDatabase 中。

Listing 19-5 AddEmployeeTransaction.h

```cpp
#ifndef ADDEMPLOYEETRANSACTION_H
#define ADDEMPLOYEETRANSACTION_H

#include "Transaction.h"
#include <string>

class PaymentClassification;
class PaymentSchedule;

class AddEmployeeTransaction : public Transaction
{
public:
    virtual ~AddEmployeeTransaction();
    AddEmployeeTransaction(int empid, string name, string address);

    virtual PaymentClassification* GetClassification() const = 0;
    virtual PaymentSchedule* GetSchedule() const = 0;

    virtual void Execute();

private:
    int itsEmpid;
    string itsName;
    string itsAddress;
};

#endif
```

Listing 19-6 AddEmployeeTransaction.cpp

```cpp
#include "AddEmployeeTransaction.h"
#include "HoldMethod.h"
#include "Employee.h"
#include "PayrollDatabase.h"

class PaymentMethod;
class PaymentSchedule;
class PaymentClassification;

extern PayrollDatabase GpayrollDatabase;

AddEmployeeTransaction::~AddEmployeeTransaction()
{
}

AddEmployeeTransaction::
AddEmployeeTransaction(int empid, string name, string address)
    : itsEmpid(empid)
    , itsName(name)
    , itsAddress(address)
{
}

void AddEmployeeTransaction::Execute()
{
    PaymentClassification* pc = GetClassification();
    PaymentSchedule* ps = GetSchedule();
    PaymentMethod* pm = new HoldMethod();

    Employee* e = new Employee(itsEmpid, itsName, itsAddress);
    e->SetClassification(pc);
    e->SetSchedule(ps);
    e->SetMethod(pm);

    GpayrollDatabase.AddEmployee(itsEmpid, e);
}
```

### 全局变量

到目前为止，你已经注意到了 `GpayrollDatabase` 这个全局变量。
几十年来，教科书和老师一直有充分理由反对使用全局变量。
尽管如此，全局变量本身并非邪恶或有害。
这个特定情况是使用全局变量的理想选择。
`PayrollDatabase` 类只可能有一个实例，并且它需要被非常广泛的受众知晓。

你可能认为使用 SINGLETON 或 MONOSTATE 模式可以更好地实现这一点。
确实，它们可以满足目的。
然而，它们本身也是通过全局变量来实现的。
SINGLETON 或 MONOSTATE 根据定义就是全局实体。
在这种情况下，我觉得使用 SINGLETON 或 MONOSTATE 会显得过度设计。
简单地在一个全局变量中保存数据库实例更容易。

## 考勤卡、销售凭条和服务费

Fig 19-7 显示了向员工登记考勤卡的事务的静态结构。
Fig 19-8 显示了动态模型。
基本思想是，事务从 PayrollDatabase 获取 Employee 对象，向 Employee 请求其 PaymentClassification 对象，然后创建 TimeCard 对象并将其添加到该 PaymentClassification中。

注意，我们不能向一般的 PaymentClassification 对象添加 TimeCard 对象；只能向 HourlyClassification 对象添加。
这意味着我们必须将从 Employee 对象接收的 PaymentClassification 对象向下转型为 HourlyClassification 对象。
这是 C++ 中 dynamic_cast 运算符的一个良好用途，如后面的 Listing 19-15 所示。

然后创建一个 TimeCardTransaction 并调用 Execute()。
然后检查员工，看 HourlyClassification 是否包含适当的 TimeCard。

这些设计指出了事务模型与我们创建的核心模型之间的不匹配。
我们的核心 Employee 对象可以隶属于许多不同的组织，但事务模型假设任何会员资格都必须是工会会员资格。

动态模型通过搜索 Employee 对象包含的 Affiliation 对象集合中的 UnionAffiliation 对象来解决这个困境。

**代码 v. UML。**
当我在 Fig 19-12 中绘制 UML 时，我认为用 Affiliation 列表替换 NoAffiliation 是一个更好的设计。
我认为它更灵活，更不复杂。
毕竟，我可以随时添加新的会员资格，而且不必创建 NoAffiliation 类。
然而，在编写 Listing 19-16 中的测试用例时，我意识到在 Employee 上调用 SetAffiliation 比调用 AddAffiliation 更好。
毕竟，需求并没有要求员工有多个 Affiliation，因此没有必要使用 dynamic_cast 在许多可能的类型之间进行选择。
这样做会不必要的复杂。

这是一个例子，说明了为什么在代码中验证之前做太多 UML 可能是危险的。
代码可以告诉你 UML 无法告诉你的关于设计的事情。
在这里，我在 UML 中放置了不需要的结构。
也许有一天它们会派上用场，但在这之前它们需要被维护。
这种维护的成本可能不值得。

在这种情况下，即使维护 dynamic_cast 的成本相对较小，我也不打算使用它。
不使用 Affiliation 对象的列表实现起来要简单得多。
所以我将保留 NULL OBJECT 模式，使用 NoAffiliation 类。

## 修改员工信息

<img src="../imgs/fig-ch19-12a.png" width="40%"/><br/>

Fig 19-13 和 Fig 19-14 展示了修改员工属性的事务的静态结构。
该结构很容易从用例 6 推导出来。
所有事务都接受一个 EmpID 参数，因此我们可以创建一个名为 ChangeEmployeeTransaction 的顶级基类。
在这个基类之下是修改单个属性的类，例如 ChangeNameTransaction 和 ChangeAddressTransaction。
修改分类的事务有共同的目的，因为它们都修改 Employee 对象的同一字段。

### 我们是否希望开发人员做出业务决策？

这个过账的概念从何而来？
在用户故事或用例中当然没有提到。
碰巧，这是我为了解决我察觉到的一个问题而编造出来的。
我担心 Payday 方法可能会用同一个日期、或者同一计薪周期内的日期被多次调用，所以我希望确保员工不会被重复发薪。
这是我主动做的，没有询问我的客户。
这看起来是正确的事情。

实际上，我做出了一个业务决策。
我决定多次运行薪资程序会产生不同的结果。
我应该向我的客户或项目经理询问此事，因为他们可能有非常不同的想法。

在与客户核实后，我发现过账的想法违背了他的意图。³
客户希望能够运行薪资系统，然后审核工资支票。
如果任何支票有误，客户希望更正薪资信息并再次运行薪资程序。
他们告诉我，我永远不应考虑当前支付周期之外日期的考勤卡或销售凭条。

³ 好吧，我就是那个客户。

所以，我们必须放弃过账方案。
这在当时看起来是个好主意，但这不是客户想要的。

double HourlyClassification::CalculatePay(Paycheck& pc) const
{
    double totalPay = 0;
    Date payPeriod = pc.GetPayDate();
    map<Date, TimeCard*>::const_iterator i;
    for (i = itsTimeCards.begin(); i != itsTimeCards.end(); i++) {
        TimeCard * tc = (*i).second;
        if (IsInPayPeriod(tc, payPeriod))
            totalPay += CalculatePayForTimeCard(tc);
    }
    return totalPay;
}

bool HourlyClassification::IsInPayPeriod(TimeCard* tc, const Date& payPeriod) const
{
    Date payPeriodEndDate = payPeriod;
    Date payPeriodStartDate = payPeriod - 5;
    Date timeCardDate = tc->GetDate();
    return (timeCardDate >= payPeriodStartDate) &&
           (timeCardDate <= payPeriodEndDate);
}

double HourlyClassification::CalculatePayForTimeCard(TimeCard* tc) const
{
    double hours = tc->GetHours();
    double overtime = max(0.0, hours - 8.0);
    double straightTime = hours - overtime;
    return straightTime * itsRate + overtime * itsRate * 1.5;
}

namespace
{
    int NumberOfFridaysInPayPeriod(const Date& payPeriodStart,
                                   const Date& payPeriodEnd)
    {
        int fridays = 0;
        for (Date day = payPeriodStart; day <= payPeriodEnd; day++)
        {
            if (day.GetDayOfWeek() == Date::friday)
                fridays++;
        }
        return fridays;
    }
}

double UnionAffiliation::
CalculateDeductions(Paycheck& pc) const
{
    double totalDues = 0;
    int fridays =
        NumberOfFridaysInPayPeriod(pc.GetPayPeriodStartDate(),
                                   pc.GetPayPeriodEndDate());
    totalDues = itsDues * fridays;
    return totalDues;
}

## 数据库

现在这个迭代已经被分析、设计并（大部分）实现了，我们可以考虑数据库的角色了。
`PayrollDatabase` 类显然封装了与持久化相关的内容。
`PayrollDatabase` 中包含的对象必须比应用程序的任何特定运行都存活得更久。
这应该如何实现？
显然，测试用例使用的临时机制对于真实系统是不够的。
我们有几种选择。

我们可以使用面向对象数据库管理系统（OODBMS）来实现 `PayrollDatabase`。
这将允许实际对象驻留在数据库的永久存储中。
作为设计师，我们几乎不需要做更多的工作，因为 OODBMS 不会给我们的设计增加太多新东西。
OODBMS 产品的一大优点是它们对应用程序的对象模型几乎没有影响。
就设计而言，数据库几乎不存在。⁶

⁶ 这是乐观的。
在像 Payroll 这样的简单应用程序中，使用 OODBMS 对程序的设计影响很小。
随着应用程序变得越来越复杂，OODBMS 对应用程序的影响会增加。
尽管如此，其影响仍远小于 RDBMS 的影响。

另一种选择是使用简单的纯文本文件来记录数据。
在初始化时，`PayrollDatabase` 对象可以读取该文件并在内存中构建必要的对象。
在程序结束时，`PayrollDatabase` 对象可以写入新版本的文本文件。
当然，对于拥有数十万员工的公司，或希望对其薪资数据库进行实时并发访问的公司，这种选择是不够的。
然而，对于较小的公司来说可能已经足够，并且它肯定可以用作测试应用程序其余类的机制，而无需投入大型数据库系统。

还有一种选择是将关系数据库管理系统（RDBMS）整合到 `PayrollDatabase` 对象中。
然后 `PayrollDatabase` 对象的实现将对 RDBMS 进行适当的查询，以在内存中临时创建必要的对象。

关键是，就应用程序而言，数据库只是管理存储的机制。
它们通常不应被视为设计和实现的主要因素。
正如我们在这里展示的，它们可以留到最后作为细节处理。⁷
通过这样做，我们为实现所需的持久化和创建测试应用程序其余部分的机制保留了许多有趣的选择。
我们也不会将自己束缚在任何特定的数据库技术或产品上。
我们可以根据设计的其余部分自由选择所需的数据库，并且我们保留了未来根据需要更改或替换该数据库产品的自由。

⁷ 有时数据库的性质是应用程序的需求之一。
RDBMS 提供了强大的查询和报告系统，这些可能被列为应用程序需求。
然而，即使这类需求是明确的，设计者仍应将应用程序设计与数据库设计解耦。
应用程序设计不应依赖于任何特定类型的数据库。

## 薪资设计总结

在大约 50 个图表和 3300 行代码中，我们展示了薪资应用程序一个迭代的设计和实现。
该设计使用了大量的抽象和多态。
结果是，设计的大部分对薪资政策的变更保持了封闭。
例如，应用程序可以被修改以处理按季度支付、基于正常薪资和奖金计划的员工。
这一更改需要添加到设计中，但现有的设计和代码几乎不需要更改。

在这个过程中，我们很少考虑自己是在进行分析、设计还是实现。
相反，我们专注于清晰性和封闭性问题。
我们尽可能寻找底层抽象。
结果是我们为薪资应用程序建立了一个良好的起始设计，并且我们有了一组与整个问题领域相关的核心类。

### 历史

本章中的图源自于我在 1995 年出版的《Designing Object-Oriented C++ Applications using the Booch Method》一书相应章节中的 Booch 图。
这些图创建于 1994 年。
在创建它们的同时，我也编写了一些实现它们的代码，以确保这些图有意义。
然而，我没有编写出这里所展示的那么多代码。
因此，这些图没有从代码和测试中获得足够的反馈。
这种反馈的缺乏是显而易见的。

我按照此处呈现的顺序编写了本章。
在每种情况下，测试用例都在生产代码之前编写。
在许多情况下，这些测试是逐步创建的，随着生产代码的演进而演进。
生产代码的编写是为了符合这些图，只要这是合理的。
有几个情况下这并不合理，因此我更改了代码的设计。

其中一个最早发生这种情况是在第 219 页，当时我决定不在 Employee 对象中使用多个 Affiliation 实例。
另一个是在第 229 页，当时我发现我没有在 ChangeMemberTransaction 中考虑记录员工的工会会员资格。

这是正常的。
当你在没有反馈的情况下设计时，你必然会犯错误。
正是测试用例和运行代码所施加的反馈为我们发现了这些错误。
