🔖 测试 🔖 数据库

---
内存数据库是一种完全在主内存中运行、不涉及磁盘的数据库。
它们通常以嵌入式数据库的形式运行：在进程启动时创建，在进程内嵌入式运行，并在进程结束时销毁。

虽然大多数人认为数据库是依赖磁盘的大型系统，但内存数据库也有其小而活跃的世界。
有些应用需要快速访问某种托管数据，而这些数据不需要持久化，要么是因为它们不会变化，要么是因为它们可以重建（想象一下路由器中的路由表，或 [事件发布器](https://martinfowler.com/bliki/EventPoster.html) ）。

然而，即使是传统数据库系统的开发人员也会发现内存数据库很有用，尤其是在测试方面。
当你开发企业应用时，访问数据库的测试在运行测试套件时可能会耗费大量时间。
切换到内存数据库可以带来数量级的性能提升，从而显著缩短构建时间。
由于大多数 ThoughtWorker 员工如果最近没有看到绿色条（测试通过）就会感到不安，这对我们来说意义重大。

人们似乎在内存数据库测试方面采取两种途径。
<ins>第一种是使用 SQL 内存数据库库。
在 Java 领域，流行的似乎是 [HSQLDB](http://hsqldb.org/) 。
其他还有 [SQLite](http://www.sqlite.org/) 和 [Firebird](http://firebird.sourceforge.net/) 。
这些工具的好处是允许你使用常规 SQL 进行查询</ins>。
但一个问题是，它们可能不完全支持相同的方言或拥有目标数据库的所有功能。
<ins>你也可以通过在内存磁盘上运行基于文件的数据库来实现类似效果，这能使测试环境与生产部署更接近</ins>。

另一种途径是将所有数据库访问抽象在 [Repository](https://martinfowler.com/eaaCatalog/repository.html) 之后。
然后你可以用常规的内存数据结构替换数据库。
通常，只需为对象图的入口点准备一些哈希表就足够了。
Repository 方法的一个优势是，它也为你提供了一种一致的方式来访问（和模拟）非 SQL 数据源。
这意味着你的对象关系映射系统也隐藏在 Repository 内部。

事实上，一些人确实不喜欢使用 SQL 内存数据库，因为他们认为这会鼓励将 SQL 或对象关系映射器代码散布在领域模型中。
运行 SQL 内存数据库可能会消除缓慢访问带来的许多痛苦，但它只是掩盖了缺少 Repository 这一问题的除臭剂。

到目前为止，测试是内存数据库的主要驱动因素，但我认为未来还有更多可能性。
内存容量现在已经足够大，许多应用数据库都可以加载到内存中。
如果你采用一种方法，保存所有应用状态变更的事件日志，那么你可以将内存数据库视为应用该日志结果的缓存，根据需要重建并快照它。
这种风格在大量读取者和少量写入者的情况下，可以具有很高的可扩展性和性能。
我遇到过一些将内存数据库用于高性能应用的案例。
区别在于，这些经验往往使用的是小众商业数据库，而测试方面人们似乎更倾向于开源。

[Prevayler](http://www.prevayler.org/) 因采用这种方法而获得了大量关注。
我认识的尝试过它的人发现，它与内存对象的紧密耦合以及缺乏迁移工具导致了严重问题。
但我认为，将持久化变更日志作为记录系统的这种方法，是未来值得探索的肥沃领域。

### 后续讨论

在撰写本文后，我收到了一些有趣的邮件，因此我想分享其中的一些观点。

一位通信者提到，他喜欢将内存数据库用于 SQL 擅长而对象不太擅长的任务。
确实有些情况下，SQL 能比对象或过程式代码更优雅地解决问题，尽管我通常发现只有少数开发人员喜欢用 SQL 思考。

我的同事 Steve Sparks 告诉我一个近期项目，在测试中，他们会在第一次调用时从生产数据库拉取数据，然后将数据保存到文件中，用于初始化内存中的 Repository，以便后续查询不会命中数据库。
我第一次看到这种做法是在 C3 项目中，它将数据保存在以 SQL 查询字符串为键的哈希表中。
如果没有值，则访问 DB2 并缓存结果。

Steven Graves 指出，我最初的描述实际上没有充分讨论内存数据库的一般用途，因此我做了一些重写，并重新命名了该条目。
