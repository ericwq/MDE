## 通过提示编程

这是一项非常新的技术，我们还没有很好地掌握如何使用它。
这让人想起我们最初对 Java 和 Web 的尝试。
还有人记得 applet 吗？
我们花了好几年才弄清楚如何很好地使用 Java/C# 的基本要点。
又花了好几年才完善那些基本要点。

Ruby 和 Python 也是如此。
起初我们跌跌撞撞，然后我们逐渐找到了前进的最佳方法。
相信我，当 Fortran 第一次出现时，也有大量的恐惧、痛苦、怀疑和跌跌撞撞。

AI 也会如此。
在这一点上，我们不知道该做什么。
我们才刚刚开始勉强能够通过提示跌跌撞撞地编写程序。
我们不知道如何做好它。

所以，例如，考虑几天前我给 Grok2 的以下提示：

² Grok 3 beta（2025 年 3 月 19 日）。

> write a clojure program that finds all sentences in a given file that contain a given substring.
Choose one of those sentences at random and find the next word in the substring, or a . if no word follows.
Add the found word to the substring and remove the first if the substring is longer than three words.
Repeat the entire process until the substring ends in a . or has exceeded 50 words.
Accumulate all the words that were found and return them appended to the initial substring.

以下是 Grok 生成的代码。它大致能工作。

```clojure
(ns markov
  (:require [clojure.string :as str]))

(defn read-file [filename]
  "Reads the content of a file and splits it into sentences."
  (try
    (let [content (slurp filename)
          sentences (filter not-empty
                           (map str/trim
                                (str/split content #"[.!?]")))]
      sentences)
    (catch Exception e
      (throw (Exception. (str "Error reading file: " (.getMessage e)))))))

(defn find-sentences-with-substring [sentences substring]
  "Finds all sentences containing the substring."
  (filter #(str/includes? (str/lower-case %) (str/lower-case substring))
          sentences))

(defn get-next-word [sentence substring]
  "Finds the next word after the substring
  in the sentence, or '.' if none."
  (let [index (str/index-of (str/lower-case sentence)
                            (str/lower-case substring))]
    (if index
      (let [post-substring (subs sentence (+ index (count substring)))
            words (str/split (str/trim post-substring) #"\s+")]
        (if (seq words)
          (first words)
          "."))
      ".")))

(defn update-substring [substring next-word]
  "Updates the substring by adding the next word
  and trimming if longer than 3 words."
  (let [words (str/split substring #"\s+")
        new-words (conj (vec words) next-word)
        trimmed-words (if (> (count new-words) 3)
                        (subvec new-words 1)
                        new-words)]
    (str/join " " trimmed-words)))

(defn sentence-walk [filename initial-substring]
  "Main function to perform the sentence walking process."
  (let [sentences (read-file filename)]
    (loop [substring initial-substring
           accumulated-words []
           iterations 0]
      (if (or (= (last (str/split substring #"\s+")) ".")
              (> iterations 50))
        (str/join " " (concat (str/split initial-substring #"\s+")
                              accumulated-words))
        (let [matching-sentences (find-sentences-with-substring
                                  sentences substring)]
          (if (empty? matching-sentences)
            (str/join " " (concat (str/split initial-substring #"\s+")
                                  accumulated-words))
            (let [random-sentence (rand-nth matching-sentences)
                  next-word (get-next-word random-sentence substring)]
              (recur (update-substring substring next-word)
                     (conj accumulated-words next-word)
                     (inc iterations)))))))))

(defn -main [& args]
  (if (< (count args) 2)
    (println "Usage: program <filename> <initial-substring>")
    (let [filename (first args)
          initial-substring (second args)]
      (try
        (println (sentence-walk filename initial-substring))
        (catch Exception e
          (println (.getMessage e)))))))
```

这很容易给人留下深刻印象。
我当然也是。
但它也让我感到恐惧。
我并不是被 AI 生成代码的能力所吓倒。
我是被那个可怕提示的结构所吓倒。

仔细看看那个提示。`sentence` 的定义是什么？
`word` 的定义是什么？
`the found word` 这个短语是什么意思？
那些点字符是标点符号还是名词？
`accumulate words` 是什么意思？

是的，Grok 在这个小实验中足够好地解决了所有这些问题。
但由此产生的程序远未准备好投入生产。
它犯了很多愚蠢的小错误，其中大多数与我上一段提出的问题有关。

例如，这里是一个示例运行：

```
>clj -M -m markov
~/Documents/Books/Clean\ Code\ 2ded\ 20250311.txt "The Single"

The Single Responsibility Principle, and the Dependency
relationships and wind up back at that first solution, the one with
the project you were working on  it every day  business and personal
```

注意第三行和第四行中的双空格。
为什么会出现这种情况？

我可以通过在提示中添加澄清来修复这些错误。
例如，我可能添加：

> Make sure all accumulated words are separated by just one space.

但这种方法存在一些问题。
首先，我还没有弄清楚为什么会出现那些双空格，所以对提示的这次修改只是修复症状的补丁。
其次，我确定 `all accumulated words` 这个短语能正确指代返回值吗？

我可以尝试一下来验证；但这会导致另一个问题。
每次对提示进行新的更改，Grok 都会从头开始重新生成程序，而不是修改现有程序。
考虑到提示中的所有歧义，我如何能确定重新生成的程序不会破坏之前能工作的部分呢？
它会像之前一样使用 `word` 和 `sentence` 的相同定义吗？
它会像之前一样解释 `found word` 吗？
鉴于 LLM 算法的统计和模糊性质，它很可能会不同！

以下是 Grok 为那个修改后的提示生成的内容。
注意，这两个程序看起来像是两个不同的程序员写的。

```clojure
(ns sentence-walker
  (:require [clojure.string :as str]
            [clojure.java.io :as io]))

(defn get-sentences [filename]
  "Read file and split into sentences"
  (-> (slurp filename)
      (str/replace #"[.!?]\s+" "$0|")
      (str/split #"\|")
      (->> (map str/trim)
           (filter not-empty))))

(defn find-matching-sentences [sentences substring]
  "Find all sentences containing the substring"
  (filter #(str/includes? (str/lower-case %)
                          (str/lower-case substring))
          sentences))

(defn get-next-word [sentence substring]
  "Find word following substring in sentence, or . if at end"
  (let [idx (str/index-of (str/lower-case sentence)
                          (str/lower-case substring))
        substr-end (+ idx (count substring))
        remainder (subs sentence substr-end)]
    (if (empty? (str/trim remainder))
      "."
      (let [next-word (first (str/split (str/trim remainder) #"\s+"))]
        (if (or (nil? next-word) (empty? next-word))
          "."
          next-word)))))

(defn update-substring [substring next-word]
  "Add next word and trim if longer than 3 words"
  (let [words (str/split substring #"\s+")
        new-words (conj (vec words) next-word)]
    (if (> (count new-words) 3)
      (str/join " " (subvec new-words (- (count new-words) 3)))
      (str/join " " new-words))))

(defn walk-sentences [filename initial-substring]
  "Main function to walk through sentences"
  (let [sentences (get-sentences filename)]
    (loop [current-substr initial-substring
           accumulated-words [initial-substring]
           iterations 0]
      (if (or (str/ends-with? current-substr ".")
              (> iterations 50))
        (str/join " " accumulated-words)
        (let [matching-sentences (find-matching-sentences
                                  sentences current-substr)]
          (if (empty? matching-sentences)
            (str/join " " accumulated-words)
            (let [random-sentence (rand-nth matching-sentences)
                  next-word (get-next-word random-sentence current-substr)
                  new-substr (update-substring current-substr next-word)]
              (recur new-substr
                     (conj accumulated-words next-word)
                     (inc iterations)))))))))

;; Example usage:
;; (walk-sentences "sample.txt" "the")
```

这个新程序解决了双空格问题，但在句子结尾处产生了一个新问题。
它也不能很好地处理大小写。

> clean code is hard Writing a system that handles one user at a time .

### 初期阶段

这些是与该方法的初期阶段相关的问题。
为了通过提示有效地编写大型系统，我们将需要允许增量更改的 AI 工具。
我们还需要消除提示中歧义的方法。

简而言之，我们将需要一种形式化规范 —— 一种明确且精确的提示语言，不会因 LLM 算法的统计和模糊性质而被错误解释。
我们将需要想出一种方法，精确地说出我们的意思。

我们还需要想出一种方法，使我们的意思与所说的一致。
或者换句话说，即使我们有一种完全精确的语言，也很容易精确地说出错误的东西。
为了确保我们的精确陈述是对我们意图的准确描述，我们应该至少以两种不同的方式陈述我们的意图（就像我在这段话中所做的那样！）。

当你用两种不同的方式说某件事时，你就是在对你试图传达的概念进行 *重载 (overloading)* 。
这种重载是一种确保两个陈述中的任何错误都会被另一个检测到的方法。
我们容易出错的人类绝对需要重载。

重载是复式记账法和前面章节中描述的测试纪律背后的策略。
如果一组由人类编写的精确陈述没有被重载，那么信任它们将是极其不负责任的。
我们将需要一种创建精确且重载的提示的方法，以及一种快速验证它们一致性的方法。

### **一个猜测**

所以让我做一个科学的狂野猜测。

想象一种提示语言，它包含形式化定义和约束，并由一组 BDD 风格³ 的 Given-When-Then 场景重载。

³ [RSpec](../bib.md#rspec) 。

让我们用一个稍微简单的问题来尝试一下。
注意它看起来有多像 COBOL。
这种相似性可能会让我们停下来思考。

```
Language: Clojure
Name: Markov
Command line arguments:
  f a text file.
  s a text string.

Definitions:
  Word: A string of alphabetic characters.
  Sentence: One or more words separated by spaces and ending with
  a period, question mark, or exclamation mark.

Constraints:
  Ignore case in all comparisons.

Description:
  Find all sentences in f that contain s.
  Choose a sentence c at random with equal probability.
  Return the word in c that immediately follows s;
    if none return a period.

Scenarios to be tested with speclj:
Given f contains the following lines:
  Oh, Hello there Bob, how are you today? I'm fine.
  Hello there Bill, I trust you are well. How's the wife?
  Ah yes, hello there John, great day! Kowabunga!

When s is "not in any sentence"
Return "."

When s is "hello"
Then return "there"

When s is "are well"
Then return "."

When s is "hello there"
Then return "Bob", "Bill", or "John".
Assert a uniform distribution after 100 iterations.
```

Grok 很乐意生成以下代码。

```clojure
(ns markov.core
  (:require [clojure.string :as str]
            [clojure.java.io :as io]))

(defn get-sentences [file]
  (->> (slurp file)
       (re-seq #"[A-Za-z\s]+[.!?]")
       (map str/trim)))

(defn words [sentence]
  (str/split (str/lower-case sentence) #"\s+"))

(defn find-following-word [sentences search-str]
  (let [search-str (str/lower-case search-str)
        matching-sentences (filter
                            #(str/includes? (str/lower-case %)
                                            search-str)
                            sentences)]
    (if (empty? matching-sentences)
      "."
      (let [chosen (rand-nth matching-sentences)
            word-seq (words chosen)
            search-words (str/split search-str #"\s+")
            idx (.indexOf word-seq (last search-words))]
        (if (or (< idx -1) (>= (+ idx 1) (count word-seq)))
          "."
          (nth word-seq (+ idx 1)))))))

(defn -main [f s]
  (let [sentences (get-sentences f)
        result (find-following-word sentences s)]
    (println result)))
```

以下是 Grok 从场景中生成的测试。

```clojure
;; speclj tests
(ns markov.core-spec
  (:require [speclj.core :refer :all]
            [markov.core :refer :all]
            [clojure.java.io :as io]))

(def test-content
  "Oh, Hello there Bob, how are you today? I'm fine.
   Hello there Bill, I trust you are well. How's the wife?
   Ah yes, hello there John, great day! Kowabunga!")

(describe "Markov"
  (before-all
    (spit "test.txt" test-content))
  (after-all
    (.delete (io/file "test.txt")))

  (it "returns period when string not found"
    (should= "." (find-following-word (get-sentences "test.txt")
                                      "not in any sentence")))

  (it "returns 'there' when searching for 'hello'"
    (should= "there" (find-following-word (get-sentences "test.txt")
                                          "hello")))

  (it "returns period when searching for 'are well'"
    (should= "." (find-following-word (get-sentences "test.txt")
                                      "are well")))

  (it "returns Bob, Bill, or John for 'hello there'
      with uniform distribution"
    (let [results (repeatedly 100
                              #(find-following-word
                                (get-sentences "test.txt") "hello there"))
          freqs (frequencies results)
          expected ["bob" "bill" "john"]]
      (should= 3 (count freqs))
      (should (every? #(contains? freqs %) expected))
      (doseq [name expected]
        (let [count (get freqs name)]
          ;; Check if count is reasonably close to 33 (100/3)
          ;; with some tolerance
          (should (> count 20))
          (should (< count 50)))))))
```

尽管 Grok 做出了勇敢的努力，但这些测试并没有通过。
这应该足以说明用测试场景重载提示是多么重要！

```
Failures:

  1) Markov returns 'there' when searching for 'hello'
     Expected: "there"
        got: "." (using =)

  2) Markov returns period when searching for 'are well'
     Expected: "."
        got: "i" (using =)

  3) Markov returns Bob, Bill, or John for
     'hello there' with uniform distribution
     Expected: 3
        got: 1 (using =)
```

调试代码相对简单；但你能调试提示吗？
即使你能 “修复” 提示，你确定如果你多次应用该提示，它会生成通过的代码和测试吗？

Grok 编写了测试，但却不能利用它们来推断所需行为，这一事实暴露了 LLM 方法的局限性。
LLM 本质上是统计性的；它们通过概率而非推理来生成响应。
确实，许多推理被训练到了统计模型中；但提示的评估并不会实时推理。
推理是理性的主要操作。
如果 LLM 不主动推理，那么 LLM 就不理性！

如果你调试 Grok 生成的代码，你会发现 Grok 显然忽略了所提供的 `word` 定义，并且没有正确解释不区分大小写的约束。
Grok 被一个重载了测试场景的形式化提示搞糊涂了，这一事实并不令人鼓舞。
至少对我来说，很明显，如果没有重载的形式化规范，使用 AI 来编写我们系统的前景注定会遭受惨败。
毕竟，编程是形式化的，而人类需要重载。
