## 领域特定测试语言

上面的测试演示了为你的测试构建 *领域特定语言（Domain-Specific Language）* 的技术。
我们不是使用程序员用来操作系统的 API，而是构建一组函数和实用工具，它们利用那些 API，并使测试更方便编写和更容易阅读。
这些函数和实用工具成为测试使用的专用 API。
它们是一种测试语言，程序员用它来帮助编写测试，以及帮助那些以后必须阅读这些测试的人。

### 组合断言

`assertResponseIsXML` 和 `assertResponseContains` 函数是领域特定测试语言的一部分。
这类断言函数被称为 *组合断言（composed assertions）* 。

像这样的测试 API 不是预先设计的；
相反，它们是从持续重构那些因模糊细节而变得过于混乱的测试代码中演化而来的。
正如你看到我重构原始测试一样，有纪律的开发人员也会将他们的测试代码重构为更简洁、更具表达力的形式。

### 组合测试结果

创建领域特定测试 API 的另一种技术是创建 *组合测试结果（composed test results）* 。
当测试结果不必要地复杂并且可以被压缩成更容易理解的较小形式时，可以使用这些技术。

考虑我在原型设计一个环境控制系统时编写的测试。
在不深入细节的情况下，你可以看出，这个测试检查的是当温度 “太冷” 时，低温报警器、加热器和鼓风机是否都已开启。

```java
@Test
public void turnOnLoTempAlarmAtThreshold() throws Exception {
    hw.setTemp(WAY_TOO_COLD);
    controller.tic();
    assertTrue(hw.heaterState());
    assertTrue(hw.blowerState());
    assertFalse(hw.coolerState());
    assertFalse(hw.hiTempAlarm());
    assertTrue(hw.loTempAlarm());
}
```

当然，这里有很多细节。
例如，那个 `tic` 函数是做什么的？
事实上，我更希望你在阅读这个测试时不要担心那个。
我更希望你只关心你是否同意系统的最终状态与 “太冷” 的温度一致。

注意，当你阅读这个测试时，你的眼睛需要在被检查状态的名称和被检查状态的感知之间来回跳动。
你看到 `heaterState`，然后你的眼睛向左滑动到 `assertTrue`。
你看到 `coolerState`，你的眼睛必须向左追踪到 `assertFalse`。
这是繁琐且不可靠的。
它使测试难以阅读。

更糟糕的是，这是 14 个非常相似的测试之一。
想象一下当你试图阅读所有这些时，你的眼睛会怎样发花。

我通过如下转换大大改善了这些测试的阅读体验。

```java
@Test
public void turnOnLoTempAlarmAtThreshold() throws Exception {
    wayTooCold();
    assertEquals("HBchL", hw.getState());
}
```

当然，我通过创建一个 `wayTooCold` 函数隐藏了 `tic` 函数的细节。
但要注意的是 `assertEquals` 中的那个奇怪字符串。
大写表示 “开”，小写表示 “关”，字母总是按以下顺序排列：`{heater, blower, cooler, hi-temp-alarm, lo-temp-alarm}`。

一旦你知道含义，你的眼睛就会滑过那个字符串，你可以快速解释结果。
阅读测试几乎成为一种乐趣。
看看其中几个测试，看看它们是多么容易理解。

```java
@Test
public void turnOnCoolerAndBlowerIfTooHot() throws Exception {
    tooHot();
    assertEquals("hBChl", hw.getState());
}

@Test
public void turnOnHeaterAndBlowerIfTooCold() throws Exception {
    tooCold();
    assertEquals("HBchl", hw.getState());
}

@Test
public void turnOnHiTempAlarmAtThreshold() throws Exception {
    wayTooHot();
    assertEquals("hBCHl", hw.getState());
}

@Test
public void turnOnLoTempAlarmAtThreshold() throws Exception {
    wayTooCold();
    assertEquals("HBchL", hw.getState());
}
```

创建组合测试结果的 `getState` 函数如下所示：

```java
public String getState() {
    String state = "";
    state += heater ? "H" : "h";
    state += blower ? "B" : "b";
    state += cooler ? "C" : "c";
    state += hiTempAlarm ? "H" : "h";
    state += loTempAlarm ? "L" : "l";
    return state;
}
```

### 双重标准

你可能会抱怨，以这种方式组合测试结果是浪费计算资源的。
毕竟，我甚至没有使用 `StringBuffer` 或 `StringBuilder` 来执行连接。

这个应用程序显然是一个嵌入式实时系统，计算机和内存资源很可能非常受限。
然而，测试环境在我的笔记本电脑上运行，根本没有受到限制。

这就是测试和生产之间 *双重标准 (dual standard)* 的性质。
有些东西你在生产环境中可能永远不会做，但在测试环境中却是完全可行的。
通常它们涉及内存或 CPU 效率问题。
但它们绝不涉及整洁性问题。

### 单一断言规则

<ins>该规则指出，一个好的测试只断言一件事。
这经常被误解为测试应该只有一个断言语句。
实际上，一个测试可以有许多断言语句，但仍然断言一个逻辑事实</ins>。

例如，考虑上面第一组环境控制器测试。
它们可能因为所有这些断言而难以阅读，但它们是在断言一个单一的逻辑事实。
事实上，这就是为什么我们可以用组合测试结果来重构它们。

或者，考虑上面 `pageHierarchy` 示例中重构后的断言。
它们断言了一个单一的逻辑事实：响应是一个包含某些内容的 XML 文档。

你可能会觉得这令人困惑，或者至少是主观的。
毕竟，文档的内容和文档的类型是不同的实事，不是吗？

这种混淆是因为 *单一断言规则 (Single Assert Rule)* 命名不当。

### 单一动作规则

这条规则实际上应该被称为 *单一动作规则 (Single Act Rule)* 。
Arrange-Act-Assert 模式规定，每个测试应该由三个元素组成：*安排 (Arrange)* 、 *动作 (Act)* 和 *断言 (Assert)* 。
第一部分安排要测试的数据。
第二部分是我们希望测试的对该数据的动作。
第三部分是断言数据已被该动作正确地转换。

<ins>单一断言规则的目标是确保每个测试都测试一个且仅一个动作</ins>。
我们希望避免那些 “安排、动作、断言、动作、断言” 的测试。
我们也希望避免那些 “安排、动作、动作、断言、断言” 的测试。
我们希望每个动作都被单独测试，因为我们不希望下游的断言被上游的动作所破坏。
我们希望每个测试都是独立的。
