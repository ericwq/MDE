# 第 15 章 整洁测试

<center><img src="../imgs/fig-ch15-0.png" width="40%" /></center><br/>

整洁测试是可读的、快速的、隔离的、可重复的、自验证的、及时的和经过设计的。
可读性在单元测试中可能比在生产代码中更为重要。
是什么使测试具有可读性？
使所有代码具有可读性的相同因素：清晰性、简单性和表达的密度。
在测试中，你想用尽可能少的表达式来表达尽可能多的内容。

考虑 FitNesse 中的这段代码。
这三个测试难以理解，并且肯定可以改进。
首先，在重复调用 `addPage` 和 `assertSubString` 中存在大量重复代码。
更重要的是，这段代码充满了干扰测试表达力的细节。

```java
public void testGetPageHierarchyAsXml() throws Exception {
    crawler.addPage(root, PathParser.parse("PageOne"));
    crawler.addPage(root, PathParser.parse("PageOne.ChildOne"));
    crawler.addPage(root, PathParser.parse("PageTwo"));

    request.setResource("root");
    request.addInput("type", "pages");
    Responder responder = new SerializedPageResponder();
    SimpleResponse response =
        (SimpleResponse) responder.makeResponse(
            new FitNesseContext(root), request);
    String xml = response.getContent();

    assertEquals("text/xml", response.getContentType());
    assertSubString("<name>PageOne</name>", xml);
    assertSubString("<name>PageTwo</name>", xml);
    assertSubString("<name>ChildOne</name>", xml);
}

public void testGetPageHierarchyAsXmlDoesntContainSymbolicLinks()
    throws Exception {
    WikiPage pageOne =
        crawler.addPage(root, PathParser.parse("PageOne"));
    crawler.addPage(root, PathParser.parse("PageOne.ChildOne"));
    crawler.addPage(root, PathParser.parse("PageTwo"));

    PageData data = pageOne.getData();
    WikiPageProperties properties = data.getProperties();
    WikiPageProperty symLinks =
        properties.set(SymbolicPage.PROPERTY_NAME);
    symLinks.set("SymPage", "PageTwo");
    pageOne.commit(data);

    request.setResource("root");
    request.addInput("type", "pages");
    Responder responder = new SerializedPageResponder();
    SimpleResponse response =
        (SimpleResponse) responder.makeResponse(
            new FitNesseContext(root), request);
    String xml = response.getContent();

    assertEquals("text/xml", response.getContentType());
    assertSubString("<name>PageOne</name>", xml);
    assertSubString("<name>PageTwo</name>", xml);
    assertSubString("<name>ChildOne</name>", xml);
    assertNotSubString("SymPage", xml);
}

public void testGetDataAsHtml() throws Exception {
    crawler.addPage(root, PathParser.parse("TestPageOne"), "test page");

    request.setResource("TestPageOne");
    request.addInput("type", "data");
    Responder responder = new SerializedPageResponder();
    SimpleResponse response =
        (SimpleResponse) responder.makeResponse(
            new FitNesseContext(root), request);
    String xml = response.getContent();

    assertEquals("text/xml", response.getContentType());
    assertSubString("test page", xml);
    assertSubString("<Test", xml);
}
```

例如，看看那些 `PathParser` 调用。
它们将字符串转换为爬虫使用的 `PagePath` 实例。
这种转换与手头的测试完全无关，只会混淆意图。
围绕 `responder` 的创建以及响应的收集和转换的细节也只是噪音。
还有，从资源和一个参数构建请求 URL 的笨拙方式。
（我 20 年前帮助编写了这段代码，所以我觉得可以自由地严厉批评它。）

最终，这段代码不是为了可读性而设计的。
可怜的读者被大量的细节淹没，在测试变得有意义之前，这些细节必须被理解。

现在考虑下面改进后的测试。
这些测试做的是完全相同的事情，但它们已经被重构为更清晰、更具解释性的形式。

```java
public void testGetPageHierarchyAsXml() throws Exception {
    makePages("PageOne", "PageOne.ChildOne", "PageTwo");
    submitRequest("root", "type:pages");
    assertResponseIsXML();
    assertResponseContains(
        "<name>PageOne</name>",
        "<name>PageTwo</name>",
        "<name>ChildOne</name>");
}

public void testSymbolicLinksAreNotInXmlPageHierarchy() throws Exception {
    WikiPage page = makePage("PageOne");
    makePages("PageOne.ChildOne", "PageTwo");
    addLinkTo(page, "PageTwo", "SymPage");
    submitRequest("root", "type:pages");
    assertResponseIsXML();
    assertResponseContains(
        "<name>PageOne</name>",
        "<name>PageTwo</name>",
        "<name>ChildOne</name>"
    );
    assertResponseDoesNotContain("SymPage");
}

public void testGetDataAsXml() throws Exception {
    makePageWithContent("TestPageOne", "test page");
    submitRequest("TestPageOne", "type:data");
    assertResponseIsXML();
    assertResponseContains("test page", "<Test");
}
```

这些测试的结构清晰地体现了 *Arrange/Act/Assert (AAA)* ¹ 模式。
每个测试都明确地分为三个部分。
- 第一部分（Arrange）构建测试数据，
- 第二部分（Act）操作该测试数据，
- 第三部分（Assert）检查操作是否产生了预期结果。

¹ https://automationpanda.com/2020/07/07/arrange-act-assert-a-pattern-for-writing-good-tests/

注意，绝大部分烦人的细节已经被消除了。
测试直奔主题，只使用它们真正需要的数据类型和函数。
任何阅读这些测试的人都应该能够很快地弄清楚它们在做什么，而不会被细节误导或淹没。
