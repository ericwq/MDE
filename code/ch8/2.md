## 优先使用异常而非返回错误码

异常可能是一个棘手的问题。
在我们大多数现代语言中，它们是沿着调用栈向上传递错误信息的一种可靠方式。
在较老的语言中，最著名的是 C++，这种可靠性并不能得到保证。
而在某些语言中，比如 Go，异常根本不存在。

### 责任自负

总的来说，在可能的情况下，我更喜欢使用异常而不是错误码。
<ins>从命令函数返回错误码是对命令查询分离的微妙违反。
它促使命令被用作 `if` 语句谓词中的表达式</ins>。

```c
if (deletePage(page) == E_OK)
```

<ins>这不会遭受动词/形容词混淆的问题，但会导致深度嵌套的结构。
当你返回一个错误码时，你制造了调用者必须立即处理错误的问题</ins>。

```c
if (deletePage(page) == E_OK) {
    if (registry.deleteReference(page.name) == E_OK) {
        if (configKeys.deleteKey(page.name.makeKey()) == E_OK){
            logger.log("page deleted");
            return E_OK;
        } else {
            logger.log("configKey not deleted");
            return E_ERROR;
        }
    } else {
        logger.log("deleteReference from registry failed");
        return E_ERROR;
    }
} else {
    logger.log("delete failed");
    return E_ERROR;
}
```

程序员有时会使用守卫（guards）来假装结构不是深度嵌套的。
但那些 `else` 子句的缺失并不意味着它们实际上不存在。

```c
if (deletePage(page) != E_OK) {
    logger.log("delete failed");
    return E_ERROR;
}
if (registry.deleteReference(page.name) != E_OK) {
    logger.log("deleteReference from registry failed");
    return E_ERROR;
}
if (configKeys.deleteKey(page.name.makeKey()) != E_OK){
    logger.log("configKey not deleted");
    return E_ERROR;
}
logger.log("page deleted");
return E_OK;
```

<ins>另一方面，如果你使用异常而不是返回错误码，那么错误处理代码可以与快乐路径代码分离并得以简化</ins>：

```java
try {
    deletePage(page);
    registry.deleteReference(page.name);
    configKeys.deleteKey(page.name.makeKey());
}
catch (Exception e) {
    logger.log(e.getMessage());
}
```

### 提取 Try/Catch 块

<ins>`try/catch` 块本身就很丑陋。
它们混淆了代码的结构，并将错误处理与正常处理混在一起。
因此，最好将 `try` 和 `catch` 块的主体提取到它们自己的函数中</ins>。

```java
public void delete(Page page) {
    try {
        deletePageAndAllReferences(page);
    }
    catch (Exception e) {
        logError(e);
    }
}

private void deletePageAndAllReferences(Page page) throws Exception {
    deletePage(page);
    registry.deleteReference(page.name);
    configKeys.deleteKey(page.name.makeKey());
}

private void logError(Exception e) {
    logger.log(e.getMessage());
}
```

<ins>在上面的代码中，`delete` 函数完全是关于错误处理的。
它很容易理解，然后可以忽略。
`deletePageAndAllReferences` 函数完全是关于完全删除一个页面的过程。
错误处理可以被忽略。
这提供了一种很好的分离，使代码更容易理解和修改</ins>。

### 错误处理是一件事

<ins>正如我们所知，函数应该做一件事。
错误处理就是一件事。
因此，一个处理错误的函数应该不做其他任何事情。
这意味着（如上面的示例所示）如果一个函数中存在关键字 `try`，它应该是该函数中的第一个词（可能在一些变量声明之后），
并且在 `catch/finally` 块之后不应该有任何内容</ins>。

### 错误码的依赖磁铁

<ins>如果你必须返回错误码，要小心不要让它们变成 *依赖磁铁 (dependency magnet)* </ins>。

在 C 语言中，我们曾经创建头文件 `error.h`。
它看起来像这样（尽管它通常会更长）：

```c
#define E_OK 0
#define E_INVALID 1
#define E_NO_SUCH 2
#define E_LOCKED 3
#define E_OUT_OF_RESOURCES 4
```

系统中的每个模块都会 `#include error.h`。
每当一个新的错误码被添加到 `error.h` 时，系统中的每个模块都必须被重新编译 —— 因为构建系统使用源文件的日期来确定哪些是过时的，需要重新编译。

这给错误码带来了负面压力。
程序员不想添加新的错误，因为那样他们就必须重新构建和重新部署一切，而且在那些日子里，重新构建可能需要数小时。
所以他们以 “创造性” 的方式重用旧的错误码，而不是添加新的。
这当然导致了混乱、幻灭和心痛。

现代构建环境可以比这更智能。
例如，在 Java 中，你可以在名为 `Error.java` 的文件中使用枚举：

```java
public enum Error {
    OK,
    INVALID,
    NO_SUCH,
    LOCKED,
    OUT_OF_RESOURCES;
}
```

像这样的文件仍然是一个依赖磁铁，因为许多其他类会导入并使用它。
然而，当程序员在 `Error.java` 中添加一个新的错误码时，只有那些直接受更改影响的文件才需要被重新编译和重新部署。
那些只是使用先前存在的错误码的文件则不会。

<ins>所以，了解你的构建系统是如何工作的，以及依赖磁铁是否会导致构建的颠簸和需要重新部署，是一个好主意</ins>。

<ins>在像 Go 这样的语言中，`Error` 是一个接口，程序员想要添加的任何错误码都实现该接口。
这意味着它们可以保存在单独的源文件中，并且没有成为依赖磁铁的风险</ins>。

当然，这种方法可以在任何支持接口或等效动态多态的语言中使用。
例如，在 Python 中，错误码可以是独立的鸭子类型类。
