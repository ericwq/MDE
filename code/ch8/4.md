## 副作用

自本书第一版撰写以来的这些年里，随着函数式编程的兴起，“副作用 (side effect)” 一词的定义经历了一个转变。
二十年前，大多数程序员认为，一个带有副作用的函数有一个主要目的，但除此之外还做了一些其他的事情。
我在第一版中使用的例子是一个检查登录密码有效性的函数，但如果密码被验证有效，它还会初始化当前会话。

从那以后，这个定义被泛化了。
<ins>如今，我们将副作用定义为任何比函数存活更久的状态变更，即使该状态变更是函数的主要意图。
换句话说，一个带有副作用的函数是不纯的</ins>。

因此，例如，如果 `stack.pop()` 移除栈顶的第一个元素，那么它使该栈处于改变的状态；该状态的改变就是一个副作用。

<ins>副作用给软件系统带来了复杂性，因为它们引入了一种隐蔽的耦合形式，称为 *时间耦合 (temporal coupling)* —— 时间上的耦合。
一个带有副作用的语句通过一个状态变更将它的上方代码与下方代码分离开。
那个状态变更意味着这些代码行的顺序必须被保持</ins>。

所以你不能在打开文件之前关闭它，如果它已经打开，你也不能打开它。
你不能在获得信号量之前释放它。
你不能在分配内存块之前释放它。
你不能在获取图形上下文之前释放它。
等等。

副作用函数通常是成对出现的，比如 `open/close`、`seize/release` 或 `malloc/free`。
一个创建副作用，另一个撤销它。
所以副作用就像西斯（The Sith）：“总是有两个。”

### 我们不擅长这个

我们不擅长管理副作用的证据是，现在我们几乎所有的主要语言都具备垃圾回收功能。
垃圾回收被添加到我们的语言中，是为了治愈我们如此糟糕地平衡 `malloc` 和 `free` 的问题。
我们把这个搞砸了这么多次，并且让这么多系统在每天午夜重启，以至于我们最终创造了这个可怕的 hack 特性，作为绝望的措施来减轻我们清理内存副作用的负担。

你知道有多少语言竭尽全力帮助程序员管理内存块的所有权？
有多少语言使用了引用计数、RAII ⁹ 或天知道什么？为什么？
因为我们这些可怜、软弱的程序员似乎无法想出如何归还我们从图书馆借来的书。

⁹ 资源获取即初始化（Resource Acquisition Is Initialization）—— C++ 中旧的 `auto_ptr`（现在是 `unique_ptr` 和 `shared_ptr`）设施背后的关键见解。

问题是，像垃圾回收这样的设施只处理了我们必须应对的众多西斯式生物中的一种。
我们没有用于文件描述符、图形上下文、信号量等等的垃圾回收。
嗯，我想你明白了。
我们不擅长这个。

当顺序很重要时，时间耦合会泄漏到代码的其他部分，造成像内存泄漏一样难以调试的情况。
我敢肯定你曾经有过调试一个行为异常的系统，结果发现如果你交换两个相邻函数调用的顺序，系统突然就能工作的经历 —— 而你却不知道为什么。

<ins>由副作用产生的时间耦合是所有并发更新问题、所有可重入问题、所有竞争条件以及几乎所有初始化和终结化问题的根源</ins>。
时间耦合是大麻烦。
那么我们如何避免它们呢？

### 函数式语言

你可以通过使用函数式语言来避免很多副作用。
这不是万灵药。
仍然可以用函数式语言创建时间耦合 —— 但大多数函数式语言都有工具，使你在创建它们时非常明显。

<ins>函数式语言抑制副作用的主要机制是缺少赋值语句。
在函数式语言中，你不被允许改变变量的状态。
事实上，函数式语言中没有变量。
命名的值不能被改变</ins>。

你们中的一些人可能以前使用过函数式语言，现在可能因沮丧而将这一页撕成碎片。
请放松。让我解释一下。

函数式语言允许将名称赋值给值。
源代码可能看起来很像赋值语句。
然而，在严格函数式语言中，虽然你可能能够重新赋值名称，但你不能覆盖该值。

例如，我在我前一段时间写的一个 Clojure 程序中找到了以下内容。

```clojure
(defn update-clouds-age [ms world]
  (let [clouds (:clouds world)
        decay (Math/pow glc/cloud-decay-rate ms)
        clouds (map #(update % :concentration * decay) clouds)
        clouds (filter #(> (:concentration %) 1) clouds)
        clouds (doall clouds)]
    (assoc world :clouds clouds)))
```

名称 `clouds` 已经被赋值和重新赋值了好几次。
然而，之前的值没有被覆盖 —— 它们仍然存在。
名称 `clouds` 不代表一个被重新赋值覆盖的内存槽。
相反，四个版本的 `clouds` 引用了四个不同的内存块，它们保留着它们的值。
名称 `clouds` 不代表一个变量，因为没有任何东西是可变的。

现在，去拿些胶带把这一页粘好。

为什么函数式语言会阻止覆盖值？
因为覆盖是一种副作用。
它通过状态变更将其上方的行和下方的行分开。
它创建了一个时间耦合。
顺序很重要。

当然，在使用函数式语言时，你仍然可以创建带有副作用的代码。
大多数情况下，这是因为该语言有专门用于此目的的特殊设施。
例如，Clojure 有一个称为 `atom` 的特殊数据类型，它代表一个变量，其值可以使用一组特殊函数来更改。

而且，当然，仍然存在带有副作用的操作系统设施。
例如，文件仍然需要被打开和关闭。

更一般地说，用函数式语言模拟任何系统都是可能的 —— 包括支持副作用的系统。
例如，即使是在最严格的函数式语言中，我也可以编写一个 Lua 执行环境，然后在 Lua 中编写带有明显副作用的程序。

现在，这不是一本关于函数式编程的书，所以我不会继续长篇大论地讨论这个问题。
只需说，使用函数式语言可以帮助你管理副作用；但它不能也不会消除它们。

如果你想要对这些问题的更深入讨论，我建议你阅读我的书《Functional Design》。¹⁰

¹⁰ [Functional Design](../bib.md#functional-design) 。

### 面向对象语言

最近针对面向对象编程语言（OOPL）的一大抱怨是它们助长了副作用。
很容易理解为什么这种抱怨获得了关注。
对象是状态的容器，对象的方法经常改变它们的状态，导致副作用和时间耦合。

<ins>然而，人们不常争论的是，OOPL 有非常好的设施来抑制和隐藏副作用</ins>。
例如，考虑这个 C++ 中的简化和人为的示例。

```cpp
#include <iostream>
#include <fstream>
#include <string>
using namespace std;

class LineCounter {
public:
    static int count(const char* fileName);
private:
    static int nLines;
    static ifstream file;
    static void initialize(const char* fileName);
    static void countTheLines();
    static int finalize();
};

int LineCounter::nLines;
ifstream LineCounter::file;

void LineCounter::initialize(const char* fileName) {
    nLines = 0;
    file.open(fileName);
}

void LineCounter::countTheLines() {
    string line;
    while (getline (file, line))
        nLines++;
}

int LineCounter::finalize() {
    file.close();
    return nLines;
}

int LineCounter::count(const char* fileName) {
    initialize(fileName);
    countTheLines();
    return finalize();
}
```

我希望你在这个例子中注意到的是，`LineCounter` 类中的每一个私有方法都有一个副作用；然而，调用它们的唯一公共方法却没有。
这意味着 `LineCounter` 的任何用户都不会暴露于时间耦合。
假设这是一个单线程应用程序，副作用完全被隐藏了。

在这个例子中，我们将 `LineCounter` 用作一个受保护的命名空间。
没有 `LineCounter` 对象。
这个类只是一个允许我们隐藏可能导致时间耦合的变量和函数的地方。

<ins>注意我添加了单线程约束</ins>。
在多线程环境中，那些静态变量可能会暴露于并发更新问题。
我们可以通过用信号量包围 `count` 函数来解决这个问题。
或者我们可以通过去掉静态变量和函数并将 `LineCounter` 类变成一个真正的对象来解决，迫使用户在调用 `count` 之前创建一个实例。

<ins>关键是，大多数 OOPL 的设施提供了一种方便的方法，将副作用隐藏在封装边界后面，从而防止时间耦合泄漏到整个应用程序中</ins>。
