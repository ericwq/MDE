# 第 8 章 函数启发法

<center><img src="../imgs/fig-ch8-0.png" width="40%" /></center><br/>

以下是一些我发现有助于保持代码整洁的启发法。
我不把它们当作严格的规则来遵循，但当其他条件相同时，这些是我的偏好。

## 函数参数

<ins>你添加到函数签名中的每一个参数都会使该函数更难理解。
最容易理解的参数列表是空参数列表</ins>。

在本书的第一版中，这个说法让一些人感到困惑。
他们的抱怨是，一个空参数列表的函数除了返回一个常量之外什么也做不了。
所以，显然需要进一步的解释。

在面向对象的程序中，对象的每个方法至少有一个参数。
在 Python 和 Go 中，它被显式声明并按惯例命名为 `self`。
在 Java、C# 和 C++ 中，它是隐式的 `this`。
这个参数，无论是显式的还是隐式的，都代表了封闭的作用域。

C 语言中的函数有隐含的第一个参数吗？
当然有；它是封闭的全局作用域。
一个 C 函数总是可以访问那个作用域，所以它扮演着与 `this` 或 `self` 相同的角色。
<ins>因此，每个写出来的函数都有一个代表封闭作用域的隐含参数</ins>。

因此，当我说最容易理解的参数列表是空参数列表时，我并没有计算隐含的封闭作用域。
最容易理解的参数列表是没有声明参数的参数列表。

这样的方法或函数存在吗？
当然存在。
`Stack.pop()`、`file.close()`、`semaphore.release()`、`buffer.flush()`：它们非常常见且非常易读。

下一个最容易理解的参数列表是带有一个声明参数的列表。
调用 `f(x)` 相当容易理解。
你不可能把参数的顺序搞错。

两个参数不太难。
记住哪个在前相当容易 —— 我的意思是，只有一种方式会出错。
你可以通过使两个参数可交换来使其更容易。

三个参数开始变得困难。
有五种方式会把它们弄错顺序。
是的，我知道 IDE 在这方面已经变得相当有帮助；但是，为什么要去考验命运呢？

<ins>参数就是耦合，因此已经够难了，更不用说还要担心它们在调用序列中的顺序。
而且，它们读起来比写起来更难。
IDE 会在编写时给你很多帮助，但在阅读时帮助就少多了。
所以三个通常是我的极限</ins>。

是的，三个的极限是武断的。
你可能对更多参数感到舒适。
你做你的，我做我的。

<ins>如果我需要向函数传递超过三个参数，我会尝试找到一种对它们进行分组的方法。
我可能会把它们放入一个对象中</ins> —— 毕竟，如果四个事物如此内聚，以至于它们可以作为一个单元传递给一个函数，那么它们为什么还不是一个对象呢？
<ins>或者，我可能会把它们放入一个哈希映射中，用好的名称来标识它们</ins>。

<ins>减少参数列表的最简单方法之一是在当前类中创建字段来保存我们否则会作为参数传递的值。
实际上，OO 之所以是一个强大的工具，原因之一就是它允许我们创建上下文，使函数无需传递大量参数即可通信</ins>。

### 可变参数

有时我们希望编写接受无限数量参数的函数。
在 Java 中，`String.format` 函数就是这样的。

```java
public String format(String format, Object... args)
```

我认为可以安全地假设这个函数实际上只接受两个参数：格式字符串和名为 `args` 的对象数组。

### 超过三个？

有时顺序背后有某种逻辑。
例如，将 `distance(x1,y1,x2,y2)` 的参数保持顺序并不难。
另一方面，如果没有逻辑，那么就有 23 种方式会把顺序弄错。
即使有 IDE 的帮助，这也是一个相当大的风险。
在阅读代码时风险更大，因为你不太可能注意到参数顺序错误。
所以通常，如果超过三个参数，我会寻找其他方法。

### 关键字参数

一些语言允许你在函数调用中命名参数。
例如，在 C# 中，你可以在参数前加上参数名：

```csharp
createRental(movie: m, daysRented: 3);
```

<ins>当使用这样的语言特性时，我不太担心参数的顺序，并且有时可能会传递超过三个参数</ins>。

在某些语言中，哈希映射非常容易定义，它们提供了一种传递命名参数的好方法。
例如，在 Clojure 中，我可以像下面这样传递一个哈希映射：

```clojure
(create-rental {:movie m, :daysRented 3})
```

Ruby 提供了类似的语法糖：

```ruby
createRental(movie: m, daysRented: 3)
```

在 Ruby 中，如果 `createRental` 函数被声明为接受一个哈希映射，那么参数将自动被视为键/值对。

### 标志参数

<ins>标志参数很丑陋。
向函数传递一个布尔值通常是粗心的做法。
它立即复杂化了函数的签名，并大声宣告该函数做了不止一件事。
它在标志为 `true` 时做一件事，在标志为 `false` 时做另一件事</ins>。
它们也很难阅读。例如：

```java
String monthNames[] = getMonths(false);
```

这是什么意思？我们是在获取月份还是没有？

函数的定义告诉我们，布尔参数用于选择长月份名称还是短月份名称。
但通过查看调用无法知道这一点。
要知道它，唯一的方法是阅读函数的实现，或者至少是丑陋的 Javadoc。

```java
/**
 * Returns an array of month names.
 *
 * @param shortened a flag indicating that shortened month names should
 *                  be returned.
 * @return an array of month names.
 */
public static String[] getMonths(final boolean shortened) {
    if (shortened) {
        return DATE_FORMAT_SYMBOLS.getShortMonths();
    } else {
        return DATE_FORMAT_SYMBOLS.getMonths();
    }
}
```

如果你不知道布尔标志的含义，它们可能会相当令人困惑。
那醒目的 `true` 或 `false` 表示某种选项；但如果你不知道那个选项是什么，你就必须点击进入函数并阅读实现 —— 谁想那样做呢？

<ins>解决方案，在可能的情况下，是将函数拆分为两个函数：一个处理 `true` 情况，一个处理 `false` 情况</ins>。

```java
String[] getLongMonthNames() {…}
String[] getShortMonthNames() {…}
```

当然，这条规则也有例外。
例如，某些对象内部有二元标志，通过 `setFlag(boolean)` 方法设置。
我不会对此抱怨。

### 输出参数

参数最自然的解释是函数的输入。
但有时人们会使用参数来捕获输出值。
这通常是因为他们想从函数返回多个值。
例如，在 C# 中可以使用 `out` 参数，在 C 中可以使用指针，在 C++ 中可以传递引用，如下所示。

```cpp
void stats(double* ns, int n, double& mean, double& sum) {
    sum=0;
    for (int i=0; i<n; i++)
        sum += ns[i];
    mean=sum/n;
}
```

<ins>我尽量避免像这样的输出参数。
它们违反了 *最少惊讶原则 (Principle of Least Surprise)* 。¹
人们通常不希望参数捕获输出</ins>，所以如果他们看到下面的调用，他们可能会想知道为什么我们要把 `sum` 和 `mean` 传递给函数。

¹ 最少惊讶法则，PL/1 Bulletin，1967。

```cpp
stats(list, listSize, listMean, listSum);
```

<ins>阅读这样一行代码可能会导致读者停顿一下，停下来想想发生了什么。
这是因为他们期望数据通过参数进入函数，并通过返回值从函数输出</ins>。

在 Go、Python 或 Ruby 中，² 我们可以从函数返回多个值。

² Ruby 返回一个可变数组。责任自负。

```python
mean, sum = stats(list)
```

在其他语言中，我们可以返回一个包含两个元素的对象。

或者，在所有情况下，我们可以创建两个函数：一个用于求和，另一个用于计算平均值。
在其他条件相同的情况下，这可能是最好的解决方案。

<ins>在面向对象编程出现之前，有时需要输出参数。
然而，在面向对象语言中，对输出参数的需求大部分消失了，因为对象本身可以作为其方法的输出参数。
换句话说，最好按如下方式调用 `stats.calculate`</ins>：

```java
stats.calculate(list);
double mean = stats.getMean();
double sum = stats.getSum();
```

### 错误码

Go 程序员经常利用从函数返回多个值的能力来同时返回错误码和值：

```go
f, err := os.Open("someFile")
if err != nil {
    log.Fatal(err)
}
```

这种策略也可以在支持输出参数的语言中使用。

```java
File f = os.open("someFile", out error);
```

只要这个约定被严格且一致地应用，我认为这是一个合理的约定；尤其是在像 Go 这样没有异常的语言中。
