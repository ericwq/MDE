## 注释总结

**JOHN：**<br/>
让我们结束本节讨论。
以下是我对我们一致和分歧之处的总结。

- 我们对注释的整体看法根本不同。
我比你看重注释的价值，我相信它们在系统设计中扮演着基础和不可替代的角色。
你同意有些地方需要注释，但你认为注释并不总是使代码更容易理解，所以你认为需要注释的地方要少得多。

- 对于给定的代码，我可能会写比你多 5 到 10 倍的注释行。

- 我相信缺少注释比错误的或无用的注释更能导致生产力损失；
你认为注释总体上是一个净负面的东西，正如通常实践的那样：坏的注释花费的时间比好的注释节省的时间更多。

- 你认为注释是用英语而不是编程语言写的，这是一个问题。
我不认为这特别有问题，而且认为在许多情况下，英语效果更好。

- 你建议开发人员应该尽可能地将我认为是注释的信息重新表达为代码。
其中一个是超长的方法名称。
我认为超长名称很尴尬且难以理解，最好使用较短的名称并辅以注释。

- 我相信没有大量的注释就不可能定义接口和创建抽象。
你同意公共 API 需要，但认为团队内部接口几乎没有注释的必要。

- 你不愿意信任注释，直到你阅读代码验证它们。
我通常信任注释；通过这样做，我不需要像你那样阅读那么多的代码。
你认为这让我暴露在太多的风险中。

- 我们同意实现代码只有在代码不明显时才需要注释。
虽然我们都不主张大量的实现注释，但我比你可能更看到它们的价值。

总的来说，我们在这个话题上很难找到一致的地方。

你似乎在你遇到的注释中找到了更多的帮助。
