## 糟糕的注释

糟糕的注释通常是糟糕代码的拐杖或借口，或者是为不充分的决策辩护，无异于程序员在自言自语。

当我看到这类注释时，我会删除它们。以下是这类注释的一些具体示例。

### 喃喃自语

仅仅因为你觉得应该写注释，或者因为流程要求你写注释而草率地插入一个注释，这是一种 hack。
如果你决定写注释，那么就花必要的时间来确保它是你能写出的最好的注释。

例如，这是我在 FitNesse 中发现的一个案例。
在我看来，作者当时很匆忙，或者只是没太注意。
他的喃喃自语留下了一个谜：

```java
public void loadProperties()
{
    try
    {
        String propertiesPath = propertiesLocation + "/" + PROPERTIES_FILE;
        FileInputStream propertiesStream =
            new FileInputStream(propertiesPath);
        loadedProperties.load(propertiesStream);
    catch(IOException e)
    }
    {
        // No properties files means all defaults are loaded
    }
}
```

`catch` 块中的那个注释是什么意思？
显然它对作者有意义，但这个意义并没有很好地传达出来。
显然，如果我们得到一个 `IOException`，这意味着没有 “properties” 文件；
在这种情况下，所有默认值都被加载了。
但是谁加载了所有默认值？
它们是在调用 `loadProperties.load` 之前加载的吗？
还是 `loadProperties.load` 捕获了异常，加载了默认值，然后传递异常给我们忽略？
还是 `loadProperties.load` 在尝试加载文件之前加载了所有默认值？
作者是在安慰自己他正在让 `catch` 块保持为空吗？
还是 ——这是一个可怕的可能性—— 作者是在告诉自己以后回来写加载默认值的代码？

我们唯一的办法是检查系统其他部分的代码，以找出这里发生了什么。
任何迫使你到另一个模块中去寻找其含义的注释，都未能与你沟通，并且不值得它消耗的比特。

如果程序员写了下面这样，不是会更好吗？

```java
catch(IOException e)
{
    LoadedProperties.loadDefaults();
}
```

### 冗余注释

下面的代码展示了一个带有头部注释的简单函数，这个注释没有告诉我们任何代码本身没有说明的东西。
阅读这个注释可能比阅读代码本身花费的时间更长。

```java
// Utility method that returns when this.closed is true.
// Throws an exception if the timeout is reached.
public synchronized void
waitForClose(long timeoutMillis) throws Exception
{
    if(!closed)
    {
        wait(timeoutMillis);
        if(!closed)
            throw new Exception("MockResponseSender could not be closed");
    }
}
```

这个注释的目的是什么？
它肯定不比代码更具信息性。
它没有证明代码的合理性，也没有提供意图或理由。
它并不比代码更容易阅读。
事实上，它比代码更不精确，并引诱读者接受那种不精确性来代替真正的理解。
它就像一个握手言欢的二手车销售员向你保证你不需要看引擎盖下面。

### 误导性注释

有时，程序员怀着最好的意图，在他们注释中做出的陈述可能会导致误解。
再花一点时间思考一下我们在上一个例子中看到的那个严重冗余但也微妙地具有误导性的注释。

你发现这个注释是如何误导的吗？
这个方法并不是当 `this.closed` 变为 `true` 时返回。
它是在 `this.closed` 为 `true` 时返回；否则，它会等待一个盲目的超时，然后如果 `this.closed` 仍然不为 `true`，则抛出一个异常。

这种微妙的不准确信息，被包含在一个比代码主体更难阅读的注释中，可能会导致另一个程序员轻率地调用这个函数，期望它会在 `this.closed` 变为 `true` 时立即返回。
那个可怜的程序员随后会发现自己在调试会话中，试图找出为什么他们的代码执行得如此缓慢。

这也让我怀疑这种不精确是否延续到了代码中。

### 强制性注释

规定每个函数都必须有 Javadoc，或者每个变量都必须有注释，这简直愚蠢至极。
像这样的注释只会使代码变得杂乱，传播错误信息，并导致普遍的混乱和无组织。

例如，对每个函数都要求 Javadoc 会导致像这样的可憎之物：

```java
/**
 * @param title The title of the CD
 * @param author The author of the CD
 * @param tracks The number of tracks on the CD
 * @param durationInMinutes The duration of the CD in minutes
 */
public void addCD(String title, String author,
                  int tracks, int durationInMinutes) {
    CD cd = new CD();
    cd.title = title;
    cd.author = author;
    cd.tracks = tracks;
    cd.duration = duration;
    cdList.add(cd);
}
```

如果你在这个代码上运行 Javadoc 工具，然后删除注释并再次运行该工具，创建的两个 HTML 文件将几乎相同。
因此，这个 Javadoc 的杂乱没有增加任何东西，只会使代码变得模糊，并制造误导的可能性。

### 噪音注释

有时你会看到一些毫无意义的注释。它们重复显而易见的内容，不提供任何新信息。

```java
/**
 * Default constructor.
 */
protected AnnualDateRule() {
}
```

不，真的吗？或者这个呢：

```java
/** The day of the month. */
private int dayOfMonth;
```

还有这个冗余的典范：

```java
/**
 * Returns the day of the month.
 *
 * @return the day of the month.
 */
public int getDayOfMonth() {
    return dayOfMonth;
}
```

这些注释太吵了，以至于我们学会了忽略它们。
当我们通读代码时，我们的眼睛只是跳过它们。
最终，随着代码的变化，我们未能注意到注释已经开始说谎。

下面的第一个注释似乎是合适的。⁴ 
它解释了为什么 `catch` 块被忽略。
但第二个注释是纯粹的噪音。
显然，程序员对这个函数中编写 `try/catch` 块感到非常沮丧，以至于他需要发泄。

⁴ 当前 IDE 在注释中检查拼写的趋势，对我们这些阅读大量代码的人来说将是一种慰藉。

```java
private void startSending()
{
    try
    {
        doSending();
    catch(SocketException e)
    }
    {
        // normal. someone stopped the request.
    }
    catch(Exception e)
    {
        try
        {
            response.add(ErrorResponder.makeExceptionString(e));
            response.closeAll();
        catch(Exception e1)
        }
        {
            //Give me a break!
        }
    }
}
```

与其在一个毫无价值且嘈杂的注释中发泄，程序员应该认识到他的沮丧可以通过改进代码结构来解决。
他应该把精力转向将最后那个 `try/catch` 块提取到一个单独的函数中，像这样：

```java
private void startSending()
{
    try
    {
        doSending();
    catch(SocketException e)
    }
    {
        // normal. someone stopped the request.
    catch(Exception e)
    }
    {
        addExceptionAndCloseResponse(e);
    }
}

private void addExceptionAndCloseResponse(Exception e)
{
    try
    {
        response.add(ErrorResponder.makeExceptionString(e));
        response.closeAll();
    catch(Exception e1)
    }
    {
    }
}
```

用清理代码的决心取代制造噪音的诱惑。
你会发现这会使你成为一个更好、更快乐的程序员。

### 可怕的噪音

Javadoc 也可能是噪音。
以下 Javadoc（来自一个知名的开源库）的目的是什么？
答案：没有。
它们只是冗余的噪音注释，出于某种错位的提供文档的愿望而编写。

```java
/** The name. */
private String name;

/** The version. */
private String version;

/** The licenceName. */
private String licenceName;

/** The version. */
private String info;
```

再仔细读一遍这些注释。
你看到复制粘贴错误了吗？
如果作者在编写（或粘贴）注释时没有注意，为什么读者期望从中受益？

### TODO 注释

在本书的第一版中，我支持在代码中留下 TODO 注释，作为需要处理的事情的提醒。
我喜欢我的 IDE 中允许我快速查看项目中所有 TODO 注释的功能。

```java
//TODO-MdM these are not needed
// We expect this to go away when we do the checkout model
protected VersionInfo makeVersion() throws Exception
{
    return null;
}
```

从那以后我改变了对这件事的看法。
在阅读了几年别人和我自己写的代码之后，我逐渐理解到 TODO 意味着 “不要做”。
所以我改变了我的规则。

我仍然使用 TODO 注释，但我不会将它们签入。
我要么做需要做的事情，要么消除需要做它的理由，要么将它放入需要执行的任务积压中。

### 用函数或变量代替注释

考虑下面这段代码：

```java
// does the module from the global list <mod> depend on the
// subsystem we are part of?
if (smodule.getDependSubsystems().contains(subSysMod.getSubSystem()))
```

这个注释是什么意思？
`<mod>` 是什么，为什么它被放在尖括号里？
我把这段代码放入我的 IDE 中，提取出了几个解释性变量。
结果如下：

```java
ArrayList moduleDependants = smodule.getDependSubsystems();
String ourSubSystem = subSysMod.getSubSystem();
if (moduleDependants.contains(ourSubSystem))
```

在我看来，这次重构帮助最终的 `if` 语句读起来像写得好的散文，并且比那个注释（我仍然不理解）更容易理解。

### 位置标记

有时程序员喜欢标记源文件中的特定位置。
例如，我最近在我正在查看的一个程序中发现了这个：

```java
// Actions //////////////////////////////////
```

很少有情况下将某些函数聚集在这样的横幅下是有意义的。
但总的来说，它们是应该避免的杂乱内容 —— 尤其是结尾那串吵闹的斜线。

这样想。
横幅是引人注目且明显的，尤其是如果你不经常看到横幅的话。
所以要非常谨慎地使用它们，并且只有在收益显著时才使用。
如果你过度使用横幅，它们会落入背景噪音中并被忽略 —— 就像那个喊 “狼来了！” 的小男孩一样。

### 归属和署名

```java
/* Added by Rick */
```

这仅仅是涂鸦。请不要在源代码上喷上你的名字。
源代码控制系统非常擅长记住谁在什么时候添加了什么。
没有必要用小小的署名来污染代码。
你可能认为这样的注释有助于让其他人知道该向谁询问代码问题。
但现实是，它们往往会存在很多很多年，变得越来越不准确和相关。
PR 号和 JIRA 标签也是如此。
把它们放在提交注释中，而不是放在源代码中。

### 注释掉的代码

很少有做法像注释掉代码那样令人厌恶。
注释掉的代码是大自然和自然之神面前的恶行。
不要签入这种东西！

```java

response.setBody(formatter.getResultStream(),

// InputStream resultsStream = formatter.getResultStream();
```

看到那些被注释掉的代码的其他人不太可能有勇气删除它。
他们会认为它在那里是有原因的，而且太重要了不能删除。
所以注释掉的代码就像坏酒瓶底部的酒渣一样聚集起来。

考虑一下来自 Apache Commons 的这个：

```java

//hdrPos = bytePos;
```

为什么那两行代码被注释掉了？
它们重要吗？

还是仅仅是某人多年前注释掉、一直懒得清理的残余物？

在六十年代，曾有一段时间，注释掉代码可能是有用的。
但我们已经拥有良好的源代码控制系统很长时间了。
那些系统会为我们记住代码。
我们不再需要注释掉它。

我在调试时仍然会不时地注释掉代码。
这可能是一种有用的技术。
<ins>但我的规则是从不签入注释掉的代码</ins>。

源代码注释中的 HTML 可能很糟糕，正如你通过阅读下面的代码可以看出。

### 非本地信息

如果你必须写注释，那么确保它描述的是它附近的代码。
不要在局部注释的上下文中提供系统范围的信息。
例如，考虑下面的 Javadoc 注释。
除了它极其冗余之外，它还提供了关于默认端口的信息。
然而，这个函数对那个默认值完全没有控制权。
这个注释不是在描述这个函数，而是在描述系统中其他某个遥远的部件。
当然，无法保证当包含默认值的代码发生变化时，这个注释也会被更改。

```java
/**
 * Port on which fitnesse would run. Defaults to 8082.
 *
 * @param fitnessePort
 */
public void setFitnessePort(int fitnessePort)
{
    this.fitnessePort = fitnessePort;
}
```

### 信息过多

不要在你的注释中放入有趣的历史讨论或无关的细节描述。
下面的注释摘自一个旨在测试函数能否对 base64 进行编码和解码的模块。
除了 RFC 编号之外，阅读这段代码的人不需要注释中包含的那些晦涩信息。

```java
/*
RFC 2045 - Multipurpose Internet Mail Extensions (MIME)
Part One: Format of Internet Message Bodies
section 6.8. Base64 Content-Transfer-Encoding

The encoding process represents 24-bit groups of input bits as output
strings of 4 encoded characters. Proceeding from left to right, a
24-bit input group is formed by concatenating 3 8-bit input groups.
These 24 bits are then treated as 4 concatenated 6-bit groups, each
of which is translated into a single digit in the base64 alphabet.

When encoding a bit stream via the base64 encoding, the bit stream
must be presumed to be ordered with the most-significant-bit first.
That is, the first bit in the stream will be the high-order bit in

*/
```

### 不明显的关联

注释与其所描述的代码之间的关联应该是显而易见的。
如果你费心去写一个注释，那么至少你希望读者能够查看注释和代码，并理解注释在说什么。
例如，考虑这个来自 Apache Commons 的注释：

```java
/*
 * start with an array that is big enough to hold all the pixels
 * (plus filter bytes), and an extra 200 bytes for header info
 */
this.pngBytes = new byte[((this.width + 1) * this.height * 3) + 200];
```

什么是 filter byte？
作者是指 filler byte 吗？
这些字节与 `+1` 有关吗？
还是与 `*3` 有关？
还是两者都有关？
一个像素是一个字节吗？
为什么是 200？
注释的目的是解释那些不能自我解释的代码。
当注释本身需要解释时，这很遗憾。


### **非公共代码中的 Javadoc**

尽管 Javadoc 对公共 API 很有用，但对于由小型团队维护且不打算供公共消费的代码来说，它们更多的是一种障碍而不是好处。
团队已经了解代码，并且不太可能运行 Javadoc 工具来生成 Javadoc 页面，因此 Javadoc 注释的额外形式化只不过是赘物和干扰。

### 示例

我为第一次 XP Immersion 编写了以下模块。
它旨在作为糟糕编码和注释风格的一个示例。
然后 Kent Beck 在几十位热情的学生面前将这个代码重构为一种更令人愉快的形式。
后来，我将这个例子改编到我的书《Agile Software Development, Principles,
Patterns, and Practices》以及我在《Software Development》杂志上发表的第一篇工匠文章。

我发现这个模块有趣的是，曾有一段时间我们中的许多人会认为它 “文档齐全”。
现在我们把它看作是一个小混乱。
看看你能找到多少不同的注释问题。

```java
import java.util.*;

/**
 * This class Generates prime numbers up to a user specified
 * maximum. The algorithm used is the Sieve of Eratosthenes.
 * <p>
 * Eratosthenes of Cyrene, b. c. 276 BC, Cyrene, Libya --
 * d. c. 194, Alexandria. The first man to calculate the
 * circumference of the Earth. Also known for working on
 * calendars with leap years and ran the library at Alexandria.
 * <p>
 * The algorithm is quite simple. Given an array of integers
 * starting at 2. Cross out all multiples of 2. Find the next
 * uncrossed integer, and cross out all of its multiples.
 * Repeat until you have passed the square root of the maximum
 * value.
 *
 * @author Alphonse
 * @version 13 Feb 2002 atp
 */
public class GeneratePrimes
{
    /**
     * @param maxValue is the generation limit.
     */
    public static int[] generatePrimes(int maxValue)
    {
        if (maxValue >= 2) // the only valid case
        {
            // declarations
            int s = maxValue + 1; // size of array
            boolean[] f = new boolean[s];
            int i;
            // initialize array to true.
            for (i = 0; i < s; i++)
                f[i] = true;
            // get rid of known non-primes
            f[0] = f[1] = false;
            // sieve
            int j;
            for (i = 2; i < Math.sqrt(s) + 1; i++)
            {
                if (f[i]) // if i is uncrossed, cross its multiples.
                {
                    for (j = 2 * i; j < s; j += i)
                        f[j] = false; // multiple is not prime
                }
            }
            // how many primes are there?
            int count = 0;
            for (i = 0; i < s; i++)
            {
                if (f[i])
                    count++; // bump count.
            }
            int[] primes = new int[count];
            // move the primes into the result
            for (i = 0, j = 0; i < s; i++)
            {
                if (f[i]) // if prime
                    primes[j++] = i;
            }
            return primes; // return the primes
        }
        else // maxValue < 2
            return new int[0]; // return null array if bad input.
    }
}
```

下面你可以看到同一个模块的重构版本。
请注意，注释的使用被显著地限制了。
整个模块中只有两个注释。
两个注释本质上都是解释性的。

```java
/**
 * This class Generates prime numbers up to a user specified
 * maximum. The algorithm used is the Sieve of Eratosthenes.
 * Given an array of integers starting at 2:
 * Find the first uncrossed integer, and cross out all its
 * multiples. Repeat until there are no more multiples
 * in the array.
 */
public class PrimeGenerator
{
    private static boolean[] crossedOut;
    private static int[] result;

    public static int[] generatePrimes(int maxValue)
    {
        if (maxValue < 2)
            return new int[0];
        else
        {
            uncrossIntegersUpTo(maxValue);
            crossOutMultiples();
            putUncrossedIntegersIntoResult();
            return result;
        }
    }

    private static void uncrossIntegersUpTo(int maxValue)
    {
        crossedOut = new boolean[maxValue + 1];
        for (int i = 2; i < crossedOut.length; i++)
            crossedOut[i] = false;
    }

    private static void crossOutMultiples()
    {
        int limit = determineIterationLimit();
        for (int i = 2; i <= limit; i++)
            if (notCrossed(i))
                crossOutMultiplesOf(i);
    }

    private static int determineIterationLimit()
    {
        // Every multiple in the array has a prime factor that
        // is less than or equal to the root of the array size,
        // so we don't have to cross out multiples of numbers
        // larger than that root.
        double iterationLimit = Math.sqrt(crossedOut.length);
        return (int) iterationLimit;
    }

    private static void crossOutMultiplesOf(int i)
    {
        for (int multiple = 2*i;
             multiple < crossedOut.length;
             multiple += i)
            crossedOut[multiple] = true;
    }

    private static boolean notCrossed(int i)
    {
        return crossedOut[i] == false;
    }

    private static void putUncrossedIntegersIntoResult()
    {
        result = new int[numberOfUncrossedIntegers()];
        for (int j = 0, i = 2; i < crossedOut.length; i++)
            if (notCrossed(i))
                result[j++] = i;
    }

    private static int numberOfUncrossedIntegers()
    {
        int count = 0;
        for (int i = 2; i < crossedOut.length; i++)
            if (notCrossed(i))
                count++;
        return count;
    }
}
```


很容易说第一个注释是多余的，因为它读起来很像 `generatePrimes` 函数本身。
尽管如此，我认为这个注释有助于让读者轻松进入算法，所以我倾向于保留它。

第二个注释几乎肯定是有帮助的。
它解释了使用平方根作为循环限制背后的基本原理。
我找不到任何简单的变量名，也没有任何不同的编码结构能使这一点清晰明了。
