## 为失败做补偿

<ins>注释，充其量只是一种必要的恶。
如果我们的编程语言足够具有表达力，或者如果你和我有足够的天赋来巧妙地运用这些语言来表达我们的意图，我们就不会太需要注释 —— 也许根本不需要</ins>。

<ins>注释的正确用途是弥补我们在代码中表达自己的失败</ins>。
请注意，我使用了 “失败” 这个词。
我是认真的。
注释总是我们语言或我们能力的失败。

这并不意味着我们从不写注释。
我们有时必须写注释，因为我们并不总能想出不用注释就能表达自己的方法。
然而，它们的使用并不是值得庆祝的理由。

<ins>当你发现自己处于需要写注释的位置时，仔细思考一下，看看是否有某种方法可以扭转局面，用代码来表达自己。
每次你用代码表达自己的意图时，都值得自我肯定。
每次你写注释时，你都应该心生惋惜，并感受到我们语言的失败以及我们使用那些语言表达自己能力的失败</ins>。

你写的注释可能是必要的；但这种必要性也是不幸的。

有人说，这样的建议给了年轻程序员避免写注释的许可。
任何年轻或年长的程序员，如果把这些建议作为他们懒惰和/或不愿意添加适当解释和上下文的借口，都应该感到羞耻。
最后，我不能关心别人如何滥用我的建议。
我在这里的唯一目的是帮助那些不会滥用的人。

### 隐藏或模糊的注释

你的 IDE 会隐藏每个源文件中的第一个注释吗？我的会。
那是因为我们很少想读那个注释。
我们期望它是某种样板式的许可证/法律术语，对模块的实际意图没有任何洞察。

但折叠第一个注释并不是我们的 IDE 隐藏或模糊注释的唯一方式。

你的 IDE 用什么颜色显示注释？
对你们中的一些人来说，它将是漂亮的绿色 —— 像草一样。
因此，就像草一样，你可以忽略它们。
它们像附近的草坪一样淡入背景。

对你们中的另一些人来说，它将是一种漂亮的柔和的灰色；
不是不可见，而是强烈地淡化。

为什么？
因为我们不希望它们挡道。
我们并不真的想看到它们。
我们喜欢它们存在的事实；
但我们不希望它们出现在我们面前。

<ins>我将我的 IDE 注释设置为明亮的消防车红色。
我这样做是因为我认为如果有人写了一个注释，我应该阅读它。
然后，如果那个注释对我没有帮助，我会当场删除它。
或者如果那个注释需要调整，我会当场调整它</ins>。

注释，当它们存在时，应该是可见的！

### 说谎的注释

<ins>我为什么这么讨厌注释？
我真的不是。
我只讨厌糟糕的注释。
我完全支持好的注释。
然而，问题是我遇到的注释中有太多属于前一类</ins>。

首先，它们经常说谎。
这些谎言不是故意的，但它们也并非不常见。
注释越旧，离它描述的代码越远，它就越有可能是完全错误的。
原因很简单。
程序员无法现实地维护它们。

代码经常会改变和演进。
代码块会从这里移到那里。
那些代码块会分叉、复制，然后重新组合形成混合体和嵌合体。
不幸的是，注释并不总是（也不能总是）跟随它们。
注释常常与它们描述的代码分离，成为越来越不准确的孤立的模糊描述。
例如，看看这个注释和它旨在描述的那行代码发生了什么：

```java
MockRequest request;
private final String HTTP_DATE_REGEXP =
    "[SMTWF][a-z]{2}\\,\\s[0-9]{2}\\s[JFMASOND][a-z]{2}\\s"+
    "[0-9]{4}\\s[0-9]{2}\\:[0-9]{2}\\:[0-9]{2}\\sGMT";
private Response response;
private FitNesseContext context;
private FileResponder responder;
private Locale saveLocale;
// Example: "Tue, 02 Apr 2003 22:18:49 GMT"
```

可能之后添加的其他实例变量被插在了 `HTTP_DATE_REGEXP` 常量及其解释性注释之间。

你可能会抱怨程序员应该有足够的纪律来保持注释处于高度可维护、相关和准确的状态。
然而，我宁愿那些纪律和精力花在使代码如此清晰和富有表现力，以至于首先就不需要注释。

<ins>不准确的注释比根本没有注释要糟糕得多。
它们欺骗和误导。
它们设定了永远不会实现的期望。
它们制定了不再需要或不应该再遵循的旧规则</ins>。

<ins>真相只能在一个地方得到保证：代码。
只有代码可以被信任地告诉你它做了什么。
它是最可靠的准确信息来源。
因此，尽管注释有时是必要的，我们应当花费大量精力来最小化它们</ins>。

### 过于亲密的注释

<ins>注释的一个重要问题是，它们通常由对代码有深入了解的程序员编写，因此是从那种亲密感的角度编写的。
不幸的是，注释的目标读者并不具有那种亲密感，因此没有理解注释的上下文</ins>。

不止一次，我遇到过这样的情况：直到我理解了作者的代码，我才能够理解作者如此 “有帮助” 地提供的注释。
注释中的文字对我来说根本没有意义，也没有以任何方式帮助我。
一旦我通读了代码并理解了它，注释的意图才变得清晰 —— 但在此之前并非如此。

### 注释不能弥补糟糕的代码

编写注释的一个更常见的动机是糟糕的代码。
我们编写一个模块，我们知道它是混乱和无组织的。
我们知道它一团糟。
所以我们对自己说：“哦，我最好给它加上注释！”

不！你最好 *清理它* ！

清晰、富有表现力的代码加上很少的注释，远远优于杂乱、复杂的代码加上大量的注释。
与其花时间编写解释你所制造混乱的注释，不如花时间清理那个混乱。

### 在代码中表达你的意图

当然有时代码并不是一个很好的解释工具。
不幸的是，许多程序员已经将此理解为代码很少（如果有的话）是一种好的解释手段。
这显然是错误的。
你更愿意看到哪一个？
这个：

```java
// Check to see if the employee is eligible for full benefits
if ((employee.flags & HOURLY_FLAG) && (employee.age > 65))
```

还是这个？

```java
if (employee.isEligibleForFullBenefits())
```

<ins>只需要几秒钟的思考，就能在代码中表达你的大部分意图。
在许多情况下，这只是一个创建函数的问题，该函数表达了你想要写的注释相同的意思</ins>。
