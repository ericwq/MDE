## 好的注释

有些注释是必要的或有益的。
以下是几个值得它们所消耗的比特的注释示例 —— 或者至少不值得删除。

### 法律注释

有时我们的公司编码标准迫使我们出于法律原因编写某些注释。
例如，版权和作者声明是必要且合理的，可以放在每个源文件开头的注释中。

例如，这是我们在 FitNesse 中每个源文件开头放置的标准注释头。
我很高兴地说，我们的 IDE 通过自动折叠这个注释来防止它成为杂乱内容。

```java
// Copyright (C) 2003-2005 by Object Mentor, Inc. All rights reserved.
// Released under the GNU General Public License version 2 or later.
```

这样的注释不应该是合同或法律文件。
在可能的情况下，引用标准许可或其他外部文档，而不是将所有条款和条件都放在注释中。

### 信息性注释

有时用注释提供基本信息是有用的。
例如，考虑这个解释抽象方法返回值的注释：

```java
// 返回正在被测试的 Responder 实例
protected abstract Responder responderInstance();
```

为什么作者求助于注释，而不是给方法一个更好的名称，比如 `responderBeingTested`？
为什么我会允许这个注释，而不是更改方法的名称？
那是因为作者正在使用著名的 *Singleton* ² 设计模式。
当你使用这样的设计模式时，你应该遵循该模式指定的规范形式。
在 Singleton 模式中，访问器函数的名称总是以单词 `Instance` 结尾。
所以作者决定退回到注释，而不是放弃该模式的规范形式。

² [GOF95] 第 127 页。

这里有另一个注释添加了有用信息的案例。

```java
// format matched kk:mm:ss EEE, MMM dd, yyyy
Pattern timeMatcher = Pattern.compile(
    "\\d*:\\d*:\\d* \\w*, \\w* \\d*, \\d*");
```

我不会删除这个注释，因为正则表达式总是难以理解的。
这个也不例外，作者通过一个注释给我们提示，让我们知道这个正则表达式旨在匹配时间戳，这很周到。
任何 Java 程序员都可以从使用 `SimpleDataFormat` 类代码的 `kk:mm:ss EEE, MMM dd, yyyy` 字符串中轻易推断出这一点。

然而，这个注释是一个谎言 —— 或者至少是严重误导的。
那是因为这个正则表达式也会匹配以下字符串：`":: , , "`。
这绝对不是一个时间戳。
所以我会修复正则表达式，并保留注释。

### 意图解释

有时，注释不仅仅是关于实现的有用信息，它还提供了决策背后的意图。
在下面的案例中，我们看到一个有趣的决策被注释记录下来。
当比较两个对象时，作者决定他希望将包含该类的对象排在任何其他类型的对象之前。

```java
public int compareTo(Object o)
{
    if(o instanceof WikiPagePath)
    {
        WikiPagePath p = (WikiPagePath) o;
        String compressedName = StringUtil.join(names, "");
        String compressedArgumentName = StringUtil.join(p.names, "");
        return compressedName.compareTo(compressedArgumentName);
    }
    return 1; // we are greater because we are the right type.
    }
```

这里有一个更好的例子。
你可能不同意程序员对这个问题的解决方案，但至少你知道他试图做什么。

```java
public void testConcurrentAddWidgets() throws Exception {
    WidgetBuilder widgetBuilder = . . .
    //This is our best attempt to get a race condition
    //by creating large number of threads.
    for (int i = 0; i < 25000; i++) {
        WidgetBuilderThread widgetBuilderThread =
            new WidgetBuilderThread(widgetBuilder, text, parent, failFlag);
        Thread thread = new Thread(widgetBuilderThread);
        thread.start();
    }
    assertEquals(false, failFlag.get());
}
```

作为代码审查的一部分，我不会删除那个注释。
然而，我会倾向于通过将那个 `for` 循环提取到一个名为 `attemptRaceCondition` 的函数中来消除它。

> **Future Bob**：顺便说一句，这是一种强制竞争条件的糟糕方法。
当你启动一堆线程希望它们会竞争时，它们实际上会排成单行依次执行，而不会竞争。
如果你想强制竞争条件，你要么必须用信号量来设置竞争，要么引入随机延迟并希望线程会彼此错开并意外进入竞争配置。

#### 澄清

有时，将某个晦涩的参数或返回值的含义翻译成可读的内容是有帮助的。
通常，最好找到一种方法使该参数或返回值本身变得清晰；
但当它是标准库的一部分，或者在你无法更改的代码中时，一个有用的澄清注释可能会有所帮助。

我编写了以下注释，作为 FitNesse 中一个功能的一部分。
我担心一长串的 `assertTrue` 语句会让读者的眼睛翻白。
像这样的视觉障碍和错觉在代码中特别常见。
所以我添加了注释以示礼貌。

```java
public void testCompareTo() throws Exception
{
    WikiPagePath a = PathParser.parse("PageA");
    WikiPagePath ab = PathParser.parse("PageA.PageB");
    WikiPagePath b = PathParser.parse("PageB");
    WikiPagePath aa = PathParser.parse("PageA.PageA");
    WikiPagePath bb = PathParser.parse("PageB.PageB");
    WikiPagePath ba = PathParser.parse("PageB.PageA");

    assertTrue(a.compareTo(a) == 0); // a == a
    assertTrue(a.compareTo(b) != 0); // a != b
    assertTrue(ab.compareTo(ab) == 0); // ab == ab
    assertTrue(a.compareTo(b) == -1); // a < b
    assertTrue(aa.compareTo(ab) == -1); // aa < ab
    assertTrue(ba.compareTo(bb) == -1); // ba < bb
    assertTrue(b.compareTo(a) == 1); // b < a
    assertTrue(ab.compareTo(aa) == 1); // ab > aa
    assertTrue(bb.compareTo(ba) == 1); // bb > ba
}
```

然而，澄清注释有很大的可能是不正确的。
事实上，前面代码中的一个注释是错误的。
通读前面的示例，看看你是否能找到它；并注意验证它们是多么困难。
这种困难解释了为什么澄清是必要的，也解释了为什么它可能是有风险的。

### 警告后果

有时，警告其他程序员某些后果是有用的。例
如，这里有一个注释解释了为什么一个特定的测试用例被关闭：

```java
// Don't run unless you have some time to kill.
public void _testWithReallyBigFile()
{
    writeLinesToFile(10000000);
    response.setBody(testFile);
    response.readyToSend(this);
    String responseString = output.toString();
    assertSubString("Content-Length: 1000000000", responseString);
    assertTrue(bytesSent > 1000000000);
}
```

当然，现在我们会通过使用带有适当解释性字符串的 `@Ignore` 属性来关闭测试用例：`@Ignore("Takes too long to run")`。
但在 JUnit 4 之前的时代，在方法名前加下划线是一种常见的约定。
这个注释虽然轻率，但很好地说明了这一点。

这里有另一个更发人深省的例子：

```java
public static SimpleDateFormat makeStandardHttpDateFormat()
{
    //SimpleDateFormat is not thread safe,
    //so we need to create each instance independently.
    SimpleDateFormat df = new SimpleDateFormat("EEE, dd MMM yyyy HH:mm:ss z");
    df.setTimeZone(TimeZone.getTimeZone("GMT"));
    return df;
}
```

你可能会抱怨有更好的方法来解决这个问题。
我可能同意你的观点。
但这里给出的注释是完全合理的。³ 
它将阻止一些过于热心的程序员以效率的名义使用静态初始化器。

³ 你不得不怀疑，在互联网的语言中，一个本质上是异步的环境中，这个函数怎么会被允许保持线程不安全长达几十年。

### 强调

注释可以用来强调某些可能看起来无关紧要的事情的重要性。

下面调用 `trim()` 就是一个很好的例子。`trim` 函数被如此频繁和轻率地调用，以至于很容易被忽略。
这个注释清楚地表明你不应该忽略这一个。

```java
String listItemContent = match.group(3).trim();
// the trim is real important. It removes the starting
// spaces that could cause the item to be recognized
// as another list.
new ListItemWidget(this, listItemContent, this.level + 1);
return buildList(text.substring(match.end()));
```

### 公共 API 中的 Javadoc（及其同类）

如今，大多数语言系统都有某种文档系统，可以从源文件中提取特殊的文档注释，并将它们排列成格式良好的文档。
在 Java 中，这些被称为 *Javadoc* 。

没有什么比描述良好的公共 API 更有帮助和令人满意的了。
标准 Java 库的 Javadoc 就是一个很好的例子。
如果没有它们，编写 Java 程序将变得困难重重。

如果你正在编写一个公共 API，那么你当然应该为它编写好的文档注释。
但要记住本章中的其他建议。
文档注释可能与其他任何类型的注释一样具有误导性、非本地性和不诚实性。
