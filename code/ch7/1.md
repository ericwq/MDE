## 小！

在过去的六十年里，我写过各种不同大小的函数。
在我早年的岁月里，我写过几个令人厌恶的 3000 行的怪物。
后来我写了大量 100 到 300 行范围的函数。
随着我逐渐成熟，我写了 20 到 30 行长的函数。
在过去的二十年里，我已经将其缩短到十二行或更少。
这几十年来通过长期的试错教会我的是：<ins>函数应该非常小</ins>。

当然，我不是第一个这么说的人。
保持函数小巧的想法由来已久。
在八十年代，常听到的说法是函数不应超过一屏大小。
当然，那是在 VT100 屏幕为 24 行 ×80 列的时代，我们的编辑器使用 4 行用于管理目的。
这实际上将限制设定在20行左右。

1999年，我去俄勒冈州的家中拜访 Kent Beck。
我们坐下来一起编了些程序，以便他能向我展示 TDD ¹ 的纪律。
我当时对 TDD 持怀疑态度，想亲眼目睹它。

¹ 在那些日子里，它被称为测试优先编程。

一次一个失败的测试，我们拼凑了一个可爱的小型 Java/Swing 程序，他称之为 Sparkle。
它在屏幕上产生的视觉效果与电影《灰姑娘》中仙女教母的魔法棒非常相似。
当你移动鼠标时，火花会从光标处滴落，发出令人满意的闪烁，通过模拟的重力场落到窗口底部。
当我们一起编写代码，一个接一个地使测试通过时，我被函数之小所震撼。
我习惯于 Swing 程序中占据大量垂直空间的函数。
这个程序中的每个函数只有两行、三行或四行长。
每个函数都有一个描述性的名称。
每个函数都透明地显而易见。
每个函数都在讲述一个故事。
每个函数都以引人入胜的顺序引导你进入下一个。
正是那次经历让我深刻认识到保持函数非常小的重要性。

### 写得好的散文

保持函数非常小意味着 `if` 语句、`else` 语句、`while` 语句等内部的块将只有一两行长。
通常那个块将包含对另一个函数的调用。
这不仅保持了封闭函数的小巧，而且增加了文档价值，因为在块中调用的函数将具有漂亮的描述性名称。
这样的 `if/else/while` 语句读起来很好，因为函数名与关键字流畅地结合在一起。它们会读起来像写得好的散文。

```java
if(employee.shouldBePaidToday())
    employee.pay();
```

这也意味着小函数将不会有足够的空间容纳深度嵌套的结构。
函数的缩进级别很少会超过一或两级。
这当然使函数更容易阅读和理解。

这不是一条硬性规则，也可能做得过头。
有些函数如果不分解成更小的四行函数，读起来会更好。
但这些都是例外情况。
总的来说，保持函数小巧是最好的策略。

### 每个函数一个抽象层次

为了确保我们的函数做 “一件事”，我们需要确保函数内的语句都处于相同的抽象层次。
看一下下面这段 Go 语言代码。²

² 这来自于视频商店（Video Store）示例，我们将在 [第 10 章](../ch10/0.md) “一件事” 中更深入地学习它。

```go
func (customer *Customer) statement() string {
    totalAmount := 0.0
    frequentRenterPoints := 0
    result := "Rental Record for " + customer.name + "\n"
    for _, rental := range customer.rentals {
        thisAmount := 0.0
        switch rental.movie.movieType {
        case NewRelease:
            thisAmount += float64(rental.daysRented * 3)
        case Regular:
            thisAmount += 2
            if rental.daysRented > 2 {
                thisAmount += float64(rental.daysRented-2) * 1.5
            }
        case Childrens:
            thisAmount += 1.5
            if rental.daysRented > 3 {
                thisAmount += float64(rental.daysRented-3) * 1.5
            }
        }
        frequentRenterPoints++
        if rental.movie.movieType == NewRelease && rental.daysRented > 1 {
            frequentRenterPoints++
        }
        result += fmt.Sprintf("\t%s\t%.1f\n", rental.movie.title, thisAmount)
        totalAmount += thisAmount
    }
    return result + fmt.Sprintf("Amount owed is %.1f\n"+
        "You earned %d frequent renter points",
        totalAmount, frequentRenterPoints)
}
```

很容易看出这违反了规则。
这里有处于非常高层抽象的概念，比如循环遍历 `customer.rentals`。
也有处于中间层抽象的概念，比如选择电影类型的 `switch` 语句。
还有一些非常低层的概念，比如 `frequentRenterPoints++` 以及计算每种电影类型价格的代码。

<ins>在函数中混合抽象层次通常会令人困惑。
读者可能无法判断某个特定表达式是一个核心概念还是一个细节。
更糟糕的是，就像破窗效应一样，一旦细节与核心概念混合在一起，越来越多的细节往往会在这个函数中累积</ins>。
