## 整洁函数：更深入的探讨

一个整洁的函数应该具备五个属性。
它应该是 *可命名的 (Nameable)* 、 *隔离的 (Insulated)* 、 *同质的 (Homogenous)* 、 *上下文相关的 (Contextual)*  和 *纯粹的 (Pure)* 。
如果你重新排列，它们会拼成  *PINCH* ——但这不是介绍它们的正确顺序。

### 上下文相关的 (Contextual)

模块化的概念和规范对最早的程序员来说并不是显而易见的。
它是从纯粹的必要性中慢慢生长出来的。
在 20 世纪 40 年代末，Grace Hopper 将常见的代码序列记在她的笔记本中，以帮助她为 Harvard Mark 1 编程。
她称这些序列为 *子程序 (subroutines)* 。
它们被誊写到程序中，然后费力地穿孔到驱动机器执行的长纸带上。

那些子程序是第一批模块。
从那里，模块化的概念发展成可调用的子程序，并最终成为函数。

到了 20 世纪 60 年代，程序员们开始采用一种称为 *模块化编程 (modular programming)* 的规范，该规范指出最好的程序被分解为许多不同的模块。
在 60 年代末，Dahl 和 Nygaard 通过发明面向对象编程 ⁸ 推进了模块化的概念。
在 70 年代初，David Parnas 通过推广信息隐藏的好处继续推进了这一进程。

⁸ 尽管他们没有给它起这个名字。“面向对象” 是由 Alan Kay 在几年后创造的。

如今，我们理解每个函数都存在于一个 *上下文 (context)*  之中。
一个上下文是函数和数据结构的合作分组。
每个上下文都有一个外部接口和一个内部实现。

在面向对象语言中，上下文最常用类来定义。
例如在 Java 中，类的 `public` 方法代表外部接口，而 `private` 数据和方法构成内部实现。

在 C 语言中，我们使用 `.h` 头文件作为外部接口，使用 `.c` 文件作为内部实现。

有些语言提供了丰富的语法来定义上下文。
在其他语言中，程序员必须通过非正式的约定（如文件名、目录和注释）来定义上下文。

但无论语言和语法如何，每个函数都存在于一个上下文之中 —— 而识别、创建和管理这些上下文是程序员的工作。

一个上下文中的一些函数将是 `public` 的，这意味着它们在该上下文之外是已知的并被使用。
它们是上下文外部接口的一部分。
上下文中的其他函数将是 `private` 的，这意味着它们只在上下文中被已知和使用，而不在外部使用。

许多面向对象语言提供了将函数声明为 `public` 或 `private` 的语法。
有些语言有其他类别，如 `protected` 或 `package`，作为创建部分限制的方式。
其他语言则依赖于程序员的纪律和各种程序员约定来达到同样的结果。

上下文在上下文外部已知的事物与上下文内部保持私有的事物之间创建了一个边界。
这个由程序员指定的边界，描述了程序员关于哪些事物是高层且可能不会经常变化的，以及哪些事物是低层且可能经历频繁变化的意图。

### 可命名的 (Nameable)

在命名函数时，至少有两件事需要考虑。
名称在其上下文中必须是适当描述性的，并且必须是适当方便的。

#### 描述性的

每个整洁的函数都应该有一个描述该函数做什么的名称。
由于名称描述行为，名称应该是一个动词、一个动词短语或一个隐含动词，如 `Math.sign(x)`。

<ins>描述应该比函数内的代码稍微抽象一些。换句话说，名称应该隐藏实现</ins>。

因此，作为一个荒谬的反例：

```java
public static double addAtoBandDivideBy2(double a, double b) {
    return (a+b)/2.0;
}
```

那个名称确实告诉了我们代码在做什么；但它太具体了。
它不仅告诉我们函数做什么，还告诉我们它如何做。
它暴露了实现。
我们应该稍微抽象一下。

```java
public static double average(double a, double b) {
    return (a+b)/2.0;
}
```

这很好。
名称是一个隐含动词（计算平均值），它隐藏了实现。
这很好，因为任何看到该名称的程序员都会知道期望什么；
但任何想要更改实现的程序员都不必更改名称。
例如，将函数扩展为使用可变数量的参数根本不会影响函数的名称。

```java
public static double average(double... ns) {
    return Arrays.stream(ns).sum()/ns.length;
}
```

一个单词的名称，如 `average`，可能适用于某些函数，但其他函数将需要更多单词才能适当地具有描述性。例如：

```java
public void addSalesReceipt(SalesReceipt salesReceipt) {
    salesReceipts.add(salesReceipt);
}
```

这个函数看起来足够简单，但名称有三个单词长。
为什么？
也许我们应该看看上下文。

```java
public class CommissionedEmployee extends Employee {
    private List<SalesReceipt> salesReceipts = new ArrayList<>();
    //…
    public void addSalesReceipt(SalesReceipt salesReceipt) {
        salesReceipts.add(salesReceipt);
    }
}
```

这个函数是派生类的一个方法。
派生类比它们的基类更详细。
因此，`addSalesReceipt` 函数存在于一个详细的上下文中。
详细的上下文需要更多的单词来描述。
因此，你应该期望，在更详细的上下文中，更长的名称将是必要的，以便适当地具有描述性。

很难高估好名称的价值。
记住 Ward Cunningham 的原则：“当你读到的每个例程都与你预期的差不多时，你就知道你正在处理整洁代码。”
实现该原则的一半工作是 *为做一件事的小函数选择好名称* 。

不要害怕把名称变长。
一个长的描述性名称比一个短的费解名称要好。
一个长的描述性名称通常比一个长的描述性注释要好。
使用像 `CamelCase`、`snake_case` 或 `kebab-case` 这样的命名约定。
这允许函数名称中的多个单词容易被阅读。
这些单词应该描述函数做什么。

不要害怕花时间选择名称。
事实上，你应该尝试几个不同的名称，并在每个名称到位的情况下阅读代码。
现代 IDE 使更改名称变得微不足道，所以尝试不同的名称，直到你找到一个尽可能具有描述性的名称。

选择描述性的名称将澄清你脑海中模块的设计，并帮助你改进它。
寻找一个好名称导致代码的有利重构，这并不少见。

#### 方便的

为了便于使用，函数的名称必须简短且易于记忆。
但简短且易于记忆的名称并不总是非常具有描述性。
因此需要做出权衡。
方便性的价值取决于函数被调用的频率。
一个被频繁调用的函数应该有一个简短且易于记忆的名称。
一个只被调用一次的函数可以承受一个更长且更具描述性的名称。

描述性和方便性这两个相互冲突的优先级共同构成了我们在 [第 4 章](../ch4/0.md) 中讨论的简单启发式方法：

> 函数名称的长度应与包含它的作用域的大小成反比。

作用域 (scope) 是一个名称被知晓和使用的代码跨度。
例如，`average` 函数的作用域实际上是全局的。
而 `addSalesReceipt` 的作用域则限制为 `CommissionedEmployee` 类的使用者。
因此，上下文越详细，作用域就越小。
上下文越通用，作用域就越大。

处于小作用域中的函数不需要太多的方便性。
因此它们的名称可以更长。
这很好，因为处于详细上下文中的函数通常需要更长的名称来保持描述性。
处于大作用域中的函数需要更多的方便性。
这很好，因为那些上下文通常更通用，因此通常不需要更长的名称。

例如，函数 `File.open(String filename)` 简短且易于记忆，因为它存在于全局作用域中并且非常通用。
如果这个函数被命名为 `openFileAndThrowExceptionIfNotFound`，我们会觉得不方便。
同样，如果 `addSalesReceipt` 函数被简称为 `add`，我们会感到有些不安。

因此，作用域越大，函数越通用，名称越短。
作用域越小，函数越详细，名称越长。

由此，我们可以预测全局函数通常会有简短的、一个单词的名称。
上下文中的公共函数会有稍长的名称。
被公共函数调用的私有函数会有更长的名称。
而被其他私有函数调用的私有函数可能会有很长的名称。
你在函数层级中下得越深，名称很可能就越长。
这对于 Java、C、Clojure、Python、Ruby 或任何其他允许长名称的语言都是如此。

### 隔离的 (Insulated)

在过去的日子里，我们称这种隔离的概念为 *低耦合 (low coupling)* ，有时也称为 *封装 (encapsulation)* 。
但在我看来，这两个术语都不太足够。

*复杂 (complex)* 这个词意味着多于一根线（strand）。
使函数复杂化的因素之一是它们必须处理的输入和输出的数量。
每一个输入和输出都是一种耦合，而每一种耦合都是另一根穿过该函数的线。
因此，为了管理函数的复杂性，我们寻求限制这种耦合的数量。

一个函数拥有的参数越多，它与调用者的耦合就越多。
一个拥有五个参数的函数可能比一个拥有两个参数的函数耦合度更高。
因此，我们努力将函数参数的数量限制在某个可管理的限度内。
在可行的情况下，我倾向于限制为三个。
我将在下一章中更多地讨论这一点。

参数越少，函数的耦合度就越低，调用该函数就越简单。
一个没有参数的函数很容易调用。
然而，这样的函数并不是特别有用，除非它们存在于一个已经由其他函数为它们准备好的上下文中。

例如，你可能有一个表示有限状态机的上下文
。该上下文将包含表示机器当前状态的变量，以及状态转换网络。

让我们使用以下状态机。
它表示一个简单的地铁旋转栅门。
有两个状态：`Locked`（锁定）和 `Unlocked`（解锁）。
有两个事件：`Coin` 和 `Pass`，分别代表用户向投币口投入硬币和通过闸门。
最后，有五个动作：`alarmOff`、`alarmOn`、`lock`、`unlock` 和 `thankyou`。
状态转换表如下所示：

| 状态 | 事件 | 新状态 | 动作 |
|------|------|--------|------|
| Locked | Coin | Unlocked | alarmOff, unlock |
| Locked | Pass | Locked | alarmOn |
| Unlocked | Coin | Unlocked | thankyou |
| Unlocked | Pass | Locked | lock |

逻辑非常简单：

- 当机器处于 `Locked` 状态并收到 `Coin` 事件时，它将转换到 `Unlocked` 状态并调用 `alarmOff` 和 `unlock` 动作。
- 当机器处于 `Locked` 状态并收到 `Pass` 事件时，它将保持在 `Locked` 状态并调用 `alarmOn` 动作。
- 当机器处于 `Unlocked` 状态并收到 `Coin` 事件时，它将保持在 `Unlocked` 状态并调用 `thankyou`⁹ 动作。
- 当机器处于 `Unlocked` 状态并收到 `Pass` 事件时，它将转换到 `Locked` 状态并调用 `lock` 动作。

⁹ 也许它会点亮一个小的 “谢谢” 灯，或者从扬声器发出 “谢谢” 的声音。

由此，很明显当系统运行时，外部软件将需要发送 `Coin` 和 `Pass` 事件。
这可以通过调用名为 `coin()` 和 `pass()` 的无参数函数来完成。
我们可以将其捕获在一个名为 `TurnstileEvents` 的接口中。

```java
public interface TurnstileEvents {
    void coin();
    void pass();
}
```

五个动作也都不带参数，可以捕获在一个名为 `TurnstileActions` 的接口中。

```java
public interface TurnstileActions {
    void lock();
    void thankyou();
    void alarmOn();
    void unlock();
    void alarmOff();
}
```

然后，状态机的逻辑可以捕获在一个名为 `TurnstileFSM` 的抽象类中。

```java
public abstract class TurnstileFSM implements TurnstileActions, TurnstileEvents {
    private enum State {Locked, Unlocked}
    private enum Event {Coin, Pass}
    private State state = State.Locked;

    private void setState(State s) {
        state = s;
    }

    public void coin() {
        handleEvent(Event.Coin);
    }

    public void pass() {
        handleEvent(Event.Pass);
    }

    private void handleEvent(Event event) {
        switch (state) {
            case Locked -> {
                switch (event) {
                    case Coin -> {
                        setState(State.Unlocked);
                        alarmOff();
                        unlock();
                    }
                    case Pass -> {
                        setState(State.Locked);
                        alarmOn();
                    }
                }
            }
            case Unlocked -> {
                switch (event) {
                    case Coin -> {
                        setState(State.Unlocked);
                        thankyou();
                    }
                    case Pass -> {
                        setState(State.Locked);
                        lock();
                    }
                }
            }
        }
    }
}
```

检测和发送事件的运行系统只需要知道 `TurnstileEvents`。
它与逻辑和动作完全解耦。
状态机的逻辑位于一个非常强的隔离屏障之后。
`TurnstileFSM` 外部的任何内容都不知道状态或逻辑。

最后，`TurnstileFSM` 类是抽象的，以允许动作函数在派生类中实现，从而将机器的逻辑与动作的实现解耦。

从这个例子中，你可以看到封装了状态机逻辑、事件和动作的上下文。
你可以看到限制跨越上下文边界的函数中的参数数量如何有助于保持非常低的耦合。

<ins>当然，很多时候你会需要带有一个、两个甚至三个或更多参数的函数。
但一旦你传递超过三个参数，你就必须问自己为什么不传递一个封装它们的对象或数据结构。
如果你确实需要将这么多参数传递给一个函数，那么值得考虑是否可以将数据分离到不同的上下文中，以及是否可以将函数的行为拆分到这些上下文中</ins>。

### 同质的 (Homogenous)

一个函数中的各行应该都处于相同的抽象层次，即比函数名低一个层次。
在上一节中，我称之为 *步降规则 (The Stepdown Rule)* 。

一个函数的操作发生在由该函数名描述的特定抽象层次上。
函数名代表了函数内部各行所实现的抽象。

但如果一个函数中的各行存在于多个抽象层次上呢？例如，考虑以下函数：

```java
public static int orientation(Point a, Point b, Point c) {
    double val = (b.x() - a.x()) * (c.y() - a.y()) -
                 (b.y() - a.y()) * (c.x() - a.x());
    if (val == 0) {
        return 0;
    }
    return (val > 0) ? +1 : -1;
}
```

给定平面上的三个点 (a, b, c)，此函数确定从 a 到 b 再到 c 的行走是向右转 (−1)、向左转 (1) 还是不转弯 (0)。

第一部分确定两个向量 a→b 和 b→c 的叉积。
该乘积的符号决定了答案。

叉积的计算适当地处于名称以下的一个抽象层次。
但其他四行比第一行更低层。所以让我们将那四行放入它们自己的函数中。

```java
public static int orientation(Point a, Point b, Point c) {
    double val = (b.x() - a.x()) * (c.y() - a.y()) -
                 (b.y() - a.y()) * (c.x() - a.x());
    return sign(val);
}

private static int sign(double n) {
    if (n == 0) {
        return 0;
    }
    return (n > 0) ? +1 : -1;
}
```

现在原始函数的两行都处于相同的抽象层次。
这使得 `orientation` 函数的实现变得同质。

但我们可以做得更好，因为这些名称并不是特别具有沟通性，而且返回值没有命名，容易出错。

```java
public enum Chirality {left, right, none};

public static Chirality getChirality(Point a, Point b, Point c) {
    return chirality(crossProduct(a, b, c));
}

private static double crossProduct(Point a, Point b, Point c) {
    double abx = b.x() - a.x();
    double aby = b.y() - a.y();
    double acx = c.x() - a.x();
    double acy = c.y() - a.y();
    return abx * acy - aby * acx;
}

private static Chirality chirality(double n) {
    if (n == 0) {
        return none;
    }
    return (n > 0) ? left : right;
}
```

你可能会介意这比原始版本长了一倍；但在我看来，它更具可读性 —— 尤其是对第一次看到它的人来说。
你可能还会介意这比原始版本多消耗一些 CPU 周期。
如果你有迫切的需求要节省 50 纳秒，那么当然可以削减那些周期。
只是要记住，在你之后还会有其他人要维护这段代码，他们的时间是有价值的 —— 可能远高于那 50 纳秒的成本。

### 纯粹的 (Pure)

一个纯函数的行为仅依赖于它的参数；它的执行不会导致任何其他函数的行为发生变化。
以下是纯函数的一些优点：

- 纯函数是参数到返回值的真正映射 —— 并且可以用这样的映射替换，以用内存换取执行速度。
- 纯函数不太容易 ¹⁰ 受到竞争条件和并发更新问题的影响，因为它们不改变底层系统的状态。

¹⁰ 它们并非完全免疫，因为任何有状态系统都可以用纯函数来模拟。参见 [Functional Design]。

- 纯函数很容易组合成功能网络。这是因为它们没有外部依赖关系，因此可以随时被任何其他函数调用。
- 纯函数很容易测试。这是因为测试设置不需要将底层系统强制进入任何特殊状态，并且测试不需要断言系统的底层状态已经改变。
- 纯函数很容易在多个处理器之间分布。由于纯函数的输出仅取决于其参数，因此函数在何处或哪个处理器中执行并不重要。

好的，它们很棒。
如何创建一个纯函数？
简单。不要改变任何变量的值；
或者用《亲爱的妈咪》中的著名台词来 paraphrase：“永远不要赋值语句！”
或者用另一种方式说：纯函数是不可变的。¹¹

¹¹ [Functional Design]，第 1 章。

但这样一条规则有多现实呢？这取决于你的观点。
例如：

```java
public static double sigma(double... ns) {
    var mu = mean(ns);
    var deviations =
        Arrays.stream(ns).map(x->(x-mu)*(x-mu)).boxed().mapToDouble(x->x);
    double variance = deviations.sum() / ns.length;
    return Math.sqrt(variance);
}
```

`sigma` 函数是纯的。
其中的赋值语句是初始化，而不是赋值。
它们不会改变任何已存在变量的状态。

但如果我们通过将初始化拆分为声明和赋值来将它们变成真正的赋值呢？

```java
public static double sigma(double... ns) {
    double mu;
    mu = mean(ns);
    DoubleStream deviations;
    deviations =
        Arrays.stream(ns).map(x->(x-mu)*(x-mu)).boxed().mapToDouble(x->x);
    double variance;
    variance = deviations.sum() / ns.length;
    return Math.sqrt(variance);
}
```

这个版本的 `sigma` 仍然是纯的，因为即使变量的值发生了变化，这些变化在函数外部也是不可见的。
我们可以将这一点推进到什么程度呢？
让我们使用一个更传统的 ¹² 实现：

¹² 在本章展示的所有 `sigma` 实现中，这是我最喜欢的。
没有古怪的语法；没有点、括号和箭头的奇怪串联；没有令人烦恼的转换函数。
只是漂亮、直接的代码。

```java
public static double sigma(double... ns) {
    double mu = mean(ns);
    double variance = 0;
    for (double n : ns) {
        var deviation = n - mu;
        variance += deviation * deviation;
    }
    variance /= ns.length;
    return Math.sqrt(variance);
}
```

这个版本的 `sigma` 到处都在修改变量，但它仍然是纯的，因为所有这些修改对于任何外部观察者来说都是隐藏的。
内部实现根本不是纯的，但对于外部观察者来说，纯度的假象被保留了。

我们甚至可以更进一步，创建一个可变对象，同时仍然保持 `sigma` 函数纯。

```java
public static double sigma(double... ns) {
    return new SigmaCalculator(ns).invoke();
}

private static class SigmaCalculator {
    private double[] ns;
    private double mu;
    private double variance = 0;
    private double deviation;

    public SigmaCalculator(double... ns) {
        this.ns = ns;
    }

    public double invoke() {
        mu = mean(ns);
        for (double n : ns) {
            deviation = n - mu;
            variance += deviation * deviation;
        }
        variance /= ns.length;
        return Math.sqrt(variance);
    }
}
```

现在我们有了实例变量和各种变量操作。然而，`sigma` 函数仍然是纯的。那些非纯操作在 `sigma` 函数外部都不可见。

<ins>底线是，纯度是一个函数的外部特征，而不是内部特征。
函数的内部实现有多不纯并不重要 —— 只要所有的不纯性对外部观察者（包括其他线程）都是隐藏的，该函数就是纯的</ins>。

顺便说一句，这就是所有函数式编程语言声称纯度的方式。
它们只是隐藏了底层实现的不纯性。

### 部分纯度

正如我们刚刚看到的，纯度是一个被观察到的质量，而不是内在质量。
因此，一个函数是否纯取决于观察的是什么。

考虑 C 库函数 `fopen(char* name, char* mode)`。
这个函数有留下已命名文件处于打开状态的副作用。
这意味着 `fopen` 不是纯的，因为有一些函数（如 `fgetc` 和 `fputc`）除非先调用 `fopen`，否则无法正常工作。
实际上，如果你连续两次使用相同的参数调用 `fopen`，而没有中间调用 `fclose`，第二次调用很可能会失败，因为文件已经打开。
所以 `fopen` 不是纯的，因为它有使系统处于改变状态的副作用。

然而，我们可以通过将 `fopen` 包裹在另一个隐藏副作用的函数中，使其至少对某些观察者看起来是纯的。

```c
void openAndDo(char* fileName, void (*doTo)(FILE*)) {
    FILE* f = fopen(fileName, "r+");
    doTo(f);
    fclose(f);
}
```

这个函数打开文件，执行 `doTo` 指向的函数，然后关闭文件。
这使得系统恢复到原始状态，隐藏了 `fopen` 的不纯性。
从各方面来看，`openAndDo` 的这种使用是纯的。
我们可以像下面这样使用它：

```c
void show(FILE* f) {
    int c;
    while ((c = fgetc(f)) != EOF)
        putchar(c);
}

int main(int ac, char** av) {
    openAndDo("x.x", show);
}
```

这个程序将 `"x.x"` 文件打印到标准输出。
让我们通过修改文件内容来使其更有趣一些。
如果文件末尾没有换行符，我们将添加一个。

```c
void appendLineEnd(FILE* f) {
    int c;
    int lastC;
    while ((c = fgetc(f)) != EOF) {
        lastC = c;
    }
    if (lastC != '\n')
        fputc('\n', f);
}

int main(int ac, char** av) {
    openAndDo("x.x", appendLineEnd);
    openAndDo("x.x", show);
}
```

现在程序添加行尾，然后显示文件。
这个程序确实使系统处于改变的状态，因为 `"x.x"` 文件的内容已被更改。
然而，如果我们不关心观察 `"x.x"` 文件的内容，那么 `openAndDo` 函数就我们而言是纯的。
