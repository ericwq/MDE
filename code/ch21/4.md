## 我们还在什么时候进行设计？

带着持续设计的心态，我们通过审查我们的代码对四个 C 的遵守情况来寻求保持低成本，这四个 C 是一组我们可以持续咨询的代码标准。
我们什么时候做这个？
当然是持续地，或者至少是不断地。

但我们不仅仅在编写生产代码时考虑设计。
它几乎是软件开发的每一个步骤的一部分。

### 前期设计

我们通过确定我们的产品将为其用户带来哪些新能力来启动一个项目。
这必然需要一定程度的对系统设计的理解 —— 例如，它完成了什么以及它的约束是什么。

作为回答我们的分析和设计努力的一部分，我们可能首先产生总结性的图表，捕获系统当前设计的显著元素。
然后，我们也会创建推测性的草图，描绘为了容纳所需的新行为，设计将需要看起来像什么。

利益相关者通常希望在这个规划过程中的这个点上知道项目何时完成。
估算是设计考量：我们不仅必须对我们开发一个新功能需要多少时间有感觉，而且我们必须知道当前设计在多大程度上抵抗新功能。
理想情况下，所需的额外努力量是 “零”，如果我们已经足够好地遵守了四个 C，这可能是真的。

估算本身可能会反馈到项目计划中。
决策者可能会因为意外的高估而决定削减他们的愿望清单。
考虑到对其期望范围的这些更改，我们重新考虑设计并提供更新的估算。

我们在这时的项目估算涵盖了可能需要数周或数月才能完成的大型倡议。
因此，估算是高层次的；我们在其中投入足够的时间以获得对倡议的大致感觉。
我们可能会使用相对大小 ——小、中、大、超大—— 来弄清楚我们能够保证在下个季度交付哪些。

当我们准备开发时，我们寻求将这些更大的挑战切片成更细的工作块，我们可以在更短的时间内（也许几小时或几天）开始并交付。
在这一点上，再次需要对系统设计的理解，以确保我们围绕工作切片的想法与系统的现实对齐。

### 准备工作

当我们准备编码一个功能时，产品人员（产品负责人、产品经理、业务分析师、用户体验设计师等）正在努力确保他们已经捕获了我们开始所需的所有实际细节。
当他们与我们会面描述新功能时，我们会提问，并且我们再次深入系统的设计。

有时，当产品人员揭示功能的细节时，我们会发现 “魔鬼”。
我们发现事情并不像我们之前推测的那样理想。
也有可能系统在此期间已经发生了足够的变化，使得事情变得更加困难。

有时，对我们问题的回答揭示了隐藏的复杂性。
“哦，我没想过那个提示音或小功能会是个大问题，”
他们可能会告诉我们。
从他们的角度来看，它可能不是；从我们的角度来看，它可能是非常难以融入现有设计的东西。

### 开始工作

我们首先将工作分解为更小的行为单元。
如果我们的工作是为 Czecher 应用程序添加对副词的支持，我们可能会将该工作分解为以下更小的切片：

- 支持将单个副词添加到单词列表。
- 批量加载副词的 CSV 文件。
- 添加包含副词的抽认卡示例。

这些切片可能仍然有点太大。
我们可能会将 “支持添加副词” 拆分为几个技术挑战：

- 创建并合并 LLM 提示文本以指定副词的格式。
- 为副词添加持久化支持。
- 重写卡片构建逻辑以提供涉及副词的示例。

这种分解必然涉及对设计的意识，并且可能引发关于当前和/或推测性设计必须如何改变的讨论。

### 执行工作

我们编写测试来驱动每个单元行为。
一个单元测试描述了该行为，并提供了一个 “活” 示例，演示客户端如何与系统交互以实现该行为。
因此，测试是我们设计和记录系统接口的主要机制。

对于我们编写的每个测试，我们编码我们希望实现测试中指定的需求的行为。
我们运行测试，修正代码（即设计），直到测试通过。
我们重新审视编码的行为，并在继续下一个测试之前，为了清晰性、简洁性和内聚性而编辑它。

当我们为所有行为编写了测试，并且所有测试都通过时，我们就交付了。

设计无处不在。
