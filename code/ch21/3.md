## 在持续设计的四个 C 上航行

一个不整洁的代码系统使得以下事情更难：
- 找到你正在寻找的代码。
- 理解你需要在何处进行更改。
- 在不创建缺陷的情况下进行更改。
- 编写测试来验证其行为。

你可能从 [第 13 章](../ch13/0.md) “整洁类” 中认出这些特征。

我们有许多设计视角来帮助我们走向一个整洁代码系统。
当我们更改系统时，我们继续反思一个或多个这些视角 —— SOLID、代码坏味、简单设计、设计模式以及其他，包括各种一次性的原则，如 *迪米特法则 (Law of Demeter)* 或 *Tell-Don’t-Ask* 。

对于持续设计的概念，我们将尝试 ——正如之前许多人尝试过的那样—— 将其全部归纳为一组简单的、希望是易记的规则。
可以将其视为 YADP：*又一个设计视角 (Yet Another Design Perspective)* 。

我们的四个 C 设计考量是：

- **清晰性 (Clarity)**：程序员在系统中的所有意图都被清晰地陈述了。
- **简洁性 (Conciseness)**：程序员在系统中的意图以最少的代码量实现。
- **可确认性 (Confirmability)**：系统中的所有单元行为都可以很容易地被测试，同时以提供所做行为选择的 “活文档” 的方式。
- **内聚性 (Cohesion)**：系统中的每个模块都具有高内聚性 —— 其所有元素都最大程度地相互关联。

这些考量并不是孤立存在的。
我们将逐一讨论它们，但当我们讨论时，想想它们如何既能相互支持又能相互对立。

### 清晰性

让代码工作总是我们的第一步。
我们被挑战向代码添加一个小的、新的行为片段。
我们花少量时间思考我们想要如何解决问题，然后迅速在我们的编辑器中输入一些代码。
我们稍作修改，直到最终设法让它工作，然后继续下一个所需的逻辑片段。

如果我们永远不必再阅读那段代码，我们可能会认为自己 “完成了”。
代码完整了！
它没有坏，所以我们不会去尝试修复已经工作的东西。
为什么要冒破坏东西的风险？

但当我们后来被要求更改逻辑的细微差别时，我们将会再次阅读那段代码！
或者当我们被问到 “那段代码在这种情况下做什么？” 时。
或者当我们被要求添加新的相关行为时。
或者半小时后当我们不得不回到那段代码，因为它还没有完全完成时。

对于这些需求中的每一个，我们都希望代码尽可能清晰地被陈述。
任何不清晰的东西都会浪费时间。

一个挑战：解读 `retrieveWords` 函数的所有细微差别。
它可能会花你半分钟到两分钟。

```javascript
export const retrieveWords = async words => {
    const wordPrefix = words.length === 1 ? 'word' : 'words'
    let wordList = "";
    for (let i = 0; i < words.length; i++) {
        const currentWord = words[i];
        const quotedWord = '"' + currentWord + '"';
        wordList += quotedWord;
        if (i !== words.length - 1) {
            wordList += ",";
        }
    }
    const finalPrompt = `Given a list of nouns separated by commas, ` +
        `provide appropriate Czech language information for the ` +
        `${wordPrefix} ${wordList}`
    const response = await sendPrompt(`${format} ${finalPrompt}`)
    const startIndex = response.indexOf('[')
    const endIndex = response.lastIndexOf(']') + 1
    const jsonText = response.slice(startIndex, endIndex)
    return JSON.parse(jsonText)
}
```

这不一定是不好的代码，但它可以很容易地变得更好。你花了比必要更多的时间来解读它，所以我们将它称为不整洁的代码。

对代码清晰性的持续关注告诉我们，要生成我们都能快速消费的代码。在下面的重构代码中，`retrieveWords` 作为最底层的函数出现。从那里开始阅读。

```javascript
const sliceJSONArrayFrom = response => {
    const startIndex = response.indexOf('[')
    const endIndex = response.lastIndexOf(']') + 1
    return response.slice(startIndex, endIndex)
}

const joinQuoted = words =>
    words.map(word => `"${word}"`).join(',')

const pluralizeIfMany = (word, list) =>
    list.length === 1 ? word : `${word}s`

export const retrieveWords = async words => {
    const finalPrompt = `Given a list of nouns separated by commas, ` +
        `provide appropriate Czech language information for the ` +
        `${(pluralizeIfMany('word', words))} ${(joinQuoted(words))}`
    const response = await sendPrompt(`${format} ${finalPrompt}`)
    return JSON.parse(sliceJSONArrayFrom(response))
}
```

如果我们被要求对 `retrieveWords` 进行更改，现在理解其整体意图和流程会更快。
该函数将 `finalPrompt` 初始化为一个长文本字符串，其中包含几个嵌入的概念：

- 根据 `words` 数组的大小，文本要么是 `"word"`，要么是 `"words"`。
- 该数组中引号单词的连接字符串。

这两个概念现在是对小的、隔离的函数的调用。

然后，我们将一个更长的提示字符串发送给 LLM，接收一个文本响应。
最后，我们从响应字符串中切分出 JSON 文本（之所以存在，是因为我们向 LLM 发送了所需格式作为提示的一部分），然后解析它。

我们可以在大约十五秒内理解这样一个函数；它很大程度上是一个策略陈述。
它使用名称捕获其意图的提取函数。
每个提取函数用一到三行代码实现。
如果我们不需要更改任何这些实现，那就是一到三行我们可以暂时甚至永远忽略的隐藏细节。

如果我们需要更改其中一个辅助函数，精简的策略声明允许我们快速找到它并专注于一小点实现细节。
我们可以进行更改，而无需考虑任何其他代码。

#### 编辑我们的代码

以高清晰度编写代码表明我们足够关心我们的队友（和我们自己），愿意花一些时间在继续之前编辑我们的代码。

作为开发人员，我们擅长让东西工作 —— 这是我们的首要工作。
我们也需要提醒自己，我们也是作者，其他人必须消费我们所写的内容。
一旦我们在纸上捕捉到我们的想法，好的写作要求我们重新审视我们的 “喷涌” 并编辑它以强调清晰性。

令人遗憾的事实是，我们通常没有被教导如何编辑我们的代码。
绝大多数代码都显示了这一点，并因此浪费了你大量的时间。
每分钟的 WTFs 很高。

事实上，我们经常被明确告知不要编辑代码。
“如果它没坏，就不要修理它。”
又是那个蹩脚的、被错误应用的咒语。

如果其他人不能快速理解你的代码，那它就是坏的。

如果你拿起一本写得不好的书，一本需要你重读句子和段落才能理解的书，你会认为它是一本糟糕的、有缺陷的书（我们打赌你在大学里至少有一本这样的书）。

这个咒语之所以存在，是因为我们害怕破坏东西。
是的，代码是一种易碎的材料。
在几乎任何编程语言中，犯一个愚蠢的编码错误是相当容易的，甚至可能发现不了它。
结果，我们倾向于避免清理东西，尽管这通常很容易。

害怕更改我们的代码是一种质量坏味。
有简单的路径可以创建控制机制，在我们每次微小更改时告诉我们是否破坏了已经工作的逻辑。
请访问 [第 14 章](../ch14/0.md) “测试纪律” 来了解如何做。

#### 通往清晰性的快速步骤

- 从多用途函数中提取实现细节，创建具有简洁名称的新函数。
- 适当地将函数移动到其他模块。这会导致内聚性增加，帮助读者在他们可能期望的地方找到代码。
- 用清晰的声明替换注释。
- 编写既作为文档又作为系统中所有行为意图的测试。

#### 对清晰性的异议

经验丰富的程序员能够立即理解简短的代码短语。
一个经验丰富的 JavaScript 开发者可以快速理解以下两个例子：

```javascript
words.map(word => `"${word}"`).join(',')
list.length === 1 ? word : `${word}s`
```

然而，这样的短语仍然需要仔细阅读。
我们必须在脑海中将涉及的标记组装成它们所代表的行为概念。
存在微小的误解可能性，也存在微小的缺陷可能性。
下面这行看似惯用的代码应该让我们停下来：

```javascript
for (let i = 0; i <= words.length; i++)
```

然而，对许多人来说，它并没有。那不是惯用写法；这才是：

```javascript
for (let i = 0; i < words.length; i++)
```

第一个 `for` 循环很可能是一个缺陷。

在任何情况下，将小的实现细节提取到揭示意图的函数中，可以简化 `retrieveWords` 中的代码：

```javascript
const joinQuoted = words =>
    words.map(word => `"${word}"`).join(',')

const pluralizeIfMany = (word, list) =>
    list.length === 1 ? word : `${word}s`

export const retrieveWords = async words => {
    const finalPrompt =
        `Given a list of English nouns, separated by commas, ` +
        `provide appropriate Czech language information for the ` +
        `${(pluralizeIfMany('word', words))} ${(joinQuoted(words))}`
    // ...
}
```

#### 声明意图，而不是渗出细节

我们使用函数管道部分是因为它们允许我们用声明替换细节：

```javascript
words.map(word => `"${word}"`).join(',')
```

这比老式的过程式等价物容易理解得多：

```javascript
let wordList = "";
for (let i = 0; i < words.length; i++) {
    const currentWord = words[i];
    const quotedWord = '"' + currentWord + '"';
    wordList += quotedWord;
    if (i !== words.length - 1) {
        wordList += ",";
    }
}
```

老式代码也极大地增加了隐藏缺陷的可能性（回想一下 `for` 循环的例子）。

#### 保持管道精简

虽然在管道中编写短小的内联函数是合理的：

```javascript
export const mostExpensiveHighlyRatedBookInEachCategory = (categories) =>
    categories.flatMap(category =>
        category.books
            .filter(book => !!book.title)
            .filter(book => book.rating > 4.0)
            .sort((a, b) => b.price - a.price)
            .map((book) =>
                ({ category: book.category, title: book.title }))
            .slice(0, 1))
```

但它们打破了流程，需要仔细的逐步阅读。

将所有内联 lambda（即使是那些非常短的函数）替换为命名函数，对于我们快速理解整个流程的能力有奇效：

```javascript
export const mostExpensiveHighlyRatedBookInEachCategory = (categories) => {
    const byPrice = (a, b) => b.price - a.price
    const highlyRated = book => book.rating > 4.0
    const hasTitle = book => !!book.title
    const categoryAndTitle = (book) =>
        ({ category: book.category, title: book.title })

    return categories.flatMap(category =>
        category.books
            .filter(hasTitle)
            .filter(highlyRated)
            .sort(byPrice)
            .map(categoryAndTitle)
            .slice(0, 1))
}
```

当阅读更大的函数时，我们扫描过单行函数声明，并专注于 `return` 语句。
我们现在能够更快地阅读并在脑海中组装正在发生的事情，因为管道被抽象了，而不是充满了细节。

嗯。更新后的解决方案包含一个惯用表达式：`.slice(0, 1)`。
它返回数组的第一个元素（较不惯用），或者如果数组为空则返回一个空数组（是的，惯用）。
我们不会消除我们的惯用法，除非它们导致读者停顿。
如果是这样，我们会找到一种方法将它们抽象化。
（在这里，我们可能会创建一个 `firstOrDefault` 函数来替代 `slice` 调用。）

注意，当我们提取函数时，我们发现内聚性不足，表现为错位的逻辑片段。
这是典型的。
从这个示例的管道中提取的几个函数可能会在 `book` 模块中找到更合适的家。

### 简洁性

函数管道可以提供不仅非常清晰而且简洁的代码。
需要最少可能标记的解决方案是最大程度简洁的 —— 但这几乎从来不是我们真正想要的。

不考虑清晰性的最大程度简洁的代码是模糊的。
我们可能故意模糊代码的唯一合法时机是作为开发后部署过程的一部分（也许是为了压缩或安全利益），或者作为挑战/娱乐（参见 https://www.ioccc.org ）。

对清晰性的绝对需求意味着我们必须在简洁性和清晰性之间找到平衡。
不过，找到平衡并不困难 —— 只需问你的队友。
他们在某件事没有意义的那一刻就会让你知道。
观察他们阅读你的代码，当他们在你的超优化逻辑中挣扎时，通常会很明显的。

让我们从一个相反的例子开始 —— 代码清晰但不简洁。
下面的 `generateCard` 函数，连同几个辅助函数，组装了一个基于文本的抽认卡（好奇的是，上面还有答案！）。

```javascript
// generate integer from 0 to n-1
export const randomInt = n => {
    const randomValue = Math.random(); // Generate a random decimal
    const scaledValue = randomValue * n; // scale to desired range
    const flooredValue = Math.floor(scaledValue); // floor to int
    return flooredValue;
}

// return a word in its plural form if needed
const pluralizeIf = (word, isPlural) => {
    if (isPlural) {
        return `${word}s`; // Append 's' to make the word plural
    } else {
        return word; // Return the original word if not plural
    }
}

// generates prompt text for a language card game
const generateCard = (adjectives, nouns) => {
    // Select a random adjective and noun from the provided lists
    const randomAdjectiveIndex = randomInt(adjectives.length);
    const randomNounIndex = randomInt(nouns.length);
    const adjective = adjectives[randomAdjectiveIndex];
    const noun = nouns[randomNounIndex];

    // Determine the case and number randomly
    const nominativeOrAccusative =
        randomInt(2) === 0 ? 'nominative' : 'accusative';
    const isPlural = randomInt(2) === 0;
    const singularOrPlural = isPlural ? 'plural' : 'singular';

    // Get correct forms of the noun & adjective based on case/number
    const correctNoun = noun[singularOrPlural][nominativeOrAccusative];
    const nounGender = noun.gender.toLowerCase();
    const correctAdjective =
        adjective[nominativeOrAccusative][singularOrPlural][nounGender];

    // Construct the prompt text for the game card
    const promptText = `Adjective: ${adjective.word}
Noun: ${noun.word}
Determine the ${singularOrPlural} ${nominativeOrAccusative} case.
Correct answer: ${correctAdjective} ${correctNoun}`;

    // Return the constructed prompt
    return promptText;
}
```

这段代码看起来对我们来说很典型，这不是一件好事。
核心函数 `generateCard` 是一个从上到下的流程。
它并不特别长，但它包含注释来引导读者理解接下来几个语句中发生了什么。
该函数的每个语句都使用了清晰的变量名，并且易于理解。
我们可以逐语句仔细阅读代码，在脑海中将语句组组装成单元行为。
有什么不喜欢的呢？

确实，上面的例子是许多开发人员在职业生涯的大部分时间里快乐地继续编码的方式。但由于多种原因，它是次优的。

一个重新设计的版本会引入额外的小型辅助函数。

（再次，从底部的 `generateCard` 开始阅读。）

```javascript
export const randomInt = n => Math.floor(Math.random() * n)

const pluralizeIf = (word, isPlural) => isPlural ? `${word}s` : word

const randomElement = (array) => array[randomInt(array.length)]

const cases = ["nominative", "accusative"]
const numbers = ["singular", "plural"]

const generateRandomCardData = (adjectives, nouns) => ({
    adjective: randomElement(adjectives),
    noun: randomElement(nouns),
    grammaticalCase: randomElement(cases),
    number: randomElement(numbers)
})

const formatCard =
    (adjective, noun, number, grammaticalCase,
     correctAdjective, correctNoun) =>
        `${adjective.word} ${pluralizeIf(noun.word, number === 'plural')}
Provide the ${number} ${grammaticalCase} case.
Correct answer: ${correctAdjective} ${correctNoun}`

const generateCard = (adjectives, nouns) => {
    const { adjective, noun, grammaticalCase, number } =
        generateRandomCardData(adjectives, nouns)
    const correctNoun = noun[number][grammaticalCase]
    const correctAdjective = adjective[grammaticalCase]
                                       [number]
                                       [noun.gender.toLowerCase()]
    return formatCard(adjective, noun, number, grammaticalCase,
                      correctAdjective, correctNoun)
}
```

清晰性以几种方式得到了提高。
将 `generateCard` 提炼为三个顶级块，使读者能够快速识别整体策略。

- 使用传入的形容词和名词生成随机的抽认卡元素。
- 通过解引用传入的名词和形容词结构，确定抽认卡上挑战的正确答案。
- 返回包含所有相关信息的格式化卡片。

我们可以立即理解并信任这个解决方案中的每个支持函数或数据片段。
我们甚至可能不需要查看任何支持的代码或数据。

单独的函数通过允许我们专注于小的、可理解的块来增强清晰性。
虽然查看所涉及的数据结构（特别是单个名词和形容词对象）会有所帮助，但除此之外，每个语句都独立存在。
没有语句需要注释。
注释只会增加这段代码的开发、理解和维护成本。

至于理解数据结构，那是单元测试的用途。
尽管如此，我们可能有理由提取几个函数，以便从 `generateCard` 中的实现细节中获得再多一点隔离：

```javascript
const generateCard = (adjectives, nouns) => {
    const { adjective, noun, grammaticalCase, number } =
        generateRandomCardData(adjectives, nouns)
    const correctNoun = selectNoun(noun, number, grammaticalCase)
    const correctAdjective =
        selectAdjective(adjective, grammaticalCase, number, noun)
    return formatCard(
        adjective,
        noun,
        number,
        grammaticalCase,
        correctAdjective,
        correctNoun)
}
```

我们也发现了通过引入一个新的抽象 ——一个捕获随机卡片底层数据元素的对象的概念—— 来将看似不同的元素内聚在一起的机会。
然而，我们的函数仍然有一些问题。
返回和传递的过多参数不仅使解决方案变得混乱，而且降低了其简洁性。

让我们做最后一次清理。

```javascript
const generateRandom = (adjectives, nouns) => ({
    adjective: randomElement(adjectives),
    noun: randomElement(nouns),
})

const formatCard =
    (phrase, caseAgreement, correctAdjective, correctNoun) =>
        `${phrase.adjective.word} ${pluralizeIf(
            phrase.noun.word,
            caseAgreement.number === 'plural')}
Provide the ${caseAgreement.number} ` +
        `${caseAgreement.grammaticalCase} case.
Correct answer: ${correctAdjective} ${correctNoun}`

const selectNoun = (noun, caseAgreement) =>
    noun[caseAgreement.number][caseAgreement.grammaticalCase]

const selectAdjective = (adjective, gender, caseAgreement) =>
    adjective[caseAgreement.grammaticalCase]
        [caseAgreement.number]
        [gender.toLowerCase()]

const cases = ["nominative", "accusative"]
const numbers = ["singular", "plural"]

const generateCaseAgreementChallenge = () => ({
    grammaticalCase: randomElement(cases),
    number: randomElement(numbers)
})

const generateCard = (adjectives, nouns) => {
    const phrase = generateRandom(adjectives, nouns)
    const caseAgreement = generateCaseAgreementChallenge()
    const correctAdjective = selectAdjective(
        phrase.adjective, phrase.noun.gender, caseAgreement)
    const correctNoun = selectNoun(phrase.noun, caseAgreement)
    return formatCard(
        phrase, caseAgreement, correctAdjective, correctNoun)
}
```

稍微更深思熟虑的数据分组使得 `generateCard` 看起来不那么像一个随意杂乱的本地变量集合。
它的每一步都强调了所涉及的关键元素。
我们还重新设计了 `selectAdjective`，以接受 `gender` 参数而不是 `noun`。
我们的选择强调了名词的性别（具体来说）是确定正确形容词的关键。

#### 代码重复

代码简洁意味着每个概念只实现一次。
我们经常发现小的实现细节块在一个模块或代码库中被复制 —— 通常是从几行到几行反复出现的重复代码。
这里是一个常见的例子 —— 重复的错误处理：

```javascript
export const postItem = (request, response) => {
    const itemDetails = retrieveItem(request.body.upc)
    if (!itemDetails) {
        response.status = 400
        const errorMessage = 'unrecognized UPC code';
        logError(errorMessage)
        return response.send({error: errorMessage})
    }
    const checkout = Checkouts.retrieve(request.params.id)
    if (!checkout) {
        response.status = 400
        const errorMessage = 'nonexistent checkout';
        logError(errorMessage)
        return response.send({error: errorMessage})
    }
    const newCheckoutItem = Checkouts.addItem(checkout, itemDetails)
    sendResponse(response, newCheckoutItem, 201)
}
```

重复会增加成本，原因有很多。
控制器函数 `postItem` 的本质被重复的错误处理代码所掩盖。
这种重复也通过将实现细节混合到策略流程中而降低了清晰性。

```javascript
const sendRequestError = (response, message) => {
    response.status = 400
    logError(errorMessage)
    response.send({error: message})
}

export const postItem = (request, response) => {
    const itemDetails = retrieveItem(request.body.upc)
    if (!itemDetails)
        return sendRequestError(response, 'unrecognized UPC code')

    const checkout = Checkouts.retrieve(request.params.id)
    if (!checkout)
        return sendRequestError(response, 'nonexistent checkout')

    const newCheckoutItem = Checkouts.addItem(checkout, itemDetails)
    sendResponse(response, newCheckoutItem, 201)
}
```

通常，消除重复涉及用抽象替换具体细节。
这通常是一个四赢的局面（增加了简洁性、清晰性和可确认性，同时还为增加内聚性提供了跳板），但我们不会因为恰好看起来相同的两行代码而过度纠结。
我们寻求找到并消除概念的重复实现，而不是偶然的常见代码行。

重复会增加许多成本/精力：

- 阅读和理解的时间成本
- 一般搜索代码的时间（我们总是要浏览越来越多的不相关结果）
- 测试的时间
- 为重复概念找到所有变更点的精力
- 找不到所有必要变更点的风险
- 分析重复代码中的差异是故意的还是代表缺陷的时间
- 更改重复代码的精力
- 重构代码的成本
- 当公共代码有缺陷时，缺陷传播的成本

我们曾在许多系统上工作过，这些系统由于猖獗的代码重复而比它们本应有的规模大两到三倍。
哦，按代码行数付费的日子！（开个玩笑。这对我们任何人都没发生过。）

一个例子包括一个手术室调度系统，根据定义，它需要做很多与日期和时间戳相关的工作。
除了其他许多有趣的事情之外，我们发现了一个常见的五行的（老式）Java 日期处理逻辑。
这五行代码在整个代码库中被重复了五十多处。
当我们试图用现代库替换老式逻辑时，我们的成本急剧增加。

提取并移动再次成为我们处理重复问题的值得信赖的主力工具。

- 识别代表一个单一概念的一团实现细节。
- 将其提取到一个函数。
- 孤立地专注于新函数。如果合适，将其移动到另一个模块。
- 随着对新模块存在的认识增加，我们开始发现更多机会将其他相关行为移入其中。因此，我们模块的内聚性增加了。

#### 简洁性细节

每一个不必要的标记都会增加我们代码的杂乱。
我们可以而且应该经常使用诸如惯用结构和语法糖之类的东西来减少我们必须扫描和在脑海中组装的不必要代码。
我们的一些小细节：

#### 返回布尔表达式

学好一门语言意味着我们不仅要学习它的语法，还要学习表示常见概念的最简洁方式。
其中一些精简的结构甚至可能被归类为惯用法。
（是的，我们已经多次使用这个词；我想我们最终应该定义它：惯用代码在你第一次看到它时并不明显。）

三元运算符是惯用的：在一个孤立的上下文中，它本身并不提供你立即解读它所需的所有信息。
然而，当你第二次或第三次看到它时，你就会知道如何解释它 —— 它对你来说变得显而易见了。
这就像骑自行车一样；在那之后你很可能不需要再被提醒。

有时我们会看到反惯用法：

```javascript
const hasTitle = book => {
    if (book.title !== null) {
        return true
    } else {
        return false
    }
}
```

反惯用法？
尽管这个结构占用了五宝贵的垂直源代码行，但当我们看到它时，我们通常将其消化为一个单独的块（因为不幸的是，我们经常看到它）。
有时我们甚至注意到一个傻瓜偷偷地颠倒了 `true` 和 `false` 返回的顺序。

我们很少说在编程中事情是完全错误的，但这是其中之一。

简单地（我们不是轻易使用这个词）返回布尔表达式：

```javascript
const hasTitle = book => book.title !== null
```

#### 不必要的 else

也许我们不需要拥抱三元运算符 ——比 if-else 语句更糟糕的东西污染了我们的编码世界—— 但如果我们打算编写一个条件返回：

```javascript
const pluralizeIf = (word, isPlural) => {
    if (isPlural) {
        return `${word}s`
    } else {
        return word
    }
}
```

我们至少应该有点礼貌，不要包含不必要的 `else` 关键字。
早期返回就足够了：

```javascript
const pluralizeIf = (word, isPlural) => {
    if (isPlural) {
        return `${word}s`;
    }
    return word
}
```

不，我们真的不需要花括号，尽管我们的团队很可能采用了坚持使用它们的编码标准。
但这实际上只是过度保护的杂乱。
如果你从一个短的、单行的 `if` 语句开始，很难搞砸：

```javascript
const pluralizeIf = (word, isPlural) => {
    if (isPlural) return `${word}s`
    return word
}
```

如果我们仍然担心，我们会编写测试。
在任何情况下，对于这个例子，确实没有很好的理由避开三元运算符：

```javascript
const pluralizeIf = (word, isPlural) => isPlural ? `${word}s` : word
```

不过，如果你出于美学原因反对，我们理解。

#### 等等

我们可以用一整本书来写代码中的杂乱。
然而，大部分你会自己弄明白。
我们不寻求聪明的代码；我们寻求 *优雅的代码* 。
优雅的代码准确地表达它需要表达的内容，没有太少或太多的词。
它既清晰又简洁。

### 可确认性

我们的持续设计之旅要求我们知道我们的代码意图做什么。
没有那个知识，任何更改都是不安全的。
一个系统可能包含成千上万的行为单元。
对其中任何一个行为的未注意到的更改都可能让我们在生产中释放一个代价高昂的缺陷。

幸运的是，我们可以编写成千上万个小的、快速的单元测试来验证我们是否创建了任何回归。
这些测试可以在几秒钟内告诉我们是否破坏了某些东西。
当然，我们还需要其他类型的更高级别的测试，例如端到端功能测试、性能测试、负载测试和契约测试。
但如果我们想快速前进，我们需要能够快速创建和管理围绕单元实现的测试。

#### 恐惧降低设计

相反，缺乏这样的测试会逐渐减慢我们的速度。
随着（未经单元测试的）代码量的增加，我们验证它的成本也会增加。
我们只能手动逐步完成这么多测试用例。

我们可以编写集成测试，但它们通常构建和维护成本更高。
它们也会创建更慢的反馈循环。
最后，期望通过集成测试来覆盖进入代码库的所有数千个有意决策和逻辑变体是不现实的（集成测试在失败时也可能增加定位缺陷的难度）。

如果没有单元测试形式的快速反馈，我们就会陷入那种 “没坏就不修” 的心态。
我们的代码库根据定义就会退化。
我们没有信心确保代码保持内聚、清晰和简洁。
相反，我们习惯性地拍出 “初稿”：我们让代码工作，然后立即继续下一件事，而不做任何编辑。

一开始看起来很快，然而恐惧驱动的编码的结果很快就会在代码库中显现出来。
开发人员学会了对一个系统做最糟糕的事情，而不是他们知道的对系统最好的事情。

一个来自一个高性能、历史上著名的大型系统的真实例子：

开发人员需要创建现有行为变体，这些行为存在于通常很长的（100+ 行）C++ 成员函数中。
发布这些现有行为的缺陷版本可能每分钟给公司造成数百万美元的损失。

结果，开发人员习惯性地复制（即复制/粘贴）整个成员函数，然后在这些副本中进行更改。
他们没有更改原始函数 —— 没有人想成为破坏已经工作代码的人。
（“你为什么要碰那段代码？”）

恐惧显著增加了代码重复和成本。

#### 合并的单元意味着困难的测试

如果我们编写像下面这样的 `postCheckoutTotal` 函数，为其编写测试将是令人生畏的：


捕捉所有细微差别并为所有相关情况编写测试可能需要几个小时。
而且，很有可能我们无法覆盖所有情况，这增加了我们发布缺陷的风险。

#### 小的、隔离的单元意味着简单的测试

在我们为组装结账收据的逻辑时，编写小的、简单的测试要容易得多。
毫无疑问，你可以在 `postCheckoutTotal` 中发现一些重复的片段，以及许多将概念单元提取到新函数的机会。

这是一个改进的解决方案，一项进行中的工作。

```javascript
const sendSuccessResponse = (response, body) => {
    response.status = 200
    response.send(body)
}

const sendErrorResponse = (response, message) => {
    response.status = 400
    response.send({ error: message })
}

export const postCheckoutTotal = (request, response) => {
    const checkoutId = request.params.id
    const checkout = Checkouts.retrieve(checkoutId)
    if (!checkout)
        return sendErrorResponse(response, 'nonexistent checkout')

    const { totals, messages } = createReceipt(checkout)

    sendSuccessResponse(response, {
        id: checkoutId,
        messages,
        total: round2(totals.total),
        totalOfDiscountedItems: round2(totals.totalOfDiscountedItems),
        totalSaved: round2(totals.totalSaved)
    })
}
```

`postCheckoutTotal` 函数现在是一个策略声明，可以用几个 “端到端” 测试来覆盖。

模块 `receipt.js` 暴露了可以直接且轻松进行单元测试的代码：

```javascript
import { pad } from '../../util/stringutil'
import { calculateTotal,
         calculateTotalOfDiscountedItems,
         calculateTotalSaved } from './checkout-model'

const LineWidth = 45
const Indent = ` `

export const round2 = amount => Math.round(amount * 100) / 100

const formatAmount = amount => parseFloat(round2(amount)).toFixed(2)

const shouldApplyDiscount = (checkout, item) =>
    !item.exempt && memberDiscountPct(checkout) > 0

const calculateDiscountAmount = (checkout, item) =>
    memberDiscountPct(checkout) * item.price

const memberDiscountPct =
    checkout => checkout.member ? checkout.discount : 0

const lineItem = (text, lineAmount) => {
    const amount = formatAmount(lineAmount)
    const amountWidth = amount.length
    const textWidth = LineWidth – amountWidth
    return pad(text, textWidth) + amount
}

export const createReceiptMessages = (checkout, totals) => {
    const messages = []
    checkout.items.forEach(item => {
        messages.push(lineItem(item.description, item.price))
        if (shouldApplyDiscount(checkout, item)) {
            messages.push(lineItem(
                `${Indent}${memberDiscountPct(checkout) * 100}% mbr disc`,
                -calculateDiscountAmount(checkout, item)))
        }
    })
    messages.push(lineItem('TOTAL', round2(totals.total)))
    if (totals.totalSaved > 0)
        messages.push(lineItem('*** You saved:', totals.totalSaved))
    return messages
}

export const createReceipt = checkout => {
    const totals = ({
        total: calculateTotal(checkout),
        totalSaved: calculateTotalSaved(checkout),
        totalOfDiscountedItems: calculateTotalOfDiscountedItems(checkout)
    })
    return {
        totals,
        messages: createReceiptMessages(checkout, totals)
    }
}
```

通过分离出 `receipt.js`，我们也增加了内聚性。
`postCheckoutTotal` 函数主要关注于编排对请求的响应的创建。
它将组装收据和总计的计算细节委托给 `receipt.js` 模块。

`receipt.js` 仍然包含一些可以再次移动、然后隔离测试的实用/辅助函数（特别是 `round2` 和 `formatAmount`）。

这是最终的内聚模块 `checkout-model.js`：

```javascript
export const calculateTotal = checkout => {
    let total = 0
    checkout.items.forEach(item => {
        if (!item.exempt && (checkout.member ? checkout.discount : 0) > 0)
            total += item.price * 1.0 –
                    (checkout.member ? checkout.discount : 0))
        Else
            total += item.price
    })
    return total
}

export const calculateTotalSaved = checkout => {
    let totalSaved = 0
    checkout.items.forEach(item => {
        if (!item.exempt && (checkout.member ? checkout.discount : 0) > 0)
            totalSaved +=
                (checkout.member ? checkout.discount : 0) * item.price
    })
    return totalSaved
}

export const calculateTotalOfDiscountedItems = checkout =>
    checkout.items
        .filter(item => !item.exempt &&
                       (checkout.member ? checkout.discount : 0) > 0)
        .reduce((total, item) => total + item.price *
            (1.0 - (checkout.member ? checkout.discount : 0)), 0)
```

现在它被隔离了，我们可以专注于提高这些 `calculate` 函数内部的清晰性和简洁性。
我们可以很快地创建测试。
创建这些针对 `calculateTotal` 的测试花了十分钟：

这些测试给了我们信心，可以无畏地将 `calculateTotal` 重构为一个更清晰的解决方案：

```javascript
const memberDiscountPct = checkout =>
    checkout.member ? checkout.discount : 0

const shouldApplyDiscount = (checkout, item) =>
    !item.exempt && memberDiscountPct(checkout) > 0

const calculateDiscountedPrice = (checkout, item) =>
    item.price * (1.0 - memberDiscountPct(checkout))

export const calculateTotal = checkout => {
    const totalDiscountable = checkout.items
        .filter(item => shouldApplyDiscount(checkout, item))
        .reduce((total, item) => total +
            calculateDiscountedPrice(checkout, item), 0);

    const totalNonDiscountable = checkout.items
        .filter(item => !shouldApplyDiscount(checkout, item))
        .reduce((total, item) => total + item.price, 0);

    return totalDiscountable + totalNonDiscountable;
}
```

看起来我们的重构增加了代码行数，至少对于 `calculateTotal` 来说是这样。
然而，在我们对其他计算函数做了类似的更改之后，模块的总行数减少了。

#### 我们应该何时确保可确认性？

许多开发人员更喜欢编写一大块代码，然后稍后回来满足他们认为的实现代码覆盖率要求的义务。
对代码覆盖率的强制要求 ——衡量被测试执行的代码百分比—— 变成了一个自我实现的预言：我们得到我们要求的东西。
如果一个开发团队被强制要求最低覆盖率为 75%，我们只会得到那么多，而不会更多。

75% 的覆盖率听起来不错，直到你将其反转：我们系统的四分之一没有足够的单元测试。
它们通常也是我们系统中更复杂的部分：它们更难测试，并且在满足一个我们并不真正相信的指标时，我们会以我们能想到的最快捷的方式去做。

我们这么多代码更难测试的原因是因为在我们编码时，测试它并不是一个首要关注点。
我们的主要兴趣只是让该死的东西工作。
结果，复杂的部分甚至不那么复杂的部分都更难测试。
我们的代码不容易确认。

事后编写测试更难，因为现有代码：

- 缺乏清晰性。它过于复杂，因为它没有被编辑过。更难弄清楚函数做什么这个基本问题。
- 缺乏内聚性。辨别所有实际的开发者意图变得越来越困难，因为它们不在一个地方，而且它们没有与其他意图解耦。
- 缺乏简洁性。它包含过多的代码，以及必须在多个上下文中重新测试的过多重复结构。
- 包含深层依赖链。因此，测试需要更多的努力来设置适当的数据/上下文。存在通常是私有依赖意味着我们必须重塑代码以允许测试注入依赖。

75% 或 80% 或任何代码指标的另一个问题：我们代码的剩余部分是一个 20%+ 的 “谁知道这东西做什么” 的大块。

好的测试不仅为我们提供了无惧编辑代码的能力，而且还记录了所有开发者的意图。

如果事后编写测试会产生这么多问题（或者，更积极地说，没有给我们足够的帮助），那么明显的答案是从测试开始。
对于我们必须添加的每一个新行为，我们编写一个捕获该行为的测试。
我们测试的名称总结了该行为（这有助于我们以后找到我们正在寻找的行为）。
我们测试的代码提供了一个示例，确定了我们如何实现该行为的设计。

我们的代码覆盖率变成了一个自我实现的预言：我们在所有需要并设计到系统中的行为上都达到了完整的覆盖率。
我们获得了高度的信心，可以持续地将其设计塑造为清晰、内聚和简洁的。
我们的系统是高度可确认的。

你可能想知道那个覆盖率指标强制要求应该是多少。
正确答案是：(a) 强制要求是一个坏主意，(b) 覆盖率数字从来都不是重要的。
重要的是开发人员被说服相信交付我们知道是工作的软件的价值。

### 内聚性

在不提及内聚性的情况下达到这最后一个 C 设计标准是不可行的。
我们的持续设计标准必然相互交织以相互支持，有时它们可能相互矛盾。
例如，提高清晰性可能需要降低简洁性。

但我们就在这里，内聚性值得它自己的专注讨论。

我们正在构建 Czecher，一个旨在帮助我们巩固捷克语具有挑战性方面的抽认卡应用程序。
作为第一步，我们创建了模块 `words.js`，以允许我们将新名词添加到我们的练习词汇集合中：

```javascript
import { retrieveWord } from '../prompts/languageClient'

const definitions = {}

export const clearWords = () =>
    Object.keys(definitions).forEach(key => delete definitions[key])

export const loadDefinition = (word, definition) =>
    definitions[word] = { ...definition, word }

export const addWord = async word => {
    if (definitions[word]) return
    const definition = await retrieveWord(word)
    definitions[word] = { ...definition, word }
}

export const definition = word => definitions[word]

export const allDefinitions = () =>
    Object.values(definitions)
```

`addWord` 函数接受一个英语单词作为参数（例如，“dog”）。
如果该单词的定义已经被加载，该函数不执行任何操作。
否则，`addWord` 调用 `retrieveWord` 来使用第三方资源（本例中为 OpenAI）查找信息。
结果定义被添加到本地存储中。
使用一个单词调用 `definition` 函数会返回详细信息。

一些测试可能会增加一点色彩：

```javascript
import { when } from 'jest-when'
import { addWord, clearWords, definition,
         allDefinitions, loadDefinition }
    from './words'
import { retrieveWord } from '../prompts/languageClient'

jest.mock('../prompts/languageClient')

describe('addWord', () => {
    const orangeDefinition = {
        word: 'orange',
        gender: 'MI',
        singular: { nominative: 'pomeranč', accusative: 'pomeranč' },
        plural: { nominative: 'pomeranče', accusative: 'pomeranče' }
    }
    const dogDefinition = {
        word: 'dog',
        gender: 'MA',
        singular: { nominative: 'pes', accusative: 'psa' },
        plural: { nominative: 'psi', accusative: 'psy' }
    }

    beforeEach(() => {
        clearWords()
        jest.resetAllMocks()
    })

    it('retrieves and saves definition on add', async () => {
        when(retrieveWord).calledWith('orange')
            .mockResolvedValueOnce(orangeDefinition)
        await addWord('orange')
        expect(definition('orange')).toEqual(orangeDefinition)
    })

    it('does nothing if already added', async () => {
        loadDefinition('orange', orangeDefinition)
        const word = definition('orange')
        expect(word).toEqual(orangeDefinition)
        expect(retrieveWord).not.toHaveBeenCalled()
    })

    const add = async (word, definition) => {
        when(retrieveWord).calledWith(word)
            .mockResolvedValueOnce(definition)
        await addWord(word)
    }

    it('persists multiple words', async () => {
        await add('orange', orangeDefinition)
        await add('dog', dogDefinition)
        const definitions = allDefinitions()
        expect(definitions).toEqual([orangeDefinition, dogDefinition])
    })
})
```

`words` 模块是我们迈向 MVP ³ 的第一个增量步骤。
作为一个快速衡量，我们选择将单词持久化在一个内存中的 JavaScript 对象 (`{}`) 中，其中键是单词，值提供我们需要的语言细节。
常量 `orangeDefinition` 提供了一个示例。

³ 最小可行产品。

这是我们持续设计成绩单：

- 清晰性：通过。 所有操作都以简短、符合 JavaScript 惯用法的函数出现，没有任何“为聪明而聪明”的代码（这会让我们立即不及格）。
- 可确认性：通过。 所有代码都是由行为测试驱动产生的。
- 简洁性：通过。 代码似乎尽可能短了。
- 内聚性：不及格。 等等，不及格？

我们的意图是用一个适当的持久化机制替换 JavaScript 对象。
不幸的是，我们将我们那点定义管理逻辑与支持定义存储的逻辑混在一起了。
当我们进行更改时，我们将不得不打开 `words` 模块并修改其大部分方法以更新实现。

你很可能认识到我们在描述一个 *单一职责原则 (SRP)* 的违反。
SRP 和内聚性说的是同一件事，除了一些细微差别。
内聚性是指模块的元素与同一目的对齐的程度。

如果我们坚持一个内聚的解决方案，我们可能一开始就会发现构建解决方案更容易一些。
我们也会准备好立即容纳更改，而不是必须预重构我们的代码以支持更改。

我们现在将重构代码，以演示一个内聚的解决方案如何增加代码的清晰性。

```javascript
import { retrieveWord } from '../prompts/languageClient'
import * as Data from '../persistence/database'

export const clearWords = () =>
    Data.deleteAll()

export const loadDefinition = (word, definition) =>
    Data.add(word, definition)

export const addWord = async word => {
    if (Data.containsKey(word)) return
    const definition = await retrieveWord(word)
    Data.add(word, { word, ...definition})
}

export const definition = word => Data.get(word)

export const allDefinitions = () => Data.allValues()
```

围绕 JavaScript 对象的实现细节已被抽象所取代：`add`、`get`、`allValues`、`containsKey` 和 `deleteAll`。
底层实现可以从对象改为列表，再到与第三方键/值存储或关系数据库的交互。
现在内聚的 `words` 模块将不受这些更改的影响。

模块 `database.js` 提供了一个抽象持久化数据概念的接口，没有暴露任何泄露底层数据结构的内容。
对其实现的未来更改不会影响系统中的其他代码。

```javascript
const data = {}

export const containsKey = key => data[key]

export const deleteAll = () =>
    Object.keys(data).forEach(key => delete data[key])

export const add = (key, value) =>
    data[key] = value

export const get = word => data[word]

export const allValues = () => Object.values(data)
```
