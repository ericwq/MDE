## 持续集成

到 2000 年，即使在我们使用像 Subversion 这样的工具时，我们已经开始教授每隔几分钟提交一次的纪律。

理由很简单。
你提交得越频繁，你面临合并的可能性就越小。
如果你确实必须合并，合并将是微不足道的。

我们称这种纪律为 *持续集成* 。

当然，这关键取决于有一个非常可靠的单元测试套件。
我的意思是，没有好的单元测试，很容易犯合并错误并破坏别人的代码。
所以持续集成与良好的测试纪律携手并进。

现在，有了像 git 这样的工具，我们几乎可以无限缩小周期。

这就引出了一个问题：为什么我们如此关心缩小周期？

因为长周期阻碍了团队的进度。

提交之间的时间越长，团队中的其他人 ——也许是整个团队—— 必须等待你的可能性就越大。
这违反了承诺。

也许你认为这只是关于生产发布。
不，它实际上是关于每一个其他周期。
它是关于迭代和冲刺。
它是关于编辑/编译/测试周期。
它是关于提交之间的时间。
它是关于一切。

记住理由：“这样你就不会阻碍他人的进度。”
