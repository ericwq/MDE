## 源代码控制的历史

以下是源代码控制历史的一个回顾。

### 穿孔卡片

让我们回到 20 世纪 60 年代一会儿。
当你的源代码被打孔在一副卡片上时，你的源代码控制系统是什么？

<img src="../imgs/fig-ch31-0.png" width="80%"/><br/>

源代码不是存储在磁盘上。
它不是 “在计算机里”。
你的源代码，字面意义上，在你手里。

源代码控制系统是什么？
是你的抽屉。

当你字面意义上拥有源代码时，不需要 “控制” 它。
没有其他人可以碰它。

这就是 50 年代和 60 年代大部分时间的情况。
没有人甚至梦想过像源代码控制系统这样的东西。
你只是通过把源代码放在抽屉或柜子里来控制它。

如果有人想 “签出” 源代码，他们只需去柜子里拿走。
当他们完成后，他们把它放回去。

我们当然没有合并问题。
两个程序员同时修改相同的模块在物理上是不可能的。

但事情在 70 年代开始改变。
将源代码存储在磁带甚至磁盘上的想法变得有吸引力。

我们编写了行编辑程序，允许我们在磁带上的源文件中添加、替换和删除行。

这些不是屏幕编辑器。
我们在卡片上打出添加、更改和删除指令。
编辑器会读取源磁带，应用编辑卡组的更改，并写入新的源磁带。

你可能认为这听起来很糟糕。
回顾过去，确实如此。
但它比试图管理卡片上的程序要好！
我的意思是，6000 行代码在卡片上重 30 磅。
如果你掉了它……

如果你掉了一盘磁带……你可以再把它捡起来。

无论如何，注意发生了什么。
我们从一个源磁带开始，在编辑过程中，我们最终得到第二个新的源磁带。
但旧磁带仍然存在。
如果你把旧磁带放回架子上，其他人可能会不经意地将他们自己的更改应用到它上面，给你留下一个合并问题。

为了防止这种情况，我们只需在完成编辑和测试之前将主源磁带保留在我们手中。
然后，我们将新的主源磁带放回架子上。
我们通过保留磁带来控制源代码。

但现在这必须通过流程和约定来完成。
必须使用真正的源代码控制流程。
还没有软件，只有人为规则。
但是，源代码控制的概念已经与源代码本身分离了。

随着系统变得越来越大，它们需要越来越多的程序员同时处理相同的代码。
抓住主磁带并持有它对其他人来说变得非常麻烦。
我的意思是，你可以让主磁带停止流通几天或更长时间。

于是，我们决定从主磁带中提取模块。
当时模块化编程的整体概念还相当新。
一个程序可以由许多不同的源文件组成的概念是革命性的。

所以我们开始使用公告板，像这样：

<img src="../imgs/fig-ch31-1.png" width="80%"/><br/>

公告板上贴有系统每个模块的标签。
每个程序员都有自己的彩色图钉。
我是蓝色。
Ken 是红色。
我的伙伴 CK 是黄色，依此类推。

如果我想编辑 “Trunk Manager” 模块，我会查看公告板，看看那个模块上是否有图钉。
如果没有，我放一个蓝色图钉进去。

然后，我从架子上取下主磁带，并将其复制到另一个磁带上。

我会编辑干线管理器模块，而且只编辑干线管理器模块，生成一个包含我的更改的新磁带。

我会编译、测试、清洗、重复，直到我的更改工作。

然后，我会从架子上取下主磁带，并通过复制当前主磁带，但用我的更改替换 `Trunk Manager` 模块来创建一个新的主磁带。

我会把新的主磁带放回架子上。

最后，我会从公告板上移除我的蓝色图钉。

这行得通；但它只行得通，因为我们彼此认识；
我们都在同一个办公室工作；
我们都知道彼此在做什么。
而且我们一直在交流。

我会在实验室里大喊：“Ken，我要更改 `Trunk Manager` 模块。
”他会说：“放个图钉进去。”
我会说：“我已经放了。”

图钉只是提醒。
我们都知道代码的状态以及谁在做什么。
这就是系统运作的原因。

事实上，它运作得很好。
知道彼此在做什么意味着我们可以互相帮助。
我们可以提出建议。
我们可以互相警告最近遇到的问题。
我们可以避免合并。

那时，合并并不有趣。

然后，在 80 年代，磁盘出现了。
磁盘变大了，而且它们变成了永久性的。

我说的大，是指几百兆字节。
我说的永久性，是指它们被永久安装 —— 始终在线。

另一件发生的事情是我们得到了像 PDP11 和 VAX 这样的机器。
我们得到了屏幕编辑器、真正的操作系统和多个终端。
不止一个人可以同时编辑。

图钉和公告板的时代不得不结束了。

首先，到那时，我们有 20 或 30 个程序员。
没有足够的图钉颜色。
其次，我们有成百上千个模块。
我们没有足够的公告板空间。

幸运的是，有解决方案。

1972年，Marc Rochkind 编写了第一个源代码控制程序。
它被称为 SCCS，他用 SNOBOL 编写了它。¹

¹ 一种来自 60 年代可爱的字符串处理语言，具有我们现代语言的许多模式匹配功能。

后来他用 C 重写了它，它成为 PDP11 上 Unix 发行版的一部分。

SCCS 一次只能处理一个文件，但它允许你锁定该文件，以便在你完成之前其他人不能编辑它。
它是一个救星。

1982年，RCS，即修订控制系统，由 Walter Tichy 创建。
它也是基于文件的，对项目一无所知，但它被认为是对 SCCS 的改进，并迅速成为当时标准的源代码控制系统。

然后，在 1986 年，CVS，即并发版本系统，出现了。
它将 RCS 扩展到处理整个项目，而不仅仅是单个文件。
它还引入了 *乐观锁定* 的概念。

在此之前，大多数源代码控制系统都像我的图钉一样工作。
如果你已经签出了模块，没有其他人可以编辑它。
这被称为 *悲观锁定 (pessimistic locking)* 。

CVS 使用乐观锁定。
两个程序员可以同时签出并更改同一个文件。
CVS 会尝试合并任何非冲突的更改，如果它不知道如何进行合并，它会提醒你。

在那之后，源代码控制系统爆炸式增长，甚至成为商业产品。
有数百个。
一些使用乐观锁定，另一些使用悲观锁定。
事实上，锁定策略在行业中成了一种宗教分歧。

然后，在 2000 年，Subversion 被创建。
它极大地改进了 CVS，并在推动行业一劳永逸地摆脱悲观锁定方面发挥了重要作用。
Subversion 也是第一个在 “云” 中使用的源代码控制系统。

有人记得 Source Forge 吗？

到这一点为止，所有源代码控制系统都基于我在公告板时代使用的主磁带思想。
源代码维护在一个单一的中心主存储库中。
源代码从那个主存储库签出，提交被合并回那个主存储库。

但所有这一切即将改变。

### 持续集成

那是 2005 年。
多吉字节磁盘在我们的笔记本电脑中。
网络速度很快，而且越来越快。
处理器时钟频率已达到 2.6GHz。

我们离我旧的公告板源代码控制系统非常非常远。
但我们仍然在使用主磁带概念。
我们仍然有一个中央存储库，每个人都必须从中签入和签出。
每次提交；每次还原；每次合并都需要与主服务器进行网络连接。

……然后 git 来了。

嗯，实际上，git 的先驱是 BitKeeper 和 Monotone，但正是 git 引起了编程界的注意并改变了一切。

因为，你看，git 消除了主磁带。

哦，你仍然需要一个最终的权威源代码版本。
但 git 不会自动为你提供这个位置。
Git 根本不关心那个。
你决定把你的权威版本放在哪里完全取决于你。
Git 与此完全无关。

Git 将整个源代码历史保存在你的本地机器上。
你的笔记本电脑，如果那是你使用的。
在你的机器上，你可以提交更改、创建分支、签出旧版本。
并且通常可以执行任何你可以用像 Subversion 这样的集中式系统做的事情；只是你不需要连接到某个中央服务器。

你可以随时连接到另一个用户，并将你所做的任何更改推送给那个用户。
或者你可以将他们所做的任何更改拉取到你的本地存储库中。
两者都不是主存储库。
两者是平等的。
这就是为什么他们称之为点对点。

而你用于进行生产发布的最终权威位置只是另一个对等点，人们可以随时推送或拉取。

这一切的最终结果是，在将更改推送到其他地方之前，你可以自由地尽可能多地进行小规模提交。
如果你愿意，你可以每 30 秒提交一次。
你可以每次让单元测试通过时进行一次提交。

这就把我们带到了整个历史讨论的要点。

如果你退后一步，看看源代码控制系统演变的轨迹，你可以看到它们一直是由一个单一的潜在命令驱动的，也许是无意识地。

### 小周期

再次想想我们是如何开始的。
当源代码通过物理拥有卡片组来控制时，周期有多长？

你通过从柜子里取出那些卡片来签出源代码。
你保留那些卡片直到你的项目完成。
然后，你通过把更改过的卡片组放回柜子里来提交你的更改。

周期时间是整个项目。

然后，当我们在公告板上使用图钉时，同样的规则适用。
你在你正在更改的模块中保留你的图钉，直到你正在进行的项目完成。

即使在 70 年代末到 80 年代，当我们使用 SCCS 和 RCS 时，我们继续使用这种悲观锁定策略，阻止其他人接触我们正在更改的模块，直到我们完成。

但 CVS 改变了一些事情 —— 至少对我们中的一些人来说。
乐观锁定意味着一个程序员不能将其他人锁在模块之外。
我们仍然只在项目完成时提交；但其他人可以同时处理相同的模块。
因此，项目提交之间的平均时间急剧缩短。
当然，这样做的代价是合并。

我们多么讨厌做合并。

合并是可怕的。
特别是没有单元测试的时候！
它们是繁琐、耗时和危险的。

事实上，我们对合并的厌恶促使我们采用了一种新的策略。
