## 分支 vs 切换

我曾经是一个分支教条主义者。
当我在使用 CVS 和 Subversion 时，我拒绝允许我团队中的成员分支代码。
我希望所有更改尽可能频繁地返回到主线。

我的理由很简单。
一个分支只是一个长期的签出。
正如我们所看到的，长期签出通过延长集成之间的时间来阻碍他人的进度。

但后来我切换到了 git —— 一切在一夜之间改变了。

当时，我在管理开源项目 FitNesse，有大约十几个人在开发它。
我刚刚将 FitNesse 仓库从 Subversion（Source Forge）迁移到 git（GitHub）。
突然间，分支到处都是。

在最初的几天里，git 中这些疯狂的分支让我感到困惑。
我应该放弃我的分支教条主义立场吗？
我应该放弃持续集成，只是让每个人都随意创建分支，忘记周期时间问题吗？

但后来，我意识到我看到这些 “分支” 并不是真正的命名分支。
相反，它们只是开发人员在推送之间进行的提交流。

事实上，git 所做的只是记录开发人员在持续集成周期之间的行为。

所以我决定继续我的限制分支的规则。
只是现在不是提交立即返回到主线。
而是推送。持续集成被保留了。

如果我们遵循持续集成并每小时左右推送到主线，那么我们肯定会在主线上有一堆半成品功能。
通常有两种策略来处理这个问题： *分支* 和 *切换 (toggles)* 。

分支策略很简单。
你为开发该功能创建一个新的源代码分支。
当功能完成后，你将其合并回来。

如果你将分支保留在主线之外几天或几周，那么你很可能面临一个大合并；而且你肯定会阻碍团队。

然而，在某些情况下，新功能与代码的其余部分如此隔离，以至于分支它不太可能导致大合并。
在那些情况下，让开发人员在新功能上安心工作而不持续集成可能会更好。

事实上，几年前我们在 FitNesse 上遇到过这样的情况。
我们完全重写了解析器。
这是一个大项目。
花了几个星期。
而且没有办法增量地完成它。
我的意思是，解析器就是解析器。

所以我们创建了一个分支，并将该分支与系统的其余部分隔离，直到解析器准备好。

在最后有一个合并要做，但还不算太糟。
解析器与系统的其余部分隔离得很好。
幸运的是，我们有一套非常全面的单元和验收测试。

然而，大多数时候，我认为最好将新功能开发保留在主线上，并使用 *切换 (toggles)* 在准备好之前关闭这些功能。

有时我们使用标志来切换，但更常见的是我们使用命令模式、装饰器模式和工厂模式的特殊版本来确保部分编写的功能无法在生产环境中执行。

大多数时候，我们只是不给用户使用新功能的选项。
我的意思是，如果按钮不在网页上，你就无法执行该功能……

当然，在许多情况下，新功能将在当前迭代中完成 —— 或者至少在下一个生产发布之前。
所以实际上不需要任何形式的切换。

只有当你将在某些功能未完成时发布到生产环境时，你才需要切换。
那么，这种情况应该多久发生一次？
