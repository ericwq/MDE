# 第 23 章 软件的两种价值

<center><img src="../imgs/fig-ch23-0.png" width="40%"></center><br/>

软件有两种价值。
有它行为的价值，也有它结构的价值。
其中，结构价值是更大的，因为正是这种价值使软件变得 “软”。

软件之所以被发明，是因为我们需要一种能够快速、轻松地改变机器行为的方式。
但这种灵活性在很大程度上取决于系统的形状、其组件的排列方式以及这些组件相互连接的方式。

## 保留选项

保持软件 “软” 的方法是：尽可能长时间地保留尽可能多的选项。
我们需要保留的选项是什么？
*它们是那些无关紧要的细节* 。

所有软件系统都可以分解为两个主要元素：策略和细节。
策略元素体现了所有的业务规则和流程 (procedures)。
策略是系统真正价值所在。

细节是那些使人类、其他系统和程序员能够与策略通信所必需的东西，但丝毫不会影响策略的行为。
它们包括 IO 设备、数据库、Web 系统、服务器、框架、通信协议等等。

架构的目标是为系统创建一个形状，将策略视为系统中最核心的元素，同时使细节与该策略无关。
这使得关于这些细节的决策可以被推迟和延后。

例如：

- 在开发早期不必选择数据库系统，因为高层策略不应该关心使用哪种类型的数据库。
实际上，如果你足够谨慎，高层策略甚至不会关心数据库是关系型的、分布式的、层次型的，还是纯平面文件。

- 在开发早期不必选择 Web 服务器，因为高层策略不应该知道它是通过 Web 来交付的。
如果高层策略对 HTML、CSS、AJAX、JSP、JSF 或其他任何 Web 开发的大杂烩一无所知，那么你就直到项目后期才需要决定使用哪种 Web 系统。
实际上，你甚至不必决定系统是否通过 Web 交付。

- 在开发早期不必采用 REST，因为高层策略应该对外部世界的接口一无所知。
同样，也没有必要采用微服务框架、SOA 框架或 REACT……重申一下，高层策略不应该关心这些事情。

- 在开发早期没有必要采用依赖注入框架，因为高层策略不应该关心依赖关系是如何解决的。

我想你已经明白了要点。
如果你能够在不承诺其周围细节的情况下开发高层策略，那么你就能将这些细节的决策推迟很长时间。
你等待做出这些决策的时间越长，你就能掌握更多的信息来做出正确的决策。

这也为你进行不同的实验留出了选项。
如果你有一部分高层策略能够正常工作，并且它与数据库无关，那么你可以尝试将其连接到几个不同的数据库，以检查适用性和性能。
对于 Web 系统、Web 框架、甚至 Web 本身也是如此。

你保留选项的时间越长，就能进行越多的实验，尝试越多的可能性，并且在那些决策再也无法推迟的时刻到来时，你将拥有更多的信息作为依据。

如果这些决策已经被其他人做出了呢？
如果你的公司已经承诺使用某个特定的数据库、某个特定的 Web 服务器或某个特定的框架呢？
我建议你假装这些决策尚未做出，并塑造系统，使这些决策仍然可以尽可能长时间地被推迟。
你永远不知道像这样的决策什么时候会突然改变。

> 优秀的架构师最大化未做出决策的数量。
