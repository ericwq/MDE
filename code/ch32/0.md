# 第 32 章 不懈改进

> 5. 我将抓住每一个机会，无畏且不懈地改进我的作品。
我永远不会降低它们的质量。

Robert Baden Powell，美国童子军的创始人，留下了一条遗言，告诫童子军要让世界比他发现时更美好。
正是从这句话中衍生出了 “童子军规则 (Boy Scout Rule)”。

> 以比你签出时更干净的状态签入代码。

怎么做？
通过在每次签入代码时对代码执行随机的善举。
其中一项随机的善举是增加测试覆盖率。

## 测试覆盖率

你是否衡量你的代码被测试覆盖了多少？
你知道有多少百分比的代码行被覆盖？
你知道有多少百分比的分支被覆盖？
如果不知道，为什么不呢？

有很多工具可以为你衡量覆盖率。
对我们大多数人来说，这些工具作为我们 IDE 的一部分，运行起来很简单。
所以通常没有理由不知道你的覆盖率数字。

你应该如何处理这些数字？
首先，让我告诉你不要做什么。

不要把它们变成管理指标。
如果你的测试覆盖率太低，不要使构建失败。
测试覆盖率是一个复杂的概念，不应该如此天真地使用。

这种天真的使用会设置不正当的激励来作弊。
而且欺骗测试覆盖率非常容易。
记住，覆盖率工具只衡量执行的代码量，而不是实际测试的代码。
这意味着你可以通过将断言从失败的测试中移除来使覆盖率数字非常高。
当然，这使指标变得无用。

最好的政策是将覆盖率数字作为开发人员工具来帮助你改进代码。
你应该通过编写实际测试，有意义地将覆盖率推向 100%。

100% 的测试覆盖率始终是目标，但它也是一个渐进的目标。
大多数系统从未达到 100%，但这不应阻止你不断努力去实现它。

这就是你使用覆盖率数字的目的。
你使用它们作为帮助你改进的衡量标准，而不是作为惩罚团队和使构建失败的打击工具。

## 变异测试

100% 的测试覆盖率意味着对代码的任何语义更改都应该导致测试失败。
TDD、TCR，以及在较小程度上，小捆绑，是接近该目标的良好准则，因为如果你无情地遵循那些准则，每一行代码、每一个条件和每一个分支都经过测试。

然而，这种无情往往是不切实际的。
程序员是人，准则总是受制于实用性。
因此，现实是即使是最勤奋的测试驱动开发者也会在测试覆盖中留下空白。

变异测试是一种找到那些空白的方法；有变异测试工具可以提供帮助。

<ins>变异测试器运行你的测试套件并衡量覆盖率。
然后，它进入一个循环，以某种语义方式变异你的代码，然后再次运行测试套件并检查覆盖率。
语义更改包括将 `>` 更改为 `<`，或将 `==` 更改为 `!=`，或将 `x=<something>` 更改为 `x=null`。
每一个这样的语义更改都称为一个 *变异 (mutation)* </ins>。

该工具期望每个变异都导致测试失败。
没有导致测试失败的变异称为 *存活变异 (surviving mutations)* 。
显然，目标是确保没有存活变异。

运行变异测试可能是一项很大的时间投资。
即使是相对较小的系统也可能需要数小时的运行时间。
所以这类测试最好在周末或月底运行。

我经常被这些工具发现的微妙问题所打动。
所以偶尔付出努力绝对是值得的。

## 语义稳定性

测试覆盖率和变异测试的目标是创建一个确保 *语义稳定性* 的测试套件。
系统的语义是系统的所需行为。
一个确保语义稳定性的测试套件是每当所需行为被破坏时就会失败的测试套件。
我们使用这样的测试套件来消除重构和清理代码的恐惧。
没有一个语义稳定的测试套件，对变化的恐惧往往太大了。

遵循其中一种测试准则为我们提供了一个语义稳定测试套件的良好开端；但没有一种准则足以实现完全的语义稳定性。
覆盖率、变异测试和验收测试应该被用来将语义稳定性提高到完备性。

## 清理

也许最能改进代码的随机善举是简单的清理 —— 以改进为目标的重构。

可以进行哪些改进？
当然，有显而易见的消除代码坏味。
但我经常甚至在代码没有坏味时也会清理它。

我在名称、结构、组织上做微小的改进。
这些更改可能不会被其他人注意到。
有些人甚至可能认为它们使代码更不整洁。
但我的目标不仅仅是代码的状态。
通过做一些小的清理，我了解了代码。
我变得更熟悉、更舒适。
也许我的清理在客观意义上并没有真正改进代码；但它提高了我对那段代码的理解和熟练程度。
清理使我作为那段代码的开发人员得到了提升。

清理还做了其他一些不应被低估的事情。
通过清理代码，即使是以微小的方式，我也在锻炼那段代码。
确保代码保持灵活的最佳方法之一是定期锻炼它。
我做的每一点清理实际上都是对代码灵活性的测试。
如果我发现有小的清理有点困难，我就检测到了一个不灵活的区域，我现在可以纠正它。

记住，软件应该是软的。
你怎么知道它是软的？
通过定期测试那种柔软性。
通过做一些小的清理和小的改进，并感受那些更改是容易还是困难。

## 作品

上面承诺中使用的词是 *作品 (creations)*。
在本章中，我主要关注代码；但代码并不是程序员创造的唯一东西。
我们创建设计、文档、进度表和计划。
所有这些工件都是应该被持续改进的作品。

我们是人类。
人类会随着时间推移让事情变得更好。
我们不断改进我们工作的每一件事。
