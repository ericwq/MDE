## 验收测试准则

<ins>验收测试准则认识到这个简单的事实，并建议所有需求都被指定为测试。
这些测试应由业务分析师（BA）和 QA 在逐个功能的基础上，在每个功能实现前不久编写。
QA 不负责运行那些测试。
相反，该任务留给程序员；因此，程序员很可能会自动化那些测试</ins>。

<ins>没有一个心智正常的程序员想要一遍又一遍地手动测试系统。
程序员自动化事物。
因此，如果程序员负责运行测试，程序员将自动化那些测试</ins>。

然而，由于 BA 和 QA 编写测试，程序员必须能够向 BA 和 QA 证明自动化实际上执行了所编写的测试。
因此，测试自动化的语言必须是 BA 和 QA 理解的语言。
事实上，BA 和 QA 应该能够用那种自动化语言编写测试。

多年来，已经发明了几种工具来帮助解决这个问题：FitNesse、¹ JBehave、SpecFlow、Cucumber 等。
但工具并不是真正的问题。
软件行为的规范总是指定输入数据、要执行的操作和预期输出数据的简单函数。
这是众所周知的 AAA ² 模式 Arrange/Act/Assert，或行为驱动开发（behavior-driven development, BDD）的 Given-When-Then 准则。

¹ https://fitnesse.org/ <br/>
² 来源：Bill Wake。

所有测试都从安排测试的输入数据开始。
然后，测试使被测动作被执行。最后，测试断言该动作的输出数据与预期匹配。

这三个元素可以以多种不同的方式指定；但最简单的方法是简单的表格格式。

例如，下图是 FitNesse 工具中一个验收测试的一部分。
FitNesse 是一个 wiki，这个测试检查各种标记手势是否被正确翻译为 HTML。
要执行的动作是 “widget should render”，输入数据是 “wiki text”，输出是 “html text”。

| widget should render | | |
| ---- | ---- | ---- |
| wiki text | html text | |
| normal text | normal text | |
| this is ''italic'' text | this is &lt;i&gt;italic&lt;/i&gt; text | italic widget |
| this is '''bold''' text | this is &lt;b&gt;bold&lt;/b&gt; text | bold widget |
| !c This is centered text | &lt;center&gt;This is centered text&lt;/center&gt; | |
| !1 header | &lt;h1&gt;header&lt;/h1&gt; | |
| !2 header | &lt;h2&gt;header&lt;/h2&gt; | |
| !3 header | &lt;h3&gt;header&lt;/h3&gt; | |
| !4 header | &lt;h4&gt;header&lt;/h4&gt; | |
| !5 header | &lt;h5&gt;header&lt;/h5&gt; | |
| !6 header | &lt;h6&gt;header&lt;/h6&gt; | |
| http://files/x | `<a href="files/x">http://files/x</a>` | file link |
| http://fitnesse.org | `<a href="http://fitnesse.org">http://fitnesse.org</a>` | http link |
| SomePage | `SomePage<a title="create page" href="SomePage\?edit&nonExistent=true">\[\?\]</a>` | missing wiki word |

以下是 Given-When-Then 风格的一个示例：

> **Given** 一个带有 wiki 文本的页面：`!1 header`
>
> **When** 该页面被渲染。
>
> **Then** 该页面将包含：`<h1>header</h1>`

应该清楚的是，这些形式化规范，无论它们是在验收测试工具中编写的，还是在简单的电子表格或文本编辑器中编写的，都相对容易自动化。

### 准则

<ins>在最严格形式的准则中，验收测试由 BA 和 QA 编写。
BA 关注快乐路径场景，而 QA 关注探索系统可能失败的无数方式</ins>。

<ins>这些测试在它们所测试的功能被开发的同一时间或之前编写。
在一个划分为冲刺或迭代的敏捷项目中，测试在冲刺的头几天编写。
它们应该在冲刺结束时全部通过</ins>。

<ins>BA 和 QA 向程序员提供这些测试，程序员以一种让 BA 和 QA 保持参与的方式自动化它们</ins>。

<ins>这些测试成为 *完成的定义 (definition of done)* 。
一个功能在它的所有验收测试通过之前是不完整的。
当所有验收测试通过时，该功能就完成了</ins>。

这当然给 BA 和 QA 带来了巨大的责任。
他们编写的测试必须是被测试功能的完整规范。
<ins>验收测试套件是整个系统的需求文档。
通过编写那些测试，BA 和 QA 认证当它们通过时，指定的功能已经完成并正常工作</ins>。

在某些情况下，BA 和 QA 可能不习惯编写如此正式和详细的文档。
在这种情况下，程序员可能希望在 BA 和 QA 的指导下编写验收测试。
中期目标是创建 BA 和 QA 可以阅读和批准的测试。
最终目标是让 BA 和 QA 足够舒适以编写测试。

### 持续构建

<ins>一旦一个验收测试通过，它就会进入在持续构建期间运行的测试套件</ins>。

<ins>持续构建是一个自动化过程，每次 ³ 程序员将代码签入源代码控制系统时都会运行。
该过程从源代码构建系统，然后运行自动化的程序员单元测试套件和自动化的验收测试套件。
该运行的结果会被可见地发布，通常是通过电子邮件发送给每位程序员和相关方。
持续构建的状态是每个人都应该持续知晓的</ins>。

³ 在几分钟内。

<ins>所有这些测试的持续运行确保了随后对系统的更改不会破坏工作功能。
如果先前通过的验收测试在持续构建期间失败，团队必须立即响应并在进行任何其他更改之前修复它。
允许失败在持续构建中积累是自杀行为</ins>。
