## 最大化表达

在编程的早期几十年里，我们编写的代码无法揭示意图。
事实上，“代码” 这个名称本身就暗示了意图被模糊了。
在 60 年代末，代码看起来像这样：

<img src="../imgs/fig-ch18-2.png" width="70%"/><br/>

注意那些无处不在的注释。
这些注释是绝对必要的，因为代码本身根本没有揭示程序的任何意图。

然而，我们不再是在 60 年代工作。
我们使用的语言具有巨大的表达力。
通过适当的纪律，我们可以生成读起来像 “写得好的散文” 的代码。

作为这类代码的一个例子，考虑这段小 Java 代码：

```java
public class RentalCalculator {
    private List<Rental> rentals = new ArrayList<>();

    public void addRental(String title, int days) {
        rentals.add(new Rental(title, days));
    }

    public int getRentalFee() {
        int fee = 0;
        for (Rental rental : rentals)
            fee += rental.getFee();
        return fee;
    }

    public int getRenterPoints() {
        int points = 0;
        for (Rental rental : rentals)
            points += rental.getPoints();
        return points;
    }
}
```

如果你不是这个项目的程序员，你可能不会理解这段代码中正在发生的一切。
然而，即使是最粗略的一瞥，设计者的基本意图也很容易识别。
变量、函数和类型的名称具有很强的描述性。
算法的结构很容易看到。
这段代码是有表达力 (expressive) 的。
这段代码是简单的。

### 底层抽象

免得你认为表达力仅仅是给函数和变量起好名字的问题，我应该指出还有另一个关注点：层次的分离和底层抽象的展示。

<ins>如果一个软件系统的每一行代码、每一个函数和每一个模块都生活在一个定义良好的分区中，
该分区清晰地描绘了代码的层次及其在整体抽象中的位置，那么这个系统就是有表达力的</ins>。

你可能觉得最后一句话难以理解，所以让我通过更加冗长的方式让它更清楚一些。

想象一个具有复杂需求集的应用程序。
我喜欢用的例子是薪资系统。

- 小时工 (Hourly employees) 每周五根据他们提交的工时卡获得报酬。
他们一周工作超过 40 小时后，每小时的报酬是正常工资的一倍半。

- 佣金雇员 (Commissioned employees) 在每月的第一个和第三个周五获得报酬。
他们获得基本工资加上根据他们提交的销售单据计算的佣金。

- 受薪雇员 (Salaried employees) 在每月的最后一天获得报酬。
他们获得固定的月薪。

你应该不难想象一组使用复杂 `switch` 语句或 `if/else` 链来捕获这些需求的函数。
然而，这样一组函数可能会掩盖底层抽象。
那个底层抽象是什么？

```java
public List<Paycheck> run(Database db) {
    Calendar now = SystemTime.getCurrentDate();
    List<Paycheck> paychecks = new ArrayList<>();
    for (Employee e : db.getAllEmployees()) {
        if (e.isPayDay(now))
            paychecks.add(e.calculatePay());
    }
    return paychecks;
}
```

<ins>注意，代码里完全没有出现需求中那些杂乱繁琐的细节。
这个应用程序的底层真相是，我们需要在所有员工的发薪日支付他们。
将高层策略与低层细节分离，是使设计简单且具有表达力的最基本部分</ins>。

### 测试：问题的另一半

当 Kent Beck 最初写下这条规则时，他的措辞是这样的：

> 系统（代码和测试）必须传达你想传达的一切。

他以这种方式措辞是有原因的：无论你让生产代码多么具有表达力，它都无法传达它被使用的上下文。
那是测试的工作。

你编写的每一个测试，特别是如果那些测试是隔离和解耦的，都是生产代码被期望如何使用的一个演示。
编写良好的测试是它们所测试代码部分的示例用例。

因此，代码和测试一起，表达了系统的每个元素做什么以及每个元素应该如何被使用。

这与设计有什么关系？
当然，一切。
因为我们希望通过设计实现的主要目标是使其他程序员更容易理解、改进和升级我们的系统。
而实现这一目标的最好方法，莫过于通过一套全面的可执行测试来演示系统抽象的预期用途。
