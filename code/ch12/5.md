## 数据传输对象

数据结构的最典型形式是一个具有公共变量且没有函数的上下文、类或结构体。
这有时被称为 *数据传输对象 (Data Transfer Object, DTO)* 。
DTO 是非常有用的结构，尤其是在与数据库通信、解析来自 socket 的消息等情况下。
它们通常成为一系列转换阶段中的第一个，将数据库中的原始数据转换为应用程序代码中的对象。

在 Java 早期，下面显示的 “bean” 形式很流行。
Bean 具有由 getter 和 setter 操作的私有变量。
Bean 的准封装似乎让一些 OO 纯粹主义者感觉更好，但通常没有提供其他好处。
`Address` DTO 不妨直接拥有公共字段。

```java
public class Address {
    private String street;
    private String streetExtra;
    private String city;
    private String state;
    private String zip;

    public Address(String street, String streetExtra,
                   String city, String state, String zip) {
        this.street = street;
        this.streetExtra = streetExtra;
        this.city = city;
        this.state = state;
        this.zip = zip;
    }

    public String getStreet() {
        return street;
    }

    public String getStreetExtra() {
        return streetExtra;
    }

    public String getCity() {
        return city;
    }

    public String getState() {
        return state;
    }

    public String getZip() {
        return zip;
    }
}
```

### 对象/关系 “阻抗不匹配”

在 80 年代末，随着 OO 的日益普及，OO 的公共行为和私有数据概念与关系型的公共数据和无行为概念之间的差异变得明显。
程序员们试图将这两种想法合并；但他们对结果感到失望。
有一段时间，人们尝试了面向对象数据库；但它们从未真正解决这个问题。
最终，我们转向了对象关系映射器 (ORM)。

希望在于，ORM 将允许使用面向对象语言的程序员方便地访问关系数据库中的数据。
ORM 将查询数据库，从结果表行中解包数据，并将数据重新打包到他们程序中对象使用的数据结构中。
作为一种将表转换为更方便形式的方法，这工作得足够好，但它并不能解决这个困境，因为对象更多的是关于函数而不是数据。
最终，没有办法将关系数据库映射到对象，因为数据库包含数据结构，而数据结构与对象是正交的。
我们真正能做的就是从数据库中提取数据，并将其放入对象可以内部化的形式中。
<ins>ORM 不创建对象，它们只是加载数据结构</ins>。

### 使用对象和数据结构

那么我们为什么会有这两个相反的概念？
为什么我们有时希望数据结构被隐藏而行为被暴露，而有时又希望行为被隐藏而数据结构被暴露？

<ins>这一切都归结为哪个更可能增长和变化</ins>。

<ins>如果很可能有新的行为，并且现有的行为很可能变化，那么我们希望隐藏易变的行为，同时暴露静态的数据结构。
另一方面，如果数据结构和类很可能是增长和变化的，那么我们想暴露静态的行为，隐藏易变的数据结构</ins>。

我们隐藏易变的，以便变化不影响静态的。
我们建立一个屏障，保护静态的免受易变的侵害。

示例 1：一个大型企业数据库的结构相对静态。
数据本身可能会随着新记录的添加和旧记录的更新或删除而变化，但结构变化非常不频繁。
然而，使用该数据库的程序的行为变化频繁。
业务规则是易变的，但业务结构相比之下是稳定的。

示例 2：IDE 的行为相对静态。
它是一个文本文件编辑器。
但是，每当在其功能中添加一种新语言时，数据结构的类就会发生变化。
用户期望 IDE 无论使用 Ruby、Python、Java 还是 Clojure 编程都能保持一致的行为；然而这些语言具有显著不同的结构。
与行为相比，整体数据结构是易变的。

<ins>确定数据或行为哪个更静态，是一个需要一些思考和经验的决策。
这也是一个在系统不同部分可能必须以不同方式做出的决策</ins>。

一个复杂的系统可以包含两种类型的组件。
一些组件的行为相对于数据结构可能是静态的，而另一些组件的数据结构相对于行为可能是静态的。

奇怪的是，所有这些都归结为使用 `switch` 语句的决策。
