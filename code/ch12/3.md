## 数据/对象反对称性

这两个例子展示了对象与数据结构之间的区别。
<ins>对象将其数据隐藏在抽象之后，并暴露操作该数据的函数。
数据结构暴露其数据，并且没有有意义的函数。
回去再读一遍。
注意这两个定义的互补性质。
它们实际上是相反的</ins>。
这种差异可能看起来很琐碎，但它具有深远的影响。

例如，考虑下面的 `Procedural Shapes` 示例。
`Geometry` 类操作于三个形状类。
形状类是没有任何行为的简单数据结构。
所有行为都在 `Geometry` 类中。

———过程式形状———

```java
public class Square {
    public Point topLeft;
    public double side;
}

public class Rectangle {
    public Point topLeft;
    public double height;
    public double width;
}

public class Circle {
    public Point center;
    public double radius;
}

public class Geometry {
    public final double PI = 3.141592653589793;

    public double area(Object shape) throws NoSuchShapeException {
        if (shape instanceof Square) {
            Square s = (Square)shape;
            return s.side * s.side;
        }
        else if (shape instanceof Rectangle) {
            Rectangle r = (Rectangle)shape;
            return r.height * r.width;
        }
        else if (shape instanceof Circle) {
            Circle c = (Circle)shape;
            return PI * c.radius * c.radius;
        }
        throw new NoSuchShapeException();
    }
}
```

面向对象的程序员可能会对此皱起眉头，抱怨它是过程式的 —— 他们是对的。
但这种嘲讽可能并不合理。
考虑如果向 `Geometry` 添加一个 `perimeter()` 函数会发生什么。
形状数据结构将不受影响！
任何其他依赖于这些形状的模块也将不受影响！
另一方面，如果我添加一个新的形状，我必须更改 `Geometry` 中的所有函数来处理它。
再读一遍。
当你添加一个新函数时，数据结构保持不变；但当你添加一个新的数据结构时，所有函数都必须更改。

现在考虑下面的 `OO Shapes` 示例。
这里 `area()` 方法是多态的。
不需要 `Geometry` 类。
所以，如果我添加一个新的形状，现有函数都不会受到影响，但如果我添加一个新函数，所有形状都必须更改！⁵

⁵ 有经验丰富的面向对象设计者熟知的方法可以绕过这一点：例如，Visitor 或双分派。
但这些技术自身也有代价，并且通常会将结构恢复到过程式程序的状态。

———面向对象形状———

```java
public class Square implements Shape {
    private Point topLeft;
    private double side;

    public double area() {
        return side*side;
    }
}

public class Rectangle implements Shape {
    private Point topLeft;
    private double height;
    private double width;

    public double area() {
        return height * width;
    }
}

public class Circle implements Shape {
    private Point center;
    private double radius;
    public final double PI = 3.141592653589793;

    public double area() {
        return PI * radius * radius;
    }
}
```

<ins>我们再次看到这两个定义的互补性质；它们实际上是相反的！
这揭示了对象与数据结构之间的基本二分法：过程式代码（使用数据结构的代码）使得在不更改现有数据结构的情况下添加新函数变得容易。
另一方面，OO 代码使得在不更改现有函数的情况下添加新的数据结构（类）变得容易</ins>。

互补也是成立的：过程式代码使得添加新的数据结构变得困难，因为所有函数都必须更改。
OO 代码使得添加新函数变得困难，因为所有类都必须更改。

所以，对 OO 来说困难的事情，对过程式来说容易；对过程式来说困难的事情，对 OO 来说容易。

在任何复杂的系统中，总会有一些时候我们想要添加新的数据类型而不是新的函数。
在这些情况下，对象和 OO 是最合适的。
另一方面，也会有一些时候我们想要添加新的函数而不是数据类型。
在这些情况下，过程式代码和数据结构将更合适。

<ins>成熟的程序员知道 “一切都是对象” 的想法是一个迷思。
有时候你确实想要简单的数据结构和操作它们的过程</ins>。
