## 面向对象/过程式的权衡

如果我们的设计将需求的变化解释为新的类型，那么 OO 是一个好的选择，因为添加新的类型（如 `Triangle`）很容易，而无需更改其他任何东西。
然而，如果我们的设计将变化解释为新的函数，那么过程式的 `switch` 语句是最好的，因为我们不必更改任何类型。

或者，换句话说，当我们想向现有函数添加新的数据类型时，我们使用 OO；当我们想向现有数据类型添加新的函数时，我们使用过程式的 `switch` 语句。

我们再次看到这种有趣的对抗。
隐藏数据并暴露函数允许数据变化而不会产生重大影响。
隐藏函数并暴露数据允许函数变化而不会产生重大影响。

<ins>那么到底是哪一个？
我们更愿意改变哪一个，函数还是数据？
答案是，这取决于你的应用程序和你的设计如何解释对该应用程序的变化</ins>。

在大型企业模型中，我们经常针对现有的数据 schema 编写新的应用程序。
而当我们向给定的应用程序添加新功能时，我们通常将该行为封装到新的数据类型中。

就个人而言，我更喜欢后者。
在可能的情况下，我创建将变化解释为新的数据类型的设计。
这意味着我更喜欢 OO 设计。
在大多数情况下，我发现这样做效果很好。

<ins>因此，我对 `switch` 语句及其丑小鸭同胞 `if/else` 链的一般规则是，它们应该位于系统的外围（例如 `main` 模块）；
对于每个可切换的类型，最多应该有一个；其中的 case 必须创建系统其余部分使用的多态对象</ins>。

然而，这种偏好和规则并不意味着我不会在行为比数据压倒性地更易变的系统部分使用 `switch` 语句。
我不会将一个 OO 的圆钉强行塞进一个过程式的方孔中，反之亦然。
