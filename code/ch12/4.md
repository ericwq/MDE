## 迪米特法则 (Law of Demeter)

<ins>有一个著名的启发法叫做 *迪米特法则 (Law of Demeter)* ⁶，它建议一个模块不应该知道它操作对象的内部结构</ins>。
正如我们在上一节中看到的，对象隐藏它们的数据并暴露操作。
这意味着一个对象不应该通过访问器暴露其内部结构，因为这样做是暴露而不是隐藏其内部结构。

⁶ http://en.wikipedia.org/wiki/Law_of_Demeter

<ins>更准确地说，迪米特法则指出，一个类 C 的方法 f 只应该调用以下对象的方法</ins>：

- <ins>C</ins>
- <ins>由 f 创建的对象</ins>
- <ins>作为参数传递给 f 的对象</ins>
- <ins>保存在 C 的实例变量中的对象</ins>

<ins>该方法不应该调用由任何允许的函数返回的对象上的方法。
换句话说，要害羞，只和朋友交谈，不要和陌生人交谈</ins>。

以下代码 ⁷ 似乎违反了迪米特法则（以及其他一些原则），因为它调用了 `getOptions()` 返回值上的 `getScratchDir()` 函数，然后又调用了 `getScratchDir()` 返回值上的 `getAbsolutePath()`。

⁷ 在 Apache 框架的某处找到。

```java
final String outputDir =
    ctxt.getOptions().getScratchDir().getAbsolutePath();
```

### 火车残骸

这种代码通常被称为 *火车残骸 (trainwreck)* ，因为它看起来像一连串耦合的火车车厢。
像这样的调用链通常被认为是一种草率的风格，应该避免。
通常最好按如下方式拆分它们：

```java
Options opts = ctxt.getOptions();
File scratchDir = opts.getScratchDir();
final String outputDir = scratchDir.getAbsolutePath();
```

这两段代码是否违反了迪米特法则？
当然，包含的模块知道 `ctxt` 对象包含 `options`，其中包含一个 `scratch directory`，它有一个绝对路径。
对于一个函数来说，这是大量的知识。
调用函数知道如何导航许多不同的对象。

<ins>这是否违反迪米特法则，取决于 `ctxt`、`Options` 和 `ScratchDir` 是对象还是数据结构</ins>。
如果它们是对象，那么它们的内部结构应该被隐藏而不是暴露，因此了解它们的内部结构明显违反了迪米特法则。
另一方面，如果 `ctxt`、`Options` 和 `ScratchDir` 只是没有行为的数据结构，那么它们自然暴露其内部结构，因此迪米特法则不适用。

上面示例中访问器函数的使用混淆了这个问题。
如果代码写成如下形式，那么我们可能不会担心迪米特违规。

```java
final String outputDir = ctxt.options.scratchDir.absolutePath;
```

如果我们采用这样的约定，即数据结构具有公共变量且没有函数，而对象具有私有变量和抽象实现的公共函数，这个问题就不会那么令人困惑了。

### 混合体

这种混淆有时会导致不幸的混合结构，它们是半对象半数据结构的。
它们有执行重要操作的函数，同时它们也有公共变量或公共访问器和修改器，这些实际上使私有变量公开化，诱使其他外部函数以过程式程序使用数据结构的方式使用这些变量。⁸

⁸ 这在 [Refactoring](../bib.md#refactoring) 中有时被称为 *特性嫉妒 (feature envy)* 。

这种混合体使得添加新函数变得困难，同时也使得添加新的数据结构变得困难。
它们是两全其 “坏”。
避免创建它们。
它们表明设计混乱，其作者不确定 ——或者更糟糕的是，不知道—— 他们是否需要保护自己免受函数或类型的侵害。

### 隐藏结构

如果 `ctxt`、`options` 和 `scratchDir` 是具有真实行为的对象呢？
那么，由于对象应该隐藏其内部结构，我们不应该能够导航它们。
那么我们如何才能获得 scratch 目录的绝对路径呢？

```java
ctxt.getAbsolutePathOfScratchDirectoryOption();
```

或者

```java
ctx.getScratchDirectoryOption().getAbsolutePath()
```

第一个选项可能导致 `ctxt` 对象中的方法爆炸式增长。
第二个选项假设 `getScratchDirectoryOption()` 返回一个数据结构，而不是一个对象。
两种选择感觉都不好。

如果 `ctxt` 是一个对象，我们应该告诉它去做某事；我们不应该询问它的内部结构。
那么我们为什么想要 scratch 目录的绝对路径呢？
我们打算用它做什么？
考虑（同一模块中许多行之后的）这段代码：

```java
String outFile = outputDir + "/" + className.replace('.', '/') + ".class";
FileOutputStream fout = new FileOutputStream(outFile);
BufferedOutputStream bos = new BufferedOutputStream(fout);
```

不同抽象层次的混合有点令人不安。
点号、斜杠、文件扩展名和 `File` 对象不应该这样粗心地混合在一起，并与封闭代码混合。
然而，忽略这一点，我们看到获取 scratch 目录绝对路径的意图是创建一个给定名称的 scratch 文件。

那么，如果我们告诉 `ctxt` 对象这样做呢？

```java
BufferedOutputStream bos =
    ctxt.createScratchFileStream(classFileName);
```

那似乎是一个对象应该做的合理的事情！
这允许 `ctxt` 隐藏其内部结构，并防止当前函数通过导航它不应该知道的对象而违反迪米特法则。

<ins>所以，我们通常可以通过告诉对象做我们想要的，而不是遍历对象网络来收集所有资源，来修复火车残骸和迪米特法则违规。
这个建议被称为 *告诉其他人 (Tell the Other Guy)* </ins>。

很久以前，Dave Thomas 和 Andy Hunt 写了一篇可爱的文章，题为 “一句话中的 OO：保持 DRY、害羞和告诉其他人”。⁹
DRY，当然是 “不要重复自己”，而害羞指的是迪米特法则。
告诉其他人指的是 Alan Kay 的消息传递思想或命令/查询分离 (CQS)。
总之，都是好建议。

⁹ IEEE Software 21, no. 3 (May/June 2004), 101–103.
