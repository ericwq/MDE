## Switch 语句

`switch` 语句及其同类 `if/else` 链，被一些人认为是糟糕的形式，而被另一些人认为是完全必要的。
这种分歧背后的原因与静态行为或数据结构的决策相同。
考虑这个简单的程序。

———Shape.java———

```java
enum ShapeType {CIRCLE, SQUARE}

public class Shape {
    public ShapeType type;
}
```

———Square.java———

```java
class Square extends Shape {
    public int side;
    public Point topLeft;
}
```

———Circle.java———

```java
class Circle extends Shape {
    public int radius;
    public Point center;
}
```

———ShapeManager.java———

```java
public class ShapeManager {
    public static void renderShapes(List<Shape> shapes) {
        for (Shape shape : shapes) {
            switch (shape.type) {
                case CIRCLE:
                    renderCircle((Circle) shape);
                    break;
                case SQUARE:
                    renderSquare((Square) shape);
                    break;
            }
        }
    }

    private static void renderSquare(Square square) {
        //...
    }

    private static void renderCircle(Circle circle) {
        //...
    }
}
```

如果你是一名 Java 程序员，这可能看起来有点奇怪。
如果你是一名 C 程序员，这可能看起来很正常。

现在考虑添加一个 `Triangle` 的结果。

第一个需要更改的文件是 `Shape.java`，因为 `TRIANGLE` 必须被添加到 `enum` 中。
接下来，当然，`Triangle` 数据结构（类）必须被编写。
然后，最后，`Triangle` 的 case 需要被添加到 `ShapeManager` 类的 `switch` 语句中。

这个设计迫使多个模块为了一个简单的需求变更而更改，以及其他模块被添加。
这违反了 *单一职责原则 (SRP)* 和 *开闭原则 (OCP)* 。
变更的数量也意味着这是一个僵硬的设计。
需要的变更越多，设计就变得越僵硬。

但情况更糟，因为 `ShapeManager` 中的 `renderShapes` 方法并不是该类的唯一方法。
为了节省篇幅，我没有全部写出来，但还有 `dragShapes`、`eraseShapes`、`rotateShapes`、`scaleShapes` 以及其他一系列操作形状的函数。
它们中的每一个都包含那个完全相同的 `switch` 语句。
它们中的每一个都将需要添加 `Triangle` 的 case。

除了其中一些方法不使用 `switch` 语句。
它们中的一些使用 `if/else` 链。
而且，聪明的程序员可能会使用逻辑优化来消除或修改一些 `switch` 语句和 `if/else` 链。
例如，`rotateShapes` 中的 `switch` 语句可能不包含 `CIRCLE` 的 case，因为一个聪明的程序员意识到圆具有旋转对称性。

所以，我们将不得不找到所有那些 `switch/if/else` 语句，解码所有的逻辑优化，并找出某种方法让它们都能正确地处理新的 `TRIANGLE` 的 case。
而且，在大型系统中，我们几乎肯定会漏掉一个……或多个。

<ins>一个设计，当只有一个简单的需求被更改或添加时，却迫使在模块内进行许多修改，它既是僵硬的也是脆弱的 —— 它很难更改，而且容易崩溃。
需要的变更越多，设计就越脆弱</ins>。

但情况更糟。
因为，你看，我们的业务已经试图销售这个形状管理系统好几个月了，但没有取得多大成功。
我们都开始担心我们的工作。
初创公司的生活悬在一根细线上。
幸运的是，我们的 CEO 刚刚发布了一个关键公告。
他知道问题是什么，他知道如何解决它。

“我们的问题，” 他说，“是我们一直强迫我们的客户处理圆形和正方形。
客户不想要那样。他们想要一个形状管理系统，允许他们选择是否使用圆形或正方形。
如果他们只使用正方形，他们不想为圆形付费。谁能责怪他们呢？"

“所以，” 他继续说道，“我们将免费提供 `ShapeManager` 设施。
客户可以从我们的网站下载它。
但是……” 他在这里停顿了一下以制造效果，因为这是将拯救公司的洞见。
“……我们将让他们付费下载圆形。我们将让他们付费下载正方形。
如果他们想要其他形状，我们也将让他们为那些付费。
我们不是销售一个管理形状的大型系统，而是销售形状本身 —— 我们将大发横财！”

在所有的欢呼声、气球和香槟酒塞的爆裂声中，你意识到 CEO 的梦想在到达之前就已经破灭了。
它破灭是因为 `Circle` 和 `Square` 已经渗透到了这个系统的整个结构中。
所有那些 `switch` 语句，所有那些 `if/else` 语句，所有那些聪明的逻辑优化：它们都专门处理 `Circle` 和 `Square`。
这个系统的架构根本无法让 CEO 在不附带 `Circle` 和 `Square` 的情况下免费赠送 `ShapeManager`。
它们被密不可分地捆绑在一起。

一个阻止其部分与其他部分分离并独立部署的设计违反了 *依赖反转原则 (DIP)* ，并且是不可移动的。
可独立部署的部分越少，它就越不可移动。

这个设计是僵硬的、脆弱的和不可移动的。它是垃圾。
这是一个恐怖场景。
它将把公司拖垮，我们所有人也将随之而去！

### 面向对象的解决方案

我们聘请了一位著名的顾问，他飞过来，制造了很多噪音，到处乱搞一通，然后飞回家。¹⁰
他的信息是：“你的设计是过程式的。它应该是面向对象的。来，让我给你看看。” 他展示的是这样的：

¹⁰ 这些有时被称为 “海鸥顾问”。

———Shape.java———

```java
interface Shape {
    void render();
}
```

———Square.java———

```java
class Square implements Shape {
    public int side;
    public Point topLeft;

    public void render() {
        //...
    }
}
```

———Circle.java———

```java
class Circle implements Shape {
    public int radius;
    public Point center;

    public void render() {
        //...
    }
}
```

———ShapeManager.java———

```java
public class ShapeManager {
    public static void renderShapes(List<Shape> shapes) {
        for (Shape shape : shapes) {
            shape.render();
        }
    }
}
```

一个 `switch` 语句都看不见。
现在考虑当你添加 `TRIANGLE` 的 case 时会发生什么。

- `Shape.java` 不需要更改。
- `Square.java` 不需要更改。
- `Circle.java` 不需要更改。
- `ShapeManager.java` 不需要更改。

没有什么需要更改的；除了可能 `main` 程序。
但这些模块都不需要更改。
这意味着设计不是僵硬的。

没有需要查找和更改的 `switch/if/else` 语句。
所有的方法，如 `erase`、`drag`、`scale` 和 `rotate`，都包含在 `Shape` 类中。
这个设计不是脆弱的。

最重要的是，我们可以将 `Circle` 和 `Square` 与 `ShapeManager` 分开部署。
我们可以将 `ShapeManager`、`Circle` 和 `Square` 放入它们自己的 jar 文件中，并单独分发它们！

这个设计符合 `OCP` 和 `DIP`。
它是可移动的、灵活的和健壮的。
哈利路亚！我们得救了！

### 别急，Johnson

这个设计保护我们免受什么影响？
它保护我们免受新形状的影响。
每当客户想要一个新的形状，我们只需要编写一个新的 `Shape` 类的派生类，并将其放入它自己的 jar 文件中，以便可以独立分发和部署。

但是如果客户没有要求一个新的形状呢？
如果他们要求的是在 `Shape` 上添加一个新方法，用于渲染阴影呢？

现在我们的 `Shape` 抽象完全帮不上忙了。
我们将不得不把那个可爱的 OO 设计拿来，并触及每一个类。
`Shape`、`Circle` 和 `Square` 都将需要一个 `renderDropShadow` 方法；而 `ShapeManager` 将不得不调用它。
那个 `Shape` 抽象完全没有给我们带来任何好处。

但现在回顾第一个解决方案，那个有 `switch` 语句的解决方案。
对于那个方案，我们所要做的就是在 `ShapeManager` 中添加 `renderDropShadow` 函数。
我们完全不必触及 `Circle` 或 `Square`！
