## 纪律

像这样的纪律应该被认真对待；但它们并非普遍适用，也不应被盲目遵循。
例如，我是一名飞行员；我遵循使用检查单的纪律，而不是将许多复杂的程序记在脑子里。
我非常认真地对待这种纪律。
然而，有些程序我必须记住，因为时间至关重要，而拿出检查单并遵循它所花费的时间会是不安全的。
飞行员称这些程序为 *记忆项目 (memory items)* ，学习和刷新记忆项目又是另一种纪律。

### 乏味、无聊和缓慢

任何不熟悉这些纪律、并且已经做了几年以上程序员的程序员，可能会觉得这些描述令人恐惧。
它们可能听起来乏味、无聊和缓慢。
你可能会推断你将永远无法思考一个问题。
对于 TDD 和 TCR，你甚至似乎永远无法在打断自己的情况下编写一个小的 `while` 循环或 `if` 语句。
而且所有三种纪律肯定会打断你的注意力并打断你的思路。
简而言之，你可能会得出结论，这些纪律是愚蠢的。

但考虑一下。

### 调试

想象一个满是遵循其中一种纪律的程序员的房间。
随时走向你喜欢的任何一个程序员。
他们在过去几分钟内的某个时候执行并通过了他们的测试。
无论你选择谁，无论你什么时候选择：一切都在几分钟前正常工作。

如果你的一切工作在几分钟前都是正常的 ——而且这总是真的—— 你的生活会是什么样子？
你会做多少调试？

很难相信，如果一切都在不久前正常工作，你会做很多调试。
最可能的调试技术将是恢复到最后一个工作版本，然后再次尝试。

我们这些遵循这些纪律的人很少使用调试器。
哦，我有时会启动一个。
我的意思是，这仍然是软件，它仍然很难。
奇怪的事情仍然会发生。
但我花在调试器上的时间少之又少。
少到事实上，我不记得热键了。
每当我尝试使用调试器时，我都必须重新熟悉如何操作它。

遵循这些纪律中的一种（TDD）已经将我的调试时间减少了很大一个因子。
我认为，这些纪律中的任何一种都会为每一个掌握它们的信徒做同样的事情。

### 文档

你是否曾经集成过第三方包？
也许你从网站下载了一个 zip 文件。
解压后，你找到需要集成的工件，但也有一份带有帮助集成说明的 PDF 手册。
在那本手册的末尾，有一个丑陋的附录，里面全是代码示例。
当然，那是你首先去的地方。

你去代码示例是因为你希望示例代码是最新的，并且它会比手册中的文字告诉你更多真相。
如果你非常幸运，你可以从手册中复制粘贴那段代码到你的项目中，并调整它使其工作。

当你遵循一个测试纪律时，你编写了一系列微小的测试。
每一个测试都描述了系统的一部分如何工作。
如果你想知道如何创建一个对象，有测试以每一种可以创建对象的方式创建了那个对象。
如果你需要知道如何调用某个 API，有测试以每一种可以调用该 API 的方式调用了那个 API。
这些测试是整个系统的代码示例。

而且，每一个测试都与所有其他测试隔离。
测试本身不是一个系统。
每一个都可以独立理解。

所产生的测试是一个描述系统低层设计的文档。
而且那个文档是用你非常熟悉的语言编写的。
它是完全明确的，它是如此形式化以至于它可以执行，并且它不会与它所描述的应用程序不同步。
测试几乎是一种完美的低层文档形式。

这并不是说它们是高层次的文档 —— 它们不是。
但在系统的最低层，测试是几乎可以创建的最好的文档。

### 可靠性

想象一个不遵循这些纪律之一的程序员。
他刚刚完成了一个模块的编写，并已经通过了一轮手动测试。
它似乎工作得很好。
但随后过程监考官提醒他需要编写单元测试。
他觉得这是多余的额外工作，因为他已经测试了模块，所以他的努力低于标准。

他在这里和那里写了一些测试，它们通过了。
但随后他遇到了难以测试的模块。
它难以测试，因为它没有被设计为可测试的。
它耦合到不应该在测试上下文中执行的东西。
他可以重新设计那个模块以使其可测试；但那会花费他认为自己没有的很多时间。
而且，他的手动测试向他证明了一切都已经工作。
所以他走开了，没有编写那个测试。

现在，如果你已经做了几年以上的程序员，你可能认得这个场景。
我们中的许多人都在事后编写过测试；我们中的许多人也因为不想改变一个 “工作” 的设计而从一个困难的测试前走开。

不幸的是，这给测试套件留下了一个漏洞。
如果你在测试套件中留下了漏洞，你知道其他人也留下了一些漏洞。
所以每个人都知道测试套件充满了漏洞。

当你运行这样一个测试套件并看到它通过时会发生什么？
每个人都心照不宣地微笑，没有采取其他行动。
当你知道测试套件充满了漏洞时，当它通过时，你不能做出任何安全的决定。
你所能做的就是微笑，非常清楚测试套件的通过并不意味着系统正常工作。

当你遵循一个测试纪律时，情况就大不相同了。
当测试通过时，你以高度的信心知道系统应该正常工作。
这允许你做出关键决策。

例如，你可以决定部署系统。
我在这样的系统上工作过。
当测试通过时，我们部署了，因为我们对我们的测试套件有很高的信心。

即使部署不是一个选项，测试的通过也可以允许你将系统移动到一个新的阶段。
例如，你可以将它从 DEV 移动到 QA。

### 设计

当你遵循这些纪律时，还会发生其他事情。
你无法编写难以测试的模块。
通过将测试与代码一起编写，你自动地将每个模块设计为易于测试。

<ins>一个易于测试的模块是解耦的。
正是解耦使得模块易于测试。
所以最终结果是一个耦合度更低的设计。仅仅是将测试与代码一起编写的行为就改善了系统的整体设计</ins>。

### 重申

因此，通过遵循这些纪律，你很有可能：

- 显著减少你的调试时间。
- 创建一系列近乎完美的低层文档。
- 创建一个你如此信任的测试套件，以至于当它通过时你可以部署。
- 创建一个耦合度更低的设计。

虽然这四件事是好的 ——事实上非常好—— 但它们不是我们遵循测试纪律的原因。

### 天使与魔鬼

在 [第 1 章](../ch1/0.d) “整洁代码” 中，我们讨论了制造混乱的成本。
我描述了日益增长的混乱如何降低生产力。
我介绍了童子军规则，并告诉你保持代码整洁是防止那种损失的唯一方法。

那么你如何保持代码整洁呢？

想象你正坐在电脑前，滚动浏览一些你需要处理的代码。
当你滚动时，你的脸色变得苍白，你意识到这段代码是一个天理难容的混乱，处理起来将是一场地狱。

就在这时，一个小天使出现在你的右肩上，用平静而微小的声音低语道：“你可以清理它。”

但随后，在一阵火焰中，一个魔鬼出现在你的左肩上，尖叫道：“不！不要碰它！如果你碰它，你会弄坏它；如果你弄坏它，它将永远属于你。哇哈哈哈哈！”

于是你无视了天使，从代码前退开。
你任其保持原状。
你把它留给别人去处理。
你任由它溃烂、腐烂，拖累整个团队的生产力。

这是一种恐惧反应。
你害怕去清理代码。

我希望你非常仔细地想一想，允许代码失控到令你感到恐惧的程度，是多么不专业和不负责任。
你是对它做出反应，而不是它对你做出反应。
你屈从于它的要求，而不是迫使它符合你的要求。
你，作为创造者，已经失去了对你造物的控制，成为了它奇思妙想的仆从。

因为那种恐惧，那个系统中的代码唯一可能发生的事情就是腐烂。
没有人敢于做可能逆转那种腐烂的唯一一件事 —— 清理。
于是它将继续下滑，每个月都变得更糟，并将团队的生产力一起拖垮。

如果你认为这是夸大其词，去和你认识的一些年长的程序员谈谈。
他们会告诉你的。

### 封住魔鬼的嘴

让我们再次回顾那个场景。
但这一次，假设团队一直在实践一种良好的测试纪律，并且已经建立了一个非常好的测试套件。

你坐在那里，看着屏幕，滚动浏览代码。
你看到那些糟糕的代码，当你凝视其恐怖的深处时，脸色变得苍白。

而且，正如所料，小天使用平静而微小的声音低语道：“清理它！”

而魔鬼没有出现。
魔鬼失去了力量。
因为你有了测试套件。

所以你做了一个小改动，也许只是一个变量的名称。
然后你运行测试。
测试通过了，你知道你没有破坏任何东西。
所以你做了另一个小改动，也许是将一个较长的函数拆分成两个。
再次，测试通过了。
所以你将其中一个新函数移动到一个不同的类，测试失败了！
所以你迅速还原，看到测试通过了。
然后，你意识到你的错误，你再次移动了该函数，但这次是正确的，测试通过了。

如果你有一个测试套件，并且你信任那个测试套件，并且那个测试套件运行得很快，那么你将会清理代码。
你会清理，因为清理代码几乎没有风险。
而且不仅仅是你清理代码 —— 团队中的每个人都会清理代码。
团队中的每个人都会遵循童子军规则，不断提高代码质量，保持高生产力。

### 复杂性与漏洞

如果最后的讨论听起来好得令人难以置信，那确实如此。
哦，对于系统的很大一部分来说，它可能是真的；但魔鬼仍然藏在细节中。
有些情况下，编写测试要么是不可能的，要么至少是不切实际的。

例如，为在机器硬件边界之外通信的代码编写测试是不切实际的，
如果不是完全不可能的话。
例如，除非你以某种方式使用一个盯着屏幕的摄像头，否则测试图形用户界面的最终输出是不可能的。
测试鼠标的移动，或者通过 socket 进出的数据也是如此。
对这些东西进行自动化测试并非完全不可能；但在大多数情况下，编写它们是非常不切实际的。

因此，经验丰富的开发人员将设计他们的系统，使得那些不可测试的代码片段非常薄。
他们将尽可能多的智能移离硬件边界，并确保最终接触那些边界的代码尽可能地贫血。

这种技术被称为 *谦卑对象模式 (The Humble Object Pattern)* 。⁶
我在我的书《Clean Craftsmanship》中更详细地讨论了这类情况。

⁶ http://xunitpatterns.com/Humble%20Object.html

当使用第三方框架时，也可能出现另一种复杂情况。
如果一个框架不是为了可测试性而编写的，那么使用该框架的代码也可能不切实际地进行测试。
同样，优秀的设计师会预见到这一点，并尝试将尽可能多的智能推离框架，在框架和需要测试的代码之间建立一个隔离层。
在选择框架时应谨慎，因为它们有可能阻止非常大范围的代码被正确测试。

> **经验报告：** 我最近写了一个使用 Java Swing 框架的重要应用程序。
尝试测试任何接触 Swing 的代码都是不切实际的。
我不得不将应用程序分为一个可测试的组件和一个不可测试的（Swing）组件。
那个不可测试的组件变得相当大，因为 Swing API 强制构建大型的、相互连接的数据结构，其中包含回调。
这使我的应用程序的测试覆盖率约为 70%。我可以轻松地重构可测试的组件；但接触 Swing 组件总是非常冒险。
我不会再使用 Swing 了。

当你在编写一个函数，但你不知道那个函数的正确结果时，还会出现另一种复杂情况。
例如，测试字体看起来是否 “正确”，或者字段是否被 “正确地” 定位，或者报告的格式看起来是否 “好” 是困难的。
在所有这些情况下，结果都是主观的。
确定代码是否正确的唯一方法是查看结果并做出判断。
没有办法为此编写测试。
所以没有办法将代码和测试一起编写。
在事后很久才编写测试是否非常有帮助也值得怀疑，因为它所能做的就是固化一个主观的决定。

这三种情况是我遇到的仅有的测试不切实际的情况。
然而，很可能还有其他情况。
例如，你如何测试 AI 的结果？

最终，当面对系统中不切实际进行测试的区域时，尝试使这些区域尽可能小和简单，并保护系统的其余部分免受它们的影响。

### 成本与影响

如果我们遵循这些纪律，我们将每天编写几十个测试，每月几百个测试，每年几千个测试。
这些测试将覆盖几乎所有生产代码。
这些测试的巨大数量，可能与生产代码本身的大小相当，可能会带来一个令人生畏的管理问题。
