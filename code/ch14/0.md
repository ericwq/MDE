# 第 14 章 测试纪律

<center><img src="../imgs/fig-ch14-0.png" width="40%" /></center><br/>

在过去的三十年里，我们的职业已经取得了长足的进步。
在 1997 年，没有人听说过像 TDD ¹ 或 TCR ² 这样的测试纪律。
对于我们中的绝大多数人来说，单元测试是我们为了确保程序 “工作” 而编写的一些短的、一次性的代码。
我们会煞费苦心地编写我们的类和方法，然后我们可能会炮制一些临时代码来测试它们。
通常，这涉及某种简单的驱动程序，允许我们手动与我们编写的程序交互。

¹ 测试驱动开发。<br/>
² 测试 && 提交 || 还原。

我记得在 90 年代中期为一个嵌入式实时系统编写了一个 C++ 程序。
该程序是一个简单的计时器，具有以下签名：

```cpp
void Timer::ScheduleCommand(Command* theCommand, int milliseconds)
```

这个想法很简单；`Command` ³ 的 `execute` 方法将在指定的毫秒数之后在一个新线程中执行。
问题是如何测试它。

³ 参见 [GOF95](../bib.md#gof95) 中的命令模式。

我拼凑了一个简单的驱动程序，它监听键盘。
每按下一个字符键，它就会调度一个命令，该命令将在五秒后打印相同的字符。
然后，我在键盘上敲出一段有节奏的旋律，等待那段旋律在五秒后在屏幕上重播。

“我……想要一个女孩……就像……那个嫁……给……亲爱……的……老……爸爸的女孩。”

我实际上在敲击 “.” 键时唱了那段旋律，然后当点出现在屏幕上时我又唱了一遍。

那就是我的测试！
一旦我看到它工作并向同事们演示后，我就把测试代码扔掉了。

正如我所说，我们的职业已经取得了长足的进步。

如今，我编写的测试确保代码的每一个角落都如我所期望的那样工作。
我将代码与操作系统隔离，而不是创建对它的硬依赖。
如果我今天要写上面的例子，我会使用 *测试替身 (test doubles)* 来 “模拟” 操作系统的时间函数，以便我对时间有绝对的控制。
我会调度设置布尔标志的命令，然后我会使用我的测试来向前推进时间，观察那些标志，并确保它们在我将时间更改为正确的值时从 `false` 变为 `true`。

如今，一旦我让一组测试通过，我就会清理那些测试，以确保它们设计良好，并且与生产代码强解耦。
我还确保它们对于任何其他需要处理代码的人来说都是方便运行的。
我将代码和测试一起保存在同一个源包中。

在极限编程和敏捷的早期，我们只谈论一种测试纪律：TDD 。
当我写这本书的第一版时，TDD 是我介绍的唯一的测试纪律。
在随后的几年里，很明显还有其他与 TDD 一样有效或几乎一样有效的测试纪律。
也很明显，有许多程序员出于某种原因更喜欢那些其他纪律。

因此，虽然我将仍然是 TDD 纪律的坚守者，但我觉得谈论另外两种与编写整洁代码兼容的纪律是合适的。
而且，虽然我只讨论三种这样的纪律，但很可能还有其他的。
