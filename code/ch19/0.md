# 第 19 章 SOLID 原则

<center><img src="../imgs/fig-ch19-0.png" width="40%"></center><br/>

本章是我从《Clean Architecture》一书中大幅删减和编辑的摘录集。
它旨在为你提供本书其他地方提到的原则的快速参考，并为你提供进一步学习的指导。

良好的软件系统始于整洁的代码。
如果砖块制作不好，建筑的架构就无关紧要了。
另一方面，即使用制作精良的砖块，你也可能搞出一团糟。
这就是 SOLID 原则发挥作用的地方。

SOLID 原则告诉我们如何将函数和数据结构安排到类中，以及这些类应该如何相互连接。
使用 “类” 这个词并不意味着这些原则只适用于面向对象软件。
类只是函数和数据的一种耦合分组。
每个软件系统都有这样的分组，无论它们是否被称为类。
SOLID 原则适用于这些分组。

这些原则的目标是创建具有以下特征的中层软件结构：

- 容忍变化
- 易于理解
- 是可以在其他软件系统中使用的组件的基础

“中层” 这个术语指的是这些原则由工作在模块层面的程序员应用。
它们恰好在函数层面之上发挥作用，有助于定义模块和组件内部所使用的软件结构类型。

正如用精良的砖块也可能搞出一团糟一样，用设计良好的中层组件也同样可能制造出系统级的混乱。
因此，在我们介绍完 SOLID 原则之后，我们将讨论这些原则在组件层面的对应原则，然后在第三部分探讨高层架构的原则。

SOLID 原则的历史颇为悠久。
我在 20 世纪 80 年代末开始在 Usenet（一个早期的社交媒体平台）上与其他人辩论软件设计原则时，就开始将它们汇集起来。
多年来，这些原则不断演变和调整。
有些被删除了，有些被合并了，还有一些被添加进来。
最终的分组在 21 世纪初稳定下来，尽管我当时呈现的顺序有所不同。

然后，在 2004 年前后，Michael Feathers 给我发了一封电子邮件，说如果我重新排列这些原则，它们首字母的缩写将拼成单词 *SOLID* 。
就这样，SOLID 原则诞生了。
接下来的章节将详细描述每个原则。
以下是其概要：

-  *SRP——单一职责原则 (Single Responsibility Principle)* ：
软件系统的最佳结构受到使用它的组织的社会结构的强烈影响，因此每个软件模块只有一个且仅有一个需要被改变的理由。

- *OCP——开闭原则 (Open–Closed Principle)* ：
Bertrand Meyer 在 80 年代使这一原则广为人知。
其要点是：为了使软件系统易于修改，它们必须被设计成允许通过添加新代码来改变系统的行为，而不是修改现有代码。

- *LSP——里氏替换原则 (Liskov Substitution Principle)* ：
这是 Barbara Liskov 于 1988 年提出的关于子类型的著名定义。
简而言之，该原则指出：为了用可互换的部件构建软件系统，这些部件必须遵守一个契约，使得它们能够相互替换。

- *ISP——接口隔离原则 (Interface Segregation Principle)* ：
该原则建议软件设计者避免依赖他们不会使用的东西。

- *DIP——依赖反转原则 (Dependency Inversion Principle)* ：
该原则指出，实现高层策略的代码不应依赖于实现低层细节的代码。
相反，低层细节应该依赖于高层策略。

多年来，这些原则已在许多不同的出版物 ¹ 中被详细描述。
接下来的章节并非旨在取代那些详细的著作。
如果你对这些原则尚不熟悉，接下来的内容将是一个很好的介绍，但不足以让你深入理解。
