## 使用意图明确的命名

变量、函数或类的名称应该回答所有重大问题。
它应该告诉受众它为什么存在、它做什么以及它如何被使用。

如果一个名称需要注释来向受众传达信息，那么这个名称就没有揭示其意图。

```java
int d; // 以天为单位的经过时间
```

名称 `d` 揭示的内容很少。
它没有唤起经过时间的感觉；特别是天的概念。
我们应该选择一个能说明被测量的是什么以及测量单位的名称。
以下之一可能会更好：`elapsedDays`、`daysSinceCreation`、`daysSinceModification` 或 `fileAgeInDays`。

这些示例比原始名称 (`d`) 更长，但这并不一定意味着长名称比短名称好，只意味着清晰的名称比不清晰的名称好。
例如：

```java
int d = getElapsedTimeInDays();
```

这里名称完全清晰，因为它由上下文定义，并且如果包含该名称的作用域相对较小，则它是合适的。
（参见 [使用适当长度的名称](#todo)。）

### 构建一套命名体系

选择能够揭示意图的命名可以极大地简化理解和修改代码的过程。
以下是一个违反此规则的示例。你能确定这段代码的目的吗？

```java
public List<int[]> getThem() {
    List<int[]> list1 = new ArrayList<int[]>();
    for (int[] x : theList)
        if (x[0] == 4)
            list1.add(x);
    return list1;
}
```

为什么很难看出这段代码在做什么？
这里没有复杂的表达式。
间距和缩进都很合理。
只提到了三个变量和两个常量。
甚至没有任何花哨的类或多态方法，只是一个数组列表（或者看起来如此）。

问题不在于代码的简单性。
问题在于代码没有提供任何上下文。
这段代码隐含地要求我们知道以下问题的答案：

- `theList` 中是什么类型的东西？
- 下标 `0` 代表什么？
- 值 `4` 的含义是什么？
- 我将如何使用返回的列表？

这些问题的答案在代码示例中并不存在。
然而，一个好的命名体系会使它们变得清晰。

假设这段代码来自旧的扫雷游戏。¹ 
扫雷游戏的棋盘是一个名为 `theList` 的单元格列表。
让我们将其重命名为 `gameBoard`。

¹ 一款 90 年代随 Windows 3.11 一起发行的游戏。

棋盘上的每个单元格由一个基本数组表示。
下标 `0` 是状态值的位置，而状态值 `4` 表示 “已标记”。
仅仅通过为这些概念命名，我们就可以显著改进代码：

```java
public List<int[]> getFlaggedCells() {
    List<int[]> flaggedCells = new ArrayList<int[]>();
    for (int[] cell : gameBoard)
        if (cell[STATUS_VALUE] == FLAGGED)
            flaggedCells.add(cell);
    return flaggedCells;
}
```

请注意，代码的简单性没有改变。
只有清晰度得到了提高。

它仍然有完全相同数量的操作符和常量，以及完全相同数量的嵌套层级。
但通过命名，代码变得更加明确。

还要注意，如果这是你遇到的第一段代码，你也会知道这是一个游戏，有一个包含状态的单元格棋盘，其中一种状态是 “已标记”。
一个好的命名体系可以传达关于整个应用程序的大量信息。

我们甚至可以更进一步，为单元格编写一个简单的类，而不是使用 `int` 数组。
它可以包含一个意图明确的函数（称之为 `isFlagged`）来隐藏魔数。
这产生了一个新版本的函数：

```java
public List<Cell> getFlaggedCells() {
    List<Cell> flaggedCells = new ArrayList<Cell>();
    for (Cell cell : gameBoard)
        if (cell.isFlagged())
            flaggedCells.add(cell);
    return flaggedCells;
}
```

通过这些简单的名称更改，理解正在发生的事情并不困难。
这就是选择好名称的力量。

### 避免误导

程序员必须避免留下掩盖代码含义的错误线索。
例如，除非它实际上是一个 `List`，否则不要将一组账户称为 `accountList`。

<ins>词语 `list` 对程序员有特定的含义</ins>。
如果容纳账户的容器是一个数组或 JSON 文档，它可能会导致错误的结论。² 
因此，`accountGroup`、`bunchOfAccounts` 或只是简单的 `accounts` 可能会更短（因此更容易一目了然）且更诚实。

² 正如我们稍后将看到的，即使容器是一个 `List`，也可能最好不要将容器类型编码到名称中。

<ins>要警惕使用差异很小的名称</ins>。
在一个模块中看到一个名为 `XYZControllerForEfficientHandlingOfStrings` 的东西，而在稍远的地方看到 `XYZControllerForEfficientStorageOfStrings`，你需要多长时间才能发现它们之间的细微差别？
这些词语的形状非常相似。
如果它们不紧挨在一起，你能意识到它们是不同的吗？

这些名称之所以特别难以区分，是因为它们既长又有相似的开头。
你能发现下面这个视觉错觉吗？

```
XYZControllerForEfficientHandlingOfStrings
XXZControllerForEfficientHandlingOfStrings
```

用一致的拼写来表示相似的概念是一种信息。
使用不一致的拼写则是误导。
在现代环境中，我们享有自动代码补全的便利。
我们输入名称的几个字符，很快就会得到一个该名称的可能补全列表。
不一致的拼写会扰乱那个列表。

现代环境还通过为不同的语法元素使用不同的字体、样式和颜色来提供帮助。
尽管如此，小心我们字体中固有的一些视觉错觉仍然是明智的。
例如，要注意小写字母 `l` 和大写字母 `O` 的使用。
在某些字体中，它们可能分别与常量 `1` 和 `0` 无法区分。

```java
int a = l;
if ( O == l )
    a = O1;
else
    l = 01;
```

将这些字母与数字和 `x` 结合会使情况变得更糟。
考虑将 `Oxll` 作为一个名称。

### 做出有意义的区分

当程序员仅仅为了满足编译器或解释器而编写代码时，他们给自己制造了问题。
例如，当你想要在同一作用域中使用相同的名称来指代两个不同的东西时，你可能会试图随意地改变一个名称以保持它们不同。
有时这是通过拼错一个名称来实现的，导致一个令人惊讶的情况：纠正拼写错误会导致无法编译。³

³ 例如，考虑一种真正丑陋的做法：仅仅因为 `class` 这个名称被用于其他东西，就创建一个名为 `klass` 的变量。

仅仅添加数字序列或噪声词是不够的，即使编译器满意了也不行。
如果名称必须不同，那么它们也应该意味着不同的东西。

数字序列命名（`a1`、`a2`、…… `aN`）是有意命名的反面。
这样的名称不是提供误导信息，而是不提供任何信息；它们没有提供任何关于作者意图的线索。
考虑：

```java
public static void copyChars(char a1[], char a2[]) {
    for (int i = 0; i < a1.length; i++) {
        a2[i] = a1[i];
    }
}
```

当使用 `source` 和 `destination` 作为参数名称时，这个函数读起来会好得多。

一般来说，当你看到名为 `X1`、`X2`、`X3` 的变量时，代码几乎是在恳求你要么使用一个数组，要么使用一个数据结构。
考虑一下是什么使它们如此相似，以至于它们有相同的名称而只有数字上的差异，并寻找一些能够激发不同名称或完全不同的结构的含义。

在上面的代码中，这只是懒惰的命名。
将这些名称改为 `source` 和 `destination` 比试图创建一个结构、类或容器提供了更好的解决方案。
并非所有问题都是深奥的。

噪声词是另一种无意义的区分。
想象你有一个 `Product` 类。
如果你还有另一个名为 `ProductInfo` 或 `ProductData` 的类，你让名称变得不同，但没有让它们意味着任何不同的东西。
`Info` 和 `Data` 是模糊的噪声词。
它们没有添加新信息，因为每个类都包含 “数据”，每个类都包含 “信息”。

噪声词是冗余的。
`variable` 这个词永远不应该出现在变量名中。
`table` 这个词永远不应该出现在表名中。
`NameString` 比 `Name` 好在哪？
`Name` 会是一个浮点数吗？
如果是，它很可能违反了之前关于误导的规则。
想象一下找到一个名为 `Customer` 的类和另一个名为 `CustomerObject` 的类。
你应该理解它们之间的区别是什么？
哪一个代表了到达客户支付历史的最佳路径？

以下是我们在一个特定应用程序中发现的一些令人不安的无意义函数名称：

```java
getActiveAccount();
getActiveAccounts();
getActiveAccountInfo();
```

这个项目中的程序员怎么知道该调用这些函数中的哪一个？
有多少个活跃账户？
第一个函数返回了哪些？
第二个和第三个函数之间的区别是什么？
在任何情况下，这种命名 “体系” 都是一场噩梦。

### 使用可发音的名称

人类擅长使用词语。
我们大脑的很大一部分专门用于处理词语的概念。
而且，根据定义，词语是可发音的。
不利用我们大脑中那一大块进化出来处理口头语言的部分将是一种遗憾。
所以要让你的名称可发音。

如果你无法发音，你就无法方便地讨论它。
“嗯，在这里，在 bee cee arr three cee enn tee 上，我们有一个 pee ess zee kyew int，看到了吗？”
讨论的便利性很重要，因为编程是一种社交活动。

一家公司有一个名为 `genymdhms`（生成日期、年、月、日、时、分、秒）的变量，所以他们到处都说 “gen why emm dee aich emm ess”。
这很不方便，所以发音逐渐演变成了 “gen-yah-mudda-hims”。
这可能听起来很傻，但他们都理解这个玩笑，所以很有趣。

不管有趣与否，他们都在容忍糟糕的命名。
新开发人员必须向他们解释这些变量，然后他们用这些愚蠢的、编造的词语来谈论它，而不是使用正确的英语术语。

对比：

```java
class DtaRcrd102 {
    private Date genymdhms;
    private Date modymdhms;
    private final String pszqint = "102";
```

和：

```java
class Customer {
    private Date generated;
    private Date modified;
    private final String recordId = "102";
```

现在可以进行有意义的对话了：“嘿，Mikey，看看这条记录！生成时间戳被设置为明天的日期！这怎么可能？”

### 使用可搜索的名称

单个字母的名称和数字常量有一个特殊的问题，它们不容易在文本体中被定位。
人们可以很容易地 `grep` 查找 `MAX_CLASSES_PER_STUDENT`，但数字 `7` 可能更麻烦。
搜索可能会将数字作为文件名的一部分、其他常量定义以及以不同意图使用该值的各种表达式中出现。
当常量是一个长数字，并且有人可能调换了数字时，情况会更糟，从而在避开程序员搜索的同时制造了一个错误。

同样，名称 `e` 不是一个可搜索的名称。
它是英语中最常见的字母，很可能出现在每个程序的每一段文本中。

一般来说，短名称不如长名称可搜索，这是当涉及到可搜索性时，长名称可以胜过短名称的又一个原因，而且任何可搜索的名称都胜过代码中的常量。

名称 `e` 通常用于表示在 `try/catch` 块中引发的特定错误，尤其是在 Python 和 Go 中。
然而，在这种情况下，该名称在其上下文中对许多程序员来说是熟悉的，并且它出现在如此小的作用域中，以至于使得搜索变得不必要。
在有限且众所周知的情况下，短名称通常不会干扰搜索。

我们的偏好是，非常短或单字母的名称只应被用作非常短的作用域内的局部变量。
如果一个变量或常量可能在代码体中的多个地方被看到或使用，最好给它一个便于搜索的名称。
再次对比：

```java
for (int j=0; j<34; j++) {
    s += (t[j]*4)/5;
}
```

和：

```java
int realDaysPerIdealDay = 4;
const int WORK_DAYS_PER_WEEK = 5;
int sum = 0;
for (int j=0; j < NUMBER_OF_TASKS; j++) {
    int realTaskDays = taskEstimate[j] * realDaysPerIdealDay;
    int realTaskWeeks = (realTaskDays / WORK_DAYS_PER_WEEK);
    sum += realTaskWeeks;
}
```

注意，上面的 `sum` 并不是一个特别有用的名称，但至少它是可搜索的。
经过有意命名的代码使函数变得更长，但考虑一下找到 `WORK_DAYS_PER_WEEK` 比找到所有使用了 `5` 的地方并将列表过滤到仅具有预期含义的实例要容易得多。

### 使用适当长度的名称

我们关于名称长度的规则可能会让你感到惊讶，但它们经受住了时间的考验。

#### 变量名称

<ins>对于变量的名称，我们有一条简单的规则。变量名的长度应该与包含它的作用域的长度成正比</ins>。
例如：

```java
for (int n=0; n<20; n++)
    System.out.println("" + n + " " + n*n);
```

名称 `n` 是适当短的，因为它的作用域只有两行长。
如果那个变量被命名为 `theNumberToBeSquared`，我们会感到恼火。

另一方面，在更长的作用域中，这样短小的名称可能会变得晦涩。
我们通常会认为一个名为 `n` 的实例变量令人恼火；特别是如果 `m`、`p`、`i` 和 `j` 也是实例变量的话。

随着作用域大小的增加，该作用域内变量名称的长度也应该增加。
参数和局部变量的作用域限定在单个函数内，因此应该有相对较短的名称；也许一个或两个词。

<ins>实例变量的作用域限定在整个类中。
它们的名称应该相对较长。全局变量名应该更长</ins>。

#### 函数名称

<ins>我们对函数的规则正好相反。
它们名称的长度应该与它们作用域的长度成反比。
因此，全局函数将具有短名称，而类中的私有方法将具有相对较长的名称</ins>。
测试，它们的作用域是所有中最短的（实际上为零），拥有最长的名称。

我们以两种方式证明这一点。
首先，函数的作用域越大，它被使用的频率就越高。
因此，为了方便起见，我们希望名称短一些。
如果打开文件的函数被命名为 `openFileAndThrowExceptionIfNotFound` 而不是 `open`，我们会感到相当恼火。

其次，函数的作用域越大，它就越通用。
同样，`open` 是一个非常通用的函数。
类中的方法具有更窄的上下文，因此可能需要更多的词语来解释它们的意图。
类中的私有方法具有非常小的作用域，并且只从很少的地方（甚至只有一个地方）被调用。
它们根本不通用，因此可能需要很多词语来恰当地描述它们。
它们的名称应该相应地更长。

#### 类名称

<ins>我们对类的规则与对函数的规则相同。
作用域越长，名称越短。
全局作用域中的类应该有相对较短的名称（一两个词），而派生类、内部类和私有类应该有更长的名称</ins>。

#### 属性和特性名称

有些语言，如 C++ 和 C#，具有看起来像变量但实际上却是函数的元素。
它们看起来像变量，因为它们可以放在赋值语句的左边。
因此，它们应该遵循变量命名规则。
它们名称的长度应该与包含它们的作用域成正比。

#### 命名空间名称

现在大多数语言都允许我们将类、函数和变量放入命名空间中。
命名空间名称应该是描述性的。
因此，它们可能会比较长，并且通常是命名空间层级结构的一部分。
例如，考虑 Uncle Bob 几年前编写的一个太空战争游戏⁴ 中的命名空间：`spacewar.ui.tactical-scan`。
这样长而限定的名称通常不方便，这就是为什么大多数有命名空间的语言都有一些方法可以在较小的作用域内创建命名空间别名。

⁴ https://github.com/unclebob/spacewar

因此，虽然命名空间名称的长度不是包含它们的作用域的函数，但它们的别名的长度是。
在一个非常短的模块中，我们可能使用别名 `ts`，而在一个较长的模块中，我们可能使用 `tac-scan`，在一个非常长的模块中（这种情况应该很少），我们可能使用 `tactical-scan`。

### 避免编码

我们有足够多的编码需要处理，无需再增加负担。
将类型或作用域信息编码到名称中，只会增加额外的解码负担。
要求每个新员工除了学习（通常相当庞大的）代码体外，还要学习另一种编码 “语言”，这似乎不太合理。
最重要的是，编码后的名称很少是可发音的，而且容易打错。

在过去，当我们使用受名称长度限制的语言工作时，我们出于无奈且带着遗憾地违反了这条规则。
Fortran 通过使第一个字母成为类型的代码来强制编码。
早期版本的 BASIC 只允许一个字母加一个数字。
匈牙利命名法⁵ (HN) 将这一点提升到了一个全新的水平。

⁵ 之所以这样命名，是因为它是由 Charles Simonyi 发明的，他是 DOS 时代微软的一位匈牙利出生的架构师。

HN 在 Windows C API 时代被认为相当重要，那时所有东西都是一个整数句柄、一个长指针、一个空指针，或者是 “字符串” 的几种实现之一（具有不同的用途和属性）。
那时的 C 编译器不检查类型，所以程序员需要一个拐杖来帮助他们记住类型。

在现代语言中，我们有更丰富的类型系统，编译器会记住并强制检查类型。
更重要的是，有一种趋势是趋向于更小的类和更短的函数，这样人们通常可以看到他们使用的每个变量的声明点。

今天的程序员从他们的编译器和 IDE 中获得了足够的帮助，他们通常不需要在变量名中编码类型。
所以如今，HN 和其他形式的类型编码仅仅是障碍。
它们使得更改变量、函数或类的名称或类型变得更加困难。
它们使得阅读代码变得更加困难。
而且它们制造了编码系统可能误导读者的可能性。

```java
PhoneNumber phoneString;
// 类型更改时名称未更改！
```

#### 成员前缀

用类似 `m_` 这样的前缀来标记成员变量是另一种不再必要的类型编码形式。
你的类和函数应该足够小，以至于你不需要这样的拐杖。
你应该使用一个能够突出显示或着色成员以使它们与众不同的编辑环境。

```java
public class Part {
    private String m_dsc; // 文本描述
    void setName(String name) {
        m_dsc = name;
    }
}
```

对比：

```java
public class Part {
    String description;
    void setDescription(String description) {
        this.description = description;
    }
}
```

#### 接口与实现

我们不建议用 `I` 作为接口的前缀，因为那只是另一种类型编码。
例如，假设你正在构建一个用于创建 Shape 的抽象工厂⁶。
这个工厂将是一个接口，并由一个具体类实现。
我们应该如何命名这些类？
`IShapeFactory` 和 `ShapeFactory`？
我们更喜欢让接口不加修饰。
前面的 `I` 往好里说是分散注意力，往坏里说是信息过载。
毕竟，接口的全部意义在于用户不需要知道它是一个接口。
我们只想让他们知道它是一个 `ShapeFactory`。
<ins>所以，如果我们必须对接口或实现进行编码，我们更倾向于给实现添加后缀；例如，`ShapeFactoryImp`</ins>。

⁶ [GOF95]。

### 使用适当的词性

我们代码中的一些元素最好由名词表示，另一些则由动词表示。

#### 类名称

<ins>类和对象通常应该有名词或名词短语名称，如 `Customer`、`WikiPage`、`Account` 和 `AddressParser`。
通常，名词应该是单数而不是复数</ins>。
代表客户（customer）的类应该被命名为 `Customer` 而不是 `Customers`。
另一方面，一个持有许多 `Customer` 实例的类可能应该被称为 `Customers`。

避免在类名中使用像 `Manager`、`Processor`、`Data` 或 `Info` 这样的噪声词。
我们已经知道类管理和处理数据和信息 —— 你不需要告诉我们。

#### 方法名称

<ins>方法通常应该有动词或动词短语名称，如 `postPayment`、`deletePage` 或 `save`</ins>。

根据你的语言，访问器、修改器和谓词应该按照本地惯例命名。
在 Java 中，它们根据 JavaBeans 标准⁷ 以其值为名，并加上 `get`、`set` 和 `is` 前缀。

⁷ http://java.sun.com/products/javabeans/docs/spec.html

在某些语言中，存在一种事实上的惯例，即根据函数返回的值来命名函数，即作为名词。
例如，返回客户名称的函数可能被称为 `name`。
我们不偏好这种惯例，但当与使用它的团队合作时，我们会遵循它。

在大多数情况下，最好将修改器命名为它所引起的修改，例如 `add`、`remove`、`sort` 等等。
这些往往是动词名称，因此标准的建议是 “用动词名称命名方法”。

```java
string name = employee.getName();
customer.setName("mike");
if (paycheck.isPosted())…
```

C++、Java 和 C# 有以类名命名的构造函数。
这意味着你不能给构造函数一个有意义的名称。
当这样的构造函数被重载时，最好使用静态工厂方法，其名称描述参数。例如：

```java
Complex fulcrumPoint = Complex.FromRealNumber(23.0);
```

通常比

```java
Complex fulcrumPoint = new Complex(23.0);
```

更好。
考虑通过将相应的构造函数设为私有来强制使用它们。

### 考虑关键字参数

如果你的语言允许关键字参数或哈希映射参数，例如 Python、C#、Ruby 和 Clojure，你可能会发现最好限制函数的位置参数，并为大多数变体使用显式的仅关键字参数。

```python
def sort(iterable, *, key=None, reverse=False):
    … # 函数体省略

pets_sorted = sort(pets)
pets_reversed = sort(pets, reverse=True)
pets_by_age = sort(pets, key=lambda x: x.birthdate())
```

### 不要耍小聪明

如果名称太花哨，它们只会被那些与作者有相同幽默感的人记住，而且只有当他们还记得那个玩笑时才会记住。
他们会知道名为 `HolyHandGrenade` 的函数应该做什么吗？
当然它很可爱，但也许在这种情况下，`DeleteItems` 是一个更好的名称。
选择清晰性而不是娱乐价值。

代码中的小聪明通常以口语或俚语的形式出现。
例如，不要用 `whack()` 来表示 `kill()`。
不要讲像 `eatMyShorts()` 这样依赖于文化的小笑话来表示 `abort()`。

说你想说的。
表达你真正的意思。

### 每个概念选一个词

为一个概念选择一个词，并坚持使用它。
例如，不要在一个模块中使用 `amount`，在另一个模块中使用 `fee`，在第三个模块中使用 `price`，在第四个模块中使用 `cost`。
为每个概念选择一个名称，并在整个过程中使用它。
确保团队中的每个人都知道这些名称。

我们经常会审计系统中的名称以确保一致性。
这是一项小任务，而且通常 IDE 会提供 “大纲视图” 或 “对象视图” 选项，或者 “折叠/折叠所有函数”，以便你可以查看方法和变量名而无需滚动。
我们强烈建议协调给定类、模块或测试套件中的所有名称。
我们相信，你会发现这很令人满意。

一个一致的词汇表（ 通用语言 (Ubiquitous Language)⁸ ）对那些必须使用你代码的程序员来说是一个巨大的福音。

⁸ [DDD]。

### 使用解决方案领域名称

请记住，阅读你代码的人将是程序员。
他们会熟悉解决方案领域的术语。

当你在领域层面之下并进入纯粹的实现时，可以继续使用计算机科学 (CS) 术语、算法名称、模式名称、数学术语等等。
不从问题领域提取每个名称是明智的，因为我们不希望我们的同事为了了解他们已经以不同名称知道的概念，而不得不来回找客户询问每个名称的含义。

对于熟悉 Visitor⁹ 模式的程序员来说，名称 `AccountVisitor` 意味着很多东西。
哪个程序员会不知道 `JobQueue` 或 `FIFO` 是什么？

⁹ [GOF95]。

程序员有很多非常技术性的事情要做。
为做技术性的事情选择技术性名称通常是最合适的做法。
程序通常最好用编程来描述。
你不必让所有东西看起来都像英语散文或数学公式。
使用最适合算法和受众的抽象级别。

### 使用问题领域名称

使用来自问题领域的名称。
它们可能是熟悉的，并有助于为团队中的开发人员设置上下文。
如果不是，那么至少维护你代码的程序员可以询问领域专家它的含义。

分离解决方案和问题领域概念是优秀程序员和设计师工作的一部分。
与问题领域概念更相关的代码应该拥有来自问题领域的名称。
我们不会将解决方案领域名称强加于问题，也不会将问题领域名称强加于解决方案。

### 添加有意义的上下文

有一些名称本身是有意义的 —— 大多数不是。
相反，你需要通过将名称封装在命名良好的类、函数或命名空间中，为读者提供上下文。

想象你有名为 `firstName`、`lastName`、`street`、`houseNumber`、`city`、`state` 和 `postcode` 的变量。
综合起来，很明显它们形成了一个地址。
但如果你只是在一个方法中单独看到 `state` 变量呢？
你会自动推断它是地址的一部分吗？
还是会推断你正处于一个有限状态机中，并追踪该机器当前处于哪个状态？

你可以通过创建一个名为 `Address` 的类或数据结构来消除这种歧义。
然后，即使是编译器也会知道这些变量属于一个更大的概念。

程序员有时会陷入 *基本类型偏执 (Primitive Obsession)* ¹⁰ 的代码坏味中，过长时间地避免创建类、结构和模块。
例如，处理 `GlobalLocations` 比处理以小时、分钟和秒表示的纬度和经度的基本类型变量要好得多。
处理两个 “位置” 比处理 12 个名称相似的浮点整数要容易得多。

¹⁰ [Refactoring] 中的代码坏味之一。

作为另一个例子，考虑下面的 Python 代码。
这些变量是否需要更有意义的上下文？
函数名只提供了部分上下文；算法提供了其余部分。

```java
private void printGuessStatistics(char candidate, int count) {
    String number;
    String verb;
    String pluralModifier;
    if (count == 0) {
        number = "no";
        verb = "are";
        pluralModifier = "s";
    } else if (count == 1) {
        number = "1";
        verb = "is";
        pluralModifier = "";
    } else {
        number = Integer.toString(count);
        verb = "are";
        pluralModifier = "s";
    }
    String guessMessage = String.format(
        "There %s %s %s%s", verb, number, candidate, pluralModifier
    );
    print(guessMessage);
}
```

一旦你通读了这个函数，你会看到三个变量 ——`number`、`verb` 和 `pluralModifier`—— 是 “猜测统计” 消息的一部分。
不幸的是，上下文必须被推断。
当你第一次看到这个方法时，这些变量的含义是不透明的。

这个函数有点太长，而且变量被到处使用。
为了将函数拆分成更小的部分，我们需要创建一个 `GuessStatisticsMessage` 类，并使这三个变量成为该类的字段。
这为三个变量提供了一个清晰的上下文。
它们明确地属于 `GuessStatisticsMessage`。
上下文的改进还允许通过将算法分解成许多更小的函数来使其更加清晰。

```java
public class GuessStatisticsMessage {
    private String number;
    private String verb;
    private String pluralModifier;

    public String make(char candidate, int count) {
        createPluralDependentMessageParts(count);
        return String.format(
            "There %s %s %s%s",
            verb, number, candidate, pluralModifier );
    }

    private void createPluralDependentMessageParts(int count) {
        if (count == 0) {
            thereAreNoLetters();
        } else if (count == 1) {
            thereIsOneLetter();
        } else {
            thereAreManyLetters(count);
        }
    }

    private void thereAreManyLetters(int count) {
        number = Integer.toString(count);
        verb = "are";
        pluralModifier = "s";
    }

    private void thereIsOneLetter() {
        number = "1";
        verb = "is";
        pluralModifier = "";
    }

    private void thereAreNoLetters() {
        number = "no";
        verb = "are";
        pluralModifier = "s";
    }
}
```

### 不要添加不必要的上下文

在一个名为 Gas Station Deluxe 的虚构应用程序中，给每个类添加 `GSD` 前缀是一个坏主意。
坦率地说，你是在与你的工具作对。
你输入 `G` 并按补全键，结果得到系统中每个类的一长串列表。
这明智吗？
为什么要让 IDE 难以帮助你？

同样，假设你在 GSD 的会计模块中发明了一个 `MailingAddress` 类，并将其命名为 `GSDAccountAddress`。
后来，你需要为客户联系应用程序提供一个邮寄地址。
你会使用 `GSDAccountAddress` 吗？
它听起来像正确的名称吗？
17 个字符中有 10 个是多余的或无关的。

名称 `accountAddress` 和 `customerAddress` 作为 `Address` 类的实例是不错的名称，但作为类名可能是不好的。
`Address` 是一个不错的类名。
如果我们需要区分 MAC 地址、端口地址和 Web 地址，我们可以考虑 `PostalAddress`、`MAC` 和 `URI`。
由此产生的名称更加精确，这正是所有命名的意义所在。
