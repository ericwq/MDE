名称在软件中无处不在。
我们命名变量、函数、参数、类和包。
我们命名源文件和包含它们的目录。
我们命名 jar 文件、dll 文件和 gem 文件。
我们不停地命名和命名；正因为我们做了这么多，我们最好把它做好。

看起来命名是如此主观，以至于定义 “好” 的原则似乎是徒劳的。
然而，尽管它们具有主观性，我们知道好的餐厅、好的电影、好的绘画和好的书籍。

<ins>主观性被这样一个认识所调和：任何作品只要被其受众接受，它就是好的。
这意味着我们不是在处理个人的偏好和偏见，而是处理集体受众的期望</ins>。

本书的受众是一群对改进他们的代码技艺足够感兴趣，以至于购买、借阅或以其他方式获取本书副本的程序员。
如果这些文字能触达你并帮助你，那么我们就以足够好的方式写出了足够好的文字。

作为代码的作者，你的受众是那些将在你的代码库中工作的人。
你不仅是一位作者，也是代码库社区的一员。
受众比你更大，他们将共同决定在代码库中什么是受欢迎的，什么是不受欢迎的。

<ins>为你的受众编写，而不是为你自己。
你必须记住，你编写代码的经验不如他们阅读代码的经验重要，也不如它持久</ins>。

话虽如此，我们发现不同受众之间存在相当一致的偏好范围，而这份通用建议旨在帮助你找到当前软件受众的 “最佳点”。

选择好的名称需要时间，但节省的时间比花费的更多。
所以要注意你的命名，并在找到更好的名称时更改它们。
如果你这样做，每个阅读你代码的人（包括你自己）都会更开心。
