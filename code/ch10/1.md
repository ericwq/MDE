## 提取方法重构

你的 IDE 有 “Refactor” 菜单吗？
我的有。
其中一个菜单项是 “Extract Method” 。
IDE 有这个菜单项已经二十年了。
我相信你们都使用过它。
但以防万一，让我为你描述一下。

如果你看到一个有点太大的函数，并且你决定要把它拆分成两个函数，你可以用鼠标选择你想从父函数中拉出（提取）的代码。¹ 
然后，你选择 “Extract Method” 重构，然后会弹出一个对话框，询问你想要为新函数起什么名字。
该对话框还会告诉你它计划向新函数传递什么参数，以及它计划返回什么。
该对话框给你提供了更改其中一些内容的选项。
当你准备好时，你点击那个对话框上的 “Refactor” 按钮，IDE 就会从原始函数中剪切选定的代码，并用对新函数的调用替换它。
然后，它将选定的代码粘贴到那个新函数中，并创建允许它被调用的胶水代码。

¹ 在 1974 年，没有一个程序员能理解这句话。四十年前，有些人可能有一丝理解。

我的意思是……这太神奇了！

那么，“一件事” 是什么意思呢？

> 如果你不能有意义地从中提取另一个函数，那么一个函数就只做一件事。

好的，现在暂且忽略 “有意义地” 这个词，思考一下那个陈述。
你能反驳它吗？
我认为你不能。
<ins>如果你能把一个函数拆分成两个，那么原始函数就做了两件事。
所以，一个只做一件事的函数，就是你无法从中提取另一个函数的函数</ins>。

好的，现在，在这个上下文中，“有意义地” 这个词是什么意思？
考虑这个函数：

```java
public void addRental (Rental rental) {
    rentals.addElement (rental);
}
```

将这个函数的主体提取到一个新函数中是没有意义的：

```java
public void addRental (Rental rental) {
    doTheAdd(rental);
}

public void doTheAdd (Rental rental) {
    rentals.addElement (rental);
}
```

提取一个函数的整个主体，只留下一个纯粹的委托器，是没有意义的。² 
这样的提取不是有意义的。

² 除了那些你正在创建一个委托器以便将提取的函数移动到一个新模块的罕见情况。

或者考虑这个函数：

```java
void clearTotals() {
    totalAmount=0;
    renterPoints=0;
}
```

将这两行提取到两个不同的函数中几乎肯定是没有意义的：

```java
void clearAmount() {totalAmount=0;}
void clearPoints() {renterPoints=0;}
```

这已经将提取做得过火了。
`clearAmount` 和 `clearPoints` 函数的名称与它们的实现无法区分。
<ins>一个有意义的抽象是遵循步降规则 (The Stepdown Rule) 的抽象，其中函数的名称比实现更抽象</ins>。

我将把 “有意义” 这个词的其余解释留给你。
只需说，你可能提取得太少，也可能提取得太多。

<ins>那么我们如何确保我们所有的函数都只做一件事呢？
我们提取，再提取，直到我们不能再有意义地提取为止。
或者，换句话说</ins>：

> 提取到底为止！(Extract till you drop!)

好的，也许这有点厚颜无耻。
我并不真的希望你倒下 (drop)。
另一方面，我确实希望你考虑尽可能多的提取。
你可能不会选择全部完成，但你至少应该考虑它们。

因此，你的大多数函数将相当小。
有多小？几行。
这个数字可能是三、四或六行。
对于某些 `switch` 语句、某些格式化语句或在某些语言中，它可能会更大。
但是，总的来说，遵循这个建议将导致你创建大量的小函数。

你将要提取什么？
<ins>通常你会提取 `if/else` 语句和 `for/while` 循环的主体。
你也可能会从这些语句中提取出谓词，以便这些语句仅由关键字和函数调用组成</ins>。

例如：

```java
if (shouldDeleteRecord(r))
    deleteRecord(r);
```

如果你仔细阅读它，你会发现它读起来像写得好的散文。

### 这不应该是有争议的

多年来，这个特别的建议，来自本书的第一版，一直是最具争议的。
但为什么呢？有很多原因。

1. 人们担心，如果他们遵循这条规则，他们将淹没在大量微小函数的海洋中。
2. 人们担心，遵循这条规则会模糊函数的意图，因为他们无法在一个地方看到全部。
3. 人们担心，调用所有这些微小函数的性能损失会导致他们的应用程序在冬天像糖浆一样慢。
4. 人们认为他们将不得不在函数之间跳来跳去，才能理解任何事情。
5. 人们担心，由此产生的函数将过于纠缠，无法孤立地理解。

让我们逐一解决这些问题。

#### 1. 淹没

很久以前，我们的语言非常原始。
例如，Fortran 的第一个版本允许你编写一个函数。
而且它不被叫做函数。
它只是被称为程序。
没有模块，没有函数，没有子程序。
正如我所说，那是原始的。

COBOL 也好不到哪里去。
你可以使用 `goto` 语句从一个段落到另一个段落跳转；但可以用参数调用的函数的概念仍然是十年后的事。

当 Algol 出现，后来 C 出现时，函数的概念像波浪一样涌向我们。
突然间，我们可以创建可以单独编译的模块。
模块化编程变得风靡一时。³

³ 正如软件中的所有事物一样，它被严重滥用了。
一些经理坚持认为，任何模块都不应超过 500 字节。
因此，程序员被迫在模块的末尾放置一个 `goto` 以调用下一个模块。

但随着岁月流逝，我们的程序变得越来越大，我们开始意识到函数还不够。
我们的名字开始冲突。
我们在保持它们唯一性方面遇到了麻烦。
而且我们真的不喜欢在每个名字前面加上它所属模块名称的想法。
我的意思是，没有人喜欢像 `io_files_open` 这样的函数名。

所以我们向语言中添加了类和命名空间。
这些给了我们可爱的、有名字的小隔间，我们可以将函数和变量放入其中。
而且，这些命名空间和类很快变得层次化。
我们可以将函数放在命名空间内，而这些命名空间又位于其他命名空间内。

这就是解决 “微小函数的海洋” 恐惧的方案。
你不会淹没在那片海洋中，因为不会有海洋。
相反，你将拥有一个排列整齐、命名良好的命名空间和类层次结构，你可以将你命名良好的函数塞进去。
那些好的名称将是其他程序员用来定位你的函数的路标。
更好的是，那些路标将提供其他程序员用来理解你的函数的上下文。

让我换一种说法。
我们中的一些人真的很喜欢处理大型函数。
这些函数的形状有某种令人愉悦的东西。
我们喜欢缩进的内外起伏。
我们后脑中的某些东西在其中找到了安慰。

为什么？
也许是因为，如果你将代码列表向右旋转 90°，它看起来像地平线。
那些起伏变成了山峰和山谷。
而我们这些在热带草原上进化的人类，利用地平线上那些形状来确定我们的位置。
我们知道东边两座山峰之间有一个水坑；右边的山谷是一只饥饿的剑齿虎的家。

还记得我的 `gi` 函数吗？
我对那个函数了如指掌。
我在地理上知道它！
如果有人要求我改变 x 轴上的缩放，我会对自己说：“x 轴上的缩放……那在大注释块之后的第三个缩进处。”
然后我会向下滚动到大的注释块，数 1..2..3，然后它就在那里 —— 设置 x 轴缩放的代码。

现在换一个从未见过 `gi` 的新程序员。
让那个可怜的家伙去改变 x 轴上的缩放。
他到底应该去哪里？
他不知道水坑在哪里。
他完全不知道那边的山谷里有一只剑齿虎在游荡。
他只会在那 3000 行的代码迷宫中摸索，直到运气好，偶然发现某个看起来像是设置 x 轴缩放的东西。

如果有一个名为 `setScalingOnX` 的函数，那对那个可怜的程序员来说不是很好吗？
如果那个函数位于 `Axis` 命名空间中，那岂不是很棒？
我希望我已经把我的观点说清楚了。
那么，转到第 2 点。

#### 2. 小函数不会模糊意图

对第 2 点的回答与对第 1 点的回答相同。
你不能通过将代码放入一个设计良好、命名良好的组织结构中来模糊代码的意图。
一个设计良好、命名良好的命名空间、类和函数结构揭示了意图。
它不会模糊它。
稍后会详细介绍。

#### 3. 性能

好的，第 3 点呢？
性能：这是一种真实的恐惧。
但只有那些必须保护和掌控每一纳秒的程序员才会真正担心这一点。
如果你正在编写一款第一人称射击游戏、一个高速交易应用程序或一个高超音速导弹的制导系统，那么纳秒可能相当重要。

另一方面，如果你正在编写一个旅游网站、一个薪资系统，甚至一架小型飞机的自动驾驶仪，纳秒不是你需要担心的。

很久以前，一个函数调用需要几微秒。
那时的机器很慢。
所以我们小心调用函数的数量。
但现在，函数调用只需要几纳秒。
你几乎不可能通过提取方法来显著减慢你的应用程序。
而且，如果你的测量结果显示有减速，你所要做的就是将其中最关键的那些函数重新内联回来。

记住，好的编译器通常会为你做内联，而你并不知情。
如果一个好的编译器看到你只从一个地方调用了某个函数，它很可能会简单地用函数内部的代码替换该调用。

#### 4. 跳来跳去

好的，那么。
第 4 点：跳来跳去。
我同意这一点 —— 或者至少如果相关函数在代码中随机分散的话，我会同意。
但谁会做那样的事呢？
那将是非常不礼貌的。

我喜欢按照函数被调用的顺序来组织我提取的函数。
所以，当一个函数调用另一个函数时，你所需要做的就是向下滚动，就能看到被调用的函数 —— 就在那里。
如果函数 A 调用 B 和 C，那么它们在源文件中的顺序应该是 A、B、C。 ⁴
这有什么难的？

⁴ 在像 Clojure 这样的语言中，应该是 C、B、A。

所以，不，如果作者礼貌的话，你将不会在代码中跳来跳去。

相反，你将能够从高层到低层阅读代码。
不仅如此，高层代码将被组织起来并与低层代码分开 —— 因为当你提取函数时，你几乎总是从高层代码中提取低层代码。

实际上，我将在本章后面向你展示一个这样的例子。
但首先我想讨论最后一点。

#### 5. 纠缠

在所有抱怨中，这是最合理的，也是 John Ousterhout 在附录中提出的观点。
不可否认的是，当你从一个函数中提取另一个函数时，你可能会纠缠这两个函数的逻辑。
换句话说，低层函数可能并不独立于高层函数的操作。
要理解低层函数，你必须对高层函数有很好的理解。

如果这种纠缠很严重 ——也就是说，在阅读低层函数时，你必须记住高层函数建立的几个不同的事实—— 那么这种提取很可能不值得做。
然而，如果纠缠很小，那么提取的函数有一个好的描述性名称，并且它直接出现在其父函数之后，这一事实很可能会使提取值得进行。

或者更不同地说：这是一个判断。明智地选择。
