## 报纸隐喻

想象一篇写得很好的报纸文章。
你垂直地阅读它。
在顶部，你期望一个标题，告诉你故事是关于什么的，并让你决定这是否是你想读的东西。
第一段给你整个故事的概要，隐藏所有细节，同时给你一个概览。
随着你继续向下阅读，细节逐渐增多，直到你获得所有的日期、名字、引语、声明和其他细节。

我们中的大多数人不会完整地阅读一篇文章。
我们从标题开始，如果它有趣，我们就继续读。
如果那段话吸引了我们，我们就继续读。
我们停留在一个非常简单的循环中：

```
while (interested) readMore;
```

<ins>一旦文章变得无聊，我们就停止。
允许我们使用这个循环的文章是有礼貌的 —— 它们让我们提前退出。
迫使我们浪费时间阅读大量不必要细节的文章是粗鲁的</ins>。

一份报纸由许多文章组成；大多数很短。
有些稍长一些。
很少有文章包含一页能容纳的那么多文字。
这使得报纸可用。
如果报纸只是一个长长的故事，包含混乱的事实、日期和名称的集合，那么我们根本不会读它。

我们希望一个模块的源代码就像一篇报纸文章。
模块的名称应该简单但具有解释性。
名称本身就应该足以告诉我们是否在正确的模块中。
模块最顶层的部分应该提供高层概念和算法。
随着我们向下移动，细节应该增加，² 直到最后我们找到模块中最低层的函数和细节。

² 某些语言，如 Clojure，由于要求声明在使用之前出现，因此反转了垂直顺序。
因此，低层细节放在顶部，高层策略放在底部。

一篇混合了两个不同故事的报纸文章将是一种可恶的东西。
同样，一个包含两个或更多不同主题的模块也是如此。³ 因此，模块内的类和函数都应该与一个单一主题相关 ——一个单一的职责—— 并具有良好的从高层策略到低层细节的结构。

³ 单一职责原则 (SRP)。

### 礼貌待人

当你编写封装单个抽象层次的函数时，你允许你的读者提前退出。
他们不必阅读大量代码就能理解该函数在该层次上做什么。
有时那个层次就是他们关心的全部，他们不想被来自较低层次的所有细节所困扰。

例如，我认为上面的 `makeStatement` 函数是有礼貌的。
读者可以瞥一眼就看到它做了什么。
如果读者不关心任何其他事情，那么他们就完成了，回到他们之前正在做的任何其他事情。

现在考虑 `makeStatement` 所演变的原始代码。

```go
func (customer *Customer) statement() string {
    totalAmount := 0.0
    frequentRenterPoints := 0
    result := "Rental Record for " + customer.name + "\n"
    for _, rental := range customer.rentals {
        thisAmount := 0.0
        switch rental.movie.movieType {
        case NewRelease:
            thisAmount += float64(rental.daysRented * 3)
        case Regular:
            thisAmount += 2
            if rental.daysRented > 2 {
                thisAmount += float64(rental.daysRented-2) * 1.5
            }
        case Childrens:
            thisAmount += 1.5
            if rental.daysRented > 3 {
                thisAmount += float64(rental.daysRented-3) * 1.5
            }
        }
        frequentRenterPoints++
        if rental.movie.movieType == NewRelease && rental.daysRented > 1 {
            frequentRenterPoints++
        }
        result += fmt.Sprintf("\t%s\t%.1f\n", rental.movie.title, thisAmount)
        totalAmount += thisAmount
    }
    return result +
        fmt.Sprintf(
            "Amount owed is %.1f\nYou earned %d frequent renter points",
            totalAmount, frequentRenterPoints)
}
```

我认为这段代码是粗鲁的。
我认为作者不够体贴。
为了理解这段代码的高层意图，我必须处理所有低层细节 —— 这需要时间。

这样想。
假设你在某个地方阅读代码，遇到了对礼貌的 `makeStatement()` 的调用。
函数名告诉你它做了什么，但也许你想检查对账单是否包括页脚。
所以你点击到 `makeStatement` 的实现，你看到四行简单的代码，它们准确地告诉你需要知道的内容。
两秒钟后，你点击回到你原来的位置并继续阅读，没有感到任何中断 —— 只是一个简单的问题在两秒内被提出并回答。

现在假设你在某个地方阅读代码，遇到了对粗鲁的 `statement()` 函数的调用。
这个名字是一个名词，没有描述任何动作。
你必须推断出这个函数构建了对账单。
同样，你不确定对账单是否包括页脚。
所以你点击到实现，面对的是 30 行深度详细的代码。
页脚在里面吗？
构建页脚的代码在正确的时间被调用了吗？
一两分钟后，你确信页脚是完整的，但现在你已经忘记了你为什么会担心那个问题。
你点击回到你原来的位置，你失去了你的思路，不得不回溯几行，再花几分钟，来提醒自己你在做什么，并在脑海中重新创建那个思路。

那是粗鲁的。
它就像那个冲进你的隔间，在你还没确认他之前就向你抛出问题的人一样粗鲁。
