## 为什么需要并发？

并发是一种解耦策略。
它帮助我们将 “做什么” 与 “何时做” 解耦。
在单线程应用程序中，“做什么” 和 “何时做” 是如此紧密耦合，以至于通常可以通过查看堆栈回溯来确定整个应用程序的状态。
调试这样一个系统的程序员可以设置一个断点，或一系列断点，并通过哪些断点被触发来了解系统的状态。

将 “做什么” 与 “何时做” 解耦可以显著提高应用程序的吞吐量和结构。
从结构的角度来看，应用程序看起来像是许多小型协作计算机，而不是一个大型主循环。
这可以使系统更容易理解，并提供一些强大的方式来分离关注点。

例如，考虑 Web 应用程序的标准 “servlet” 模型。
这些系统在 Web 服务器的框架下运行，该服务器部分地为管理并发。
每当 Web 请求进来时，servlet 被异步执行。
servlet 程序员不必管理所有传入的请求。
原则上，每个 servlet 执行都生活在自己小世界中，并且与其他所有 servlet 执行解耦。

当然，如果那么容易，本章就没有必要了。
事实上，Web 服务器提供的解耦远非完美。
Servlet 程序员必须非常清楚，非常小心，以确保他们的并发程序是正确的。
然而，servlet 模型的结构优势是显著的。

但结构并不是采用并发的唯一动机。
一些系统具有响应时间和吞吐量约束，需要手工编码的并发解决方案。

例如，考虑一个单线程信息聚合器，它从许多不同的网站获取信息，并将这些信息合并成每日摘要。
因为该系统是单线程的，它依次访问每个网站，总是在开始下一个之前完成一个。
每日运行需要在 24 小时内完成。
然而，随着越来越多的网站被添加，时间增长，直到收集所有数据需要超过 24 小时。
单线程在 Web socket 上等待 IO 完成时涉及大量等待。
我们可以通过使用一次访问多个网站的多线程算法来提高性能。

或者考虑一个每次处理一个用户、每个用户只需要一秒时间的系统。
这个系统对少数用户来说响应相当快，但随着用户数量的增加，系统的响应时间也会增加。
没有用户愿意排在 150 个其他用户后面！
我们可以通过同时处理许多用户来提高这个系统的响应时间。

或者考虑一个解释大型数据集但只有在处理完所有数据集后才能给出完整解决方案的系统。
也许每个数据集可以在不同的计算机上处理，以便许多数据集被并行处理。

### 传言与误解

因此，有令人信服的理由采用并发。
然而，正如我们之前所说，并发是困难的。
如果你不小心，你可能会制造一些非常糟糕的情况。
考虑这些常见的传言和误解：

- **并发总是提高性能。** 
并发有时可以提高性能，但只有在多个线程或多个处理器之间可以共享大量等待时间时。
两种情况都不简单。

- **编写并发程序时设计不会改变。** 
实际上，并发算法的设计与单线程系统的设计可能有显著不同。
将 “做什么” 与 “何时做” 解耦通常对系统结构有巨大影响。

- **在使用 Web 服务器时，理解并发问题不重要。** 
实际上，你最好知道你的服务器在做什么，以及如何防范本章后面描述的并发更新和死锁问题。

以下是关于编写并发软件的一些更平衡的观点：

- 并发会带来一些开销，无论是在性能方面还是在编写额外代码方面。
- 正确的并发是复杂的，即使对于简单的问题也是如此。
- 并发错误通常不可重复，因此它们经常被忽略为一次性事件 ² ，而不是实际缺陷。
- 并发通常需要设计策略的根本改变。

² 宇宙射线、故障等。

### 挑战

是什么使并发编程如此困难？
考虑下面这个简单的类：

```java
public class X {
    private int lastIdUsed;

    public int getNextId() {
        return ++lastIdUsed;
    }
}
```

假设我们创建了一个 `X` 的实例，将 `lastIdUsed` 字段设置为 42，然后在两个线程之间共享该实例。
现在假设这两个线程都调用了 `getNextId()` 方法；有三种可能的结果：

1. 线程一得到值 43，线程二得到值 44，`lastIdUsed` 为 44。
2. 线程一得到值 44，线程二得到值 43，`lastIdUsed` 为 44。
3. 线程一得到值 43，线程二得到值 43，`lastIdUsed` 为 43。

当两个线程相互踩踏时，就会产生令人惊讶的第三种结果。
这是因为两个线程在那一行代码中可能走许多不同的路径，其中一些路径会产生不正确的结果。

有多少种不同的路径？
要真正回答这个问题，我们需要理解编译器对生成的字节码做了什么，并理解 Java 内存模型认为什么是原子操作。

一个快速回答，仅基于生成的字节码，是对于在 `getNextId` 方法中执行的两个线程，有 12,870 种不同的可能执行路径。
如果 `lastIdUsed` 的类型从 `int` 改为 `long`，可能的路径数增加到 2,704,156。
当然，这些路径中的大多数会产生有效的结果。
问题是其中一些不会。
