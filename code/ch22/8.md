## 测试线程代码

证明代码正确是不切实际的。
测试并不能保证正确性。
然而，好的测试可以最小化风险。
这在单线程解决方案中都是正确的。
一旦有两个或更多线程使用相同的代码并处理共享数据，事情就会变得复杂得多。

**建议** ：编写有潜力暴露问题的测试，然后频繁地运行它们，使用不同的程序配置、系统配置和负载。
如果测试曾经失败，追踪失败。
不要仅仅因为测试在后续运行中通过就忽略一次失败。

这是一个需要考虑很多的事情。
以下是一些更细粒度的建议：

- 将偶发故障视为候选线程问题。
- 首先让你的非线程代码工作。
- 使你的线程代码可插拔。
- 使你的线程代码可调优。
- 运行比处理器数量更多的线程。
- 在不同平台上运行。
- 对你的代码进行插桩以尝试强制失败。

### 将偶发故障视为候选线程问题

线程代码会导致 “根本不可能失败” 的事情失败。
大多数开发人员对线程如何与其他代码交互没有直觉感受（包括作者在内）。
线程代码中的错误可能在一千次或一百万次执行中才出现一次症状。
尝试重现系统可能会令人沮丧。
这通常导致开发人员将失败归咎于宇宙射线、硬件故障或其他某种 “一次性” 事件。
最好假设一次性事件不存在。
这些一次性事件被忽略的时间越长，就有越多的代码构建在可能有缺陷的方法之上。

**建议** ：不要将系统故障视为一次性事件而忽略。

### 首先让你的非线程代码工作

这似乎是显而易见的，但强化一下没有坏处。
确保代码在其线程使用之外也能工作。
通常，这意味着创建由线程调用的简单模块。
由于这些模块不是线程感知的，它们可以在线程环境之外进行测试。
你能将越多的系统放置在这样的模块中，就越好。

**建议** ：不要试图同时追踪非线程错误和线程错误。确保你的非线程代码在线程之外工作。

### 使你的线程代码可插拔

编写并发支持代码，使其可以在几种配置中运行：

- 作为一个线程、几个线程或随执行变化而编写。
- 线程代码与可以是真实的或测试替身的东西交互。
- 使用运行快速、缓慢、可变的测试替身执行。
- 使用运行多次迭代的测试执行。

**建议** ：使你的基于线程的代码特别可插拔，以便你可以在各种配置中运行它。

### 使你的线程代码可调优

获得正确的线程平衡通常需要反复试验。
早期，找到方法在不同配置下对系统的性能进行计时。
允许线程数容易被调优。
考虑允许它在系统运行时更改。
考虑允许基于吞吐量和系统利用率进行自我调优。

### 运行比处理器更多的线程

当系统在任务之间切换时，事情会发生。
为了鼓励任务交换，运行比处理器或核心更多的线程。
你的任务交换越频繁，你就越有可能遇到缺少临界区或导致死锁的代码。

### 在不同平台上运行

在 2007 年中期，我们开发了一门并发编程课程。
课程开发主要是在 OS X 下进行的。
该课程是在运行在虚拟机下的 Windows XP 上展示的。
为演示失败条件而编写的测试在 XP 环境中不如在 OS X 上运行频繁失败。

在所有情况下，被测试的代码都是已知不正确的。
这仅仅强化了一个事实，即不同的操作系统有不同的线程策略，每一种都会影响代码的执行。
多线程代码在不同的环境中表现不同。⁹ 
你应该在每个潜在的部署环境中运行你的测试。

⁹ 你知道 Java 中的线程模型不保证抢占式线程吗？现代操作系统支持抢占式线程，所以你可以 “免费” 获得它。即便如此，JVM 并不保证这一点。

**建议** ：尽早并经常在所有目标平台上运行你的线程代码。

### 对你的代码进行插桩以尝试强制失败

并发代码中的缺陷隐藏起来是正常的。
简单的测试通常不会暴露它们。
事实上，它们通常在正常处理过程中隐藏起来。
它们可能每隔几小时、几天或几周才出现一次！

线程错误之所以可能不频繁、零星且难以重现，是因为在成千上万条可能通过脆弱部分的路径中，只有极少数路径实际上会失败。
因此，执行失败路径的概率可能低得惊人。
这使得检测和调试非常困难。

你如何增加捕获此类罕见事件的机会？
你可以通过对代码进行插桩，并通过添加对像 `Object.wait()`、`Object.sleep()`、`Object.yield()` 和 `Object.priority()` 等方法的调用来强制它以不同的顺序运行。

这些方法中的每一种都可以影响执行顺序，从而增加检测缺陷的可能性。
坏代码尽可能早和尽可能频繁地失败是更好的。

代码插桩有两种选择：

- 手工编码
- 自动化

#### 手工编码

你可以通过手工在代码中插入对 `wait()`、`sleep()`、`yield()` 和 `priority()` 的调用。
当你在测试一段特别棘手的代码时，这可能正是需要做的事情。

下面是一个这样做的例子：

```java
public synchronized String nextUrlOrNull() {
    if(hasNext()) {
        String url = urlGenerator.next();
        Thread.yield(); // inserted for testing.
        updateHasNext();
        return url;
    }
    return null;
}
```

插入的 `yield()` 调用将改变代码所采取的执行路径，并可能导致代码在以前没有失败的地方失败。
如果代码确实崩溃了，那不是因为你添加了对 `yield()` 的调用。¹⁰ 
相反，你的代码是坏的，这仅仅是使失败变得明显。

¹⁰ 这并非严格如此。由于 JVM 不保证抢占式线程，一种特定的算法可能总是在不抢占线程的操作系统上工作。反之亦然，但原因不同。

这种方法存在许多问题：

- 你必须手动找到适当的位置来这样做。
- 你怎么知道在哪里放置调用以及使用什么类型的调用？
- 将这样的代码留在生产环境中会不必要地减慢代码速度。
- 这是一种散弹枪式的方法。你可能会也可能不会发现缺陷。事实上，几率并不站在你这边。

我们需要一种在测试期间这样做但在生产环境不这样做的方法。
我们还需要轻松地混合不同运行之间的配置，这会增加在总体上发现错误的机会。

显然，如果我们将系统划分为对线程一无所知的简单模块和其他控制线程的模块，那么找到对代码进行插桩的适当位置将更容易。
此外，我们可以创建许多不同的测试装置，在不同的调用 `sleep`、`yield` 等的方案下调用这些模块。

#### 自动化

你可以使用像 CGLIB 或 ASM 这样的工具，通过程序化地对代码进行插桩，添加对抖动器的调用。
例如，你可以使用一个只有一个方法的类：

```java
public class ThreadJigglePoint {
    public static void jiggle() {
    }
}
```

你可以在代码中的各个位置添加对这个方法的调用：

```java
public synchronized String nextUrlOrNull() {
    if(hasNext()) {
        ThreadJigglePoint.jiggle();
        String url = urlGenerator.next();
        ThreadJigglePoint.jiggle();
        updateHasNext();
        ThreadJigglePoint.jiggle();
        return url;
    }
    return null;
}
```

想象一下 `ThreadJigglePoint` 类有两个实现。
第一个实现 `jiggle` 什么也不做，用于生产环境。
第二个生成一个随机数，以在休眠、让出或直接通过之间进行选择。如果你用随机抖动运行一千次测试，你可能会发现一些缺陷。
如果测试通过，至少你可以说你已经尽职尽责了。
虽然有点简单，但这可能是一个合理的选择，以代替更复杂的工具。

关键是要抖动代码，以便线程在不同的时间以不同的顺序运行。
编写良好的测试和抖动的结合可以显著增加发现错误的机会。

**建议** ：使用抖动策略来找出错误。
