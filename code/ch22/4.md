## 了解你的执行模型

在并发应用程序中，有几种不同的方式来划分行为。
为了讨论它们，我们需要理解一些基本定义。

| 术语 | 说明 |
| ---- | ---- |
| Bound resources | 在并发环境中使用的、容量或数量固定的资源。例如数据库连接、固定大小的读写缓冲区。 |
| Mutual exclusion | 同一时刻只允许一个线程访问共享数据或共享资源。 |
| Starvation | 一个或一组线程长时间（甚至永久）无法继续执行。举例：若持续优先放行执行速度快的线程，慢速线程就会产生饥饿。 |
| Deadlock | 两个或多个线程互相等待对方执行完毕。每个线程都持有对方所需的资源，并且双方只有获取对方资源才能完成任务。 |
| Livelock | 线程同步交替尝试执行任务，但总是被对方阻碍。受这种相互影响，线程持续尝试推进工作，却长时间（甚至永久）无法取得进展。 |

基于这些定义，我们现在可以讨论并发编程中使用的各种执行模型。

### 生产者-消费者 ⁵

⁵ http://en.wikipedia.org/wiki/Producer-consumer

一个或多个生产者线程创建一些工作并将其放入缓冲区或队列中。
一个或多个消费者线程从队列中获取这些工作并完成它。
生产者和消费者之间的队列是一种受限资源。
这意味着生产者在写入之前必须等待队列中有空闲空间，而消费者必须等到队列中有东西可以消费。
通过队列在生产者和消费者之间进行协调涉及生产者和消费者互相发出信号。
生产者写入队列并发出队列不再为空的信号。
消费者从队列中读取并发出队列不再为满的信号。
两者都可能等待被通知何时可以继续。

### 读者-作者 ⁶

⁶ http://en.wikipedia.org/wiki/Readers-writers_problem

当你有一个共享资源，它主要作为读者的信息来源，但偶尔由作者更新时，吞吐量是一个问题。
强调吞吐量可能导致饥饿和过时信息的积累。
允许更新可能影响吞吐量。
协调读者，使他们不读取作者正在更新的内容，反之亦然，是一项艰难的平衡工作。
作者往往会长时间阻塞许多读者，从而导致吞吐量问题。

挑战在于平衡读者和作者的需求，以满足正确操作、提供合理的吞吐量并避免饥饿。
一个简单的策略是让作者等待，直到没有读者才允许作者执行更新。
然而，如果有连续的读者，作者将被饿死。
另一方面，如果有频繁的作者并且他们被赋予优先级，吞吐量将受到影响。
找到这种平衡并避免并发更新问题正是该问题所要解决的。

### 哲学家就餐问题 ⁷

⁷ http://en.wikipedia.org/wiki/Dining_philosophers_problem

想象一些哲学家围坐在一张圆桌旁。
每个哲学家的左手边放着一把叉子。
桌子中央有一大碗意大利面。
哲学家们思考，直到饥饿。
一旦饿了，他们拿起两侧的叉子并吃饭。
一个哲学家除非拿着两把叉子，否则不能吃饭。
如果他右边或左边的哲学家已经占用了他需要的一把叉子，他必须等到那个哲学家吃完并把叉子放回去。
一旦哲学家吃完，他把两把叉子放回桌上，并等待再次饥饿。

将 “哲学家” 替换为 “线程”，将 “叉子” 替换为 “资源”，这个问题类似于许多企业应用程序中进程竞争资源的情况。
除非经过精心设计，否则以这种方式竞争的系统可能会遇到死锁、活锁、吞吐量和效率下降的问题。

**建议** ：你很可能遇到的并发问题将是这三种问题的变体。
研究这些算法并自己编写使用它们的解决方案，这样当你遇到并发问题时，你将更有准备去解决它们。
