## 并发防御原则

以下是一系列用于保护您的系统免受并发代码问题影响的原则和技术。

### 单一职责原则

SRP 指出，给定的方法/类/组件应该只有一个改变的理由。
并发设计本身就足够复杂，足以成为一个改变的理由，因此应该与其余代码分离。

不幸的是，并发实现细节直接嵌入其他生产代码中的情况非常普遍。
以下是一些需要考虑的事项：

- 并发相关代码有其自己的开发、变更和调优生命周期。
- 并发相关代码有其自己的挑战，这些挑战与非并发相关代码不同，且通常更困难。
- 错误编写的基于并发的代码可能失败的方式很多，如果没有周围应用程序代码的额外负担，这已经足够具有挑战性。

**建议** ：将您的并发相关代码与其他代码分开。

### 推论：限制数据的作用域

正如我们所见，两个线程修改共享对象的同一字段可能会相互干扰，导致意外行为。
一种解决方案是使用像 Java 的 `synchronized` 关键字来保护使用共享对象的代码中的临界区。
限制此类临界区的数量很重要。
共享数据可以被更新的地方越多，就越有可能：

- 你会忘记保护其中一个或多个地方 —— 有效地破坏了所有修改该共享数据的代码。
- 需要重复努力以确保所有内容都得到有效保护（违反 DRY ³ ）。
- 难以确定故障来源，这些故障已经够难找了。

³ [Prag](../bib.md#prag)。

**建议** ：认真对待数据封装；严格限制任何可能被共享的数据的访问。

> **Future Uncle Bob**：在编写并发模块时，考虑使用函数式语言，或至少使用函数式风格。

### 推论：使用数据副本

避免共享数据的一个好方法是首先避免共享数据。
在某些情况下，可以复制对象并将其视为只读。
在其他情况下，可以复制对象，在这些副本中从多个线程收集结果，然后在单个线程中合并结果。

如果有一种简单的方法可以避免共享对象，那么生成的代码将更不可能引起问题。
你可能会担心所有额外对象创建的成本。
值得通过实验来发现这实际上是否是一个问题。
然而，如果使用对象副本允许代码避免同步，那么避免固有锁所节省的开销很可能足以弥补额外的创建和垃圾回收开销。

### 推论：线程应尽可能独立

考虑编写线程代码，使每个线程都存在于自己的世界中，不与其他任何线程共享数据。
每个线程处理一个客户端请求，其所需的所有数据都来自非共享源，并作为局部变量存储。
这使得每个线程的行为都像是世界上唯一的线程，没有同步需求。

例如，从 `HttpServlet` 继承的类通过 `doGet` 和 `doPost` 方法传入的参数接收所有信息。
这使得每个 Servlet 的行为都像是拥有自己的机器。
只要 Servlet 中的代码只使用局部变量，Servlet 就不会引起同步问题。
当然，大多数使用 Servlet 的应用程序最终都会遇到共享资源，如数据库连接。

**建议** ：尝试将数据划分为独立的子集，这些子集可以由独立的线程操作，可能在不同的处理器上。
