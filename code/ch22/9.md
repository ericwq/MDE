## 2025 年更新与现场报告

> 现代技术栈在处理多个用户且这些用户不共享数据时表现良好。
以下是一些仍然值得记住的并行/线程问题知识的情况。

一点背景：现代开发技术栈往往声称可以处理我们在编写《Clean Code》第一版时手动处理的许多问题。
然而，许多原始问题仍然存在于现代系统中，即使是那些为你处理 “所有多用户事务” 的系统。

以下是我们恰好在《Clean Code》第二版发布前一年遇到的一些示例集合。

### 数据完整性

在过去几年里，我们遇到了许多多用户系统存在潜在数据完整性问题的案例。
所有这些系统都有多个同时用户（并行）执行更新共享数据的操作。

这些示例来自两个不同的基于 React Native 的多用户系统。
它们使用 AWS Lambda 作为后端，并在某种数据存储中存储。
这类系统本身并没有什么固有问题。
如果两个用户不共享数据，那么很可能不存在数据完整性问题。
然而，当多个用户确实依赖于共享数据时会发生什么？

这些示例包括：

- 加入游戏
- 在共享设计上工作
- 玩家并行工作以创建一副牌
- 在 React Native 中使用 2D 库重新渲染时双重删除资源
- 加载图标资源

#### 加入游戏

想象一个用于培训研讨会的移动游戏平台。
学生登录到一个游戏。
一个游戏有六名玩家的限制，所以当第六名玩家加入后，后续加入游戏的尝试将被拒绝。
每个玩家被分配一个角色，编号为 1 到 6。

后端系统使用 DynamoDB，它提供 “最终一致性” 结果。
几个月来，我们偶尔会遇到一些混乱，似乎我们正在丢失玩家。
结果发现这是一个关于我们何时决定分配玩家角色以及让玩家立即加入游戏的问题。

在原始实现中，我们将登录与加入游戏和分配角色给玩家结合在一起。
将玩家分配到游戏和角色，加上 DynamoDB 中的最终一致性，导致用户获得相同的角色或游戏超员。

虽然可以重写我们与 DynamoDB 交互的方式，但在发现这个缺陷之前，还有另一个期望的更改。
该更改将通过将登录与加入游戏和随后的角色分配分离来使原始问题消失。

原始问题是将角色分配给从多个移动客户端加入游戏的多个用户，即并行地。
为了解决这个问题，我们首先扩展了领域。
玩家不是在登录时加入游戏，而是加入一个等待室。
稍后，管理员创建游戏，然后发出一个请求，将所有等待的玩家分配到游戏中。

这将原本在没有事务隔离的情况下不安全的两件事 ——加入游戏和角色分配—— 从可能并行执行变为后来从单个线程/由单个用户执行。
原始实现并不是我们想要游戏工作方式的本质部分；它是关于如何处理同时进行多个游戏的最初想法之一。

这种方法的一个副作用是管理员会提前创建游戏，然后告诉特定的人登录特定的游戏。
用户会输入他们的名字、游戏名和游戏密码。
通信问题很常见，导致人们加入错误的游戏。

更改之后，所有玩家都加入一个等待室，其名称是管理员的电子邮件地址，在下拉列表中提供。
因此，玩家不是选择游戏名、用户名和密码，而是选择一个等待室名称并提供他们的名字。
这使得用户体验更简单，更不容易出错。

这将工作中多线程安全的部分 —— 进入系统 —— 与多线程不安全的部分—— 加入特定游戏并分配用户角色 —— 分离开来。

#### 在共享设计上工作

接下来是一个允许共享创建商业安全系统安装/更新设计的系统。
对于这个系统，我们使用关系数据库作为数据存储。

这样的计划有几十张图片，每张图片可能有几个元素，这些元素可能是连接的。
你如何确保多个人可以同时在同一个设计上工作，而不会发生冲突？

对于这个特定领域，一个设计上的用户数量通常少于五个，并且用户倾向于在整体设计的不同部分工作。
所以，虽然冲突的可能性存在，但考虑到系统的典型使用，它发生的可能性很小。

系统中预先存在选择元素进行编辑的需求。
这自然成为锁定元素的地方。
我们在元素上使用一个标志来表示它是否被锁定。
当已经锁定时，任何锁定尝试都会失败，并通知用户该元素已被锁定。
取消选择后，元素的锁被释放。
我们选择在元素上设置一个标志，而不是在数据库中锁定元素，因为后者需要长时间运行的事务。

通过适当的事务隔离，这是一个针对特定问题的干净、安全的解决方案。

#### 玩家并行创建一副牌

这是一个反例，也就是说，我们选择不解决这个问题。

想象第二个移动游戏，这个游戏允许小群玩家竞争创建一副具有特定特征的牌。

在这种情况下，我们有最多四个人在创建一副牌。
这些玩家可能是远程的、本地的、同地的或不是。
如果两个玩家创建了同一张牌会发生什么？

玩家尝试创建一副具有特定特征的牌。
如果他们碰巧得到重复的牌，教练会拒绝他们的牌组。
然而，当这种情况发生时，团队可以清理他们的牌组并重新提交。

此外，这种体验也会引发关于协作和沟通的良好讨论，所以试图确保它不发生会降低体验的价值。

在这种情况下，有一个共享资源：牌组。
牌的添加是并行完成的。
可能存在 “数据完整性” 问题，重复工作，但最终结果很容易恢复，全部通过人际交互完成。

早期，我们意识到这是一个潜在的问题。
当我们考虑解决方案时，我们决定在游戏中保留这种可能性。
教练可以以不同的方式、使用不同的规则来运行游戏。
所以，在这种情况下，解决方案是保持原样。

#### 在 React Native 中使用 2D 库重新渲染时双重删除资源

我们正在使用 React Native 和 React Native Web 为客户生成 Web 和移动应用程序。
我们还使用了名为 Skia 的 2D 图形库。

Skia 是一个强大的库，它有自己独立的渲染引擎。
这意味着至少有两个渲染引擎同时运行 ——React Native 和 Skia—— 并且这两个渲染引擎是不同步的。
直到我们添加了设计的异步加载，我们才注意到问题。

当用户打开一个设计时，我们在进入应用程序的设计视图时异步加载它。
当我们开始这样做时，我们发现 Skia 频繁崩溃。

最终导致这种情况的是在我们完成加载之前渲染了 Skia 视图。
在 React Native 中，这是正常的。
它会重新渲染视图。
然而，由于 Skia 有自己独立的渲染线程，当 React Native 在意外时间重新渲染视图时，Skia 会开始删除，然后重新删除相同的资源。
删除已删除的内存导致 Skia 崩溃，并需要重新启动应用程序。
这不是 Skia 的问题；而是我们如何使用它的问题。

解决方案是在加载完成之前不渲染 Skia 视图。
我们有明确定义的位置，在这些位置我们需要 Skia 进行渲染，以及不需要它的位置。
我们确保：

- 仅在加载完成时渲染 Skia 视图；否则，我们渲染一个空视图。
- 每当我们发出导致 Skia 视图重新渲染的更改时，首先清除一个设置。这将导致 Skia 视图停止渲染。
- 设置一个新值，导致所有内容被重新渲染。

最终解决方案使整体代码更干净。
解决方案是仅在设计加载时允许 “并行” 渲染线程。
没有设计？
没有 Skia 渲染。
有设计？
Skia 渲染。
每当我们更改设计时，我们首先设置状态以停止渲染 Skia，加载设计，并在完成后再次开始使用 Skia。

#### 加载图标资源

我们遇到了图标加载顺序的问题。
有可能在加载图标的代码开始执行之前就将设计加载到系统中。
当这种情况发生时，我们必须重新加载设计，或者会有几个缺失的图标。

由于系统的其他部分也需要这些资源，我们将它们移到了 React Native 中所谓的 provider 中。
然后，任何可能导致设计被加载的代码总是在该 provider 下执行，也就是说，provider 和使用图标的任何东西之间存在父子关系。
父元素首先初始化，保证了执行顺序。

与前面的示例一样，这导致了更干净的代码。
相关的事物在单一位置下靠得更近，并且我们消除了重复。

### 共享数据

在所有这些示例中，都存在与共享数据相关的问题：

- 允许玩家加入特定游戏，并在最终一致性数据库中并行分配角色。
- 允许多个用户并行编辑共享设计。
- 允许玩家并行创建卡片。
- 多个、依赖的渲染循环不同步，其他异步活动影响它们。
- 在异步环境中没有显式控制资源的执行/加载。

我们对这些问题采取了不同的方法：

- 隔离非线程安全的代码，并在稍后以单线程执行（隔离并分离）。
- 使用关系数据库，通过标志锁定对象。
- 什么都不做。人类可以根据当前游戏规则选择接受或拒绝。
- 避免在真正需要之前使用第二个渲染线程，并在清理其他所有内容之前清理它。
- 使加载部分成为父子关系的一部分，使得子元素在父元素准备好之前不渲染。

一旦你发现了共享数据的问题，你可以采取许多方法来解决它。我们已经看到了五个示例和针对特定问题的五种不同方法。
