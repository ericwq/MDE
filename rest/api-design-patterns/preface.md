# 前言

在学校里，我们学习计算机科学的方式，就像学习物理定律一样。
我们使用 Big-O 记号分析运行时间和空间复杂度，学习各种排序算法的工作原理，并探索遍历二叉树的不同方式。
因此，正如你可能想象的那样，毕业后，我本以为我的日常工作本质上是科学和数学性质的。
但请想象一下，当我发现事实并非如此时，我是多么惊讶。

事实证明，我需要做的大部分工作更多地涉及设计、结构和美学，而不是数学和算法。
我从来不需要考虑使用哪种排序算法，因为已经有库可以处理（通常是像 `array.sort()` 这样的东西）。
然而，我确实必须深入思考我要创建的类、这些类上会存在的函数，以及每个函数会接受哪些参数。
而这比我预期的要困难得多。

在现实世界中，我了解到，优化完美的代码远不如设计良好的代码有价值。
而对于 Web API 来说，这一点更是如此，因为它们通常拥有更广泛的受众和更多样化的用例。

但这引出了一个问题：软件 “设计良好” 意味着什么？
什么是 “设计良好的 Web API”？
在相当长的一段时间里，我不得不依赖一堆杂七杂八的资源来回答这些问题。
对于某些主题，可能会有有趣的博客文章探讨当今使用的一些流行替代方案。
对于其他主题，Stack Overflow 上可能有特别有用的答案，可以为我指明正确的方向。
但在许多情况下，关于相关主题的材料相对较少，我只能自己尝试提出答案，并希望我的同事们不会太讨厌它。

经过多年的这种情况（并随身携带一个封面上写着 “可怕的 API 问题” 的笔记本），我终于决定是时候写下我收集并亲眼见证过有效的所有信息了。
<ins>起初，这是我和 Luke Sneeringer 为 Google 编纂的一套规则，最终成为了 AIP.dev 。
但这些规则读起来有点像一部法律书籍；它们说了你应该做什么，但没有说你为什么应该那样做。
经过大量研究并一遍又一遍地问自己这个确切的问题，这本书就在这里，它呈现了这些规则，同时也解释了原因。</ins>

尽管这本书如果能成为解决世界 API 设计问题的终极方案会很棒，但遗憾的是，我认为情况并非如此。
原因很简单：就像建筑学一样，任何形式的设计通常都是观点问题。
这意味着，你们中的一些人可能会认为这些指南优美而优雅，并在所有未来的项目中都使用它们。
与此同时，你们中的一些人可能会认为这本书呈现的设计丑陋且过于严格，并将其用作构建 Web API 时不应做什么的示例。
<ins>既然我无法让每个人都满意，我唯一的目标就是提供一套经过实战检验的指南，并对其为何如此形态提供合乎逻辑的解释。</ins>

无论你是将它们作为遵循的示例还是避免的示例，这都取决于你。
至少，我希望本书中涵盖的主题能够引发许多对话，以及未来在这个迷人、复杂且精妙的 API 设计领域的大量工作。
