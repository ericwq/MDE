在设计任何 API 时，我们总是需要考虑我们希望作为输入接受、理解并可能存储的数据类型。
有时这听起来相当直接：一个名为 “name” 的字段可能只是一个字符串。
然而，这个问题背后隐藏着复杂的细节。
例如，字符串应如何表示为字节（事实证明对此有很多种选择）？
如果在 API 调用中省略了 name 字段，会发生什么？
这与提供一个空名称（例如 { "name": "" }）有何不同？
在本章中，我们将探讨在设计或使用 API 时几乎肯定会遇到的各种数据类型，如何最好地理解其底层数据表示，以及如何以合理且直接的方式处理各种类型的默认值。

<a id="introduce"></a>
## 5.1 数据类型简介

数据类型几乎是每种编程语言的一个重要方面，它告诉程序如何处理一块数据，
以及它应如何与语言或类型本身提供的各种运算符进行交互。
即使在动态类型语言中（其中单个变量可以充当多种不同的数据类型，而不是仅限于一种），
在某个时间点的类型信息仍然相当重要，它决定了编程语言应如何处理该变量。

<ins>然而，在设计 API 时，我们必须跳出单一编程语言的思维模式，
主要是因为我们的 API 的一个主要目标是让任何人使用任何编程语言都能与服务进行交互。</ins>
我们实现这一点的标准方式是依赖于某种序列化协议，该协议将我们在所选编程语言中的结构化数据表示，转换为与语言无关的序列化字节表示，然后再发送给请求它的客户端。
在另一端，客户端将这些字节反序列化，并转换回内存中的表示形式，以便从他们使用的语言（可能与我们的语言相同，也可能不同）与之交互。
图 5.1 概述了这一过程。

虽然这种序列化过程提供了巨大的好处（本质上允许 API 被任何编程语言使用），但它并非没有缺点。
最大的问题在于，由于每种语言的行为方式都有所不同，因此某些信息会在转换过程中丢失。
<ins>换句话说，由于不同编程语言的特性和功能存在差异，所有序列化协议都会以某种方式存在 “有损” 的情况。</ins>

这让我们回到数据类型及其在 API 中使用方式的重要性。
<ins>简而言之，在考虑使用 Web API 的用户时，仅仅依赖我们所选编程语言提供的数据类型从根本上是不够的。
相反，我们必须考虑所选序列化格式（最常见的是 JSON）所提供的数据类型，
以及在该格式无法满足我们需求时如何扩展该格式。</ins>
这意味着我们需要决定我们想要发送给客户端和从客户端接收的数据的类型，并确保它们得到充分的文档记录，
以便客户端永远不会对其行为感到意外。

这并不是说 Web API 必须具有像关系数据库系统那样的严格 schema；
毕竟，现代开发工具最强大的地方之一在于动态无 schema 结构和数据存储所提供的灵活性。
然而，重要的是要考虑我们正在交互的数据的类型，并在必要时通过额外的注解加以澄清。
如果没有这些额外的数据上下文，我们可能会陷入困境，只能猜测客户端的实际意图。
例如，a + b 对于数值（例如 2 + 4 可能得到 6）可能以一种方式运作，但对于文本值（例如 "2" + "4" 可能得到 "24"）可能表现得完全不同。
如果没有这种类型上下文，当客户端使用 + 运算符时，我们将被迫猜测其意图：是加法还是拼接？
如果一个值是数字而另一个是字符串呢？
这可能会导致更多的猜测。
但如果一个值被完全省略了呢？

<a id="missing-or-null"></a>
### 5.1.1 缺失值与 null 值

令人惊讶的是，最令人困惑的方面之一来自于数据缺失而非存在的情况。
首先，在许多序列化格式中有一个 null 值，它是一个标志，表示非值（例如，一个字符串可以是普通值，也可以是字面量 null）。
那么，当尝试将 null 和 2 相加时，API 应如何表现？
任何使用支持此类 null 值的序列化格式的 API 都需要决定如何处理这种类型的输入。
它应该假装 null 在数学上等价于 0 吗？
那么尝试将 null 和 "value" 相加呢？在这种情况下，null 是否应被解释为空字符串 ("") 并尝试进行拼接？

更糟糕的是，动态数据结构（例如 JSON 对象）带来了一个新的问题：如果值根本不存在怎么办？
换句话说，如果存储该值的键完全缺失，而不是提供的值恰好被显式设置为 null，那该怎么办？
这是否与显式的 null 值处理方式相同？
为了理解这意味着什么，假设你有一个 Fruit 资源，其中应包含 name 和 color 字段，两者都是字符串数据类型。请考虑以下 JSON 对象示例，以及 API 可能为该资源的 color 值推断出的值：

```typescript
fruit1 = { name: "Apple", color: "red" };
fruit2 = { name: "Apple", color: "" };
fruit3 = { name: "Apple", color: null };
fruit4 = { name: "Apple" };
```

如你所见，第一个 color 值是明确的（fruit1.color == "red"）。
然而，我们应该如何处理其他情况呢？
空字符串颜色 ("") 是否与显式的 null 颜色处理方式相同（fruit2.color 与 fruit3.color 的处理方式有区别吗）？
缺少 color 值的那个 fruit 呢？
fruit3.color 与 fruit4.color 的处理方式有区别吗？
这些可能看起来只是 JSON 的特性；
然而，它们确实存在于许多其他序列化格式中（例如，Google 的 Protocol Buffers \[ https://opensource.google/projects/protobuf ] 在这方面有一些令人困惑的行为），并且它们提出了每个 API 都必须解决的问题，否则可能会变得极其不一致，令 API 使用者感到困惑。
换句话说，你不能简单地假设序列化库会做正确的事情，因为几乎可以肯定每个人都会使用不同的序列化库！

在本章中，我们将逐一介绍所有常见的数据类型，从简单的类型（有时称为基本类型）开始，逐渐过渡到更复杂的类型（例如 map 和集合）。你应该已经熟悉其中的大多数概念，因此重点将不在于每种数据类型的基础知识，而更多在于将它们用于 Web API 时必须考虑的事项。我们将深入探讨每种数据类型需要注意的各种“陷阱”，以及如何最好地为任何 API 解决这些问题。我们还将坚持使用 JSON 作为首选的序列化格式，但大多数建议将适用于支持动态数据结构（同时使用推断类型和显式类型定义）的任何格式。让我们从最简单的开始：真和假值。

<a id="booleans"></a>
## 5.2 布尔值

在大多数编程语言中，布尔值是最简单的可用数据类型，表示两个值之一：true 或 false。
由于值集有限，我们倾向于依赖布尔值来存储标志或简单的 “是/否” 问题。
例如，我们可能会在聊天室中存储一个标志，表示该房间是否已归档，或者是否允许聊天机器人在该房间中。

*清单 5.1 带有布尔标志的 ChatRoom 资源* <br/>

```typescript
interface ChatRoom {
  id: string;
  // ...
  // 此处还会有聊天室的大量其他字段
  archived: boolean;
  // 该标记用于标识聊天室是否已归档
  allowChatbots: boolean;
  // 用于说明聊天室是否允许聊天机器人接入
}
```

然而，布尔标志在未来可能会变得非常受限，因为一个 “是/否” 问题可能会演变成一个更普遍的问题，需要比布尔字段所能提供的更细致的答案。
例如，未来聊天室可能允许许多不同类型的参与者，而不仅仅是普通用户和聊天机器人。
在这种情况下，我们当前的设计将导致一长串允许（或不允许）的每种类型的列表，例如 allowChatbots、allowModerators、allowChildren、allowAnonymousUsers 等等。
如果这种情况可能发生，那么避免使用一堆布尔标志，
而是依赖不同的数据类型或结构来定义特定聊天室允许或不允许的参与者类别，实际上可能更合理。

假设布尔字段是某个变量的正确选择，那么还有其他一些有趣的方面需要考虑。
布尔字段的名称中隐藏着该字段是正向还是负向的陈述。
在 allowChatbots 的例子中，该字段的 true 值表示允许聊天机器人进入聊天室。
但同样可以很容易地命名为 disallowChatbots，其中 true 值将禁止聊天机器人进入聊天室。
为什么要选择其中一种而不是另一种呢？

<ins>一般来说，正向布尔字段对我们大多数人来说最容易理解，原因很简单：人类在处理双重否定时需要多动点脑筋。
而负向字段的 false 值正是双重否定。</ins>
例如，假设字段是 disallowChatbots。
你如何检查聊天机器人是否被允许进入给定的聊天室？

*清单 5.2 如果允许，将聊天机器人添加到房间的函数* <br/>

```typescript
function addChatbotToRoom(chatbot: Chatbot,
                          roomId: number): void {
  let room = getChatRoomById(roomId);
  // 此处检查是否禁止聊天机器人接入。如果为 false，则允许加入该聊天室
  if (room.disallowChatbots === false) {
    chatbot.join(room.id);
  }
}
```

这很难理解吗？可能不是。
但与简单得多的版本（ `if (room.allowChatbots) { ... }` ）相比，它是否增加了认知负担？
对我们大多数人来说，可能是的。
仅基于这一点，选择正向布尔标志几乎总是一个好主意。
但在某些情况下，依赖负向标志可能是合理的，这主要是在我们考虑字段的默认值或未设置值时。

例如，在某些语言或序列化格式中（例如，直到最近，Google 的 Protocol Buffers v3），许多基本类型，如布尔字段，只能具有零值，而不能具有 null 或缺失值。
正如你可能猜到的，对于布尔值，这个零值几乎总是等同于 false。
这意味着，当我们考虑在创建聊天室时 allowChatbots 字段的值时，如果没有进一步干预，聊天室不允许聊天机器人（defaultChatRoom.allowChatbots == false）。
但我们无法区分用户所说的 “我没有设置这个值，所以请按你认为最好的方式处理”
（即 null 或缺失值）和 “我不想允许聊天机器人”（即显式的 false 值）。
在这两种情况下，值都只是 false。我们该怎么办？

<ins>虽然这个问题有很多解决方案，但一个常见的选择是依靠布尔字段名称的正向或负向方面来得出 “正确” 的默认值。
换句话说，我们可以为布尔字段选择一个名称，使得零值提供我们想要的默认值。</ins>
例如，如果我们希望默认允许匿名用户，我们可能会决定将字段命名为 disallowAnonymousUsers，这样零值（false）就会产生我们想要的默认值（允许匿名用户）。
不幸的是，这种选择将默认值锁定在字段名称中，这阻碍了未来的灵活性（即，你以后无法更改默认值），
但正如他们所说，非常时期需要非常手段。

<a id="numbers"></a>
## 5.3 数字

从简单的 “是/否” 问题稍微复杂一些，数值允许我们存储各种有价值的信息，
例如计数（例如 viewCount）、大小和距离（例如 itemWeight）或货币值（例如 priceUsd）。
总的来说，对于任何我们可能想要进行算术计算（或者即使这些计算只有在逻辑上合理）的东西，数字字段是理想的数据类型选择。

有一个值得注意的例子实际上并不适合这种数据类型：数字标识符。
这可能会令人惊讶，因为许多数据库系统（几乎所有的关系数据库系统）使用自动递增的整数值作为其行的主键标识符。
那么，为什么我们不在 API 中也使用标识符呢？

<ins>虽然我们可能由于各种原因（例如性能或空间限制）在底层仍然使用数字字段，但在 API 表面，数字类型最好用于那些因其实际数字属性而能提供某种形式的算术益处的值。</ins>
换句话说，如果一个 API 暴露的条目具有以克为单位的重量值，我们可以想象将所有这些值相加，以确定一组条目的总克重。
另一方面，将一组数字标识符相加并对该值进行某些操作通常没有任何意义。
相反，一堆数字 ID 的加法很可能毫无用处。
因此，重要的是依赖于数字数据类型的数字或算术益处，
而不是依赖于它们恰好只用数字字符（可能偶尔带个小数点）编写这一事实。
<ins>一般来说，那些碰巧看起来像数字但行为更像令牌或符号的值，或许应该使用字符串值（参见 [第 5.4 节](#strings) ）。</ins>

综上所述，在 API 中使用数值时，有几个事项需要考虑。
让我们从如何为这些数字字段定义边界或可接受值的范围开始。

<a id="number-bounds"></a>
### 5.3.1 边界

在为数字字段定义边界时，无论是整数、小数（或其他数学表示形式，如分数、虚数等），重要的是要考虑上限或最大值、下限或最小值以及零值。
由于这些因素相互影响，我们先考虑绝对值的边界，然后再决定是否同时利用该范围的负数和正数部分。

<ins>谈到边界，我们的主要关注点在于它们的大小。</ins>
换句话说，所有数字最终都需要存储在某处，这意味着我们需要知道为这些值分配多少空间（以位为单位）。
对于小整数，8 位可能就足够了，具有 256 个可能值（–127 到 127）。
对于大多数常见的数值，32 位通常是一个可接受的大小，大约有 40 亿个可能值（从负 20 亿到正 20 亿）。
对于我们可能关心的多数事物，64 位是一个安全的大小，大约有 1800 亿亿个可能值（从负 900 亿亿到正 900 亿亿）。
当我们引入浮点数时，这个范围会变得更加复杂，因为有许多不同的表示形式，这些值的存储空间可达 256 位，但关键在于，通常总有一种表示形式可以满足你在 API 中所设想的范围。

虽然这些都是可行的选择，但你可能会问，为什么我们要关心数据库中数字的大小呢？
毕竟，API 的目的不就是抽象掉所有这些细节吗？
没错；但之所以重要，是因为不同的计算机和不同的编程语言处理数字的方式远非统一。
例如，JavaScript 甚至没有真正的整数类型，而只有一个 number 类型来处理该语言的所有数值。
此外，许多语言以截然不同的方式处理超大数字。
例如，在 Python 2 中，int 类型能够存储 32 位整数，而 long 类型可以处理任意大的数字，至少存储 36 位。
简而言之，这意味着如果 API 响应向消费者发送一个非常大的数字，接收端所使用的语言可能无法正确解析和理解它。
此外，这些潜在巨大数字的接收方需要知道分配多少空间来存储它们。
<ins>简而言之，边界将是非常重要的。</ins>

<ins>因此，常见的做法是在内部对整数依赖 64 位整数类型，除非有充分的理由不这样做。</ins>
总的来说，即使目前你可能远远用不到 64 位的范围，软件中绝对确定的事情也很少，
因此设置留有增长余地的上下限要安全得多。

### 5.3.2 默认值

正如我们在 [第 5.1.1 节](#missing-or-null) 中所了解的，对于大多数数据类型，我们还需要考虑其他场景，特别是 null 值和字段被完全省略的缺失值。
与布尔值（ [第 5.2 节](#booleans) ）类似，但在不提供让基本类型持有 null 值的机制的序列化格式中，
我们将无法区分真正的 0（或 0.0）值与用户表示 “我对此没有意见，你可以为我选择最佳值” 的默认值。

虽然可能依赖零值作为默认值的标志，但这存在一些问题，原因有几点。
<ins>首先，零值实际上可能是有意义且必要的，是 API 的一部分；</ins>
然而，如果我们将其用作默认值的指示符，我们就无法再表示真正的零值。
换句话说，如果我们使用 0 来表示 “做最合适的事情”（在这种情况下可能意味着值为 57），那么我们就无法实际指定一个有意的 0 值。
<ins>其次，特别是在零值在逻辑上可能有意义的情况下，将该值用作标志可能会引起混淆，并导致意想不到的后果，从而违背优秀 API 的一些关键原则（在本例中是可预测性）。</ins>

要回答如何处理数值默认值的问题，我们实际上需要转换思路，更详细地讨论这些值应如何序列化。

<a id="numbers-serialization"></a>
### 5.3.3 序列化

正如我们在第 5.3.1 节中所了解的，某些编程语言对数值的处理方式与其他语言不同。
当我们处理非常大的数字时，这一点尤其明显，至少是超过 32 位的数字，但超过 64 位限制的数字更是如此。
在处理十进制数时，由于浮点精度问题，这种情况也经常出现，这是该格式设计普遍存在的已知缺陷。

但归根结底，我们需要向 API 用户发送数值（并接收来自这些用户的传入数值）。
如果我们打算仅仅依赖序列化库而不进行更深入的探究，那么我们很可能会大失所望。

*清单 5.3 两个数字不同，但因数值过大而被视为相等*

```typescript
const compareJsonNumbers(): boolean {
  // 这两个数值明显不一样（相差1）
  const a = JSON.parse('{"value": 9999999999999999999999999}');
  const b = JSON.parse('{"value": 9999999999999999999999998}');
  // 但是，如果解析包含它们的JSON文档并进行比较，Node.js会认为二者相等！
  return a['value'] == b['value'];
}
```

这个问题不仅限于大整数。十进制数的浮点数运算同样存在隐患。

*清单 5.4 数字相加导致浮点数运算问题*

```typescript
const jsonAddition(): number {
  const a = JSON.parse('{"value": 0.1}');
  const b = JSON.parse('{"value": 0.2}');
  // 遗憾的是，该函数返回 0.30000000000000004，而不是 0.3
  return a['value'] + b['value'];
}
```

那么我们该怎么办呢？
<ins>清单 5.4 中的场景应该足以说明，使用数值并假设它们在不同语言中会保持一致可能相当危险。
简短的答案可能会让某些纯粹主义者感到沮丧，但它恰好效果不错：使用字符串。</ins>

这种简单的策略，即在序列化时将数值表示为字符串值，仅仅是一种避免将这些原始数值解释为实际数值的机制。
相反，这些值本身可以由一个库来解释，该库在处理这类场景方面可能做得更好。
<ins>换句话说，与其让 JSON 库将 0.2 解析为 JavaScript 的 Number 类型，我们可以使用像 Decimal.js 这样的库将该值解析为任意精度的十进制类型。</ins>

清单 5.5 正确执行数字相加以避免任何浮点问题

```typescript
const Decimal = require('decimal.js');

const jsonDecimalAddition(): number {
  // 注意这些数值是字符串，并非真正的数字
  const a = JSON.parse('{"value": "0.1"}');
  const b = JSON.parse('{"value": "0.2"}');
  // 当我们使用 decimal.js 这类任意精度库做加法时，可以得到正确结果（0.3）
  return Decimal(a['value']).add(Decimal(b['value']));
}
```

由于此策略的基础依赖于字符串，让我们花点时间探讨字符串字段。

<a id="strings"></a>
## 5.4 字符串

在几乎每种编程语言中，字符串往往是我们认为理所当然的东西，而没有真正理解它们在底层是如何工作的。
即使是我们这些花时间学习过 C 语言如何处理字符串的人，也倾向于回避字符编码和广阔的 Unicode 世界。
虽然不必成为 Unicode、字符编码或其他字符串相关主题的专家，但在考虑如何处理 API 中的字符串时，有几个方面相当重要。
由于 API 中的大多数字段往往是字符串，这就更加重要了。

在西方世界，将字符串视为表示文本内容的单个字符的集合是相当安全的。
这是一个相当大的概括，但这不是一本关于 Unicode 的书，所以我们只能进行概括。
由于我们希望在 API 中传递的大量内容本质上是文本，字符串可能是所有可用数据类型中最有用的。

字符串也可能是构建 API 时最通用的数据类型。
它们可以处理像姓名、地址和摘要这样的简单字段；它们可以负责大段的文本；
并且，在序列化格式不支持通过线路发送原始字节的情况下，它们可以表示编码后的二进制数据（例如 Base64 编码的字节）。
字符串也是存储唯一标识符的最佳选择，即使这些标识符碰巧看起来像数字而不是文本。
我们可能在底层将它们存储为字节（更多信息请参见 [第 6 章](ch6.md) ），但 API 中的表示形式几乎肯定最好使用字符串。

在我们开始大谈特谈字符串如何是世界的救星之前，让我们花点时间看看字符串字段的一些潜在陷阱，以及我们如何最有效地使用它们，首先从边界条件开始。

<a id="strings-bounds"></a>
### 5.4.1 边界

正如我们在 [第 5.3.1 节](#number-bounds) 中所学的，边界条件很重要，因为归根结底我们必须考虑分配多少空间来存储数据。
与数值一样，字符串值也有同样的方面需要考虑。
如果你曾经为关系数据库定义过模式，最终得到了 VARCHAR(128)，其中 128 是一个完全随意的选择，你应该对这种有时不受欢迎的必要性感到熟悉。

正如我们对数字所了解的，这些大小限制很重要，因为数据的接收方需要知道分配多少空间来存储这些值。
同样与数字类似，由于 API 生命周期早期低估而导致的大小增加是一种相当不舒服和不幸的情况。
因此，在选择字符串字段的最大长度时，通常最好倾向于向上取整。

不过，下一个值得解决的问题是如何定义最大长度。
事实证明，我们将字符串定义为字符集合的原始定义只在某些有限的情况下成立，因为许多语言并不像我们希望的那样严格遵守这一概念。
然而，更大的问题在于，存储空间的计量单位（磁盘上的字节数）与字符串长度的计量单位（我们所谓的字符）之间并不保持一对一的对应关系。
我们能做些什么呢？

<ins>为了避免写成整整一章关于 Unicode 的内容，对这个问题的简单回答是，继续以字符（尽管这些实际上是 Unicode 码点）为单位进行思考，然后为了存储目的而假设最冗长的序列化格式：UTF-32。</ins>
这意味着当我们存储字符串数据时，每个字符分配 4 个字节，而不是我们使用 ASCII 时可能预期的典型单字节。

无论这个存储空间难题如何，对于每个字符串字段，我们还需要考虑另一个方面：处理过长的输入。
对于数值，超出范围的值可以被 API 安全地拒绝，并附带友好的错误消息：“请选择 0 到 10 之间的值。”
对于字符串值，我们实际上有两种不同的选择。
我们可以像处理数字超出范围一样拒绝该值，但根据情况和上下文，这可能有点不必要。
<ins>或者，我们也可以选择在文本超过定义的限制时将其截断。</ins>

虽然截断看起来可能是个好主意，但它可能产生误导并让人感到意外，正如我们在 [第 1 章](ch1.md) 中所探讨的，这两者都不是优秀 API 的特征。
它还会为 API 引入一组新的选择（该字段应截断还是拒绝？），这可能导致进一步的不确定性，因为不同的字段表现出不同的行为。
<ins>因此，与数字类似，通常最合理的做法是拒绝任何超出字段定义限制的输入。</ins>

### 5.4.2 默认值

与数字和布尔字段类似，许多序列化格式不一定允许将不同的 null 值（null）与零值（""）区分开来。
因此，可能很难确定用户指定字符串应为空字符串，与用户根据其余上下文特别要求 API 对该字段 “做最合适的事情” 之间的区别。

幸运的是，有多种选择。
在许多情况下，空字符串对于字段来说根本不是有效值。
因此，空字符串确实可以用作一个标志，表示应注入并保存默认值。
在其他情况下，字符串值可能有一组特定的合适值，而空字符串是其中一种选择。
在这种场景下，完全允许选择 "default" 作为标志，表示应存储默认值。

<a id="strings-serialization"></a>
### 5.4.3 序列化

由于 Unicode 标准的普及，几乎所有的序列化框架和语言都以大致相同的方式处理字符串。
这意味着，与我们 [第 5.3 节](#numbers) 中探讨的数值不同，我们的重点不在于精度或微妙的溢出错误，
而在于安全地处理可能涵盖人类语言全范围（而不仅仅是西方世界使用的字符）的字符串。

在底层，字符串只是一块字节。
然而，我们解释这些字节的方式（编码）告诉我们如何将它们转换成看起来像实际文本的东西 —— 无论我们使用哪种语言。
简而言之，这意味着当需要序列化我们在 API 服务器上使用的字符串时，我们不能只是以我们当时碰巧使用的任何编码将其发送回去。
相反，我们应该标准化为一种编码格式，并在所有请求和响应中一致地使用它。

虽然有许多编码格式（例如 ASCII、UTF-8 [https://tools.ietf.org/html/rfc3629 ] 、UTF-16 [https://tools.ietf.org/html/rfc2781 ] 等），但世界已经倾向于 UTF-8，因为它对大多数常见字符相当紧凑，同时仍然足够灵活以编码所有可能的 Unicode 码点。
大多数面向字符串的序列化格式（例如 JSON 和 XML；https://www.w3.org/TR/xml/ ）已经采用 UTF-8，而其他格式（例如 YAML）则没有明确说明必须使用哪种编码。
<ins>简而言之，除非有充分的理由不这样做，否则 API 应该对所有字符串内容使用 UTF-8 编码。</ins>

如果你认为这是一个我们可以简单地让库来完成工作的地方，你几乎是对的，但也不完全正确。
事实证明，即使我们指定了一种编码，由于 Unicode 的规范化形式（https://unicode.org/reports/tr15/#Norm_Forms ），仍然有多种方式来表示相同的字符串内容。
这有点像我们可以表示数字 4 的各种方式：4、1+3、2+2、2*2、8/2 等等。
在 UTF-8 编码的字符串中，二进制表示也可能发生同样的情况。
例如，字符 “è” 可以表示为单个特殊字符（“è” 或 0x00e9），也可以表示为基本字符（“e” 或 0x0065）和重音字符（“`” 或 0x0301）的组合。
这两种表示在视觉和语义上是相同的，但它们在磁盘上不由相同的字节表示，因此，对于进行精确匹配的计算机来说，它们是完全不同的值。

为了解决这个问题，Unicode（http://www.unicode.org/versions/Unicode13.0.0/ ）支持不同的规范化形式，并且某些序列化格式（例如 XML）
标准化为特定形式（在 XML 的情况下，为规范化形式 C），以避免这些语义相同的文本表示形式混用。
虽然这对于表示 API 资源长格式描述的字符串来说可能并不那么重要，但当字符串表示标识符时，它就变得极其重要。
如果标识符可以有不同的字节表示，那么相同的语义标识符可能实际上指向不同的资源。
<ins>因此，对于 API 来说，拒绝未使用规范化形式 C 进行 UTF-8 编码的传入字符串是一个好主意，但对于碰巧表示资源标识符的字符串来说则是绝对必要的。</ins>
关于标识符及其格式的更多信息，请参见 [第 6 章](ch6.md) 。

<a id="enumerations"></a>
## 5.5 枚举

枚举，有点像程序员的 “下拉选择器”，是强类型编程语言中的一个基本特性。
虽然这些在 Java 等语言中可能是很好的东西，但它们移植到 Web API 的世界中往往是一个错误。

虽然枚举可能非常有价值，因为它们既可以作为一种验证形式（只有指定的值被认为是有效的），也可以作为一种压缩手段（每个值通常由一个数字表示，而不是我们在代码中引用的文本表示），但在 Web API 中，这两点好处通常是以降低灵活性和清晰度为代价的。

*清单 5.6 API 中将枚举用作类型*

```typescript
// 此处我们可以定义一组可用的颜色
enum Color {
  Brown = 1,
  Blue,
  Green,
  // 该列表后续还可以继续增加更多选项
}

interface Person {
  id: string;
  name: string;
  // 我们可以使用该枚举来表示人的眼睛颜色
  eyeColor: Color;
}
```

例如，让我们考虑清单 5.6 中的枚举。
如果我们使用其真实的整数值，最终可能会将 person.eyeColor 设置为 2。
显然，这比将 person.eyeColor 设置为 "blue" 要令人困惑得多，因为前者需要我查找数字值实际代表什么。
在代码中这通常根本不是问题；然而，在查看请求日志时，这会变得相当繁琐。

此外，当服务器添加新的枚举值时，客户端将需要更新他们自己本地映射的副本（通常需要更新客户端库），而不是简单地发送一个不同的值。
更糟糕的是，如果 API 决定添加一个新的枚举值，而客户端尚未被告知该值的含义，客户端代码将会感到困惑，不确定该怎么做。

例如，考虑 API 添加一个新的 Color 值（如 Hazel（#4））的场景。
除非客户端代码已更新以适应这个新值，否则我们可能会遇到一个相当令人困惑的情况。
另一方面，如果我们使用不同类型的字段（例如字符串），我们可能会因为一个先前未知的值而遇到类似的错误，但我们不会对该值的含义感到困惑（"hazel" 比 4 要清晰得多）。

<ins>简而言之，当另一种类型（如字符串）可以替代时，通常应避免使用枚举。</ins>
当预计会添加新值时尤其如此，而当所讨论的值存在某种标准时更是如此。
例如，与其对有效文件类型（PDF、Word 文档等）使用枚举，不如使用允许特定媒体类型（以前称为 MIME 类型）的字符串字段，例如 "application/pdf" 或 "application/msword"，这样要安全得多。

<a id="lists"></a>
## 5.6 列表

现在我们已经掌握了各种基本数据类型，可以开始深入探讨这些数据类型的集合，其中最简单的是列表或数组。
简而言之，列表只不过是一组其他数据类型的集合，例如字符串、数字、map（参见 [第 5.7 节](#maps) ）甚至其他列表。
这些集合通常可以通过列表中的索引或位置使用方括号表示法（例如 items[2]）来寻址，并且几乎所有序列化格式（例如 JSON）都支持它们。

虽然并非所有存储系统都原生支持条目列表，但请记住，API 的目标是提供对远程用户最有用的接口，而不是按数据库中的存储方式精确地暴露数据。
话虽如此，列表是当今 Web API 中最常被误用的结构之一。
那么，什么时候应该使用列表呢？

一般来说，列表非常适合表示 API 资源固有的简单基本类型集合。
例如，如果你有一个 Book 资源，你可能想要显示关于该书籍的类别或标签列表，这最好表示为字符串列表。

*清单 5.7 在 Book 资源上存储类别列表*

```typescript
interface Book {
  id: string;
  title: string;
  // 此处，书籍关联了一组字符串类型的分类
  categories: string[];
}
```

### 5.6.1 原子性

在这个例子中隐藏着一些需要记住的重要事项：列表字段虽然包含多个条目，
但最好在条目被视为一个原子数据块的情况下使用，即整体修改和替换，而不是逐个修改。
<ins>换句话说，如果我们想要更新 Book 资源上的类别，我们应该通过完全替换整个条目列表来实现。</ins>
换言之，永远不应该有一种方式来更新列表字段中的第二个条目。
这有许多很好的理由，例如当我们按条目在列表中的位置来寻址时，顺序变得极其重要，或者我们可能无法保证在此期间没有插入新条目，从而将目标条目推移到新的位置。

此外，就像资源上的任何其他字段一样，允许从两个不同的地方存储和修改数据几乎总是一个坏主意，因此允许多种方法更新列表字段中的内容是值得避免的。
这一点尤其具有诱惑力，因为我们被训练依赖关系数据库的规范化原则。
例如，如果我们使用 MySQL 之类的东西在 Book 资源上存储此类别列表，我们可能实际上有一个单独的 BookCategories 表，
其中包含唯一标识符、指向书籍的外键以及具有唯一性约束的类别字符串。
通过公开一个 API 来更新这些书籍类别，提供一个书籍的唯一 ID 和我们想要编辑的类别，这种编辑类别的做法是很有诱惑力的（因为从技术上讲，这足以唯一标识所讨论的行）。

<ins>允许这种修改会打开一个与一致性相关的可怕 “潘多拉魔盒”：可能有人在设置类别列表的同时，另一个人正在使用不同的入口点编辑单个类别。
在这种情况下，即使依赖其他事务隔离机制（例如 ETags；https://tools.ietf.org/html/rfc7232#section-2.3 ）也不会有太大用处，导致 API 充满意外。</ins>

对于列表值，一个很好的经验法则是几乎将其视为实际是 JSON 编码的字符串条目列表。
<ins>换句话说，你不是在设置 book.categories = ["history", "science"]，而是类似于 book.categories = "[\"history\", \"science\"]"。
你永远不会期望 API 允许你修改字符串中的单个字符，所以也不要期望 API 允许你修改列表字段中的单个条目。</ins>

关于这些主题以及资源之间的相互关系，请参阅 [第 4 部分](part4.md) ，特别是第 13、14 和 15 章，它们都涉及使用列表字段在 Web API 中表示关系数据的思想。

接下来要考虑的是，列表是否应允许同一列表中有不同的数据类型。
换句话说，将字符串值与数值混合在同一个列表中是个好主意吗？
虽然这样做并不完全是灾难性的，但它可能导致一些混淆，特别是考虑到 [第 5.3.3 节](#numbers-serialization) 关于处理大数字和小数的指导。
这些值可能被表示为字符串，因此可能很难分辨给定条目实际上是字符串，还是仅以字符串表示的数值。
<ins>基于此，通常最好坚持使用单一数据类型，并保持列表值的同质性。</ins>

### 5.6.2 边界

最后，列表值一个非常常见的场景涉及大小：当列表变得过长以至于难以管理时会发生什么？
<ins>为了避免这种令人沮丧的情况，所有列表都应该有一些强制的边界，指定它们最多可以包含多少项，以及每项的最大大小</ins>
（关于如何处理数字和字符串数据类型的边界，请参见 [第 5.3.1 节](#number-bounds) 或 [第 5.4.1 节](#strings-bounds) ）。
<ins>此外，超出这些边界的输入应该被拒绝而不是截断（原因与 [第 5.4.1 节](#strings-bounds) 中所述相同）。</ins>
这有助于避免因意外增长到难以处理的大小的超大列表值而带来的意外和困惑。

<ins>如果列表的潜在大小难以估计，或者有充分的理由怀疑它可能在没有硬性边界的情况下增长，那么最好依赖实际资源的子集合，而不是资源上的内联列表。</ins>
虽然这可能看起来很麻烦，但当资源不会因为无界列表字段而变得巨大时，API 在将来会更容易管理。
然而，如果你最终陷入困境，请参考分页模式（ [第 21 章](ch21.md) ），它可以帮助将庞大而难以管理的资源分解成较小的可管理块。

### 5.6.3 默认值

列表与字符串类似，因为在某些序列化格式和库中，没有简单的方法来区分零值（对于列表为 []）和 null 值。
然而，与字符串不同的是，空列表作为值几乎总是合理的，这使得 API 不太可能依赖空列表值来表示 “使用某个默认值而不是空列表” 的请求。
这给我们留下了一个复杂的问题：在这种场景下，你如何指定你想要的是默认值，而不是字面上的空列表？

不幸的是，在这种情况下似乎没有任何简单优雅的答案。
要么可以在创建时使用默认值（假设空列表对于新创建的资源不是有效的），要么列表值根本就不是这种信息的正确数据类型。
如果前一种情况因某种原因不适用，那么唯一其他安全的选择是完全跳过列表值，转而将此数据作为从父资源中单独管理的适当子资源集合进行管理。
显然这不是理想的解决方案，但考虑到这些限制，这肯定是最安全的选择。

<a id="maps"></a>
## 5.7 Maps

最后，我们可以讨论我们可用的最通用和最有趣的数据类型：map。
在本节中，我们将实际考虑两种相似但不同的基于键值的数据类型：
自定义数据类型（我们一直称之为资源或接口）和动态键值 map （通常 JSON 称之为对象或 map ）。
虽然这两者并不完全相同，但它们之间的区别是有限的，主要区别在于是否存在预定义模式。
换句话说，map 是键值对的任意集合，而自定义数据类型或子资源可能以相同的方式表示；
然而，它们具有预定义的键集以及对应值的特定类型。让我们从具有预定义模式的那些开始。

随着资源演变为表示越来越多的信息，一个典型的步骤是将类似的信息分组在一起，而不是保持所有内容扁平化。例如，当我们向 ChatRoom 资源添加越来越多的配置时，我们可能会决定将其中一些配置字段分组在一起。

*清单 5.8 将数据直接存储在资源上，还是存储在单独的结构中*

```typescript
interface ChatRoomFlat {
  id: string;
  name: string;
  password: string;
  // 在扁平化方案中，所有字段直接存储在资源对象上
  requirePassword: boolean;
  allowAnonymousUsers: boolean;
  allowChatBots: boolean;
}

interface ChatRoomReGrouped {
  id: string;
  name: string;
  // 这里我们把所有和聊天室访问相关的信息提取到独立结构中
  securityConfig: SecurityConfig;
}

// 这里我们把所有和聊天室访问相关的信息提取到独立结构中
interface SecurityConfig {
  password: string;
  requirePassword: boolean;
  allowAnonymousUsers: boolean;
  allowChatBots: boolean;
}
```

在这种情况下，我们只是根据它们共同的主题（控制聊天室的安全和访问）将几个字段分组在一起。
这种抽象层次之所以有意义，仅仅是因为我们真正在考虑的是对资源中相似字段进行分组。
另一方面，如果这些字段与资源相关，但在资源上下文之外也具有根本性的不同和意义，那么探索单例子资源可能是值得的，这将在 [第 12 章](ch12.md) 中解释。

现在我们已经探讨了具有预定义模式的自定义数据类型，让我们花点时间看看动态键值 map 。
<ins>虽然它们最终可能以相同的方式呈现，但这两种结构通常以非常不同的方式使用。
我们使用自定义数据类型作为将相似字段折叠在一起并将它们隔离在单个字段中的方式，而动态键值 map 更适合存储任意、动态的、没有预期结构的数据。
换句话说，自定义数据类型只是重新排列我们已知并希望更好组织的字段的一种方式，而 map 更适合处理键在我们定义 API 时未知的动态键值对。</ins>
此外，虽然这些键在不同资源之间可能存在一些重叠，但绝对不要求所有资源都像自定义数据类型字段那样具有相同的键。

<ins>这种任意结构的键值对非常适合处理动态设置或依赖于特定资源实例详细信息的配置。</ins>
为了理解这意味着什么，假设我们有一个用于管理杂货店商品产品信息的 API。
显然，我们需要一种方式来说明每种产品中含有什么成分以及含量，例如 3 克糖、5 克蛋白质、7 毫克钙等等。
用一个预定义模式列出所有可能的成分来做这件事会相当困难，即使我们能够做到，这些项目的许多值也会为零，因为每个项目都有各种不同的成分。
在这种情况下， map 可能最合理。

*清单 5.9 使用 map 字段跟踪成分和含量*

```typescript
interface GroceryItem {
  id: string;
  name: string;
  calories: number;
  // 我们可以使用 map 结构保存配料到用量的对应关系
  ingredientAmounts: Map<string, string>;
}
```

使用定义的 schema，GroceryItem 的 JSON 表示可能类似于清单 5.10。
在这种情况下，成分是动态的，并且每个不同项目都可以自由变化。

*清单 5.10 成分表的 JSON 表示示例*

```typescript
{
  "id": "514a0119-bc3f-4e3f-9a64-8ad48600c5d8",
  "name": "Pringles",
  "calories": "150",
  "ingredientAmounts": {
    "fat": "9 g",
    "sodium": "150 mg",
    "carbohydrate": "15 g",
    "sugar": "1 g",
    "fiber": "1 g",
    "protein": "1 g"
  }
}
```

需要注意的是，由于我们可以选择 map 键的数据类型，从技术上讲，我们可以自由选择任何类型。
某些键类型的选择可能是灾难性的（例如，某种不易序列化的丰富数据类型）。
其他选择可能看起来可以接受，但仍然是个坏主意。
例如，从技术上讲，允许数值作为 map 的键类型可能看起来合理；但正如我们在 [第 5.3.3 节](#numbers-serialization) 中所学，
数值存在一些相当危险的问题，特别是当它们很大时，有时甚至只是小的十进制值也会有问题。
因此，字符串几乎肯定是 map 键数据类型的最佳选择。

更重要的是，由于 map 键在技术上是唯一标识符，这些字符串值应以 UTF-8 格式编码也很重要，
而且正如我们在 [第 5.4.3 节](#strings-serialization) 中学到的（并将在 [第 6 章](ch6.md) 中了解更多），这些字符串应采用规范化形式 C，以避免因字节表示问题而导致重复的键值。

### 5.7.1 边界

虽然自定义数据类型的模式避免了任何边界问题（相反，schema 定义了自身的边界条件），但 map 与列表非常相似，因为它们都很容易失控增长。
<ins>因此，与列表一样，map 应定义字段中可包含的键值对数量的上限。</ins>
这一点变得相当重要，因为它设定了字段内容可能增长到多大的预期。
<ins>除此之外，设置每个键和每个值作为字符串的最大长度也很重要（有关字符串值边界的更多信息，请参见 [第 5.4.1 节](#strings-bounds) ）。
通常，这可以规定键最多约 100 个字符，值最多约 500 个字符。</ins>

在极少数情况下，值的大小可能分布不均。
因此，一些 API 选择对 map 字段中存储的总字符数提供上限，允许用户自由决定这些不同字符的分布方式（几个非常小的值和一两个非常大的值）。
虽然这在绝对必要时是一种可接受的策略，但应尽量避免，因为它往往会导致滑坡效应，使得越来越多的数据最终被存储在映射中，而实际上这些数据可能更适合存储在其他地方。

### 5.7.2 默认值

<ins>与列表不同，在几乎所有序列化格式和语言中，区分空 map 值或零值（{}）与 null 值（null）是相当容易的。</ins>
在这种情况下，让 null 值表示 API 应根据 API 请求的其余部分对该字段做最合适的处理，是相当安全的。
另一方面，空 map 是用户指定 map 不应包含任何数据的方式，这本身就是一个有意义的陈述。

<a id="summary"></a>
## 本章小节

- 对于每个值，我们还需要考虑 null 值和未定义或缺失的值，它们可能具有相同含义，也可能不同。
- 布尔值最适合用于标志，并且命名时应当使 true 值表示正向含义（例如 enableFeature 而不是 disableFeature）。
- 数值应当具有真正的数字含义，而不仅仅是数字字符组成。
- 为避免大数字（超过 32 位或 64 位）或浮点数运算问题，在缺乏适当原生表示的语言中，数值应以字符串形式序列化。
- 字符串应使用 UTF-8 编码，对于任何用作标识符的字符串，应规范化为规范化形式 C。
- 通常应避免使用枚举，转而依赖字符串值，并在服务端（而非客户端）进行验证。
- 列表应被视为原子集合，其中条项仅在客户端可单独寻址。
- 列表和 map 都应限制集合中允许的条项总数；此外，map 还应进一步限制键和值的大小。
