# 序言

这一切始于一套电子鼓。
2019年夏天，我的一个朋友让我迷上了用电子鼓套件打鼓，我全身心地投入其中。
有时我确实会打鼓，但我花了相当多的时间编写代码，使用 MIDI SysEx 命令与我的鼓套件配置进行交互。

当 COVID-19 疫情来袭时，我在考虑我所在当地教会的音视频需求时，突然有了截然不同的优先事项，无论是在我们远程礼拜期间，还是在考虑我们如何能再次线下聚会时。
这涉及学习诸如 VISCA、NDI 和 OSC（用于摄像机和音频调音台）等协议，以及与 Zoom、VLC、PowerPoint、Stream Deck 等更多软件层面的集成。

这些项目没有大量的业务逻辑。
几乎所有的代码都是集成代码，这既令人沮丧，又极大地赋能 (empower)。
之所以令人沮丧，是因为协议文档晦涩难懂，或者并非真正为我试图实现的那种用途而设计，又或者只是彼此之间不一致。
之所以令人赋能，是因为一旦你攻克了集成的难题，你就可以站在多个巨人的肩膀上，非常轻松地编写出有用的应用程序。

虽然我过去几年的经验主要是本地集成，但沮丧与赋能的这种共存同样适用于 Web API。
我每次接触一个新的 Web API 的经历，都伴随着一条情绪反应曲线，其中包含兴奋、困惑、烦恼、接受以及最终不安的平静等各种情绪。
一旦你彻底理解了一个强大的 API，你就会感觉自己像是一个宏伟管弦乐队的指挥，随时准备演奏你提供的任何音乐 —— 即使小提琴手的音符只是最终一致，并且你不得不因为一些不明显的原因，为铜管乐队使用不同颜色的指挥棒。

这本书本身不会改变这一点。
它只是一本书。但如果你阅读它并遵循它的指导，你可以帮助改变你的用户的体验。
如果很多人阅读它并遵循它的指导，我们也许能够共同推动指针，朝向更一致、更少令人沮丧的 Web API 体验。

重要的是要理解这本书的价值不仅仅在于其各部分的总和。
对于 JJ 深入探讨的任何一方面，任何一个团队都可能做出合理的选择（尽管可能错过这里指出的某些边界情况）。
由于上下文的局限性，那个选择甚至可能比本书中提供的推荐更适合特定情况。
这种方法会做出许多局部最优的决策，但会导致高度碎片化的全局图景，即使是同一家公司内部的 API，也可能采用几种不同的方法。

除了针对任何给定问题的一致性之外，本书还提供了一种跨多个 API 设计领域的一致方法。
API 设计者很少有机会深入思考这一点，我很幸运能与 JJ 和其他人（尤其是 Luke Sneeringer）一起讨论书中的许多主题。
我很高兴 Google 在 API 设计方面的投资能够通过本书以及 https://aip.dev 上的 AIP 系统为其他开发者带来回报。

虽然我对本书的价值充满信心，但它并不能让你轻松设计出一个出色的 API。
相反，它消除了 API 设计中附带的大量复杂性，让你能够专注于你真正想要构建的 API 所独有的方面。
你仍然需要思考，并且深入思考，但要相信思考的结果可以是一个使用起来令人愉悦的 API。
你的用户可能永远不会明确地感谢你；一个设计良好的 API 往往感觉显而易见，尽管它是大量辛勤工作的成果。
但你可以安心入睡，因为你知道他们不会体验到那种 API 感觉不太对劲的挫败感，即使它能正常工作。

把这本书当作一个脚凳，帮助你设计的 API 成为一个巨人，为他人提供可以站立的肩膀。

<p align="right">—Jon Skeet，Staff Developer Relations Engineer，Google</p>
