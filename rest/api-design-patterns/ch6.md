<a id="what"></a>
## 6.1 什么是标识符？

首先，当我们谈论资源标识符时，我们具体指的是什么？
<ins>简而言之，标识符为我们提供了一种在 API 中唯一寻址和指代单个资源的方式。</ins>
用更技术的术语来说，这些标识符是一块字节（通常是字符串值或整数），我们可以用它们作为指向资源集合中恰好一个资源的方式。
几乎在所有情况下，这些标识符都使 API 的用户能够执行某种类型的查找操作。
换句话说，这些标识符用于在更大的资源集合中寻址单个资源。

事实证明，我们在日常生活中也经常使用这样的标识符；然而，并非所有标识符都同样有用（甚至同样唯一）。
例如，许多政府使用姓名和出生日期作为个人标识符，但已有大量案例表明，基于 “没有两个人共享相同的姓名和出生日期” 这一假设会导致人员混淆。
更好的选择，至少在美国，是社会保障号码（政府分配的九位数字），它用于在大多数金融交易（例如纳税或申请贷款）中唯一标识个人，但该号码也有其自身的一系列缺点。
例如，SSN 目前总共限制为最多 10 亿人（九位数字），因此随着美国人口逐年增长，该国可能会用完可供发放的号码。

在 API 中为资源拥有标识符显然很重要；
然而，这些标识符具体应该长什么样则远不那么清楚。
换句话说，我们未必已经说明了什么属性使某些标识符好，而另一些标识符差。
在下一节中，我们将更详细地探讨这些问题。

<a id="what-makes-good-identifier"></a>
## 6.2 什么因素造就了好的标识符？

由于我们在 API 中需要交互的几乎所有资源都需要标识符，显然标识符很重要。
而且由于作为 API 设计师，我们需要选择这些标识符的表示形式，这就留下了一个大问题：什么因素造就了好的标识符？
为了回答这个问题，我们需要探索标识符的许多不同属性，以及我们需要在它们之间进行选择的各种选项。
目前，我们将只专注于属性本身，稍后（在 [第 6.3 节](#what-does-good-identifier-look-like) 中）再给出更具体的建议。

### 6.2.1 易于使用

<ins>最简单的起点也是最明显的之一：标识符在最常见的场景中应易于使用。</ins>
标识符最典型的场景可能是在 Web API 中查找单个资源（即我们在第 1.4 节中学习的标准 get 方法）。这意味着向服务器发送 “请给我资源 \<ID>” 的请求应尽可能简单直接，同时最大程度地减少出错的可能性。
特别地，这必须考虑到标识符经常出现在 URI 中的事实。
这意味着，例如，在标识符中使用正斜杠（“/”）或其他保留字符会有些棘手，因为它们在 URI 中具有特殊含义，应尽量避免使用。

### 6.2.2 唯一性

<ins>好的标识符的另一个明显要求可能是它必须是真正唯一的。</ins>
换句话说，根据定义，标识符必须是完全独一无二的，否则它就无法真正完成其工作，即唯一标识单个资源。
这可能看起来有点过于简单，但关于 “真正唯一” 的含义，有一些细微之处需要我们注意。
其中之一是，唯一性很少是绝对的，而通常取决于考虑标识符的上下文或范围。
例如，在计算机公司的范围内，Apple 被视为唯一标识符（在计算机公司的范围内只有一个 Apple），
但在所有公司的范围内，Apple 实际上并不是唯一的（还有 Apple Records、Apple Bank 等）。
我们需要决定标识符需要在同一类型的所有资源中唯一、在同一个 API 的所有资源中唯一，还是在世界上所有资源中唯一。
诚然，真正的全局唯一性在理论上是不可行的，但考虑到足够大的键空间（标识符的可能选择）且没有故意的恶意行为者，在实践中应该是可行的。

<a id="permanent"></a>
### 6.2.3 永久性

<ins>接下来，稍微更微妙的一点是，标识符一旦分配，可能就不应该更改。</ins>
这主要是因为标识符确实发生更改的场景中会引入潜在问题（因此需要做出进一步决策）。
例如，想象一下 Book (id=1234, name="Becoming") 更改了其标识符并变为 Book (id=5678, name="Becoming")。
这本身可能没什么大不了的，但再考虑一下，一本新书被创建了：Book (id=1234, name="Design Patterns")。
在这种情况下，这本新书重用了原始标识符（1234），这最终意味着，根据你何时请求 Book 1234，你会得到不同的结果。

对于大多数场景来说，这可能没什么大不了的，但想象一下用户可以指定他们最喜欢的书，而有人选择了 Book 1234 作为他们最喜欢的书（User (favoriteBook=1234, ...)）。
这就引出了一个非常合理的问题：他们最喜欢的书是 Becoming 还是 Design Patterns？
在这个标识符不是永久性的世界里，为了回答我们指的是哪本书的问题，我们还需要知道该偏好是何时选择的，或者更具体地说，它是什么时候检索了 Book 1234。
没有这些信息，就不清楚我们实际谈论的是哪本书。
因此，不仅标识符最好是永久性的，而且最好是一次性的，永远不变。
换句话说，一旦 Book 1234 存在，即使在原始的 Book 1234 被删除之后，你也永远不应再使用相同的标识符。

### 6.2.4 快速且易于生成

到目前为止，我们一直使用像 “1234” 这样的简单数字作为示例标识符，但在现实生活中，这些不太可能是实际的标识符。
<ins>相反，这些标识符更有可能具有某种随机性元素，而不是依赖于递增的整数。
由于这通常意味着在选择这些标识符时有更多的计算，因此确保进行该选择不会花费太长时间是很重要的。</ins>

例如，由于我们说所有标识符必须是永久性的且永远一次性使用，这意味着我们需要确保我们选择的任何 ID 之前都未被使用过。
我们可以通过维护所有资源的列表并随机选择 ID，直到找到之前未使用过的 ID 来实现这一点，但这并不是最高效也不是最简单的选择。
而且随着时间的推移，它可能会变得越来越慢，使其成为更糟糕的选择。
<ins>无论我们选择什么方案，它都应该快速且易于实现，而且最重要的是，具有可预测的性能特征。</ins>

<a id="unpredictable"></a>
### 6.2.5 不可预测性

<ins>虽然标识符在选择时快速且易于实现（且具有可预测性）很重要，但同样重要的是，让别人难以预测下一个标识符将是什么。</ins>
归根结底，这涉及到安全性，并且可以通过足够大的键空间轻松解决，但如果选择这些标识符的方法像选择下一个可用数字一样简单，
那么攻击者就更容易针对和利用潜在漏洞，例如配置错误的安全规则。

例如，如果一个攻击者只是在随机探测，在 256 位整数的随机分配键空间中检查意外未受保护的资源，那么他们碰巧落在某个存在的资源上的可能性非常小，更不用说配置错误的资源了。
另一方面，如果我们使用一种更可预测的方法，例如在同一键空间（1, 2, 3, ...）上对整数进行计数，那么攻击者几乎可以肯定能找到存在的资源，并希望碰巧遇到一个配置错误、向世界开放而不是被锁定的资源。

<a id="read-share-verify"></a>
### 6.2.6 可读、可分享且可验证

接下来，虽然我们作为工程师可能不愿承认，但我们在 API 中使用的标识符有时可能需要通过电话传达、粘贴到文本消息中，或通过其他非计算媒介分享。
这意味着，例如，我们不希望数字 1、小写字母 l、大写字母 I 或竖线字符（|）之间产生混淆，因为将它们写在纸上可能很棘手（尝试在电话中传达 "l1Il|lI1I1lIl1I1l1lI"，即使在代码字体中也很棘手！）。
<ins>简而言之，我们应该考虑到标识符将由人类解释和传达，因此它们在这一方面不应不必要地难以使用。</ins>

<ins>除了便于沟通之外，一个好的标识符还应能让你快速判断标识符本身是否被抄错。</ins>
换句话说，我们应该能够区分指向空无一物的有效标识符和永远不会指向任何东西的完全无效标识符。
提供这一点的一个简单方法是使用标识符的简单校验和段。
这并非异想天开，而是经常被使用。
例如，用于书籍的标识符称为 ISBN（ https://en.wikipedia.org/wiki/International_Standard_Book_Number ），它们正是以这种方式工作，即书籍 ISBN 的最后一位数字用作校验位，以验证其他数字实际上是否合理且没有被输入错误。

### 6.2.7 信息密度高

最后，标识符将一直被使用，因此大小和空间效率将很重要。
<ins>这意味着我们应该力求在尽可能短的值中打包尽可能多的信息。</ins>
这可能意味着选择更密集的字符集，例如 Base64（ https://tools.ietf.org/html/rfc4648 ），而不是密度较低的字符集，例如简单的数字。
在这个例子中，考虑一下，如果我们使用数字 ID，每个字符只能存储总共 10 种选择，但如果使用 Base64 编码文本，每个字符可以存储 64 种选择。

优化信息密度将与其他构成好标识符的属性取得平衡。
例如，Base64 有许多可用字符，但这些字符包括小写 “i”、大写 “I” 和数字 “1”，我们了解到，这些字符在书写或阅读时可能会造成混淆。
为了了解这一切如何综合起来，让我们看看在选择这些标识符格式时可能涉及的各种设计考虑因素。

<a id="what-does-good-identifier-look-like"></a>
## 6.3 好的标识符实际长什么样？

现在我们已经对好的标识符应具备哪些属性有了不错的了解，我们可以尝试实现一种用于定义资源标识符的方案。
首先，我们将逐步介绍建议的实现方式，然后将其与 [第 6.2 节](#what-makes-good-identifier) 中描述的各项标准进行比较。

### 6.3.1 数据类型

在我们深入探讨其他方面之前，首先需要确定用于存储这些标识符的数据类型。
<ins>虽然有很多合理的选择，但字符串到目前为止是最通用的，因此也是推荐的选择。</ins>
它们提供了最高的信息密度（在 HTTP 上每个字符使用 7 位熵），使用起来很熟悉，并且在决定如何使它们易于分享、阅读和复制方面提供了很大的灵活性。

虽然有其他几种选择，从常见的（例如正整数）到不太常见的（原始未解释的字节），
但这些选择都因其类型而带来了人为的限制（例如，整数限于每个 ASCII 字符 10 种选择，或在 HTTP 上每个 ASCII 字符约 3.3 位熵）
或其他缺点（例如，原始字节在许多编程语言中不便处理）。

由于我们已经确定了使用字符串，因此我们面临着一系列全新的问题。
首先，这些字符串的字符集是什么？
我们可以使用任何有效的 Unicode 字符串吗？
还是有限制？之后，我们必须决定是否允许所有字符。
例如，在 HTTP 中，正斜杠字符（“/”）通常用于表示分隔符，因此我们可能不希望它在我们的标识符中。
此外，正如我们之前了解的，某些字符（如竖线字符 “|”）容易与其他字符（如 “I”、“1” 或 “l”）混淆。
我们该如何处理这些？让我们从字符集开始。

### 6.3.2 字符集

尽管我很想回顾并解释 Unicode 及其所有内部工作原理，但这不仅会花费太长时间，而且我怀疑我对该标准的了解仍然存在空白。
因此，我将专注于一些涉及字符集的简单示例，以阐明为什么此实现将依赖于 ASCII（美国信息交换标准代码）。

ASCII 非常简单：7 位数据表示 128 个不同的字符。
这些数据通常被塞入 8 位字节中，当今大多数 Web API 交互时所使用的 HTTP 请求都会使用该字节。
正如你可能猜到的，远不止 128 个不同的字符，这正是 Unicode 规范旨在解决的问题。
这很好；然而，在追求终极向后兼容性的使命中，Unicode 实际上允许有多种方式来表示我们认为相同的文本块。
例如，“á” 可以表示为单个 Unicode 码点（U+00E1），也可以是 “a” 和重音符码点（U+0061 和 U+0301）的组合。
虽然这些在我们的屏幕上（或纸上）看起来都像 “á”，但当存储在数据库中时，它们看起来非常不同——这正是问题所在，因为计算机看到的不是视觉上的 “á” 字符；它们看到的是构成它的字节。

虽然确实有一些方法可以解决这个问题（例如，使用规范化形式 C 和其他 Unicode 技巧），但这些模糊性带来的问题远多于它们的价值
（例如，你现在必须指定如何处理未以规范化形式 C 提交的数据等）。
<ins>因此，对于现代 Web API 来说，最安全的选择是依赖 ASCII 作为唯一标识符。</ins>

现在我们确定了使用 ASCII，我们需要决定是否由于其他考虑而进一步将其限制为 128 个字符的子集。

### 6.3.3 标识符格式

如果我们能使用 ASCII 提供的全部 128 个字符（甚至 Unicode 标准可以表示的所有字符串），那当然很好，
但我们需要考虑标识符的一个重要且理想的属性，即我们在 [第 6.2.6 节](#read-share-verify) 中讨论过的：易于阅读、分享和复制。
简单来说，这意味着我们需要避免使用 ASCII 中容易与其他字符混淆或可能混淆 HTTP 请求中 URL 的字符。
<ins>这引出了一个非常有用的序列化格式：Crockford 的 Base32（ https://www.crockford.com/base32.html ）。</ins>

Crockford 的 Base32 编码依赖于使用 128 个可用 ASCII 字符中的 32 个，而不是全部 128 个。
这包括 A 到 Z 和 0 到 9，但去掉了许多特殊字符（如正斜杠）以及 I、L、O 和 U。
前三个字符被去掉是由于潜在的混淆（I 和 l 可能与 1 混淆，O 可能与 0 混淆），而第三个字符（U）被去掉则是出于另一个有趣的原因：避免脏话。
事实证明，通过去掉 U 字符，标识符中意外出现英文脏话的可能性实际上降低了。

说到这里，你可能还注意到了另一个令人费解的地方：我们为什么要费心去掉 L？
毕竟，大写形式不会与任何东西混淆；然而，小写形式（与 1）可能会混淆。
原因是这种格式具有单一的规范形式，由大写字母（除上述提到的以外）和 0–9 组成，但它在解码各种输入时更能包容错误。
在这种情况下，该算法不会简单地说 L 是无效字符，而是会假设它（在小写形式下）被误认为是数字 1，并按此处理。
这种大小写不敏感性更普遍地适用（例如，a 被视为 A），并且也适用于其他可能混淆的字符，例如 O 和 o（将被视为 0）。
换句话说，这种格式对错误极其友好，其设计目的是基于这些错误将继续发生的假设，从而能够做出正确的处理。

最后，Crockford 的 Base32 编码将连字符视为可选的，这意味着我们可以灵活地根据需要引入连字符以提高可读性。
这意味着我们可以有像 abcde-12345-ghjkm-67890 这样的 ID，它在 Crockford 的 Base32 中的规范表示形式为 ABCDE12345GHJKM67890。

<ins>简而言之，Crockford 的 Base32 编码满足了 [第 6.2 节](#what-makes-good-identifier) 中概述的相当多的标准：它易于使用，易于生成唯一值，提供了相当高的信息密度（每个 ASCII 字符 32 种选择或 5 位），易于使其不可预测，
而且最重要的是，由于其包容和灵活的解码过程，它非常可读、可复制和可分享。</ins>
现在我们只需要解决几个更多的问题。

<a id="checksums"></a>
### 6.3.4 校验和

[第 6.2.6 节](#read-share-verify) 中列出的关键要求之一是能够区分缺失的标识符（例如，它从未被创建或已被删除）与根本不可能存在的标识符，后者意味着标识符中明显存在错误。
一种简单的方法是在标识符中包含某种形式的完整性检查。
这种完整性检查通常采取标识符末尾固定数量的校验和字符的形式，这些字符派生自标识符本身的其余内容。
然后，在解析标识符时，我们可以简单地重新计算校验和字符并测试它们是否匹配。
如果它们不匹配，则标识符的某一部分已被损坏，因此被视为无效。

Crockford 的 Base32 包含一个基于模运算的简单算法。
简而言之，我们将该值视为一个整数，将其除以 37（大于 32 的最小质数），并计算该值的余数。
然后我们使用一个 Base37 数字（该规范包含 5 个额外的校验和数字字符）来表示余数值。

### 6.3.5 资源类型

虽然我们主要关注标识符的唯一部分，但从标识符中获知资源的类型也非常有价值。
换句话说，仅仅被告知一个资源的 ID 是 abcde-12345-ghjkm-67890 并不是很有用，除非你还被告知所涉及资源的类型（例如，以便你可以决定调用哪个 RPC 或访问哪个 URL 来检索该资源）。
一个常见的解决方法是在 ID 前面加上所涉及集合的名称，例如 books/abcde-12345-ghjkm-67890。
通过这样做，我们可以获取该标识符，了解它所指的资源类型，并对其进行有用操作。
通过使用正斜杠作为分隔符，我们最终得到一个适合放在 HTTP 请求中的完整标识符（例如，GET /books/abcde-12345-ghjkm-67890 ）。
还有许多其他可选方案（例如，使用冒号字符，得到类似 book:abcde-12345-ghjkm-67890 的 ID）；
然而，鉴于与 HTTP 的良好关系以及在标准 URL 中的实用性，使用带集合名称的正斜杠往往是一个很好的选择。

<a id="hierarchy-and-uniqueness-scope"></a>
### 6.3.6 层级结构与唯一性作用域

既然我们已经决定将集合名称作为标识符的一部分（例如 books/1234 而不是仅 1234），这就引出了一个新的问题：层级结构在标识符中如何工作？
例如，如果我们同时有 Book 资源和 Page 资源（页面属于书籍），我们是在标识符中表达这种层级关系，还是将每个资源都作为各自的顶级资源？
换句话说，Page 资源的标识符会是像 pages/5678（顶级资源）这样，还是像 books/1234/pages/5678（在标识符中表示层级关系）这样？

<ins>答案是，层级关系非常有用，应在适当时使用，但只有在一组特定的场景下它们才有意义（而在许多情况下，层级结构并不是一个好的选择）。
API 设计者常常依赖层级关系来表达两个资源之间的关联关系，而不是归属关系，这可能会带来问题。</ins>
例如，我们可能会说 “Book 1 当前在 Shelf 1 上”，最终得到像 shelves/1/books/1 这样的资源标识符。
不幸的是，由于书籍可能会随着时间的推移在书架之间移动，我们会想要更改标识符以反映这种移动。
而且，正如你可能猜到的那样，这直接违背了我们在 [第 6.2.3 节](#permanent) 中定义的永久性要求。

虽然规定 “书籍永远不得在书架之间移动”（在这种情况下，这种标识符是完全合理的）可能完全合理，但这种行为限制实际上并不必要。
相反，我们应该认识到书籍在当前书架上的位置是书籍本身的一个可变属性，
并将 shelfId 作为 Book 资源的一个属性存储。

<ins>究竟什么时候使用层级标识符才有意义？
一般来说，只有当层级关系表示一个资源对另一个资源的真正归属关系时，特别是关注关系的级联特性时，API 才应依赖层级关系。
这意味着当我们想要级联删除（如果你删除父级，它也会删除子级）或级联安全规则（在父级上设置安全规则，它们会向下流向子级）时，我们应该将资源放置在另一个资源之下。</ins>
而且，正如我们之前所指出的，资源显然不应能够从一个父级移动到另一个父级。
例如，虽然 Books 可能会在 Shelves 之间移动，但 Pages 通常不会在 Books 之间移动。
这意味着我们会将 Page 资源标识为 books/1/pages/2，而不是仅仅 pages/2。

此外，在我们依赖层级标识符来表达归属关系的情况下，重要的是要记住，子资源（页面）只存在于其父级（书籍）的上下文中。
这意味着我们永远不能单独谈论 page 2，因为它会引出一个显而易见的问题：是哪本书的第 2 页？
实际上，这意味着页面的标识符始终包含父资源的标识符。

这就引出了一个稍微更微妙但仍然相当重要的问题：我们可以有多个 ID 都为 “2” 的页面吗？
例如，我们可以同时有 books/1/pages/2 和 books/9/pages/2 吗？
这个具体的例子应该能使答案明显为 “是”。
毕竟，很多书都有第二页。
由于父资源不同，且标识符是两者在层级关系中的组合，虽然这两个标识符相似（都以 “pages/2” 结尾），但这两个字符串完全不同，并且这两个页面属于完全不同的书（在本例中，是 book 1 和 book 9）。

现在我们已经了解了好的标识符可能是什么样子，让我们看看创建和使用符合这些期望的标识符所涉及的一些较低级别的技术细节。

<a id="implementation"></a>
## 6.4 实现

到目前为止，我们已经探讨了标识符的特征和一些具体细节，但还有许多更深层次的技术细节需要正式确定，这正是本节的重点。
让我们从标识符中一个直接且基本的问题开始：它有多大。

### 6.4.1 大小

给定的标识符应该有多长？
虽然我们可以简单地说它会随时间变化（即标识符的长度可能会随着创建更多而增长），但这可能会使使用 API 的人在存储这些标识符到他们的数据库时变得相当复杂，
因此，通常最好为这些标识符的空间需求提供一些可预测性，并简单地为其长度选择一个固定大小。

在这种情况下，根据我们的需求，有几种不同的选择。
<ins>首先，最简单的选择是，我们可能只需要在单一资源类型内唯一的标识符。</ins>
换句话说，同时存在 book 1 和 author 1 可能完全没问题，因为我们有不同类型的资源来区分这两个 “1”。
在这种情况下，我们可能只需要大约 64 位的存储空间（类似于在 MySQL 等关系数据库中使用单个 64 位整数）。
使用 Crockford 的 Base32，每个 ASCII 字符总共有 32 种选择（或 5 位），
这意味着我们可能可以用总共 12 个字符作为标识符（为标识符提供 60 位）。
在序列化（和反序列化）时，我们还需要一个字符作为校验和数字，总共 13 个字符，
从而得到像 books/AHM6A83HENMP\~（或 books/ahm6a83henmp\~ 或 books/ahm6-a83h-enmp\~，使用小写和可能的连字符作为分隔符以提高可读性）这样的标识符。

<ins>在其他一些情况下，我们可能需要全局唯一的标识符 —— 不仅是在资源类型或甚至这个 API 中唯一，而是在任何地方的所有资源中都唯一。</ins>
为了实现这一点，我们可能应该以至少与标准 UUID（通用唯一标识符）相同数量的可能标识符为目标，UUID 是一个由 32 个十六进制数字表示的 128 位 ID。
由于其中 6 位保留用于 ID 的元数据，因此剩下 122 位用于标识符值。
使用 Crockford 的 Base32，我们需要大约 24 个字符，这将给我们一个 120 位的标识符。
再加上一个额外的校验和数字，总共 25 个字符，从而得到像 books/64s36d-1n6rv-kge9g-c5h66\~ 这样的标识符
（请记住，连字符是可选的，技术上可以放在任何位置，并且所有字母都不区分大小写）。

正如我们稍后讨论别名时会了解的，我们可能希望引入一个前导 “0” 字符来区分标识符和别名，这将为我们的常规 ID 增加一个额外字符。
不过，在这一切之后，是时候讨论一个重要但微妙（且到目前为止一直被假定）的问题了：谁来生成 ID。

<a id="generate"></a>
### 6.4.2 生成

我们已经讨论了标识符应采用的数据类型和格式；
然而，一直有一个隐含的假设，即这些只是随机标识符，而我们还没有说过如何实际创建它们。
让我们从这个方面的一个重要问题开始：来源。

#### 来源

在讨论如何生成这些标识符之前，我们首先应该讨论谁应该实际创建它们。
<ins>简而言之，值得注意的是，允许 API 用户选择自己的标识符是一件非常危险的事情，应该予以避免。</ins>

<ins>首先，当该名称在过去某个时间点已被使用时，这可能会导致沮丧和困惑。</ins>
由于我们对永久性的要求（ [第 6.2.3 节](#permanent) ）意味着标识符永远不能重用（即使在被删除之后），
一个想要重新创建资源的用户可能会因为收到关于 ID 冲突的错误消息而感到困惑，因为他们确信具有该 ID 的资源不存在
（它现在可能确实不存在，但它在过去的某个时间点存在过）。
虽然这可以通过足够大的可用 ID 集来缓解，但人类特别不擅长从给定的集合中随机选择值。

<ins>其次，当 API 用户想要选择自己的标识符时，他们往往会做出糟糕的决定，例如，将个人身份信息放入标识符本身。</ins>
换句话说，有人可能会创建一个标识符为 pad(base32Encode("harry-potter-8"))（相当于 D1GQ4WKS5NR6YX3MCNS2TE05===）的书籍，显然，作者希望对外界保密这一点。
然而，这可能很困难，因为大多数系统不会将 ID（即使是 Base32 编码的）视为秘密信息。
相反，标识符通常被视为不透明的随机数据块，以便在最方便的时候使用。
这意味着它们通常被认为可以安全地存储在日志文件中并与任何人共享。
这包括在办公室周围的大仪表板上显示这些 ID，以突出显示单个资源的潜在错误或统计数据。
如果 API 允许用户选择的标识符，那么总有一天，一个大客户（或政府）会要求将某些 ID 保密，而这可能异常困难（甚至不可能）实现。

最后，我们对标识符的最后要求之一是它们是不可预测的（参见 [第 6.2.5 节](#unpredictable) ）。
虽然你的 API 用户肯定可能具有密码学或伪随机数生成器的背景知识，但正如我们之前所指出的，通常情况并非如此。
因此，要求用户选择自己的标识符可能会带来问题。
在最好的情况下，如果被要求这样做可能会令人烦恼（“你为什么不能直接为我生成一个 ID？”），但在最坏的情况下，即使这是一个可选功能，也可能会很危险。
特别是，这为用户生成可预测的标识符创造了机会，使其成为安全漏洞的容易攻击目标。

#### 伪随机数生成器

与大多数编程问题一样，我们有几种不同的方法来生成随机标识符。
一种选择是使用加密安全的随机字节生成器（例如 Node.js 的 crypto.randomBytes() 函数），并将其转换为 Crockford 的 Base32
（例如，使用 Node.js 的 base32-encode 包）。
另一种选择是使用随机选择算法，从 Crockford 的 Base32 字母表中选出一组固定数量的字符。
这两种方法都没有绝对的对错，只是不同而已。

前者关注随机选择的标识符所涉及的字节数（选择标识符时如同将其存储在数据库中），
而后者更关注面向用户的标识符（选择标识符时如同用户实际看到的那样）。
只要你提前计算好，知道你希望字节表示多少个字符，或者你选择的字符在数据库中需要预留多少字节，两者都是合理的。

计算本身相当简单，因为我们只是要在 8 位字节和 5 位字符之间进行转换。
这意味着，ID 中的每个字节数据，每个字节的 8 位都必须由能够容纳 5 位的字符来表示。
简而言之，这意味着 base32Length == Math.ceil(bytes * 8 / 5)。

为了便于说明，让我们看看如何生成一个以字节为先的随机标识符。

*清单 6.1 生成一个随机的 Base32 编码标识符*

```typescript
const crypto = require('crypto');
const base32Encode = require('base32-encode');

function generateId(sizeBytes: number): string { // 这里的 sizeBytes 代表ID的字节数量
  const bytes = crypto.randomBytes(sizeBytes); // 先生成若干随机字节
  return base32Encode(bytes, 'Crockford'); // 返回 Crockford Base32 编码结果
}
```

现在我们知道了如何生成一个 ID，我们需要确保这个 ID 未被使用（且过去也未曾被使用过）。
让我们简要看看如何做到这一点。

### 6.4.3 墓碑化

正如我们在关于标识符永久性的章节中所了解的，标识符在 API 的生命周期内使用不能超过一次，这一点至关重要。
这意味着即使资源已被删除，我们也不能重复使用相同的标识符。
有很多方法可以做到这一点，有些方法比其他方法需要更多的存储空间。

<ins>一种简单的选择是依赖软删除的概念（在 [第 25 章](ch25.md) 中讨论）。</ins>
在这种设计模式中，我们不是实际删除资源及其所有数据（“硬删除”），而是可以简单地将资源标记为已删除。
然后，从我们的标识符生成代码的角度来看，我们只需继续生成随机值，直到我们找到一个尚未被占用的值，在此过程中检查我们的数据库以确保该 ID 确实可用。
虽然无论我们是否关心墓碑化的标识符，这种模式都可能有其用处，但它存在执行时间不可预测的老问题，从统计数据来看，随着创建越来越多的标识符和可用 ID 集逐渐耗尽，这种情况只会变得更糟。
话虽如此，对于 120 位的标识符，其键空间大约与地球上存在的细菌细胞数量相当。
这意味着两次选择同一个 ID 有点像从地球上所有的细菌细胞中挑选一个，然后再次随机挑选出完全相同的那一个。
换句话说，遇到冲突应该是极其罕见的。

<ins>在依赖软删除模式不合理的情况下（例如，所涉及的数据很重要，并且由于某种原因你必须清除它，比如监管要求），你有很多其他选择。
例如，你可以只将已被占用的标识符存储在某个地方的哈希映射中，或者保留一个布隆过滤器，并在 ID 开始被使用时将其添加到该过滤器中。
尽管如此，避免冲突的最佳方法仍然是使用相对于你将创建的资源数量而言足够大的标识符，并使用可靠且加密安全的随机源来生成你的标识符。</ins>

<a id="checksum"></a>
### 6.4.4 校验和

如 [第 6.3.4 节](#checksums) 所述，计算校验和就像将我们的字节值视为一个整数，并使用模 37 值作为校验和值一样简单。
这意味着我们将该数字除以 37，并使用余数作为校验和。
然而，有时代码比文字更有说服力。
请注意，我们将依赖 BigInt 类型来处理可能由任意长度的字节缓冲区产生的大整数。

*清单 6.2 计算 Base32 校验和值*

```typescript
function calculateChecksum(bytes: Buffer): number {
  // 首先将字节缓冲区转换为 BigInt 数值
  const intValue = BigInt(`0x${bytes.toString('hex')}`);
  // 通过计算除以37后的余数，得到校验和值
  return Number(intValue % BigInt(37));
}
```

此外，我们还需要一种方法将此校验和值编码为字符串（而不仅仅是数值）。
为此，我们可以在标准 Base32 字母表的基础上增加五个额外字符：*、~、,、#、= 和 U（由于 Crockford 的 Base32 不区分大小写，在解析值时这也包括 u）。
这样，我们的校验和计算得出的任何值（范围从 0 到 36）都将有一个字符值可用于标识符中。

清单 6.3 使用 Base37 字母表选择校验和值字符

```typescript
function getChecksumCharacter(checksumValue: number): string {
  // 定义字符集（Base32加上5个额外字符）
  const alphabet = '0123456789ABCDEFG' +
                   'HJKMNPQRSTVWXYZ*~$=U';
  // 返回校验和值对应位置的字符
  return alphabet[Math.abs(checksumValue)];
}
```

此时，你可能会想：“好的，我有了一个校验和字符。然后呢？”
很简单，我们可以在向用户显示标识符时将此字符附加到 Base32 编码标识符的末尾，并且在提供标识符时，我们可以依赖此校验和字符的正确性。
让我们从更新 generateId 函数以包含校验和字符开始。

清单 6.4 生成带有校验和字符的 Base32 标识符

```typescript
const crypto = require('crypto');
const base32Encode = require('base32-encode');

function generateIdWithChecksum(sizeBytes: number): string {
  const bytes = crypto.randomBytes(sizeBytes);
  // 计算校验和并获取对应的校验字符
  const checksum = calculateChecksum(bytes);
  const checksumChar = getChecksumCharacter(checksum);
  const encoded = base32Encode(bytes, 'Crockford');
  // 返回追加了校验字符的 Base32 序列化标识符
  return encoded + checksumChar;
}
```

在另一端，我们应将所有传入的标识符解析为两部分：标识符本身和校验和字符。
如果我们检查校验和字符，发现它不正确，这并不意味着校验和计算错误。
它实际上意味着标识符本身可能存在笔误或其他错误，我们应该拒绝该标识符并将其视为无效。
为了了解其工作原理，清单 6.5 实现了一个 verifyIdentifier 函数，该函数返回一个布尔值，表示给定标识符是否应被视为有效。

*清单 6.5 根据校验和值验证 Base32 标识符*

```typescript
function verifyId(identifier: string): boolean {
  // 将标识符拆分为两部分：主体值和校验字符
  const value = identifier.substring(0, identifier.length-1);
  const checksumChar = identifier[identifier.length-1];
  // 将 Base32 值解码还原为原始字节
  const buffer = Buffer.from(base32Decode(value, 'Crockford'));
  // 返回计算得到的校验字符与传入的校验字符是否相等
  return (getChecksumCharacter(calculateChecksum(buffer)) == checksumChar);
}
```

现在我们已经介绍了如何计算和验证校验和值，让我们继续讨论这一切在数据存储的视角下是如何工作的。

<a id="database-storage"></a>
### 6.4.5 数据库存储

尽管我们一直在讨论不使用自增整数，但大多数数据库都推荐使用自增整数并为此进行了大量优化，这就引出了一个显而易见的问题：如果我们使用这种新奇的随机 Base32 编码标识符，我们应该如何存储它，才能使我们的数据库不会因耗尽或混乱而崩溃？

首先，我们必须决定数据库中究竟需要存储什么。
显然，标识符本身需要存储，但校验和字符呢？
<ins>这个值（以及我们在向用户提供标识符时可能编码到其中的任何其他元数据）不应存储在数据库中。
相反，我们应该始终动态计算该值，作为对传入 ID 的验证步骤（并在传出 ID 上动态附加它）。
如果我们将来不得不更改计算校验和值所用的算法，知道我们不需要遍历并重写数据库中的每个条目来反映新的校验和字符，这将是一个巨大的解脱。</ins>

现在我们已经决定唯一需要存储的数据是实际的标识符，我们需要考虑具体如何存储它。
关于如何存储这些数据，有很多不同的选择，但我们将讨论三种不同的方式，从最简单的开始：字符串。

<ins>许多数据库（特别是键值存储系统）非常擅长使用字符串值作为标识符。</ins>
如果你恰好使用其中一种，那么存储资源的标识符就变得异常简单：你只需存储资源标识符的字符串表示形式，就像它展示给你的客户那样（当然，在去除校验和字符之后）。
这基本上是最直接和简单的方式，所以如果你能采用这个选项，那就选择它。
还要记住，Crockford 的 Base32 编码保留了排序顺序，这意味着我们不会出现任何奇怪的情况，比如数据库中的排序与客户端上的排序表现不同。

<ins>不幸的是，并非所有数据库都像其他数据库一样擅长存储（和索引）字符串值。</ins>
此外，存储标识符的字符串表示形式实际上是在浪费空间（因为每个 8 位字符仅代表 5 位实际数据）。
考虑到这一点，我们总是可以选择可用的最低级别：存储原始字节。
<ins>许多数据库非常擅长使用原始字节字段作为标识符。</ins>
对于这些类型的数据库，我们可以依赖原始字节数据类型（例如，MySQL 称之为 BINARY）作为我们的主键，强制唯一性约束并添加索引，使单键查找查询快速而简单。

<ins>最后，如果我们正确选择标识符的大小，我们可以将其大小设置为能很好地适应常见整数类型（例如 32 位或 64 位）。</ins>
如果可能，这可能是最好的选择，因为几乎所有数据库都极其擅长存储和索引数值。
为此，我们只需获取标识符所表示的字节，并将其视为表示一个整数，我们在学习如何计算给定 ID 的校验和值时已经看到过如何做到这一点（例如 byteBufferreadBigInt64BEInt(0)）。
<ins>使用整数作为底层存储格式可能是最普遍支持的选项，因为它几乎适用于所有现有的数据库系统。</ins>

<a id="uuid"></a>
## 6.5 那 UUID 呢？

如果你不熟悉 UUID，跳过本节可能是安全的。
简而言之，UUID 是常见的 128 位标识符格式，有着相对较长的历史（其规范 RFC-4122 的日期为 2005 年 7 月）。
UUID 基本上是一种标准标识符格式，具有许多便利的特性，例如命名空间、大量可用 ID，因此冲突的可能性可以忽略不计。
我们不会深入探讨 UUID 的所有细节，但你可能通过其带连字符的格式识别出它们，看起来像这样：123e4567-e89b-12d3-a456-426655440000。

如果你知道 UUID 是什么，并且读到这里在想：“我们为什么不直接使用 UUID 然后就完事了呢？”
那么有这种想法的不仅是你一个人（一方面，如果真是这样，跳过这一章会快得多）。
简短的答案是，如果你需要 UUID，它们完全没问题，但有三点值得一提，说明为什么我们没有将整章替换为 “就用 UUID” 这句话。

<ins>首先，UUID 很大（总共 122 位标识符空间，总共 128 位数据），这在最常见的场景中显得过大。</ins>
在这种情况下，如果你知道自己不会创建数万亿个资源，你可能会想要使用一种更短、更易读的 ID 格式。

<ins>其次，UUID 的字符串格式在信息密度上并不高，因为它们在传输时仅依赖十六进制（Base16）表示法。</ins>
简而言之，这意味着我们每个 ASCII 字符只携带 4 位信息，而使用 Base32 编码每个字符可以获得 5 位。
虽然这对计算机来说可能不重要（毕竟，如今的压缩技术已经相当不错了），但当我们需要通过非技术手段（例如，通过电话分享标识符）复制和分享这些标识符时，高信息密度当然是一个很好的优势。

<ins>最后，UUID 根据定义不附带自己的校验和值。</ins>
这意味着我们没有一个好方法来明确区分一个缺失的 UUID 与一个根本不可能存在的 UUID（因此很可能存在笔误）。
在这种情况下，向标识符引入一个额外的校验和值是有意义的，这样我们就可以区分这两种情况，或许可以使用类似于 Base32 计算校验和字符的方法。

考虑到所有这些，在内部使用 UUID 值，但仍然呈现 Base32 字符串作为面向客户的标识符，可能是有意义的。
这使你能够受益于 UUID 提供的所有特性，例如命名空间（UUID v3 和 v5）或基于时间戳的值（UUID v1 和 v2），以及 Base32 的特性集，例如校验和值、可读性和更高的信息密度。

你可以生成一个带有校验和字符的 Base32 编码的 UUID v4（随机生成）。

*清单 6.6 生成随机的 Base32 编码 UUID v4*

```typescript
const base32Encode = require('base32-encode');
const uuid4 = require('uuid/v4');
// 本示例使用 NPM 上的 uuid 包

function generateBase32EncodedUuid(): string {
  // 先分配一个16字节缓冲区，用于存放UUID
  const b = Buffer.alloc(16);
  // 生成UUID（此处为随机的UUID v4）并存入缓冲区
  uuid4(null, b);
  // 计算校验和并获取对应的Base37校验字符
  const checksum = calculateChecksum(b);
  const checksumChar = getChecksumCharacter(checksum);
  // 返回经过 Crockford Base32 编码的值（附带校验字符）
  return base32Encode(b, 'Crockford') + checksumChar;
}
```

如果我们有一个特别擅长存储和索引 UUID 的数据库，而不是像我们在 [第 6.4.5 节](#database-storage) 中提到的将它们存储为字符串、原始字节或整数，我们可能也会想要这样做。

<a id="summary"></a>
## 本章小节

- 标识符是用于在 API 中唯一指向特定资源的值。
- 好的标识符易于使用、唯一、永久、快速且易于生成、不可预测、可读、可复制、可分享且信息密度高。
- 从客户的角度来看，标识符应使用字符串，采用 ASCII 字符集，理想情况下依赖 Crockford 的 Base32 序列化格式。
- 标识符应使用校验和字符，以区分不存在的资源与永远不可能指向任何资源的标识符（后者很可能是错误的结果）。
