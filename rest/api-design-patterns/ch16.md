在构建软件系统时，多态提供了对象呈现多种不同形式的能力，通常依赖于显式的对象继承。
在本模式中，我们将探讨如何将这一强大的工具从面向对象编程的世界转换到面向资源的 API 设计世界。
我们还将研究一些关于何时应依赖多态资源而非完全独立资源的指导原则。

<a id="motivation"></a>
## 16.1 动机

在面向对象编程（OOP）中，多态是指在不同的具体类型上使用单一通用接口的思想，从而最大限度地减少我们为了与特定类型交互而需要理解的实现细节。
换句话说，如果我们有 Triangle 类和 Square 类，它们可能都实现了一个通用的 countSides() 方法，并通过扩展一个共享的 Shape 接口来指定这一点。

*清单 16.1 TypeScript 中的多态示例*

```typescript
interface Shape {
  // 该接口声明了一个必须实现的函数
  countSides(): number;
}

// 两个不同的类实现了该接口，因此都要实现所声明的方法
class Triangle implements Shape {
  countSides() { return 3; }
}

// 两个不同的类实现了该接口，因此都要实现所声明的方法
class Square implements Shape {
  countSides() { return 4; }
}
```

由于我们有了这个通用接口，我们可以编写只处理 Shape 接口的代码，这意味着我们不必关心具体形状是 Triangle 还是 Square（或其他什么），只要它实现了 Shape 接口所指定的要求即可。

*清单 16.2 对任何形状计算边数的多态方法*

```typescript
// 我们不必指定输入为Triangle或Square。只要求该类实现Shape接口即可。
function countSides(shape: Shape): number {
  return shape.countSides();
}
```

这个思想在 OOP 中非常强大，能带来更清晰、更模块化的代码，因此我们希望在 Web API 中也拥有这种能力是理所当然的。
问题出现在我们试图弄清楚如何将这一概念从面向对象编程语言的世界准确地转换到 JSON 和 HTTP 的世界时。
毕竟，在面向资源的 Web API 中，countSides() 方法的等价物是什么？
代表我们想要的东西的正确资源是什么？
本模式的目标是展示一种安全、灵活且可持续的方式，将面向对象编程最强大的特性之一引入面向资源的 API 世界。

<a id="overview"></a>
## 16.2 概述

在本模式中，我们将探讨多态资源的概念。
这些资源采用通用接口（例如 Shape）的形式，并带有一个明确的字段来指定资源的更详细类型（例如 triangle 或 square）。
虽然依赖这种策略有很多好处，但最重要的好处是我们不必为每个具体实现重复标准方法。
换句话说，我们不需要 ListTriangles 和 ListSquares，而是可以使用一个单一的 ListShapes 方法。

虽然这种策略简化了多态行为（例如，与通用资源而非具体实现交互的方法），但它没有涉及多态的数据存储方面。
换句话说，虽然正方形有边长，但三角形有底和高，这意味着要真正表示这些不同形状的细节，我们实际上需要在资源上存储不同的字段。
<ins>为了解决这个问题，我们最终必须采用一些服务器端验证，使得我们的通用接口是所有必要字段的超集，从而能够存储对应于所有各种子类型的字段。
换句话说，Shape 资源可能有一种方式来存储半径（用于圆形）、底和高（用于三角形）以及长度（用于正方形），并根据类型规范来验证这些值。</ins>

然而，一如既往，细节才是复杂之处。
例如，如果 API 请求包含适用于错误资源类型的字段（例如，为类型为 square 的 Shape 定义半径），我们应该怎么办？
这应该是一个错误，还是应该被忽略？
在下一节中，我们将更详细地探讨所有这些如何工作。

<a id="implementation"></a>
## 16.3 实现

多态在许多编程语言中显然是一个非常强大的工具，因此多态资源对 Web API 同样非常有价值是合乎情理的。
为了充分利用这一概念，我们需要理解这些资源在行为层面和结构层面如何工作。
但在我们这样做之前，我们需要理解究竟什么时候依赖多态才有意义。

### 16.3.1 决定何时使用多态资源

在设计 API 时，我们常常会发现两个拟议资源之间存在共性，这让我们重新考虑它们是否应该是两个独立的资源。
例如，在一个聊天 API 中，我们可能会考虑一个 TextMessage 资源以及 PhotoMessage、VideoMessage 或 AudioMessage 资源。
它们每一个都有共同点（例如，它们都表示通过聊天 API 发送的消息），但它们也都有彼此略微不同之处（在这种情况下，就是消息的内容）。

如果我们在本地编程时遇到同样的场景，我们可能会考虑一个 Message 接口和几个实现该接口的其他类，目标是编写只处理通用 Message 接口类型的值而非该接口具体实现的代码。
但这种逻辑是否同样适用于 Web API 呢？
<ins>换句话说，我们是否应该使用同样的通用性论据来决定是使用单个 Message 资源，还是为每种消息类型使用几个独立的资源？</ins>

虽然直觉可能是正确的，但逻辑并不完全适用。
<ins>更具体地说，在本地编程语言中工作时，我们关注的是通用性以及编写支持未来扩展和代码重用之类功能的函数。
在我们的 Web API 中，我们更应该关注我们期望各种标准方法如何工作，以及这些标准方法是否在所有资源上完全相同地运作，还是对不同类型有某些行为差异。</ins>

<ins>例如，一个很好的指标可以表明某事物应依赖多态资源（例如 Message）而非独立资源（例如 VideoMessage），那就是考虑将所有不同类型一起列出是否有意义。
换句话说，我们是想调用单个方法并在单个响应中检索所有资源类型，还是只需要按不同的子类型列出资源？</ins>
在聊天 API 的情况下，答案相当明显：我们几乎肯定希望列出 ChatRoom 资源中的所有消息，无论其类型如何。
否则，我们将很难检索到正确的消息列表，需要发出多个 API 调用（然后按创建时间交错结果）才能正确显示聊天内容。

考虑另一个场景，其中 API 可能有 ChatRoom 资源以及广播组，其中中心权威机构可以向所有用户发送单向更新。
虽然这个 “广播” 概念在本质上有类似于 ChatRoom 资源（因为它们都包含消息），但我们与它们交互的方式差异巨大。
成员资格是不确定的，它们只能由 API 的管理员创建，消息只单向发送，如此等等。
因此，即使这个概念可能被塞进一个多态的 ChatRoom 资源中（为广播使用一个特殊的类型），但如果创建一个单独的 Broadcast 资源，它虽然与 ChatRoom 相似，但本质上是不同的并独立对待，那么访问模式很可能更容易管理。

现在我们已经有了一些关于如何在独立资源和多态资源之间进行选择的指示，让我们探讨如何构建这些特殊的资源。

### 16.3.2 多态结构

<ins>多态资源有一个重要的区别字段：type。
由于多态资源本身类似于我们编程语言中的通用接口，我们需要一种明确的方式来传达这个通用接口的实例是特定的子类型。</ins>
例如，对于我们的 Message 接口，我们需要一种方式来指定消息是视频消息、音频消息还是其他。
但这个 type 字段应该是什么样子呢？

#### 定义 type 字段

虽然依赖枚举可能很有诱惑力，但回想 [第 5 章](ch5.md)，枚举往往带来许多问题，并且对其使用有一套非常具体的标准。
相反，我们可以使用一个简单的字符串字段，并对可以存储在此字符串字段中的值进行一些验证。

*清单 16.3 带有 type 字段的多态资源示例*

```typescript
interface Message {
  id: string;
  sender: string;
  // type 字段只是一个普通字符串，用于存储允许的子类型
  type: 'text' | 'photo' | 'audio' | 'video';
  // ...
}
```

由于这个字段是一个简单的字符串，我们现在可以像使用任何其他字段一样使用它。
例如，如果我们想要列出所有消息但只列出照片，我们可以发出一个 ListMessages() 调用，并对 type 字段应用过滤器，正如我们将在 [第 22 章](ch22.md) 中看到的。
这也意味着创建新的 Message 资源可以采用任何相关形式，并将正确的值传递到 CreateMessage() 调用中。

尽管这就像任何其他字段一样，但我们确实有一个重要的问题需要解决：这个字段应该是永久性的，还是可以在现有资源上更改？
<ins>换句话说，我们能否将资源从一种类型（例如视频消息）变形为另一种类型（例如文本消息）？
虽然从技术上讲，资源上没有任何东西直接阻止其按预期工作，但通常不鼓励这样做。</ins>
原因是随着 API 变得更加复杂，不同资源之间有更多关系，更改多态资源的类型可能会破坏恰好引用该多态资源的现有资源所做的假设。
当我们到处更改类型并破坏这样的假设时，往往会给用户带来令人困惑的情况，并在 API 本身中产生错误。
因此，如果可能的话，应避免这样做。

这种多态资源数据的想法引出了下一个问题：我们究竟如何存储消息的内容？
毕竟，对于每种不同的消息类型，存储的内容都大不相同。

#### 数据结构

多态资源的主要好处是，根据定义，它能够呈现许多不同的形式。
虽然这通常源于资源的行为（例如，当我们对多态资源的不同类型调用相同的 API 方法时会发生不同的事情），但这些资源很少会具有完全相同的结构。
相反，几乎可以肯定不同类型需要存储不同的信息。

在形状的示例中，我们需要为圆形存储半径，但为正方形存储长度。
对于我们在聊天中的 Message 资源，文本消息可以只存储文本内容；
然而，照片消息需要存储某种图像，这显然完全不同。
那么我们该如何处理这个问题呢？

<ins>处理这个问题的最简单方法（恰好也是更严格的接口定义语言所偏爱的方法）是让资源充当每种单独类型所有字段的超集。
换句话说，一个 Message 资源可能有一个用于存储文本内容的字段，另一个用于存储照片内容，另一个用于存储视频内容，依此类推。</ins>

*清单 16.4 为每个属性存储具有不同字段的数据*

```typescript
interface Message {
  id: string;
  sender: string;
  type: 'text' | 'photo' | 'audio' | 'video';
  // 该资源通过定义所有相关字段，构成一个超集
  text?: string;
  photoUri?: string;
  videoUri?: string;
  audioUri?: string;
}
```

有时这种超集安排是一种要求，但在许多接口定义语言中（例如我们在本书中一直使用的 TypeScript），我们实际上可以重用单个字段来表示这些字段中的每一个。
换句话说，与其拥有 text、videoUri 等字段，我们可以拥有一个单一的 content 字段，它根据 type 字段承担不同的含义。

*清单 16.5 为多个字段存储数据的单个字段*

```typescript
interface Message {
  id: string;
  sender: string;
  type: 'text' | 'photo' | 'audio' | 'video';
  // 该字段现在表示文本内容或媒体资源URI，具体取决于这条Message资源的类型
  content: string;
}
```

在这个例子中，到目前为止，每个不同的内容类型都表示为一个简单的字符串，但如果有更多内容呢？
例如，如果我们需要跟踪媒体内容类型（例如视频的编码格式）以及视频文件的位置呢？
在这种情况下，我们可能会为媒体内容定义一个单独的接口，同时对基于文本的内容仍然使用简单的字符串值。

*清单 16.6 根据消息类型具有不同类型的字段*

```typescript
interface Message {
  id: string;
  sender: string;
  type: 'text' | 'photo' | 'audio' | 'video';
  // 在这种情况下，content可以是多种不同的类型
  content: string | Media;
}

// 我们可以将Media定义为一个URI引用，该URI保存实际内容以及内容类型，例如video/mp4
interface Media {
  contentUri: string;
  contentType: string;
}
```

在所有这些示例中，一般指导原则是，我们应该只在结构仍然具有实际意义的情况下进行抽象。
对于消息，我们可以在文本和通用的媒体概念之间进行抽象，这没有问题，而且检查资源的类型然后适当地解释 content 字段仍然完全合理。

然而，对于具有不同类型的 Shape 资源，尽管大多数字段都是数字类型，但字段的名称实际上相当重要。
因此，我们可能有一个 dimension 字段来保存各种尺寸，但有多种类型来存储每个形状的不同尺寸信息。

*清单 16.7 为不同形状存储不同的字段名称*

```typescript
interface Shape {
  id: string;
  type: 'square' | 'circle' | 'triangle';
  // dimension字段存储不同图形的各类定义方式
  dimension: SquareDimension | CircleDimension | TriangleDimension;
}

interface SquareDimension {
  // 每种图形的dimension拥有数量不同、名称各异的字段
  length: number;
}

interface CircleDimension {
  radius: number;
}

interface TriangleDimension {
  base: number;
  height: number;
}
```

现在我们已经讨论了结构，花点时间考虑一下我们可能如何与该结构交互，可能是有意义的。
更重要的是，当我们试图 “变通规则” 时，应该发生什么？

#### 数据验证

正如我们在上一个主题中所看到的，多态资源的不同类型可能存储不同的信息。
此外，虽然有时可以使用完全相同的字段并根据类型不同地解释它，但其他时候我们需要为需要存储的不同信息指定具有不同类型的字段。
当在创建或更新多态资源时提供了无效数据，这两种场景都会导致更多复杂问题。

<ins>换句话说，正如字段可能根据资源的 type 字段以不同方式解释一样，这也意味着验证规则需要以不同方式应用。</ins>
例如，如果我们依赖一个带有 content: string 字段的简单 Message 资源，如果类型是 text，这个字段可能存储任意文本内容，但如果类型是媒体类型（如照片），它应该是一个 URI。
因此，如果有人指定一条消息应被视为照片消息，那么如果 content 字段不是有效的 URI，我们返回错误就至关重要。

其他结构在要求上更为微妙。
例如，在我们可用的各种形状的示例中，dimension 字段的每个接口都有一组不同的字段名（尽管它们都具有相同的类型）。
如果我们提供了额外的字段，使得要求得到满足但数据并不完全合理，会发生什么？
换句话说，如果我们通过调用 `CreateShape({ type: 'square', dimension: { radius: 10, length: 10 } })` 创建一个 Shape 资源呢？
显然正方形没有半径，所以这个额外信息完全无用。

虽然像处理格式不正确的 URI 那样抛出错误可能很有诱惑力，但在这种情况下，
<ins>更好的选择是验证我们确实需要的输入是否按预期提供，并简单地丢弃其他任何内容，就像我们在创建或更新任何其他资源时处理未知字段一样。</ins>

现在我们已经了解了如何处理多态资源上的数据，让我们探讨这些特殊资源的行为差异。

### 16.3.3 多态行为

到目前为止，我们的讨论完全围绕多态资源的结构和设计，但我们几乎没有谈到我们可能如何与这些资源交互。
正如我们在 [第 16.1 节](#motivation) 中所看到的，多态在编程语言或 Web API 中的部分好处是，我们可以对通用接口而非具体实现进行操作，但操作的结果将根据该具体实现而有所不同。
以我们在 [第 16.1 节](#motivation) 中的 `countSides()` 函数为例，我们可以很容易地将其转换为 Web API。

*清单 16.8 计算不同形状边数的 API 方法*

```typescript
abstract class ShapeApi {
  @post("/{id=shapes/*}:countSides")
  CountShapeSides(req: CountShapeSidesRequest): CountShapeSidesResponse;
}

interface CountShapeSidesRequest {
  id: string;
}

interface CountShapeSidesResponse {
  sides: number;
}
```

在这个例子中，你可以想象响应：正方形会返回 { sides: 4 }，而三角形会返回 { sides: 3 }，其他形状类型依此类推。
简而言之，得益于我们选择资源作为通用接口（例如 Shape 或 Message），我们定义的方法将一如既往地对资源进行操作，任何行为上的偏差都可以归咎于我们期望从各种字段值不同的资源中看到的典型偏差。
简而言之，我们早期的设计选择导致了一个非常方便的结果，与资源上的任何其他标准或自定义方法没有太大区别。

但这确实提出了一个真正应该解决的重要问题：如果我们有独立的资源，并希望单个 API 方法能够操作各种资源类型，那该怎么办？
在下一节中，我们将详细探讨这一点，并解释为什么这通常是一个坏主意。

### 16.3.4 为什么不用多态方法？

到目前为止，我们几乎只讨论了一种可以呈现多种形式的单一资源。
这为 API 方法带来了极大的简单性，因为它们的行为与任何其他资源完全一样；
然而，还有一种我们甚至没有提到的完全不同的多态类型：多态方法。

<ins>就本节而言，我们将多态方法定义为能够操作多种不同资源类型的 API 方法。</ins>
为了看一个人为的例子，让我们设想一个 API 中的通用 DeleteResource() 方法，它能够删除 API 中的任何资源，无论资源类型如何。
请特别注意 HTTP URL 映射到 "*/*" 而非像 "chatRooms/*" 这样的特定集合。

*清单 16.9 多态方法支持对不同资源类型的行为*

```typescript
abstract class GenericApi {
  // 此URL映射可对应任意类型的资源
  @delete("/{id=*/*}")
  DeleteResource(req: DeleteResourceRequest): void;
}

interface DeleteResourceRequest {
  // 该字段可表示任意资源类型的标识符
  id: string;
}
```

看到这个例子时，一个常见的下意识反应是：“等等。这简单多了。为什么我们不直接这样做，而不是为每个资源都设置所有这些单独的标准 delete 方法？”
有趣的是，从技术层面上讲，这实际上是可行的，因为这里的方法基本上能够处理任何资源的删除。
换句话说，由于 DeleteResourceRequest 接口中提供的标识符是任意字符串，我们可以传入任何有效的资源标识符，指向任何可能的资源类型，该资源就会被删除。
在某种程度上，这有点像在 TypeScript 中定义一个带有方法签名的函数，看起来像 `function deleteResource(resource: any): void`。
然而，这样的方法往往弊大于利。

<ins>重要的是要记住，仅仅因为两个 API 方法具有相同的名称、目标、请求格式或方法签名，并不意味着它们是相同的。
当我们假装这两个方法相同并将它们合并在一起时，就像我们在这里所做的那样，我们很可能在未来遇到麻烦</ins>。

<ins>在多态标准 delete 方法的这个例子中，我们显然可以删除任何资源，但并不能保证所有资源都应该以完全相同的方式删除。</ins>
例如，也许我们想在某些特定资源上支持软删除（ [第 25 章](ch25.md) ）或验证请求（ [第 27 章](ch27.md) ），但不是所有资源。
这超出了这个单一示例，并延伸到任何可能操作多种资源类型的方法。

任何能够操作多种不同类型资源（或所有资源）的方法都意味着这些资源类型彼此行为如此相似，以至于它们应该有一个共享的 API 方法来与它们交互。
然而，不知何故，与此同时，它们的表示又如此关键地不同，以至于它们应该成为完全独立的资源类型。

另一个重要的含义是，所讨论的资源将永远永远保持足够相似的行为，并且多态方法的期望行为的任何变化都将适用于所有资源。
换句话说，方法的行为将始终对所有资源类型发生变化，而不是逐个情况变化。

在这两种情况下，我们都做出了相当大的跳跃。
在第一种情况下，我们说资源在行为上是相同的，应该有一个单一的 API 方法，但在表示上又完全不同，应该独立定义资源。
在第二种情况下，我们假设这种相同的行为是永久性的，所有资源都将在整个 API 中统一改变其行为。

<ins>虽然确实有可能存在使这些含义合理的场景，但更可能的是，无论现在还是将来，其中一个都会瓦解。
而且由于我们没有水晶球来帮助预测 API 的未来，更安全的假设是事情会发生变化，并且会以各自独特的方式变化，而不是作为一个统一的群体。
基于此，支持多态 API 方法几乎从来都不是一个好主意</ins>。

不幸的是，这确实意味着要打更多的字。
另一方面，API 保持灵活和适应性，而不是脆弱和笨重。

### 16.3.5 最终 API 定义

在下面的示例中，我们可以看到如何为 Message 资源依赖面向资源的多态，从而得到一组简化的 API 方法，并享有资源布局上的多态优势。

*清单 16.10 最终 API 定义*

```typescript
abstract class ChatRoomApi {
  @post("/{parent=chatRooms/*}/messages")
  CreateMessage(req: CreateMessageRequest): Message;
}

interface CreateMessageRequest {
  parent: string;
  resource: Message;
}

interface Message {
  id: string;
  sender: string;
  type: 'text' | 'image' | 'audio' | 'video';
  content: string | Media;
}

interface Media {
  uri: string;
  contentType: string;
}
```

<a id="trade-offs"></a>
## 16.4 权衡

API 中的多态是一个非常强大的工具，但它也可能很复杂。
虽然很多时候它可能是完美的选择（例如，多种类型的 Message 资源的示例），但在其他情况下，资源可能看起来相似，但仍有一些根本性的差异。
一个很好的经验法则是考虑这些资源是否都确实是通用资源类型的特殊类型（就像 PhotoMessage 确实是 Message 的一种特定类型一样）。
原因是依赖此模式确实会将资源锁定在特定的表示形式中，这种表示形式在未来很难（如果不是不可能的话）以非破坏性的方式解开。

最重要的是，出于前面讨论的原因，Web API 中的多态理想情况下应侧重于多态资源，而不是多态方法。
虽然在某些情况下多态方法可能有用，但请非常仔细地考虑资源的行为随时间发生偏离的可能性有多大。
这是因为这类方法现在可能带来便利和更少的打字量，但其代价是一副手铐，限制了 API 未来的灵活性。

<a id="summary"></a>
## 本章小节

- API 中的多态允许资源呈现不同的类型，以避免重复共享功能。

- 一般来说，当用户可以合理地期望将多种类型的资源一起列出时（例如，列出聊天室中的消息，其中每条消息可能属于不同类型），依赖多态是有意义的。

- 多态资源的类型信息应是一个字符串字段，但应谨慎更改（添加或移除）此字段的可能选项，以避免破坏现有客户端代码。

- 对于无效的输入数据，不应抛出错误，而应验证所需数据是否存在，并忽略任何不相关的数据。

- 通常应避免多态方法，因为它们会阻止未来行为随时间的偏离。
