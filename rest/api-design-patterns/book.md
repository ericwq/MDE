# 关于本书

《API 设计模式》的编写旨在提供一套安全、灵活、可复用的模式，用于构建 Web API。
本书首先介绍一些通用的设计原则，并在此基础上展示一组设计模式，旨在为构建 API 时的常见场景提供简单的解决方案。

<a id="who"></a>
## 谁应该阅读这本书

《API 设计模式》面向任何正在构建或计划构建 Web API 的读者，特别是当该 API 将向公众开放时。
熟悉某些序列化格式（例如 JSON、Google Protocol Buffers 或 Apache Thrift）或常见存储范式（例如关系数据库模式）当然很有帮助，但绝不是必需的。
如果你已经熟悉 HTTP 及其各种方法（例如 GET 和 POST），那也是很好的加分项，因为它是本书示例中首选的传输协议。
如果你发现自己正在设计 API、遇到问题并心想 “我敢肯定一定有人已经解决过这个问题了”，那么这本书就是为你准备的。

<a id="roadmap"></a>
## 本书的组织方式：路线图

本书分为六个部分，前两部分涵盖 API 设计中更一般性的主题，后四部分专门讨论设计模式本身。
第 1 部分首先为本书的其余部分设定舞台，提供一些关于 Web API 本身的定义和评估框架，以及我们将来将应用于这些 Web API 的设计模式。

- *第 1 章* 首先定义了我们所说的 API 的含义以及 API 为何重要。
它还提供了一个评估框架，用于衡量一个 API 到底有多好。

- *第 2 章* 在第 1 章的基础上展开，探讨如何将设计模式应用于 API，并解释它们如何对任何构建 API 的人有所帮助。
它涵盖了 API 设计模式的组成部分，以及一个简短的案例研究，说明使用这些设计模式之一如何能带来整体上更好的 API。

第 2 部分旨在进一步建立在第 1 部分奠定的基础之上，概述了在构建任何 API 时都应考虑的一些通用设计原则。

- *第 3 章* 探讨了我们在 API 中可能需要命名的所有不同组件，以及为它们选择名称时需要考虑的因素。
它还展示了命名为何至关重要，尽管看起来像是表面功夫。

- *第 4 章* 更深入地探讨了较大的 API，其中可能存在多个相互关联的资源。
在讨论了确定资源及其关系时需要问的一些问题之后，本章最后涵盖了一些应避免的事项的示例。

- *第 5 章* 探讨了如何在 API 中使用不同的数据类型以及这些数据类型的默认值。
它涵盖了最常见的数据类型，如字符串和数字，以及更复杂的可能性，如映射和列表。

第 3 部分标志着设计模式目录的开始，从几乎适用于所有 API 的基础模式开始。

- *第 6 章* 仔细研究了 API 的用户如何识别资源，深入探讨了标识符的底层细节，例如墓碑机制、字符集和编码，以及使用校验和来区分缺失 ID 与无效 ID。

- *第 7 章* 详细概述了 Web API 的不同标准方法（get、list、create、update 和 delete）应该如何工作。
它还解释了为何每个标准方法在所有资源中的行为方式必须完全相同，而不是为了适应每个资源的独特方面而变化，这一点非常重要。

- *第 8 章* 扩展了两个特定的标准方法（get 和 update），以解决用户如何与资源的某一部分而不是整个资源进行交互的问题。
它解释了为什么这是必要且有用的（对用户和 API 都是如此），以及如何尽可能少地侵入来保持对此功能的支持。

- *第 9 章* 超越了标准方法，使用自定义方法为 API 中可能需要的任何类型的操作打开了大门。
特别强调了何时使用自定义方法是有意义的（以及何时没有意义），以及如何在你自己的 API 中做出这个决定。

- *第 10 章* 探讨了 API 方法可能不是即时完成的独特场景，以及如何通过长时间运行的操作（LRO）以方便用户的方式支持这一点。
它探讨了 LRO 如何工作以及 LRO 可以支持的所有方法，包括暂停、恢复和取消长时间运行的工作。

- *第 11 章* 涵盖了重复执行的工作的概念，有点像 Web API 的 cron 作业。
它解释了如何使用 Execution 资源，并按计划或按需运行它们。

第 4 部分关注资源以及它们之间的关系，有点像第 4 章更广泛的探索。

- *第 12 章* 解释了小的、孤立的关联数据片段如何被隔离到单例子资源中。
它详细说明了在什么情况下这是一个好主意，以及在什么情况下不是。

- *第 13 章* 概述了 Web API 中的资源应如何使用引用指针或内联值来存储对其他资源的引用。
它还解释了如何处理边缘情况行为，例如随着引用数据随时间变化而发生的级联删除或更新。

- *第 14 章* 扩展了资源之间的一对一关系，并解释了如何使用关联资源来表示多对多关系。
它还涵盖了如何存储关于这些关系的元数据。

- *第 15 章* 探讨了在处理多对多关系时，使用 add 和 remove 快捷方法作为依赖关联资源的替代方案。
它还涵盖了使用这些方法时的一些权衡，以及为什么它们可能并不总是理想的选择。

- *第 16 章* 探讨了多态性的复杂概念，其中变量可以采用多种不同的类型。
它涵盖了如何处理 API 资源上的多态字段，以及为什么应避免使用多态方法。

第 5 部分超越了每次涉及单个 API 资源的交互，开始着眼于针对与整个资源集合进行交互的 API 设计模式。

- *第 17 章* 解释了如何在 API 中复制或移动资源。
它探讨了细微的复杂情况，例如处理外部数据、从不同父级继承的元数据，以及应如何处理子资源。

- *第 18 章* 探讨了如何调整标准方法（get、create、update 和 delete），使其一次操作于一个资源集合而不是单个资源。
它还涵盖了一些棘手的问题，例如应如何返回结果以及如何处理部分失败。

- *第 19 章* 扩展了第 17 章中的批量删除方法的概念，以删除与特定过滤器匹配的资源，而不仅仅是特定标识符。
它还探讨了如何解决一致性问题以及避免意外数据破坏的最佳实践。

- *第 20 章* 仔细研究了非资源数据的导入，这些数据本身并非直接可寻址。
它涵盖了如何使用匿名写入，以及一致性问题，以及在什么情况下这种类型的匿名数据导入适合 API 的权衡考量。

- *第 21 章* 解释了如何使用分页来处理大型数据集的浏览，并依赖不透明的页面令牌来遍历数据。
它还演示了如何在单个大型资源内部使用分页。

- *第 22 章* 探讨了如何对列表资源应用过滤条件，以及在 API 中表示这些过滤器的最佳方式。
这直接应用于第 19 章涵盖的主题。

- *第 23 章* 探讨了如何处理 API 中资源的导入和导出。
它还深入探讨了导入导出操作与备份恢复操作之间的细微差别。

第 6 部分关注 API 中安全性和保障方面那些不那么令人兴奋的领域。
这意味着既要确保 API 免受攻击者的侵害，也要确保所提供的 API 方法对用户自身的错误是安全的。

- *第 24 章* 探讨了版本控制的话题，以及不同版本之间兼容意味着什么。
它深入探讨了兼容性作为一个连续谱的概念，以及在整个 API 中保持一致兼容性策略定义的重要性。

- *第 25 章* 通过提供一种模式（软删除），允许资源从视图中移除而无需从系统中完全删除，从而开始保护用户免受自身操作的影响。

- *第 26 章* 尝试使用请求标识符来保护系统免受重复操作的影响。
它探讨了使用请求 ID 的陷阱，以及在大规模系统中确保这些 ID 被正确处理的算法。

- *第 27 章* 专注于验证请求，允许用户在无需执行底层操作的情况下预览 API 中的操作。
它还探讨了如何处理更高级的主题，例如在实时请求和验证请求期间的副作用。

- *第 28 章* 引入了资源修订版本的概念，作为随时间追踪变更的一种方式。
它还涵盖了基本操作，例如恢复到之前的修订版本，以及更高级的主题，例如如何将修订版本应用于层级结构中的子资源。

- *第 29 章* 提供了一种模式，用于在应重试 API 请求时通知用户。
它还包含了关于不同 HTTP 响应码及其是否可安全重试的指南。

- *第 30 章* 探讨了对单个请求进行认证的话题，以及在 API 中对用户进行认证时要考虑的不同安全标准。
它提出了一种对 API 请求进行数字签名的规范，该规范遵循安全最佳实践，以确保 API 请求具有可验证的来源和完整性，并且事后无法被否认。

## 关于代码

本书包含许多源代码示例，既有编号列表形式，也有与正文混排的。
在两种情况下，源代码都使用像这样的等宽字体进行格式化，以与普通文本区分。
有时代码还会以 **粗体** 显示，以突出显示与本章前面步骤相比发生更改的代码，例如当新功能添加到现有代码行时。

在许多情况下，原始源代码已被重新格式化；我们添加了换行并重新调整了缩进，以适应本书的可用页面空间。
在极少数情况下，即使这样也不够，列表中还包含了换行续接标记（➥）。
此外，当代码在正文中已有描述时，列表中的源代码注释通常已被删除。
代码注释附在许多列表旁边，以突出显示重要概念。

在与我们的早期读者和审阅团队进行了大量讨论之后，我决定使用 TypeScript 作为标准语言，原因有多种。
首先，TypeScript 对于熟悉动态语言（如 JavaScript 或 Python）以及静态语言（如 Java 或 C++）的任何人都易于理解。
此外，虽然它可能不是每个人的最爱，并且并非所有读者都能立即编写自己的 TypeScript 代码，但代码片段可以被视为伪代码，大多数软件开发人员应该能够理解其含义。

当使用 TypeScript 定义 API 时，有两个部分需要处理：资源和方法。
对于前者，TypeScript 的原语（例如接口）在定义 API 资源的模式时非常具有表现力，使得 API 定义足够简短，几乎总是只占几行。
因此，所有 API 资源都被定义为 TypeScript 接口，这还有一个额外的好处，即 JSON 表示形式变得非常明显。

对于 API 方法，问题则稍微复杂一些。
在这种情况下，我选择使用 TypeScript 抽象类来表示整个 API 本身，并使用抽象函数来定义 API 方法，遵循 Google 的 Protocol Buffers 的 RPC 常用的约定。
这提供了仅定义 API 方法而无需担心底层实现的能力。

在考虑 API 方法的输入和输出时，我决定再次从 Protocol Buffers 中汲取灵感，以请求和响应接口的角度来思考。
这意味着在大多数情况下，会有表示这些输入和输出的接口，以 API 方法命名并带有 `-Request` 或 `-Response` 后缀（例如，`CreateChatRoomRequest` 用于 `CreateChatRoom` API 方法）。

最后，由于本书大量依赖 RESTful 概念，必须有一种方法将这些 RPC 映射到 URL（和 HTTP 方法）。
为此，我选择使用 TypeScript 装饰器作为各种 API 方法的注解，每个不同的 HTTP 方法对应一个装饰器（例如 `@get`、`@post`、`@delete`）。
为了指示 API 方法应映射到的 URL 路径，每个装饰器接受一个模板字符串，该字符串也支持请求接口中变量的通配符。
例如，`@get("/{id=chatRooms/*}")` 将填充请求中的 `ID` 字段。
在这种情况下，星号表示除正斜杠字符外的任何值的占位符。

尽管依赖 OpenAPI 规范来描述所有这些设计模式本来会很棒，但存在一些问题往往对本书的读者不利。
首先，OpenAPI 规范主要供计算机使用（例如代码生成器、文档渲染器等）。
由于本书的目标是向其他 API 设计者传达复杂的 API 设计主题，OpenAPI 似乎不是达成该目标的最佳可用选择。

其次，虽然 OpenAPI 是一个了不起的项目，但无论我们以 YAML 还是 JSON 格式表示 API，它都相当冗长。
不幸的是，使用 OpenAPI 表示这些复杂的主题是完全可能的，但并非最简洁的选择，导致会添加大量额外的内容而没有增加那么多价值。

最终，在 OpenAPI、Protocol Buffers 和 TypeScript 之间，早期读者和审阅者给出了相当明确的反馈，即 TypeScript 选项最适合这个特定的用例。
请记住，我完全不主张人们使用 TypeScript 来定义他们的 API。
它只是非常适合这个项目。
