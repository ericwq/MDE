API 优先是一种现代开发流程，涉及在构建应用程序其余部分之前先设计应用程序编程接口（API）。
这种策略将 API 视为所有服务所依赖的核心产品，而非软件开发生命周期后期才构建的辅助通信层。

当企业采用 API 优先策略时，会在应用程序开发流程之初就考虑几个因素：内部利益相关者、外部开发团队或业务合作伙伴想要访问哪些数据？
他们需要执行哪些操作？
他们需要哪些端点来实现这些目标？

一旦开发团队考虑了这些因素，并与各利益相关者协作定义了 API 契约，他们便构建 API。
然后，再构建用户界面和应用程序的其余部分。

## 为什么 API 优先很重要？

API 优先策略能够极大地加速企业的数字化转型。

以 [亚马逊著名的 API 优先指令](https://hbr.org/2021/04/apis-arent-just-for-tech-companies) 为例。
2002 年，Jeff Bezos 发出一份备忘录，要求公司每个团队必须 “通过服务接口暴露其数据和功能”，并且 “不得使用其他形式的进程间通信”。
团队还必须 “从零开始将这些服务接口设计为可供外部开发者使用……无一例外。”

在这项指令之后，亚马逊的每个团队都梳理了自己拥有的资源和数据，然后通过 API 将它们提供给其他团队和外部开发者。

这种向 API 优先的转变极大地推动了公司的发展。
在短短几年内，亚马逊从一家图书销售商转型为一家占据主导地位、市值数十亿美元的云计算巨头。

## 为什么 API 优先在当今如此流行？

两个字：[微服务架构](https://www.contentful.com/resources/microservice-architecture/) 。

许多创新企业正在摒弃单体应用 —— 那种将一系列业务功能和客户端应用捆绑在一个 “一刀切” 包中的做法。
取而代之的是，它们正在采用定制化的方式，通过混合搭配软件组件（如微服务）来构建模块化的技术栈，从而提供应对独特业务挑战所需的功能。

API 对于这种微服务架构至关重要。
它们充当接口层，使微服务生态系统中的各个组件能够相互通信并共享功能。

你可能已经明白为什么 API 优先的方法如此重要了。
因为这种策略专注于在任何其他工作开始之前，先定义并构建服务之间的 API 连接，从而产生最灵活、最易用的 API。
这使得构建健壮的微服务架构变得更加容易。

API 优先还提供了最佳的开发者体验，因为使用你 API 的开发者不会遇到任何隐藏的功能。
一切都可以直接使用，而某些代码优先或 UI 优先设计的工具则不同 —— 你也许能在 UI 中执行某个操作，但该操作在编程方式下却无法直接调用。
这会给希望自动化任务或将系统集成到更广泛工作流中的开发者带来困扰。

## API 优先 vs. 代码优先

为了深入探讨最后一点，让我们将 API 优先策略与更传统的 API 设计流程 ——代码优先开发—— 进行比较。

在代码优先开发中，构建新产品的团队会首先开发整个应用程序。
之后，一旦他们确定了应用最常见的用例，才会构建一个 API，该 API 仅针对这些特定用例暴露必要的数据和功能。

显而易见，在这种方式下，API 设计是事后才考虑的。
这就是为什么代码优先开发往往导致 API 不够理想、开发者体验不佳以及存在诸多令人沮丧的限制。
我们将在下一节说明其中的原因。

## 为什么选择 API 优先的应用或平台？

### 1. 通过 API 获得数据和功能的完整访问权限

还记得 API 优先策略是先构建 API，之后再添加用户界面吗？

这种策略的一大好处是，用户界面将提供与后端相同的数据和功能访问权限。
无论你是通过用户界面手动操作，还是通过 API 以编程方式操作，你都能执行相同的任务。

与之对比的是代码优先的 API 策略。
这种方式仅通过 API 暴露应用或平台的一小部分数据和功能，限制了你可以通过编程方式完成的任务。
你只能访问开发者认为你应该访问的数据和功能 —— 对于其他所有任务，你都需要在应用中手动完成。

### 2. 支持可组合架构

开发可组合应用意味着通过 API 将独立服务组合起来，创建可定制的技术栈。
例如，假设你正在 Contentful 中构建一个内容翻译工作流。
你可能会构建一个内部翻译服务，并将其与外部第三方服务集成，比如无头 CMS 和 [数字资产管理](https://www.contentful.com/help/media/managing-assets/working-with-a-dam-service/)（DAM）系统（以支持媒体资产的本地化）。

由于 Contentful 是一个 API 优先的平台，你可以获得构建翻译微服务连接器所需的所有数据和功能。
只需使用 Contentful 的 Read API 获取并翻译内容，然后使用 [Content Management API](https://www.contentful.com/developers/docs/references/content-management-api/) 将其写回即可。

如果你使用的是 API 优先的 DAM 服务，你将能够检索与待翻译内容相关的所有媒体资产（如包含嵌入文本的图片或区域特定视频），对其进行更新，然后重新上传到 DAM，同时更新 Contentful 中的资产引用。

这非常强大。
你实际上是在创建可组合应用，而无需编写任何胶水代码 —— 只需以通用的定义方式与 API 交互，无需使用特殊工具。
这大大减少了实现你独特目标所需的开发工作量。

### 3. 单一事实来源

如前所述，API 优先的开发流程先构建后端，再在其之上构建轻量级用户界面。
这意味着 UI 在访问和操作数据时，使用的与你相同的 API。
无论你使用前端还是后端，你面对的都是单一事实来源。

对比代码优先策略。
在软件开发流程末尾才构建 API 来暴露数据和功能，意味着需要构建第二套用于访问和操作数据的工具集。
当你用两种不同的方式操作数据时，往往会导致两个事实来源 —— 这是灾难的根源。

### 4. 自动化

<ins>当应用或平台采用 API 优先策略时，你在用户界面中执行的任何任务都可以通过脚本在后端完成。
这意味着不再有重复的手动工作。
同时，你也可以为内容同步、迁移乃至复杂的大规模数据操作等任务构建高级工作流。</ins>

下面是一个使用 API 优先工具构建的简单工作流示例：假设你在 Contentful 中创建了一个 [空间](https://www.contentful.com/help/getting-started/spaces-and-organizations/)（空间类似于内容、设置和结构的容器；每个项目通常都有自己的空间），但错误地选择了德语而非英语作为主语言环境。
由于 Contentful 采用 API 优先策略，你可以编写一个脚本来处理此事。
只需输入五六行代码并运行，你就拥有一个完全按需配置的新空间，无需打开 UI。

构建更复杂任务的工作流同样容易。
来看一个真实的工作流案例：Contentful 的一位客户发现，每当内部团队需要创建微站点时，他们都要手动生成一个新空间（而且这种情况发生得很频繁）。
于是，他们利用通过 Contentful API 暴露的功能和数据来自动化这一流程。

现在，他们可以从模板自动配置空间、构建它、将其部署到托管平台上，并邀请用户加入。
内部团队可以根据需要开始原型设计和定制，无需浪费开发者的时间在重复的手动任务上。

### 5. 更好的文档，更好的开发者体验

当新产品的开发团队采用 API 优先策略时，他们已经考虑了所有可能的用途和端点，因此添加清晰、全面的 API 技术文档只是水到渠成的一步。

这些资源将清晰地列出开发者在用 API 实现新工作流时需要的所有信息，例如：

- 所有可用的 [API 端点](https://www.contentful.com/blog/api-endpoint/)
- 这些端点如何工作
- 如何处理常见错误
- 是否使用 API 规范
- 该 API 规范是什么
- 展示如何在不同语言（如 JavaScript、C# 或 PHP）中使用 API 的示例

经过最周全设计的 API 优先应用甚至还会提供辅助工具，如软件开发工具包（SDK）。
这些工具能让你在不同场景（如移动应用）中使用 API 时更加得心应手。

至此，你可能认为 API 技术文档和辅助工具只是一个不错的附加项。
但实际上，它们是 API 优先平台和应用的一大卖点。

将其与传统产品对比一下。
如果你使用这些传统工具，很快就会发现获取技术文档需要花费多少精力。
更糟糕的是，你得到的文档往往不完整、过时，或者根本没有多大用处。
这使得你的开发者难以实现目标，也难以助力企业的数字化转型。

### 6. 无需等待访问审批

采用 API 优先策略，除了可能需要等待获取 API 密钥之外，你可以立即获得所需的一切访问权限。
你无需请求支持人员为你开放特定数据的访问权限 —— 所有端点已经存在。

例如，Contentful 的许多客户会查阅我们通过 API 优先开发流程生成的全面 API 文档，从而了解他们可以从系统中获取哪些信息，以及可以向系统中写入哪些信息。
开发者也很容易看到如何自动化流程和过滤数据，从而创建节省时间的智能工作流。

Contentful 的 API 优先策略为每位开发者提供了构建自己创新解决方案所需的工具。
相比之下，那些通过 API 提供有限访问权限且文档质量低劣的应用和平台，可能需要等待数周才能获得你的开发者所需的访问权限和文档。

## 如何实施 API 优先的方法

在组织内有效采用 API 优先的开发方法需要规划、清晰的沟通和明确定义的指南。
当组织内各团队汇聚一堂并就共享标准达成一致时，这种方法通常效果最佳。
以下是一组目标和最佳实践，你可以将其整合到 API 优先策略中，以确保更顺畅的实施或过渡：

### 1. 理解使用场景

API 优先始于对产品预期功能的共同理解，并需要产品团队、前端和后端开发者以及其他利益相关者之间的跨职能对齐。
这些团队应在 API 的规划阶段（在编写任何代码之前）达成一致。
虽然全组织范围的对齐是理想状态，但在开始时并非总是必要的。
最重要的是开发团队要确定谁将使用 API（是第三方开发者、内部团队、AI 工具还是前端？）以及他们需要实现什么目标。
这反过来将决定你如何构建 API，使其易于被每个相关团队使用。

从了解消费者将如何使用你的产品出发，你从一开始就将用户体验放在心上，设计 API 来满足这些需求。

### 2. 首先定义 API 契约

一旦你们明确了关键特性和功能，就需要在实际编写任何代码之前，使用 [OpenAPI](https://www.openapis.org/) 或 [GraphQL SDL](https://www.apollographql.com/tutorials/lift-off-part1/03-schema-definition-language-sdl) 等格式定义 API 契约，以便清晰地描述每个端点将做什么。
这将有助于使契约更加具体，并避免混淆或返工。
API 契约不仅作为文档，还作为帮助团队并行规划、构建和验证的共同协议。

此阶段的关键内容包括：

- 将端点映射到产品的功能
- 基于使用场景设计 API
- 以清晰和稳定为目标设计 API：使用约定俗成的命名规范和一致的状态码
- 包含带降级策略的错误处理
- 考虑分页、过滤和速率限制（如需要）

### 3. 通过模拟服务器支持并行开发

一旦 API 契约定义完成并经过内部评审，后端团队就可以着手实现该规范。
你可以启动一个模拟服务器，让前端能够与后端并行工作，质量保证（QA）团队也可以根据契约准备测试用例。
这种分离使得所有团队能够基于单一事实来源协同工作。

### 4. 使用 API 版本管理

API 版本管理可确保你在演进每个端点时保持 API 的向后兼容性。
最简单的方式是将其包含在 API URL 中（如 `/v1/`、`/v2/`）。
每次更新端点时，避免对现有版本进行破坏性更改，并确保缓慢地弃用旧版本，同时根据需要保持旧版本在线，给消费者足够的时间进行迁移。

### 5. 保持错误响应的一致性

以一致的格式返回错误会使 API 消费者更容易处理错误。
例如，你可以决定始终返回一个 `status` 字段（包含 HTTP 状态码）和一个用于进一步说明的人类可读的 `message` 字段。
你可以在 OpenAPI 规范中提供有关边缘情况的有用信息，以便消费者知道预期什么以及如何处理这些情况或超时。

### 6. 建立 API 治理

为避免每次创建新 API 时都重新发明轮子，最佳实践是建立关于架构结构和命名规范的集中式指南。
这有助于提高团队间的一致性，并有利于长期可维护性。
API 治理有助于防止混乱或碎片化，并支持大规模协作。

### 7. 将文档和测试确立为核心实践

将文档和测试确立为核心实践有助于使你的 API 易于理解、便于使用，并具备随时间扩展的能力。
[Swagger UI](https://swagger.io/tools/swagger-ui/)、[Redocly](https://redocly.com/) 和 [Stoplight](https://stoplight.io/) 等工具可以直接从 OpenAPI 规范生成交互式文档，使文档始终与实际契约保持一致。
作为 CI/CD 流水线一部分运行的契约测试可以帮助在破坏性变更进入生产环境之前将其捕获。

## API 优先如何支持 AI 集成

<ins>目前涌入市场的大多数 AI 工具都是通过 API 访问的，因此，如果你的产品是采用 API 优先方法论构建的，那么集成这些 AI 工具应该相对顺畅。
由于你的 API 是松耦合的，你可以在不进行重大重构或影响系统其他部分的情况下，替换或升级 AI 服务。</ins>

这使得 AI 驱动的推荐、聊天机器人和任务自动化等功能能够更快地推向市场。
API 优先的产品可以将多个 AI API 作为构建块使用 —— 比如翻译、音频转录和摘要。
所有这些额外功能都可以轻松连接到 API 已提供的数据。
拥有 API 优先的产品意味着，任何新出现的 AI 服务都可以轻松集成，使你的产品始终保持技术前沿。

## 为什么 AI 智能体偏爱 API 优先的系统

随着 AI 不断演进并日趋成熟，AI 智能体正越来越多地被设计为以编程方式代表用户执行操作，以检索数据、执行操作和触发工作流。
这要求智能体通过明确定义的接口与你的系统交互。

<ins>API 优先的系统在这方面具有优势，因为智能体可能需要的所有数据都通过 API 以一致的方式暴露出来，并配有文档完善的 [REST/GraphQL](https://www.contentful.com/blog/graphql-vs-rest-exploring-how-they-work/) 端点。</ins>

考虑一个被赋予以下目标的智能体示例：“找到所有近期给出负面反馈的客户。总结他们的反馈内容，并发送一封带有个性化道歉的邮件给他们。”

## 在可组合架构中可用的现成 API

| 功能 | 示例 API |
|------|----------|
| 内容管理 | Contentful |
| 电商 | Stripe、Swell、Commerce.js |
| 通信 | Twilio、Sendbird、Intercom |
| 搜索 | Algolia、Typesense |
| 媒体 | Cloudinary、Mux |

可组合架构是一种构建应用的新方法，你将通常由 API 交付的不同模块化组件组装在一起。
你无需自己构建所有内容并依赖单一的单体平台，
而是可以将内容管理、电商和身份验证等领域中一流的 SaaS API 整合在一起，然后组合它们来构建定制化解决方案。

这种模式由 API 优先的思维方式驱动。
每个服务都通过明确定义的 API 被构建为易于使用、集成和替换的。
例如，在构建无头电商网站时，你可能会使用 Contentful（用于内容管理）、像 Twilio 这样的通信 API（用于客户支持或聊天机器人）、Stripe（用于支付），以及像 React 这样的 [JavaScript 框架](https://www.contentful.com/blog/best-javascript-frameworks/) 来减少前端工作量。
这使你能够选择所需的确切功能，而不会被锁定在任何一个平台上。

## 总结

API 优先意味着在开发新产品时，API 是开发过程中首要且最重要的关注点。

作为终端用户，这意味着你将获得最佳的 API 使用体验。
作为开发者或构建者，你将获得构建强大定制技术栈以解决业务问题所需的一切工具。
你将能够自由创建创新工作流，改善工作方式并节省大量时间。
API 优先还能为你的组织带来更大的协作和创新空间，使集成 AI API 的前沿功能以及向其他团队或外部客户暴露内部能力变得更加容易。

简而言之，当你选择使用 API 优先的应用时，你可以在不重新架构整个系统的情况下，将应用扩展到新的方向。
你的创造力是唯一的限制！
