# 第 6 章 设计读写面向资源服务

在 [第 5 章](ch5.md) 中，我设计了一个虚构的 Web 服务，它提供各种行星 ⁑ 的地图图像、在地图上移动的导航信息，以及关于行星上地点（餐馆、陨石坑等）的信息。
这是大量需要提供的数据，但所有这些数据都可以包含在一个预先制作好的数据集中。
用户无法将自己的数据放到服务器上。

⁑ 请记住，我使用 “行星” 作为 “可通过经纬度寻址的天体” 的简写。
我指的不只是国际天文学联合会本周决定算作行星的 8 个或 11 个天体。

前一章中地图服务的客户端可以对地图和地点做各种有趣的事情，但它们不能依赖服务器来跟踪除预设数据之外的任何内容。
在本章中，我将扩展地图服务的范围。它将变得更不像搜索引擎的 Web 服务，而更像 Amazon S3 以及 Flickr 和 del.icio.us 的 API。
它不仅提供数据，还代表其客户端存储数据。

我应该让这个新服务有多开放？
一个完全开放的服务将允许用户提供标准数据集中所有内容的自己的版本。
客户端可以创建自己的行星，并上传自定义地图和地点数据库。
如果我懒得自己找地图数据（我确实懒），我甚至可以从一个空数据库开始，并允许社区填充我的整个数据集。
del.icio.us 和 Flickr 就是这么做的。

这是一个好主意吗？
在设计 Web 服务时，哪些状态的杠杆应该暴露，哪些应该自己保留？
这取决于你的用户想要做什么，以及你愿意为他们编写多少应用程序代码。

客户端使用 Web 服务，是因为该服务拥有它想要的东西：某些数据、一个存储数据的地方，或一个秘密算法。
Web 服务是一个抽象层，就像操作系统 API 或编程语言库一样。
如果你编写了一个用于处理无穷级数的数学库，而你所有的用户都开始使用它来估算 π 的值，你很可能会将该功能添加为一个更高级别的库函数。
这样，你所有的用户都可以使用相同的经过良好测试的 π 估算代码，而不是每个人编写自己的实现。
类似地，如果你所有的用户都在你的 Web 服务之上实现相同的功能，你可以通过将这些功能移入服务中来帮助他们。
如果你所有的用户都想向数据集中添加某些类型的自定义数据，你可以开始支持一种新类型的资源，这样他们就不必定义自己的本地结构了。

我在这里的目标相当适度：说明面向资源服务设计的概念。
当然，设计一个从空数据集开始并通过用户贡献获取所有内容的地图服务是可能的，但这样的服务将拥有比我需要解释的概念更多的活动部件。
如果我决定向你展示该服务，本章会有一个好的开头，但一旦我解释了所有概念，我仍然会有大量特定领域的设计工作要做，这会变得乏味。

我希望地图服务拥有的活动部件数量与我需要解释的新概念数量大致相当。
我将把前一章的服务扩展得刚好足够，以便客户端可以用自定义地点来注释地图。
每个自定义地点都与一个用户账户相关联，并且可以对该账户公开或私有。

## 将用户账户作为资源

<ins>如果我要让任何拥有 Web 服务客户端的人都能在我们的世界上进行注释，我需要某种方式来区分他的自定义地点和我数据库中的标准地点。
我还需要一种方式来区分一个用户的地点和所有其他用户的地点。
基本上，我需要用户账户。</ins>

当客户端用自定义地点注释地球或火星时，他所创建的地点会与他的用户账户相关联。
这样，客户端以后就能找到他的地点。
如果客户端选择公开暴露该地点，其他客户端将在他们获取的表述中看到指向该地点的链接。

大多数现有的 Web 服务都有某种系统让人们注册用户账户或 “API 密钥”。
即使是只提供只读访问的服务，也常常要求你注册一个账户，以便他们跟踪和配额你的使用。
如果你已经跟随书中的所有示例，那么到现在你应该已经拥有一个 Amazon Web Services 账户、一个 del.icio.us 账户和一个 Flickr 账户。

Yahoo! Web Services 的做法略有不同。
它不是将密钥与你个人绑定，而是你可以注册任意数量的应用程序密钥。
你可以将应用程序密钥与你的应用程序一起分发，任何人都可以使用它。
Yahoo! 跟踪的是应用程序的使用情况，而不是个人使用情况。
我为特定的 “应用程序”（即本书）注册了密钥 “restbook”。
你和其他任何人都可以使用该密钥来运行本书中的 Yahoo! Web Services 示例代码。

注册这些 Web 账户的过程差别不大。
你使用 Web 浏览器访问一个网站并填写一些 HTML 表单。
你通常需要点击同意一份法律协议，也许还需要回复一封验证邮件。
有时你的 Web 服务账户与你在该对应网站上已有的账户绑定。

我即将设计的用户账户系统工作方式略有不同。
在我的地图服务中，用户账户是资源，就像地图本身一样。
事实上，它们是我的第一批读写资源。
我的客户端将不必使用他们的 Web 浏览器来注册用户账户：他们可以使用通用的 Web 服务客户端来创建一个。

### 为什么用户账户应该是资源？

为什么我决定将我的用户账户设计得与几乎所有现有 Web 服务不同？
我有两个理由。第一：大多数 Web 服务要求你通过 Web 应用程序注册账户。
Web 应用程序设计是一个已被充分理解的主题，但不是本书的主题。
Web 服务确实与 Web 应用程序非常相似，但资源创建是它们不同的地方之一。
这里的主要区别在于，HTML 表单目前只支持 GET 和 POST。
这意味着 Web 应用程序必须使用重载 POST 来传达任何不安全的操作。
如果我试图涵盖获取用户账户的典型方法，我最终会略过那些与 Web 服务无关的细节。
将用户账户视为读写资源，意味着我可以在你可能熟悉的数据结构上演示新的面向资源设计流程。

第二，我想展示当你将日常数据结构视为资源并使其服从统一接口时，新的可能性就会出现。
考虑一个连接到我的地图服务的具有互联网功能的 GPS 设备。
大约每隔一小时，它就用其当前位置注释地球（通过我的 Web 服务暴露），创建一条 GPS 设备随时间推移的位置记录。

这些设备会有成千上万个，而且每个设备应该只能看到自己的注释。
负责为设备编程的人不应该被限制为仅供个人使用创建一个用户账户。
购买该设备的每个人也不应该在能够使用他们购买的设备之前，必须先访问我的网站并填写表格。

由于用户账户是资源，这些设备中的每一个都可以在我的 Web 服务上拥有自己的账户（可能使用基于序列号的用户名），并且这些账户可以自动创建。
它们可以在设备制造时批量创建，或者每个设备可以在其所有者首次开机时为自己创建一个账户。

最终用户可能永远不会知道他们正在使用 Web 服务，他们也永远不必注册密钥。
设备程序员确实需要知道我们的 Web 服务如何工作，并且需要编写能够创建用户账户的软件。
如果用户账户是资源，那么设备程序员如何做到这一点就很明显了。
HTTP 的统一接口提前给出了大部分答案。

### 认证、授权、隐私与信任

一旦我开始暴露用户账户，我就需要某种方式来确定给定的 HTTP 请求是由哪个用户（如果有的话）发起的。
*认证* 是将请求与用户关联起来的问题。
如果你想在火星上命名一个新地点，我需要某种方式知道这个新地点应该与你的用户账户关联，而不是其他人的。
*授权* 是确定对于给定用户允许哪些请求通过的问题。
有些 HTTP 请求我会接受来自用户 A 的，但拒绝来自用户 B 的：比如 “DELETE user A” 或 “GET 所有 user A 的私有地点” 这类请求。
在我的服务中，如果你以用户 A 的身份认证，你被允许操作用户 A 的账户，但不能操作其他人的。

我将在 [第 8 章](ch8.md) 中对 RESTful 的认证和授权模式有更多说明，但这里有一些基础知识。
当 Web 服务客户端发出 HTTP 请求时，它可能会在 HTTP 标头 `Authorization` 中包含一些凭据。
服务检查这些凭据，并决定它们是否能正确地将客户端识别为特定用户（认证），以及该用户是否确实被允许执行客户端尝试执行的操作（授权）。
如果两个条件都满足，服务器执行请求。
如果凭据缺失、无效或不足以提供授权，则服务器发送响应码 401（“Unauthorized”）。
它会设置 `WWW-Authenticate` 响应标头，并附带关于将来如何发送正确凭据的说明。

有几种标准类型的认证。
最常见的是 HTTP Basic、HTTP Digest 和 WSSE。
一些 Web 服务实现自定义形式的认证：在 [第 3 章](ch3.md) 中，我展示了 Amazon S3 如何使用复杂的请求签名机制实现认证。
由于我并没有实际实现这个服务，我选择哪种认证机制其实并不重要，但假设我选择最简单的选择：HTTP Basic 认证。

还有一个隐私的概念。
鉴于用户 A 的私有注释列表不能被任何其他用户访问，该列表的表述仍然需要通过互联网传输。
数据在到达客户端之前会经过许多计算机。
什么能阻止其中一台计算机检查这个据称是私有的列表呢？
为了解决这个问题，我将通过 SSL 加密每个 HTTP 事务。
在上一章中，我展示的 URI 以 `http://maps.example.com/` 开头。
在本章中，我的 URI 都以 `https://maps.example.com/` 开头。

使用 HTTPS 而不是 HTTP，可以防止其他计算机窃听客户端和服务器之间的对话。
这在您使用 HTTP Basic 认证时尤其重要，因为该认证机制涉及客户端以纯文本形式发送其凭据。

现在，我已经有了客户端和服务器之间安全、可信赖的通信方式。
但还有一层关系需要考虑：客户端软件和人类最终用户之间的关系。
为什么最终用户应该信任客户端软件处理其认证凭据呢？
让我问你一个问题来阐明这个问题。
每当你登录一个网站时，你都是在信任你的 Web 浏览器会将你的用户名和密码发送给该网站，而不会发送到其他地方。
你为什么会信任你的浏览器来处理这些信息呢？
你怎么知道你的浏览器没有一个秘密后门，将你输入的所有内容广播到某个低劣的 IRC 频道呢？

有几种可能的答案。
你可能正在使用像 Firefox 这样的开源浏览器，它具有良好的源代码控制，并且有很多人在查看源代码。
你可能会说人多安全：数百万人在使用你这种品牌的浏览器，并且没有任何可追溯到浏览器本身的问题。
你可能会监控你的网络流量，以确保你的浏览器只发送你告诉它发送的数据。
但大多数人只是凭信念相信他们的 Web 浏览器是可信赖的。

那是人类使用的 Web。
现在想象一下，我发送给你一个很酷的新 Web 服务客户端，用于管理你的 del.icio.us 书签。
你会用你的 del.icio.us 用户名和密码信任那个客户端吗？
你会像信任你的 Web 浏览器那样信任它来处理相同的信息吗？
希望不会！没有任何 Web 服务客户端能像 Web 浏览器那样受欢迎，也没有任何 Web 服务客户端能像浏览器那样有那么多人在查看源代码。
在人类使用的 Web 上，我们通常通过凭信心一跃并信任我们的 Web 浏览器来忽略这个问题。
在可编程的 Web 上，这个问题更加明显。
我们不一定信任我们自己的客户端来处理我们的认证凭据。

HTTP 标准中没有任何内容来处理这个问题，因为这是最终用户和客户端之间的问题：HTTP 存在于客户端和服务器之间。
解决这个问题需要放弃所有标准的认证信息发送方式：Basic、Digest 和 WSSE 都不起作用，因为它们要求客户端知道凭据。
（你可以使用 Digest 或 WSSE 解决这个问题，方法是让一个微小的、可信赖的账户管理器向实际的、不可信赖的客户端发送加密的认证字符串。
我不知道有任何 Web 服务客户端使用这种架构。）

像 Google、Amazon、eBay 和 Flickr 这样的 Web 服务大公司已经提出了让客户端在不知道实际认证凭据的情况下进行 Web 服务请求的方法。
你在 [第 3 章](ch3.md) 中看到了这一点的一个提示：我展示了如何签署 Amazon S3 请求并将一个特殊的 URI 交给其他人，他们可以在不知道你的密码的情况下使用它。
我将在 [第 8 章](ch8.md) 对此有更多说明。
现在，我只是想让你知道，在可编程的 Web 上有一个你可能从未考虑过的复杂问题。
因为目前还没有任何标准的解决这个问题的方法，我现在将暂时回避它，并为我的服务使用 HTTP Basic 认证。
我的用户将不得不像信任他们的 Web 浏览器一样信任他们的客户端。

### 将需求转化为读写资源

现在我已经确定了新的数据集（用户账户），我将按照与前一章开发数据集（行星、行星上的地点、行星的地图以及地图上的点）时相同的设计流程来进行。
但是前一章的流程只适用于只读资源。
本章使得客户端能够创建、修改和删除资源。
因此，我在该流程中增加了两个步骤（步骤 3 和步骤 4）。

1. 确定数据集
2. 将数据集拆分为资源

   对于每种资源：

3. 使用 URI 命名资源
4. 暴露统一接口的一个子集
5. 设计从客户端接受的表述
6. 设计提供给客户端的表述
7. 使用超媒体链接和表单，将此资源集成到现有资源中
8. 考虑典型的事件流程：预期会发生什么？
9. 考虑错误条件：可能出什么问题？

### 确定数据集

大多数拥有用户账户的网站都试图将个人信息（如你的姓名或电子邮件地址）与你的账户关联。
我对这些都不关心。
在我的地图服务中，与用户账户关联的信息只有两条：

- 账户名称
- 用于访问账户的密码

每个用户账户还有一些与之关联的从属资源（行星上的自定义地点），但我稍后会解决这部分问题。
我现在需要的只是一种标识特定用户账户的方式（用户名），以及一种让客户端提供凭据以将其与特定用户账户绑定的方式（密码）。

由于我不追踪任何个人信息，除了传统习惯之外，甚至没有理由将其称为 “用户账户”。
我可以称之为 “受密码保护的注释集”。
但我将坚持使用传统术语。
这使服务更容易形象化，也让你更容易想出对用户账户系统自己的增强。

### 将数据集拆分为资源

在 [第 5 章](ch5.md) 中，当我的数据集庞大而模糊（“行星、地点和地图”）时，这一步相当大。
这里的数据集相当有限：“用户账户”。
我将把每个用户账户暴露为一个资源。
用 [第 5 章](ch5.md) 的术语来说，这些新资源是第二类型的资源。
它们是我的服务暴露其底层用户对象的门户。
另一个站点可能也会将用户账户列表本身暴露为独立资源，或者暴露允许客户端搜索用户列表的算法资源。
我不会费心去做这些。

### 使用 URI 命名资源

这部分也很简单，因为我只有一种资源。
我将使用如下形式的 URI 暴露用户账户：`https://maps.example.com/user/{user-name}`。

### 暴露统一接口的一个子集

这是第一个新步骤。
在设计只读资源时我跳过了它，因为没有什么需要决定的。
根据定义，只读资源暴露的 HTTP 方法不超过 GET、HEAD 和 OPTIONS。
现在我正在设计可以在运行时创建和修改的资源，我还需要考虑 PUT、POST 和 DELETE。

即便如此，这一步也相当简单，因为统一接口始终是相同的。
<ins>如果你发现自己希望有更多的 HTTP 方法，首先要做的是回到第二步，尝试拆分你的数据集，以便你有更多种类的资源。
只有当这失败时，你才应该考虑通过使特定资源支持重载 POST 来引入 RPC 风格的元素。</ins>

重申 [第 5 章](ch5.md) 的例子：如果你有 “读者” 资源和 “已发布专栏” 资源，并且你开始想 “如果 HTTP 中有一个 SUBSCRIBE 方法就好了”，最好的做法是创建一种新类型的资源：“订阅”。
作为 HTTP 资源，订阅服从 HTTP 的统一接口。
如果你决定放弃统一接口，并通过在你的 “读者” 资源上重载 POST 来处理订阅，那么为这些资源定义接口将变得困难得多。

我可以通过询问有关预期用途的问题来决定暴露统一接口的哪些部分：

- 客户端会创建这种类型的新资源吗？当然会。
否则用户无法进入系统。

- 当客户端创建这种类型的新资源时，谁负责确定新资源的 URI？
是客户端还是服务器？
客户端负责，因为 URI 完全由常量字符串（`https://maps.example.com/user/`）和客户端控制的变量（`{user-name}`）组成。

从这两个问题我得到第一个结果。
要创建用户账户，客户端将向账户的 URI 发送 PUT 请求。
如果第二个问题的答案是 “服务器负责最终 URI”，我会期望我的客户端通过向某个 “工厂” 或 “父” URI 发送 POST 请求来创建用户。
请参阅本章后面的 [自定义地点](#custom-places) 部分，了解第二个问题的答案是 “服务器负责” 的情况。

- 客户端会修改这种类型的资源吗？
是的。是否允许用户更改其用户名是有争议的（为简单起见，我不打算允许），但应该始终允许用户更改其密码。

- 客户端会删除这种类型的资源吗？
当然。当你不再需要某个账户时，你可以删除它。

- 客户端会获取这种类型资源的表述吗？
这有待商榷。
目前，与用户账户关联的信息不多：只有用户名（它是 URI 的一部分）和密码（我不会给出）。
我将回答 “是”，这意味着我将在用户账户资源上暴露 GET 和 HEAD。
至少，客户端会想知道他们想要的用户名是否已经存在。
一旦我允许用户定义自定义地点，客户端就会想要查看特定用户定义的公共地点。

### 设计从客户端接受的表述

我的数据集没有内置用户账户：每个账户都是由某个客户端创建的。
这个设计中显而易见的下一个步骤是指定客户端应该如何创建用户账户。

让我们暂时回到 [第 3 章](ch3.md) 和 Amazon S3。
客户端通过向存储桶的 URI 发送一个空的 PUT 请求来创建 S3 存储桶。
客户端不需要在请求中发送实体主体，因为存储桶除了名称之外没有其他状态。
在存储桶内创建 S3 对象需要更多工作。
S3 对象有两种状态：名称和值。
名称进入 URI，即 PUT 请求的目标地址。
但值需要进入 PUT 请求的实体主体中。
S3 接受该实体主体中的任何数据，因为其全部意义在于 S3 对象的值可以是任何东西，但必须有一些东西存在：你不能有一个空对象。

大多数 Web 服务对实体主体中的内容要求稍微严格一些：它必须符合某种特定格式并传达某些资源状态信息。
我的用户账户有两个资源状态元素：用户名和密码。
如果 PUT 请求要成功创建用户账户，它需要传达这两个状态信息。
用户名包含在作用域信息中：任何创建账户的 PUT 请求都会在 URI 中包含该账户的用户名。
那么密码呢？

客户端将新用户的密码作为表述的一部分，放在实体主体中发送。
在 [第 5 章](ch5.md) 中，我将表述介绍为服务器发送给客户端的文档：服务器传达资源状态的一种方式。
表述也可以反向流动。
它们是客户端建议更改资源状态的方式。
当你 PUT 一个 S3 对象时，你发送的实体主体是该对象的一个表述。
你随 PUT 请求发送的表述是对资源新状态的断言。

在 [第 5 章](ch5.md) 的 [表示行星列表](ch5.md#represent-planet-list) 中，我考虑了几种可能的表述格式。
我查看了纯文本、JSON、使用虚构词汇表的 XML 以及 Atom（同样是 XML，但使用预先存在的词汇表）。
我决定使用 XHTML，这是一种面向标记人类可读文档的预先存在的 XML 词汇表。
在那个章节中，问题是什么格式在提供给客户端时最有用。
现在，问题是客户端应该如何格式化其建议的状态更改。
什么格式能让客户端最容易地向服务器传达密码？

当状态复杂时，服务器接受它发送的相同表述格式会很有帮助。
客户端可以使用 GET 请求获取表述，修改该表述，然后将其 PUT 回去，将其更改提交到底层资源状态。
正如我们将在 [第 9 章](ch9.md) 中看到的，Atom 发布协议有效地使用了这种技术。
当然，S3 按字节原样提供对象的表述，就像客户端首次将其 PUT 到系统中时一样。
S3 甚至不假装知道它所提供的表述的含义。

在这里，我只有一个状态项（密码），而且服务器永远不会将其发送给客户端。
现在是引入一种适用于像这样简单情况的表述格式的好时机。

<div style="background-color: darkgreen; padding: 8px; border-left: 4px solid lightgreen;">
<center>表单编码</center>

这种表述除了其媒体类型（`application/x-www-form-urlencoded`）之外，并没有正式的名称，但你以前可能见过它。
它有时被称为 “CGI 转义”。
当你在 Web 浏览器中提交 HTML 表单时，这是浏览器用来将表单数据编排成可以放入 HTTP 请求的格式。
考虑一个像示例 6-1 那样的 HTML 表单。

*示例 6-1. 一个简单的 HTML 表单*

```html
<form action="http://www.example.com/color-pairs" method="POST">
  <input name="color1" type="text"/>
  <input name="color2" type="text"/>
</form>
```

如果用户在文本字段 `color1` 和 `color2` 中输入值 “blue” 和 “green”，那么该数据的表单编码表述将是 `color1=blue&color2=green`。
当表单提交时，浏览器向 `http://www.example.com/color-pairs` 发出 POST 请求，并在实体主体中发送 `color1=blue&color2=green`：那是一种表述。
如果表单的 `method` 属性是 GET，那么当用户提交表单时，浏览器将向 `http://www.example.com/color-pairs?color1=blue&color2=green` 发出 GET 请求。
它包含相同格式的相同数据，但在这里，数据是标识资源的作用域信息，而不是表述。

当一个对象的状态可以表示为键值对时，表单编码是最简单的表述格式。
几乎每种编程语言都有内置的用于进行表单编码和解码的工具：它们通常位于该语言的 HTTP 或 CGI 库中。
</div><br/>

我的地图服务在客户端尝试创建或编辑用户时，接受表单编码的表述。
我与用户关联的唯一状态信息是用户名和密码。
用户名包含在 URI 中，并且我决定它不能更改，因此我的用户表述看起来就像 `password={the-password}`。
示例 6-2 是使用地图服务创建用户账户的假设 Ruby 代码。

*示例 6-2. 创建用户账户的假设地图客户端*

```ruby
require 'rubygems'
require 'rest-open-uri'
require 'cgi'
require 'uri'

def make_user(username, password)
  open("https://maps.example.com/user/#{URI.escape(username)}",
       :data => CGI::escape("password=#{password}"), :method => :put)
end
```

💡 这里需要注意几点。
首先，我已经开始通过网络传输敏感数据（密码），因此我现在使用的是 HTTPS。
其次，我实际上在这个代码示例中使用了两种不同的编码。
进入 URI 的用户名使用 `URI.escape` 进行 URI 编码。
进入表述的密码使用 `CGI::escape` 进行表单编码。
URI 编码与表单编码类似，但并不相同，混淆它们是常见且难以察觉的错误来源。

更改账户密码与最初创建账户的方式相同。
客户端向账户 URI 发送 PUT 请求，并附上账户的新表述（即新密码）。
当然，未经授权，任何人都不能更改账户的密码。
要修改用户账户，客户端还必须提供一个 `Authorization` 标头，让我的服务确信其有权修改该账户。
简而言之，更改用户密码需要知道当前密码。
如前所述，我的服务期望传入的 `Authorization` 标头符合 HTTP Basic 认证标准。

DELETE 请求从来不需要表述，但从我的服务中删除用户将需要正确的 `Authorization` 标头。
也就是说，要删除用户账户，你必须知道该用户的密码。

### 设计提供给客户端的表述

客户端将 GET 用户账户的 URI 以检索用户账户的表述，就像客户端 GET 地图或地点的 URI 以检索该地图或地点的表述一样。
用户账户的表述应该是什么样子呢？

目前它看起来不会有太多内容，因为我只有两种状态信息需要传达，而且其中一种（密码）我不想发送出去。
事实上，在一个设计良好的系统中，我甚至不会有密码可以发送。
我只会拥有其加密版本，用于认证目的。
一旦我将自定义地点集成到这个表述中，它看起来会更好。
现在，示例 6-3 是一个相当稀疏的 XHTML 文档。

*示例 6-3. “你的” 用户账户的表述* <a id="example-6-3"></a>

```html
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.1//EN"
"http://www.w3.org/TR/xhtml11/DTD/xhtml11.dtd">
<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="en">
<head>
  <title>User homepage for leonardr</title>
</head>
<body>
  <p class="authenticated">
    You are currently logged in as
    <a class="user" href="/user/leonardr">leonardr</a>.
  </p>
  <p>User homepage for
    <a class="user" href="/user/leonardr">leonardr</a>
  </p>
  <form id="modifyUser" method="put" action="">
    <p>Change your password:
      <input class="password" name="password" /><br />
      <input class="submit" />
    </p>
  </form>
</body>
</html>
```

我再次使用表述来传达当前的资源状态，并帮助客户端驱动到其他状态。
我使用 HTML 表单来描述客户端如果希望更改用户密码（资源状态的一项）可能发出的未来 PUT 请求。
请注意，没有表单告诉客户端如何获取表述，或如何删除此用户。
这是理所当然的，你使用 HTTP GET 和 DELETE 来实现这些。
我只在复杂的事情上需要超媒体：指向其他资源的链接（以便客户端知道要 GET 或 DELETE 哪个 URI）以及表述的描述。

💡 你可能已经注意到示例 6-3 中的一个问题。
它的表单指定了 HTTP 方法为 PUT，但 HTML 表单只允许 GET 和 POST。
与 [示例 5-11](ch5.md#example-5-11) 中的 “repeat” 语法一样，我使用尚未发布的 XHTML 5 来规避当前版本 HTML 的缺点。
另一种处理方式是发送 WADL 片段而不是 HTML 表单，或者使用 [第 8 章](ch8.md) 中描述的技术通过重载 POST 来运行 PUT 请求。

如果你 GET 他人的用户账户，你将看到不同的表述，类似于示例 6-4。

*示例 6-4. 他人用户账户的表述*

```html
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.1//EN"
"http://www.w3.org/TR/xhtml11/DTD/xhtml11.dtd">
<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="en">
<head>
  <title>User homepage for samruby</title>
</head>
<body>
  <p class="authenticated">
    You are currently logged in as
    <a class="user" href="/user/leonardr">leonardr</a>.
  </p>
  <p>User homepage for <a class="user" href="/user/samruby">samruby</a></p>
</body>
</html>
```

这个表述没有用于改变资源状态的控件，因为客户端未被授权这样做：客户端以 `leonardr` 的身份认证，而这是 `samruby` 的页面。
目前，该表述除了向 `leonardr` 确认存在一个名为 `samruby` 的用户之外，什么也没有做。
如果没有这样的用户，对 `/user/samruby` 的 GET 请求将返回状态码 404（“Not Found”），客户端可以自由地通过 PUT 请求创建 `samruby`。

### 将此资源链接到现有资源

在上一章中，我定义了几类资源：地图列表、单个地图、地点和地点列表（即搜索结果列表）。
这些都与用户账户没有直接关系，但此时我可以添加一些不错的功能。

一个不错的功能是，在每种资源的表述中都添加 “authenticated” 消息（如上面两个示例表述中所示）。
每当客户端提交带有有效凭据的请求时，都会显示该消息。
“authenticated” 消息是一段超媒体，它向已认证的客户端展示如何检索其用户账户的数据。
现在，每个资源都链接到请求它的用户的用户账户。

另一个不错的超媒体功能是，向未认证的客户端展示如何创建用户账户。
放置这段超媒体的最佳位置是行星列表的表述：毕竟，那是服务的 “主页”。
它已经包含指向服务其他主要部分的链接，因此它也应该包含指向这个新部分的链接。

再一次，HTML 超媒体并不能完全胜任这项工作。
同样，我将使用 XHTML 5（它对 HTML 做了微小改动），而不是在一章中间引入像 WADL 这样的全新技术。
示例 6-5 是一个 XHTML 5 片段，它告诉客户端如何创建用户。

*示例 6-5. 描述如何创建用户账户的超媒体*

```html
<form id="createUser" method="PUT" template="/user/{username}">
  <p>Username: <input type="text" name="username" /><br />
  <p>Password: <input type="password" name="password" /><br />
  <input class="submit" />
</form>
```

💡 与你熟悉的 HTML 相比，这里有两个偏离：`method` 属性（如 [示例 6-3](#example-6-3)，它指定了 PUT，而 HTML 4 只允许 GET 和 POST）以及全新的 `template` 属性，它使用 URI 模板标准（ http://www.ietf.org/internet-drafts/draft-gregorio-uritemplate-00.txt ）将表单变量（“username”）插入到 URI 中。

💡 在撰写本文时，URI 模板是 HTML 5 的提议添加内容，但尚未被批准。
它有可能被拒绝，那样的话，示例 6-5 将不再比它对 HTML 4 有效时更有效。
在这种情况下，你可以非正式地使用 URI 模板（迫使你的用户编写自定义客户端），或者切换到 WADL。

超媒体表单谈论的是 PUT 请求的语法，但它无法对语义说太多。
Web 服务客户端可以读取示例 6-5 中的 HTML 表单，但其理解是有限的。
它知道表单被标记为 “createUser”，但它不知道 “createUser” 是什么意思。
它知道如果它将某个表述 PUT 到某个 URI，服务器很可能会接受它。
它知道 PUT 意味着什么，因为 PUT 总是意味着同样的事情。
它知道表述应该包含一个 “username”，但它不知道 username 是什么。
需要人类 ——程序员—— 来理解用户是什么，理解 “createUser” 意味着 “创建用户”，理解用户名是什么，以及所有其余内容。
程序员需要设定关于何时以及如何创建用户账户的规则。
这段超媒体只是告诉客户端，当需要 “createUser” 时（无论那意味着什么），如何构建 PUT 请求。
这是 Web 服务对客户端的一个承诺。

许多 Web 服务为了便于客户端程序员使用，将所有这些数据放在前端，放在单个 WSDL 或 WADL 文件中。这有些违背 REST 设计哲学，因为它违反，或者至少是颠覆了连通性原则。但在 Web 服务中，由于客户端必须预先编程，这种冲动是可以理解的，而且通常不会引起任何问题。

### 预期会发生什么？

让我们考虑一下当客户端向 `/user/leonardr` 发送 PUT 请求时可能发生的情况。
与 HTTP 通常的做法一样，服务器读取此请求，在后台采取某些操作，并提供一个响应。
我需要决定响应将使用哪个数字响应码，以及将提供哪些 HTTP 标头和/或实体主体。
我还需要决定该请求将如何影响资源状态：也就是说，它将产生哪些实际效果。

如果 PUT 请求一切顺利，会发生什么并不难看出。
如果没有名为 “leonardr” 的用户，服务将使用指定的密码创建一个。
响应码为 201（“Created”），`Location` 标头包含新创建用户的 URI。

如果用户账户已经存在，资源状态将被修改，以使其符合客户端建议的新表述。
也就是说，账户的密码将被修改。
在这种情况下，响应码可以是 200（“OK”），响应实体主体可以包含用户账户的表述。
或者，由于密码更改永远不会影响表述，响应码可以是 205（“Reset Content”），而响应实体主体可以完全省略。

PUT 请求是唯一复杂的请求，因为它们是唯一包含表述的请求。
GET 和 DELETE 请求完全按照统一接口工作。
成功的 GET 请求具有响应码 200（“OK”）和实体主体中的表述。
成功的 DELETE 请求也具有响应码 200（“OK”）。
服务器可以发送实体主体来响应成功的 DELETE，但它可能只包含状态消息：不再有资源可以发送其表述了。

### 可能出什么问题？

创建、修改或删除资源的请求比仅检索表述的请求有更多的失败情况。
以下是这种新资源的一些错误条件。

最明显的问题是客户端的表述可能不被服务器理解。
我的服务器期望表单编码格式的表述；客户端可能发送了 XML 文档。
这种情况下的状态码是 415（“Unsupported Media Type”）。

另外，客户端可能根本没有提供表述。
或者它可能提供了格式错误或包含无意义数据的表单编码表述。
这种情况下的状态码是 400（“Bad Request”）。

也许表述有意义，但它告诉服务器将资源置于不一致或不可能的状态。
也许表述是 `password=`，而我不允许空密码账户。
确切的状态码取决于错误；在空密码的情况下，可能是 400（“Bad Request”）。
在另一种情况下，可能是 409（“Conflict”）。

也许客户端发送了错误的凭据，发送了完全不同的用户账户的授权凭据，或者根本没有发送 `Authorization` 标头。
客户端只有提供该用户的凭据时，才能修改或删除该用户。
这种情况下的状态码是 401（“Unauthorized”），我将设置 `WWW-Authenticate` 标头并附带对客户端的说明，提示如何根据 HTTP Basic 认证规则格式化 `Authorization` 标头。

如果客户端尝试创建一个已存在的用户，一个可能的响应码是 409（“Conflict”）。
这是合适的，因为执行 PUT 请求将使服务的资源处于不一致状态：会有两个具有相同用户名的用户资源。
另一种可能性是将 PUT 请求视为尝试更改现有用户的密码而不提供任何认证，并发送响应码 401（“Unauthorized”）。

如前一章所述，服务器端可能出现未指明的问题：响应码 500（“Internal Server Error”）或 503（“Service Unavailable”）。

## 自定义地点

现在我准备再次完整地走一遍资源设计流程。
这次我要设计客户端可以创建的自定义地点：这些地点将与内置地点一起显示在地图上。
希望你到现在已经掌握了这个流程的要点（如果没有，也别灰心：我将在下一章中再做几次），所以这次我们走得会简短一些。
这次我想重点关注自定义地点与用户账户的不同之处。

### 确定数据集

Web 服务客户端可以在任何有地图的行星上创建任意数量的地点。
自定义地点将出现在搜索结果列表中，就像前一章中的内置地点一样。
自定义地点可以拥有与内置地点相同的数据：类型（“city”）、名称（“Springfield”）、经纬度坐标（“39.81E 89.64W”）和文本描述（“伊利诺伊州首府”）。
多个自定义地点可以共享相同的坐标（“我家” 和 “我当前位置”），并且自定义地点可以与内置地点共享位置。

每个自定义地点都与某个用户账户关联。
自定义地点可以是公开的或私有的。
私有地点只有提供 “拥有” 该地点的用户账户凭据的人才可见和可修改。

### 将数据集拆分为资源

每个自定义地点都将成为一个资源，就像每个内置地点一样。
我还希望让客户端获取其自定义地点的列表。
在我的设计中，用户账户只是一个受密码保护的地点列表，因此我不会将地点列表暴露为单独的资源。
相反，我将扩展 “用户账户” 资源，使其包含用户的地点列表。
这类似于 Amazon S3 中的存储桶被表示为对象列表的方式。

### 使用 URI 命名资源

自定义地点显然是一个从属资源，但它从属于什么？
我可以合理地将其与用户账户、某个行星上的地理点，或像城市、国家或行星这样的包含性地点关联。
我应该用 URI 捕获这些关系中的哪一种呢？

我选择以与命名内置地点大致相同的方式来命名自定义地点。
每个地点都与一个地理点相关联，并可以使用如下形式的 URI 访问：`/user/{username}/{planet}/{latitude},{longitude}/{place name}`。
新元素是 `{username}`，旨在区分不同人对同一地点的看法：
例如，Sam 对 Joe's Diner 的评价位于 `/user/samruby/Earth/45.2;-114.2/Joe's%20Diner`，
而 Leonard 不那么好评的评价位于 `/user/leonardr/Earth/45.2;-114.2/Joe's%20Diner`。

像 `/Earth/USA?show=Joe's+Diner` 这样的 URI 会像以前一样工作：它返回美国境内名为 “Joe's Diner” 的地点的搜索结果。
唯一不同的是，现在可能有更多可搜索的地点：不仅是内置地点数据库，还有每个用户的公开地点列表，以及你自己的私有地点列表。

内置地点仍然享有特权。
碰巧的是，日本有一个主题公园，其中包括一个三分之一比例的拉什莫尔山模型。
如果客户端在东京北部创建一个名为 “Mount Rushmore” 的自定义地点，`/Earth/Mount%20Rushmore` 仍然指向南达科他州的原址。
它不会突然变得模糊，不确定该 URI 指的是哪个 “Mount Rushmore” 资源。
然而，`/Earth?show=Mount+Rushmore` 将同时显示这两个地点。

### 暴露统一接口的一个子集

客户端可以使用 GET 和 HEAD 来检索内置地点、它们自己的地点（无论是公开还是私有）以及他人创建的公开地点的表述。
客户端可以使用 DELETE 删除它们自己的地点，并使用 PUT 更改它们地点的状态。

客户端创建地图注释的方式有两种。
客户端可能会对地图上现有的地点（“拉什莫尔山”）添加评论，或者它可能会为某个经纬度点赋予一个新名称（“我亲吻 Betty 的玉米地”）。

在第一种情况下，正在创建的资源是 “拉什莫尔山（从 leonardr 的角度来看）”。
创建此资源时，客户端不应该需要知道拉什莫尔山在地图上的确切位置。
“拉什莫尔山” 是一个共识名称，并且有一个同名的内置地点。
客户端可以依赖服务器来查找坐标。
在第二种情况下，正在创建的资源是一个全新的地点，服务器从未听说过，并且客户端负责知道坐标。

我如何将这个功能融入我的面向资源的设计中呢？
“拉什莫尔山（从 leonardr 的角度来看）” 是另一个资源的从属资源：即内置地点 “拉什莫尔山”。
该资源已经存在并且有一个 URI：其中之一是 `/Earth/Mount%20Rushmore`。
如果客户端想要重用一个地点的共识名称，它不应该需要查找其位置。
客户端可以省略确定注释最终 URI 并对其发送 PUT 请求的步骤，而是直接向 “拉什莫尔山” URI 发送 POST 请求，让服务器确定最终的 URI。

类似地，如果客户端想要评论阿拉巴马州议会大厦，它可以 POST 到 `/Earth/USA/AL/State%20capitol`，而不是找出确切的坐标或街道地址。
任何标识内置地点的 URI 都可以成为对该地点发表评论的 POST 请求的目标。

那自定义名称呢？
如果客户端想要将 “Mount Rushmore” 这个名字赋予的，不是南达科他州的原址，而是今市市的那个比例模型，该怎么办？
如果客户端想要为 “我亲吻 Betty 的玉米地” 创建一个注释，又该怎么办？

在这种情况下，客户端必须知道它想要创建的地点的纬度和经度。
这意味着它将拥有创建新资源 URI 所需的所有信息：世界、世界上的一个地理点、地点的名称以及它自己的用户名。
客户端可以向类似 `/user/bob/Earth/42;-93.7/the%20cornfield%20where....` 的 URI 发送 PUT 请求。
这将与通过向 `/user/bob` 发送 PUT 请求来创建用户账户的方式类似。

即使在这种情况下，使用 POST 也更简洁。
地图上的一个全新地点是一个从属资源：它从属于行星上的某个点，就像对内置地点的评论从属于行星上的某个地点一样。
因此，客户端也可以通过向 `/Earth/42;-93.7` 发送 POST 请求来在地图上放置一个新地点。
其工作方式与对现有地点的评论（向 `/Earth/Mount%20Rushmore` 发送 POST）相同，只是这里的地点是通过经纬度而不是共识名称来标识的。

我的服务将支持对全新地点使用 POST，因为这更简单。
无论你是向行星添加一个全新地点，还是对某个共识地点发表评论，接口都将是相同的。
其他服务可能支持这两种方法：如果客户端愿意确定最终 URI，则向其发送 PUT；如果不愿意，则向父 URI 发送 POST。

最后，请注意，尽管我使用的是 POST，但它并不是重载 POST。
我的服务的客户端仅在想要在现有资源 “之下” 创建资源时才使用 POST。
新资源的 URI（`/user/leonardr/Earth/43.9;-103.46/Mount%20Rushmore`）可能不会直接扩展旧资源的 URI（`/Earth/Mount%20Rushmore`），但资源之间存在概念上的关系。

### 设计从客户端接受的表述

当客户端在地球上插入图钉并创建一个自定义地点时，它需要提供哪些信息？
它必须标识一颗行星以及该行星上的一个地点：即图钉所在的位置。
该地点可以通过经纬度来标识，也可以通过引用像 “Mount Rushmore” 这样的规范名称来标识。
将这些变量称为 `planet`、`latitude`、`longitude` 和 `name`。
服务器必须知道客户端在地图上放置的是什么类型的地点。
一个地点可以是公开的或私有的，并且客户端可以提供对该地点的自定义描述。
最终 URI 还包含用户名，但客户端已经在 `Authorization` 标头中提供了该信息。
没有必要让客户端发送两次该信息。

这些都是键值对。
我可以让客户端像表示用户账户那样表示地点：作为表单编码的字符串。
这里没有可能需要 JSON 或 XML 表示的复杂数据结构。

客户端请求可以选择发送某些键值对而省略其他键值对。
作为作用域信息存在于 URI 中的信息，不需要在表述中重复。
当客户端向 `/Earth/43.9;-103.46` 发送 POST 时，它不需要指定纬度和经度，因为这些信息已经在 URI 中。
它需要指定 `name` 和 `type`。

当客户端向 `/Earth/Mount%20Rushmore` 发送 POST 时，它不应该指定 `latitude`、`longitude` 或 `name`。
客户端正在基于一个众所周知的现有地点创建一个新地点，并且新地点将继承现有地点的名称和位置。
客户端可以指定自定义类型（“national-park”、“political”、“places in North Dakota”）或继承默认类型（“monument”）。

*示例 6-6. 创建从属资源的 HTTP 请求*

```
POST /Earth/USA/Mount%20Rushmore HTTP/1.1
Host: maps.example.com
Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ=
Content-Type: application/x-www-form-urlencoded

type=national-park&description=We%20visited%20on%203/5/2005
```

客户端可以始终选择省略 `description` 和 `public`。
我的服务为这些变量设置了默认值：描述默认为空，地点默认为公开。

当客户端修改其自定义地点之一时，该地点的任何内容都可能发生变化：其名称、位置、类型、描述或公开状态。
修改地点的 PUT 请求可以指定与创建地点时相同的键值对，并且可以任意组合。
服务器将进行相应的更改，前提是这些更改是合理的。

示例 6-6 显示了一个创建新自定义地点的示例 HTTP POST 请求。
结合表单编码的表述和 URI 中的作用域信息，共同传达了新资源所需的所有状态。
新资源的名称和位置来自作用域信息；其类型和描述来自表述。
由于表述没有为 `public` 指定值，因此默认值生效，此新资源将被设为公开。

### 设计提供给客户端的表述

这里的大部分工作已经完成。
在 [第 5 章](ch5.md) 中，我为地点定义了一种基于 XHTML 的表述格式。
自定义地点看起来与内置数据库中的地点相同。

唯一的新部分是：当已认证的客户端请求其某个自定义地点的表述时，我们的服务会在表述中附加一些超媒体内容，向客户端展示如何编辑该地点（参见示例 6-7）。
我不需要告诉客户端如何删除该地点：统一接口已经处理了这一点。
但我确实需要传达我上面用文字描述的信息：地点由行星、纬度、经度等定义。

*示例 6-7. 向客户端展示如何编辑其某个地点的超媒体表单*

```html
<form id="modifyPlace" method="PUT" action="">
  <p>Modify this place:</p>
  <p>
    Name: <input name="name" value="Mount Rushmore" type="text" /><br />
    Type: <input name="type" value="national-park" type="text" /><br />
    Position:
    <input name="latitude" value="43.9" type="text" />,
    <input name="longitude" value="-103.46" type="text" /><br />
    Description:
    <textarea name="description">We visited on 3/5/2005</textarea><br />
    Public?
    <input name="public" type="checkbox" value="on"/>
    <input type="submit" />
  </p>
</form>
```

之前的注意事项在这里同样适用。
这不是有效的 XHTML 4，尽管它是有效的 XHTML 5，因为它将 PUT 指定为其方法。
此外，除非客户端预先编程，否则它不知道如何处理此表单。
计算机不知道 “modifyPlace” 是什么意思，也不知道 “latitude” 可能的好值是什么。

由于客户端必须预先编程才能理解这些表单，当今的大多数服务不会在资源的表述中包含用于修改该资源的表单。
它们要么预先提供所有表单（在 WSDL 或 WADL 文件中），要么用文字说明（就像我上面做的那样），留给服务程序员去解决。
是否真的有必要在提供表述的同时提供表单，这尚有争议，但提供它们总比仅仅用文字指定 API 然后让程序员去实现要好。

### 将此资源链接到现有资源

我有三种集成需要做。
第一种是数据集成。
当你 DELETE 一个用户账户时，该账户的自定义地点——即 `/user/{username}` 下的所有内容 —— 也应该被删除。
曾经能正常工作的这些资源的 URI，现在将返回响应码 410（“Gone”）或 404（“Not Found”）。

其他类型的集成现在你应该已经熟悉了。
它们涉及更改现有资源的表述，以提及新资源。
我希望搜索结果链接到自定义地点。
我希望地球上的点能够展示用户如何在该点创建自定义地点。
我想通过将 “自定义地点” 资源连接到我已经定义的资源，来改善我的连通性。

### 预期会发生什么？

这种新资源，即自定义地点，其工作方式与我已定义的其他资源大致相同。
自定义地点响应 GET 的方式与内置地点相同。
它响应 PUT（附加以键值对组成的表述）和 DELETE（无表述）的方式与 “用户账户” 资源相同。
这里我只需要考虑几个新的边界情况。

当客户端创建自定义地点时，响应码为 201（“Created”）。
这与用户账户的工作方式相同。
但之前用户账户的 URI 不可能发生变化，因为我禁止用户更改其用户名。
而地点的名称是可以更改的，或者地点（例如一艘船）也可以在地图上的点之间移动。这两种操作都会改变 URI。

当客户端修改自定义地点但不改变其位置时，响应码为 200（“OK”）。
如果位置发生变化，响应码为 301（“Moved Permanently”），并且 `Location` 标头将包含该地点的新 URI。
客户端负责更新其数据结构以跟踪新的 URI。
这涉及到一个我将在 [第 8 章](ch8.md) 中重新讨论的争论：是拥有包含有用信息的 URI 更重要，还是拥有永不更改的 URI 更重要。
我的 URI 使用两种资源状态信息来描述自定义地点：坐标和名称（`/user/leonardr/Earth/43.9;-103.46/Mt.%20Rushmore`）。
如果其中任何一个发生变化，旧的 URI 就会失效。

失效的 URI 在人类使用的 Web 上毫无乐趣，在可编程的 Web 上则更加无趣。
如果我的自定义 “地点” 是一艘船或其他不断移动的东西，它实际上就没有永久的 URI。
这是我系统中最严重的设计缺陷。
如果我将其作为真正的 Web 服务来暴露，我可能会为每个地点提供一个 “永久链接”：一个不包含任何可变资源状态的备用 URI。
由于地点的所有内容都可能改变，除了其所在的行星和所有者之外，这些 URI 看起来不会很友好：我对拉什莫尔山的注释可能可以从 `/user/leonardr/Earth/36028efa8` 访问。
但至少它们将始终指向同一个地点。

### 可能出什么问题？

这种新类型的资源引入了新的错误条件，但其中大多数是我已经介绍过的条件的变体，因此我将快速略过它们。
客户端可能试图通过提供无效的经纬度将现有地点移出地图：响应码为 400（“Bad Request”），就像 [第 5 章](ch5.md) 中类似情况一样。
当客户端试图创建地点但未提供服务器所需的所有信息时，400 响应码也是合适的。
这类似于如果客户端告诉服务器更改用户密码但实际上并未提供新密码时，服务器发送的 400 响应码。

我的服务不允许单个用户在相同坐标处定义多个同名地点。
`/user/leonardr/Earth/43.9;-103.46/Mt.%20Rushmore` 一次只能标识一个地点。
假设客户端有两个名为 “My car” 的地点，并发出了一个 PUT 请求，试图将其中一个移动到另一个的位置。
我的服务将拒绝此请求，并返回响应码 409（“Conflict”）。
将地点移动到某个坐标集本身并没有问题；只是碰巧那里已经有另一个同名地点了。
如果客户端在相同坐标处有两个自定义地点，并试图将其中一个重命名为与另一个相同的名称，同样会发生 409 响应码。
无论哪种情况，客户端都在发出一个语法上有效的请求，但该请求会使系统资源处于不一致状态。
这类似于尝试创建一个已存在的用户。

有一个全新的错误条件值得关注：客户端可能试图访问他人创建的私有地点。
这里有两种可能性。
第一种是使用响应码 403（“Forbidden”）拒绝访问。
当客户端未提供认证或提供的认证不足时，使用 403 响应码；后者肯定适用于这种情况。

但是，响应码 403 实际上默认了该资源的存在。
服务器不应泄露此信息。如果客户端 A 创建了一个自定义地点并将其标记为私有，客户端 B 不应该能够了解到关于该地点的任何信息，甚至包括它的名称，即使是通过猜测也不行。
当揭示资源的存在会危及安全时，HTTP 标准允许服务器撒谎，并发送响应码 404（“Not Found”）。

## 回顾地图服务

这仍然是一个简单的设计，但它已经拥有了相当多的功能。
在 [第 5 章](ch5.md) 中，我的客户端可以获取地图图像、在地图上导航、收藏地球上的点，以及针对内置地点数据库进行地理搜索。
现在，它们可以跟踪自定义地点、在共识地点上注册评论，并与其他用户共享地点。
[示例 5-6](ch5.md#example-5-6) 中的表述展示了这些功能中的绝大部分。

所有这些功能都是通过暴露统一接口的资源来提供的。
偶尔，我需要用超媒体表单（在这里是 XHTML 5 表单）来补充统一接口，以告诉客户端什么样的表述可以伴随 PUT 或 POST 请求。
绝大多数请求将是 GET 请求。
这些请求不需要超媒体补充，因为 GET 始终意味着相同的事情。

客户端可以通过构造 URI 直接到达其想要的资源，也可以通过在我提供的超媒体中导航链接来到达该资源。
你可以通过跟随链接和填写表单，从服务根目录（行星列表）到达任何地方。
每个资源都相当简单，但整个服务非常强大。
这种力量来自于资源的多样性、连接它们的链接，以及每个资源都是独立可寻址的事实。

面向资源的架构（ROA）列出了一系列你需要问自己的设计问题。
我将这些问题体现在上一章的七步设计流程以及本章扩展的九步流程中。
像任何架构一样，ROA 强加了设计约束，但它不会为你做出所有设计决策。
还有很多其他方式可以用 RESTful 和面向资源的方式定义地图服务。
这一切都取决于你如何将数据集拆分为资源、为这些资源定义何种表述，以及如何用超媒体将它们联系在一起。

我所设计的应该能够工作并对客户端有用，但我无法确定，因为我不需要实现它。
我只是为了在书中说明概念而设计了它。
当设计一个真正的服务时，你还需要考虑实现问题。
你必须编写代码来支持你所做的每一个决策：关于暴露哪些资源、它们响应统一接口的哪些部分、你选择哪些 URI，以及你提供和接受哪些表述的决策。
在下一章中，我将针对不同的数据集再次做出所有这些决策，而这次我将用真正的实现来支持它们。
