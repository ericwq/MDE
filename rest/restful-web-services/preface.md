# 前言

> 一个能够正常工作的复杂系统，总是从一个能够正常工作的简单系统演化而来的。
>
> <p align="right">——John Gall，《Systemantics》</p>

我们写这本书，是为了向你介绍一项令人惊叹的新技术。
它已经来临，它正炙手可热，并且它承诺将从根本上改变我们编写分布式系统的方式。
我们所说的，是万维网。

好吧，它并非一项新技术。
它不像过去那样炙手可热，而且从技术角度来看，它也并不令人难以置信地惊叹。
但其他方面都是真实的。在过去的十年里，Web 已经改变了我们的生活方式，但它还有更多的变革等待释放。
Web 是一个简单、无处不在，但却被忽视的分布式编程平台。
本书的目标就是释放这种变革力量，并将其传递到世界中去。

声称 Web 在分布式编程方面的潜力被忽视了，这听起来可能有些奇怪。
毕竟，本书要与众多其他关于 Web 服务的书籍争夺书架上的位置。
问题在于，当今大多数 “Web 服务” 实际上与 Web 毫无关系。
与 Web 的简洁性背道而驰，它们推崇一种用于分布式对象访问的重量级架构，类似于 COM 或 CORBA。
当今的 “Web 服务” 架构要么重新发明、要么完全忽略了使 Web 获得成功的每一个特性。

事情并不一定要这样。
我们知道 Web 背后的技术能够驱动有用的远程服务，因为这些服务确实存在，而且我们每天都在使用它们。
我们知道这样的服务可以扩展到巨大的规模，因为它们已经做到了。
想想 Google 搜索引擎。
它本质上不就是一种用于查询海量数据库并返回格式化响应的远程服务吗？
我们通常不会把网站看作是 “服务”，因为那是编程术语，而且网站的最终客户端是人，但它们的本质就是服务。

每一个 Web 应用 ——每一个网站—— 都是一种服务。
你可以为可编程应用程序驾驭这种力量，前提是你与 Web 协同工作，而非与之对抗，前提是你不要将其独特的力量掩埋在层层抽象之下。
是时候把 “Web” 放回到 “Web 服务” 中去了。

使网站便于网络冲浪者使用的那些特性，同样也使 Web 服务 API 便于程序员使用。
为了找到这些服务设计背后的原则，我们只需将面向人类可读网站的原则，转化为当冲浪者是计算机程序时同样有意义的概念。

这正是我们在本书中所做的。
我们自始至终的目标是展示基本 Web 技术的威力（以及在适当情况下，它们的局限性）：HTTP 应用协议、URI 命名标准和 XML 标记语言。
<ins>我们的主题是支撑 Web 的一套原则：表述性状态转移（Representational State Transfer），即 REST。
我们首次为 “RESTful” Web 服务确立了最佳实践。</ins>
我们厘清了混淆和猜测，用具体的建议取代了民间传说和隐性知识。

<ins>我们介绍了面向资源架构（Resource-Oriented Architecture，ROA），这是一套用于设计 RESTful Web 服务的常识性规则。
我们还从客户端角度展示了视图：如何编写程序来使用 RESTful 服务。</ins>
我们的示例包括真实世界的 RESTful 服务，如 Amazon 的 Simple Storage Service（S3）、Atom Publishing Protocol 的各种实现，以及 Google Maps。
我们还选取了一些未能完全达到 RESTful 标准的流行服务，如 del.icio.us 的社会书签 API，并对它们进行改造使其符合 REST 风格。

<a id="web-is-simple"></a>
## Web 是简单的

为什么我们如此痴迷于 Web，以至于认为它可以做任何事情？
也许我们是被炒作冲昏了头脑的妄想者。
Web 无疑是互联网中被炒作得最厉害的部分，尽管事实上 HTTP 并不是最流行的互联网协议。
取决于谁来衡量，全球互联网流量的大部分来自电子邮件（归功于垃圾邮件）或 BitTorrent（归功于版权侵权）。
如果互联网明天就消失，电子邮件将是人们最想念的应用。
那么，为什么是 Web？
是什么让 HTTP ——一种最初为在物理实验室中传递项目笔记而设计的协议—— 也同样适用于分布式互联网应用？

实际上，说 HTTP 是为某种目的而设计的，已经是在给它戴上相当大的高帽了。
HTTP 和 HTML 被称为 “互联网协议中的放屁垫和嗡嗡蜂鸣器，只有当作精心设计的恶作剧才能理解” —— 而这还是出自一位喜欢它们的人之口。¹
HTTP 的第一个版本看起来确实像个玩笑。
以下是客户端与服务器之间的一次示例交互：

¹ Clay Shirky, "In Praise of Evolvable Systems" (http://www.shirky.com/writings/evolve.html)

|客户端请求|服务器响应|
|---|---|
|GET /hello.txt|Hello, world!|

就是这样。你连接服务器，给它一个文档路径，然后服务器将文档内容发送给你。
HTTP 0.9 几乎做不了其他事情。
它看起来像是更复杂的文件传输协议（如 FTP）的一个无特色的翻版。

令人惊讶的是，这在很大程度上就是答案的所在。
我们可以半开玩笑地说，HTTP 之所以特别适合分布式互联网应用，正是因为它几乎没有什么特性可言。
你告诉它你想要什么，它就会给你什么。
这简直是武侠电影剧情的翻版†：<ins>HTTP 的弱点就是它的优势，它的简洁就是它的力量。</ins>

† Legend of The Drunken Protocol（1991）

<ins>在 HTTP 的第一个版本中，巧妙地伪装成缺乏特性的外表下，我们可以看到可寻址性和无状态性：这两个基本的设计决策使 HTTP 相比其竞争对手成为一种进步，并使其可扩展性足以支撑当今的巨型网站。</ins>
HTTP 0.9 中缺失的许多特性后来被证明是不必要的，甚至是适得其反的。
重新添加它们实际上会削弱 Web。
其余大部分特性都在协议的 1.0 和 1.1 修订版中实现了。
对 Web 成功至关重要的另外两项技术 ——URI 和 HTML（以及后来的 XML）—— 在重要意义上也是简单的。

显然，这些 “简单” 的技术足以强大到为我们带来 Web 以及我们在其上使用的应用。
在本书中，我们更进一步，声称万维网是一个简单而灵活的分布式编程环境。
我们还声称知道其中的原因：为我们自己使用而设计的人类 Web，与为软件程序使用而设计的 “可编程 Web” 之间，没有本质区别。
我们认为：如果 Web 对人类来说已经足够好，那么它对机器来说也足够好。
我们只需要做出一些调整。
计算机程序擅长构建和解析复杂的数据结构，但在解释文档方面，它们并不像人类那样灵活。

<a id="big-web-services"></a>
## Big Web Services 并不简单

有许多协议和标准（大多构建于 HTTP 之上）是为构建 Web Services（注意大小写）而设计的。
这些标准统称为 WS-* 栈，包括 WS-Notification、WS-Security、WSDL 和 SOAP。
在本书中，我们用 “Big Web Services” 这个相当温和的贬义术语来统称这一系列技术。

本书不会详细深入介绍这些标准。
<ins>我们相信，你可以在不实现 Big Web Services 的情况下实现 Web 服务：Web 本身就应该是你需要的全部服务。
我们认为 Web 的基本技术已经足够好，可以被视为分布式服务的默认平台。</ins>

某些 WS-* 标准（如 SOAP）可以通过与 REST 及我们面向资源架构兼容的方式使用。
但在实践中，它们通常被用来实现基于 HTTP 的远程过程调用（RPC）应用。
有时 RPC 风格是合适的，有时其他需求会优先于 Web 的优点。
这没问题。

我们不喜欢的是不必要的复杂性。
很多时候，程序员或公司为了一个纯旧 HTTP 就能处理好的工作，却引入了 Big Web Services。
其效果是，HTTP 被降格为承载一个庞大 XML 载荷的传输协议，用于解释 “真正” 发生的事情。
最终得到的服务过于复杂、无法调试，而且除非你的客户端与你的设置完全相同，否则无法工作。

Big Web Services 确实有一个优势：现代工具可以通过一次点击从你的代码中创建 Web 服务，尤其是当你使用 Java 或 C# 开发时。
如果你正在使用这些工具生成基于 WS-* 栈的 RPC 风格 Web 服务，那么 RESTful Web 服务会简单得多，这件事可能对你无关紧要。
工具隐藏了所有复杂性，所以谁在乎呢？
带宽和 CPU 都很便宜。

当你在同质化的团队中工作，为防火墙后的其他类似团队提供服务时，这种态度是可行的。
如果你的团队有足够的话语权，你也许能让人们也在防火墙外按你的规则行事。
但如果你希望你的服务扩展到互联网规模，你就必须处理你从未预料到的客户端，它们使用定制的软件栈对你的服务执行你从未想象过的操作。
你的用户会希望将你的服务与其他你从未听说过的服务集成。
听起来很难？这在 Web 上每天都在发生。

抽象从来都不是完美的。
每一层新的抽象都会带来故障点、互操作性麻烦和可扩展性问题。
新工具可以隐藏复杂性，但无法证明其合理性 —— 而且它们总是在增加复杂性。
让服务能够与 Web 整体协同工作，意味着要关注适应性、可扩展性和可维护性。
简洁性 ——HTTP 0.9 那被轻视的优点—— 是这三者的先决条件
。系统越复杂，当出现问题时就越难修复。

如果你提供 RESTful Web 服务，你可以把复杂性花在额外功能上，或者花在让多个服务交互上。
成功提供服务还意味着成为 Web 的一部分，而不仅仅是 “在” Web 上：使你的信息在管辖优秀网站设计的相同规则下可用。
你离基础 Web 协议越近，这就越容易实现。

<a id="the-story-of-REST"></a>
## REST 的故事

REST 是简单的，但它有明确的定义，并不是以 “它们是一样的” 为借口，将 Web 服务实现为半吊子网站。
不幸的是，到目前为止，主要的 REST 参考文献是 Roy Fielding 在 2000 年博士论文中的第五章，那篇论文作为博士论文来说读起来不错，但留下了大部分现实世界的问题未作回答。‡
那是因为它将 REST 呈现为一种评判架构的方式，而非一种架构本身。
术语 “RESTful” 类似于术语 “面向对象”。
一门语言、一个框架或一个应用可以用面向对象的方式设计，但这并不使其架构成为面向对象架构。

‡ Fielding, Roy Thomas. Architectural Styles and the Design of Network-Based Software Architectures, Doctoral dissertation, University of California, Irvine, 2000 (http://www.ics.uci.edu/~fielding/pubs/dissertation/top.htm)

即使在 C++ 和 Ruby 这样的面向对象语言中，也有可能编写出并非真正面向对象的程序。
抽象的 HTTP 在 REST 的标准上表现得非常好（它理应如此，因为 Fielding 是 HTTP 标准的合著者之一，并且他的博士论文就是为了描述 Web 的架构而写的）。
但真实的网站、Web 应用和 Web 服务常常违背 REST 的原则。
你如何确信自己正确地将这些原则应用到了设计特定 Web 服务的问题上呢？

大多数关于 REST 的其他信息来源都是非正式的：邮件列表、维基和博客（我在附录 A 中列出了一些最好的）。
到目前为止，REST 的最佳实践一直属于民间传说的范畴。
需要的是基于 REST 元架构的具体架构：一套简单的指导方针，用于实现能发挥 Web 潜力的典型服务。
我们在本书中提出了这样一种架构，即面向资源架构（Resource-Oriented Architecture，见 [第 4 章](./ch4.md) ）。
它当然不是唯一可能的高层 RESTful 架构，但我们认为它是设计易于客户端使用的 Web 服务的一个好架构。

<ins>我们编写 ROA 是为了将 Web 服务设计的最佳实践从民间传说的领域中带出来。
我们所写的是一个建议基线。</ins>
如果你过去曾试图理解 REST，我们希望我们的架构能让你确信你所做的事情 “真的” 是 REST。
我们也希望 ROA 能帮助整个社区在提出和编纂最佳实践方面取得更快的进展。
我们希望让程序员能够轻松地创建优雅的、能完成设计目标的、并且参与 Web 而非仅仅寄生在 Web 之上的分布式 Web 应用。

然而，我们知道，仅仅掌握所有这些技术事实是不够的。
我们都曾在一些组织中工作过，那里重大的架构决策并不如我们所愿。
如果从未有机会使用 RESTful 架构，你就无法成功。
除了技术知识，我们还必须给你提供为 RESTful 解决方案辩护的词汇。
我们将 ROA 定位为当今 SOAP+WSDL 服务所使用的 RPC 风格架构的一个简单替代方案。
RPC 架构通过一个复杂的、类似编程语言的接口暴露内部算法，每个服务都不同。
ROA 则通过一个简单的、始终如一的文档处理接口暴露内部数据。
在 [第 10 章](ch10.md) 中，我们比较了这两种架构，并展示了如何为 ROA 进行辩护。

<a id="reuniting-the-webs"></a>
## 重新统一两个 Web

多年来，程序员们一直将网站当作 Web 服务来使用 —— 当然，这是非官方的。§
计算机很难理解为人类消费而设计的网页，但这从未阻止过黑客们使用自动化客户端获取页面并屏幕抓取有趣的部分。
随着时间的推移，这种驱动力被升华为以官方认可的方式暴露网站功能的、对程序员友好的技术 —— RSS、XML-RPC 和 SOAP。
这些技术形成了一个可编程的 Web，它扩展了人类 Web，以方便软件程序的使用。

§ 早期示例见 Jon Udell 于 1996 年在 Byte 杂志上发表的文章 “On-Line Componentware”（http://www.byte.com/art/9611/sec9/art1.htm）。
请注意：“一种强大的临时分布式计算能力自然而然地源于 Web 的架构。” 那是 1996 年的话了，各位。

<ins>本书的最终目标是重新统一可编程 Web 与人类 Web。
我们设想一个统一的互联网络：一个运行在一组服务器上、使用一组协议、并遵守一组设计原则的万维网。
一个无论你是向人类还是向计算机程序提供数据都可以使用的网络。</ins>

互联网和 Web 并非必然存在。
它们之所以来到我们面前，要归功于国防资金的错配、秘密工程项目的开展、更差即更好的工程实践、大科学、天真的自由主义理想、古怪的自由意志主义政治、技术拜物教，以及那些以为自己找到了一条轻松致富之路的程序员和投资者的汗水和资本。

令人惊叹的是，其结果是一个简单、开放（目前如此）、几乎通用的网络应用平台。
这个平台包含了大量人类知识，并支撑着人类努力的大部分领域。
我们认为，是时候认真开始将其规则应用于分布式编程，将这些信息和流程向自动化客户端开放了。
如果你同意，本书将向你展示如何做到这一点。

<a id="what-is-in-this-book"></a>
## 本书内容

<ins>在本书中，我们聚焦于实际问题：如何设计和实现 RESTful Web 服务，以及这些服务的客户端。
我们的次要重点是理论：RESTful 意味着什么，以及为什么 Web 服务应该更加 RESTful 而非相反。</ins>
我们没有涵盖所有内容，但试图覆盖当今的重大主题，并且由于这是同类书籍中的第一本，我们会反复回到核心问题 —— 如何设计 RESTful 服务。

前三章从客户端的角度介绍 Web 服务，并展示 RESTful 服务的特别之处。

**[第 1 章](./ch1.md)，可编程 Web 及其居民**

在本章中，我们一般性地介绍 Web 服务：通过 Web 访问并请求外部服务器提供数据或运行算法的程序。
我们演示了三种常见的 Web 服务架构：RESTful、RPC 风格和 REST-RPC 混合。
我们展示了每种架构的示例 HTTP 请求和响应，以及典型的客户端代码。

**[第 2 章](./ch2.md)，编写 Web 服务客户端**

在本章中，我们向你展示如何使用 HTTP 库和 XML 解析器为现有的 Web 服务编写客户端。
我们介绍了一个流行的 REST-RPC 服务（社交书签网站 del.icio.us 的 Web 服务），并演示了用 Ruby、Python、Java、C# 和 PHP 编写的客户端。
我们还为其他几种语言提供了技术推荐，但未实际展示代码。
JavaScript 和 Ajax 将在第 11 章单独介绍。

**[第 3 章](./ch3.md)，RESTful 服务有何不同？**

我们将 [第 2 章](./ch2.md) 的经验应用于一个纯粹的 RESTful 服务：Amazon 的 Simple Storage Service（S3）。
在构建 S3 客户端的过程中，我们阐述了 REST 的一些重要原则：资源、表述和统一接口。

接下来的六章构成了本书的核心。它们专注于设计和实现你自己的 RESTful 服务。

**[第 4 章](./ch4.md)，面向资源架构**

对 REST 的形式化介绍，不是以抽象形式，而是在 Web 服务特定架构的上下文中。
我们的架构基于四个重要的 REST 概念：资源、它们的名称、它们的表述，以及它们之间的链接。
其服务应通过四个 RESTful 属性来评判：可寻址性、无状态性、连通性和统一接口。

**[第 5 章](./ch5.md)，设计只读的面向资源服务**

我们提出一个将想法或需求集合转化为一组 RESTful 资源的过程。
这些资源是只读的：客户端可以从你的服务获取数据，但不能发送自己的数据。
我们通过设计一个用于提供可导航地图的 Web 服务来说明该过程，该服务受 Google Maps Web 应用启发。

**[第 6 章](./ch6.md)，设计读/写的面向资源服务**

我们将上一章的过程进行扩展，使客户端能够创建、修改和删除资源。
我们通过向地图服务添加两种新资源来演示：用户账户和用户自定义地点。

**[第 7 章](./ch7.md)，服务实现**

我们将一个 RPC 风格的服务（ [第 2 章](./ch2.md) 中我们为其编写客户端的 del.icio.us REST-RPC 混合服务）重塑为纯粹的 RESTful 服务。
然后我们将该服务实现为 Ruby on Rails 应用。
全家乐在其中！

**[第 8 章](./ch8.md)，REST 与 ROA 最佳实践**

在本章中，我们将之前关于服务设计的建议汇集在一起，并补充新的建议。
我们展示 HTTP 的标准特性如何帮助你解决常见问题和进行优化。
我们还针对事务等棘手特性给出了面向资源的设计方案，你可能曾认为这些在 RESTful Web 服务中是无法实现的。

**[第 9 章](./ch9.md)，服务的构建块**

在此我们描述在 REST 三大技术（HTTP、URI 和 XML）之上运行的其他技术。
其中一些技术是用于传递状态的文件格式，如 XHTML 及其微格式。
一些是用于向客户端展示状态杠杆的超媒体格式，如 WADL。
一些是用于构建 RESTful Web 服务的规则集，如 Atom Publishing Protocol。

最后三章涵盖了专业主题，每一章本身都可以写成一本专著：

**[第 10 章](./ch10.md)，面向资源架构 vs. Big Web Services**

我们将我们的架构（以及广义的 REST）与另一主流方案进行比较。
我们认为 RESTful Web 服务比基于 SOAP、WSDL 和 WS-* 栈的服务更简单、更具可扩展性、更易于使用、更契合 Web 的理念，并且能够更好地处理各种各样的客户端。

**[第 11 章](./ch11.md)，Ajax 应用作为 REST 客户端**

在此，我们从 Web 服务的角度解释用于 Web 应用的 Ajax 架构：Ajax 应用就是一个运行在 Web 浏览器内部的 Web 服务客户端。
这使得本章成为 [第 2 章](./ch2.md) 的扩展。
我们展示如何使用 XMLHttpRequest 和标准 JavaScript 库为 RESTful Web 服务编写客户端。

**[第 12 章](./ch12.md)，RESTful 服务框架**

在最后一章中，我们介绍三种流行的、便于实现 RESTful Web 服务的框架：Ruby on Rails、Restlet（适用于 Java）和 Django（适用于 Python）。

我们还附有三个附录，希望你觉得有用：

**[附录 A](./appendix-a.md)，REST 相关资源及 RESTful 资源**

第一部分列出了与 RESTful Web 服务相关的有趣标准、教程和社区。
第二部分列出了一些现有的、公开的 RESTful Web 服务，供你使用和学习。

**[附录 B](./appendix-b.md)，HTTP 响应码 Top 42**

描述每个标准的 HTTP 响应码（外加一个扩展码），并说明在 RESTful Web 服务中何时使用每一个。

**[附录 C](./appendix-c.md)，HTTP 首部 Top Infinity**

对 HTTP 首部做同样的事情。它涵盖了每个标准的 HTTP 首部，以及一些对 Web 服务有用的扩展首部。

<a id="administrative-notes"></a>
## 管理说明

本书有两位作者（Leonard 和 Sam），但在本书的其余部分，我们将把我们的身份合并为单一的叙述者 “我”。
在最后一章（ [第 12 章](./ch12.md) ）中，叙述者 “我” 会变得更加拥挤，因为 Django 和 Restlet 的开发者将加入进来，展示他们的框架如何让你构建 RESTful 服务。

我们假设你是一名称职的程序员，但不要求你特别具备 Web 编程经验。
我们在本书中所说的内容不绑定于任何编程语言，并且我们包含了多种语言的 RESTful 客户端和服务示例代码。
但每当不演示特定框架或语言时，我们使用 Ruby（ http://www.ruby-lang.org /）作为实现语言。
我们选择 Ruby 是因为它简洁且易于阅读，即使对于不熟悉该语言的程序员也是如此（而且因为它与 Sam 的姓氏放在一起既好看又令人困惑）。
Ruby 的标准 Web 框架 Ruby on Rails 也是 RESTful Web 服务的领先实现平台之一。
如果你不熟悉 Ruby，不用担心：我们包含了大量注释来解释 Ruby 特有的惯用法。

本书中的示例程序可以从本书的官方网站（ http://www.oreilly.com/catalog/9780596529260 ）下载。
这包括 [第 7 章](./ch7.md) 中的完整 Rails 应用，以及 [第 12 章](./ch12.md) 中对应的 Restlet 和 Django 应用。
它还包括许多客户端的 Java 实现，这些客户端在书中仅以 Ruby 实现形式出现。
这些客户端程序使用了 Restlet 库，并由 Restlet 开发者 Jerome Louvel 和 Dave Pawson 编写。
如果你更熟悉 Java 而非 Ruby，这些实现可能会帮助你理解代码背后的概念。
最值得注意的是，其中包含了 [第 3 章](./ch3.md) 中 Amazon S3 客户端的完整 Java 实现。
