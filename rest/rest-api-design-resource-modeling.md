# REST API 设计 - 资源建模

作者：Prakash Subramaniam

发布时间：2014年8月14日 [原文](https://www.thoughtworks.com/insights/blog/rest-api-design-resource-modeling)

> “REST 中信息的关键抽象是资源。
任何可以被命名的事物都可以成为资源：一份文档或图像、一种时间性服务（例如 ‘洛杉矶今天的天气’）、其他资源的集合、一个非虚拟对象（例如一个人），等等。
换句话说，任何可能成为作者超文本引用目标的概念，都必须符合资源的定义。
资源是对一组实体的概念映射，而不是在任何一个特定时间点上与该映射对应的实体。”
>
> —— Roy Fielding 的 [博士论文](http://www.ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm#sec_5_2_1_1) 。

资源是任何 REST API 设计的核心。
资源标识符（URI）、资源表示、API 操作（使用各种 HTTP 方法）等，都是围绕资源的概念构建的。
在设计 REST API 时，选择正确的资源并以适当的粒度对资源进行建模非常重要，这样才能使 API 消费者获得所需的功能，使 API 行为正确且具备可维护性。

<ins>一个资源可以是单例（singleton）或集合（collection）。</ins>
例如，“customers” 是一个集合资源，而 “customer” 是一个单例资源（在银行领域中）。
我们可以使用 URN `/customers` 来标识 “customers” 集合资源。
<ins>我们可以使用 URN `/customers/{customerId}` 来标识单个 “customer” 资源。</ins>

<ins>一个资源也可以 “包含” 子集合资源。</ins>
例如，特定 “customer” 的子集合资源 “accounts” 可以使用 URN `/customers/{customerId}/accounts` 来标识（在银行领域中）。
类似地，子集合资源 “accounts” 中的单例资源 “account” 可以这样标识：`customers/{customerId}/accounts/{accountId}`。

<ins>资源选择的起点是分析你的业务领域，并提取与业务需求相关的名词。
更重要的是，应关注 API 消费者的需求，以及如何从 API 消费者交互的角度使 API 具有相关性和实用性。
一旦确定了名词（资源），就可以将 API 的交互建模为针对这些名词的 HTTP 动词。</ins>
当它们不能很好地映射时，我们可以进行近似处理。
例如，在博客领域，我们可以轻松采用 “领域中的名词” 方法，识别出诸如 Post、Tag、Comment  等底层资源。
类似地，在银行领域，我们可以将 Customer、Address、Account、Teller 等名词识别为资源。

<ins>以 “Account” 名词为例，“open”（开户）、“close”（销户）、“deposit”（存款）、“withdraw”（取款）等是动词。
这些动词可以很好地映射到 HTTP 动词。</ins>
例如，API 消费者可以通过使用 HTTP POST 方法创建 “Account” 资源的实例来 “开户”。
类似地，API 消费者可以通过使用 HTTP DELETE 方法 “销户”。
API 消费者可以使用 HTTP “PUT” / “PATCH” / “POST” 方法来 “取款” 或 “存款”。
<ins>[本教程](http://www.restapitutorial.com/lessons/restfulresourcenaming.html) 对基本的资源选择和命名有很好的说明。</ins>

<ins>然而，这种简单的方法在抽象层面上可能有效，但一旦在实践中遇到更复杂的领域，就会失效。</ins>
最终你会遇到常规/明显名词无法涵盖的概念。
以下各节探讨了资源建模的艺术以及以适当粒度建模资源的重要性。

## 细粒度 CRUD 资源 vs. 粗粒度资源

<ins>如果围绕细粒度资源来设计 API，最终会导致消费者应用的 API 调用更加频繁（chattier）。
另一方面，如果基于非常粗粒度的资源来设计 API（设计成能处理所有事情），则可能无法提供足够的变化来满足所有 API 消费者的需求，
并且 API 可能变得过于难以使用和维护。</ins>
为了更好地理解这一点，让我们看一个博客 API 的示例：

博客文章 API（用于创建新的博客文章条目）可以通过两种方式设计。
第一种方法是设计多个 API —— 分别用于博客文章（标题和文本内容）、图片/附件、内容/图片上的标签等。
这种方法使 API 更加细粒度，导致 API 消费者与提供者之间的交互更加频繁。
这种方法要求 API 消费者向服务器发起多次 API 请求。
服务器最终会收到大量 HTTP 请求 —— 可能会影响其为多个 API 消费者提供服务的能力。
第二种方法是设计一个粗粒度的 API 用于发布博客（向 “Posts” 集合资源），该 API 可以包含文章标题、文章内容、图片和标签。
这只需要向 API 提供者发起一次 API 请求，从而减轻了服务器的负载。

相反，API 消费者应用应该能够通过向 “Likes” 子集合资源（`/posts/{post_id}/likes`）发起 API 请求来 “点赞” 一篇博客文章，
或者通过向 “Comments” 子集合资源（`/posts/{post_id}/comments`）发起单独的 API 请求来添加评论，而不必经过博客 “Post”（`/posts/{post_id}`）资源。
如果使用单个粗粒度资源 “Post”（`/posts/{post_id}`）来处理 “点赞” 或 “评论”，而不是使用这些子集合资源，那么无论是 API 提供者还是 API 消费者，工作都会变得更加困难。
使用单个粗粒度 “Post” 资源的方式下，为了添加评论或点赞博客文章，API 提供者必须为 API 消费者提供一种方式来表明该 API 请求是用于添加评论还是点赞文章 —— 可能需要在载荷中指定一个单独的 XML 元素或 JSON 属性来指示载荷类型。
在服务器端，API 提供者需要查找这些提示，并决定该请求是添加评论、点赞文章，还是实际更新博客文章内容等。
对于博客文章评论的更新也是如此。
API 消费者端的代码在使用单个粗粒度资源时也需要处理载荷中的这些变化，从而导致不必要的复杂性。

### 防止业务逻辑迁移到 API 消费者

<ins>如果期望 API 消费者直接操作底层资源（使用细粒度 API），例如 CRUD 操作，将产生两大后果：
首先，API 消费者与 API 提供者之间的交互将非常频繁。
其次，业务逻辑将开始外溢到 API 消费者端。</ins>
在我们之前的博客文章 API 示例中，细粒度 API 可能导致博客文章数据处于不一致状态，并产生维护问题。
例如，博客应用可能有一条业务逻辑规定：为内容添加标签是强制性的，或者只有当文章包含图片时才能添加图片标签等。
为了正确执行，API 消费者需要按正确顺序发起所有必需的 API 请求 —— 一次请求创建包含内容的基础文章，另一次请求上传图片，又一次请求添加标签，等等。
如果 API 消费者发起了创建博客文章的请求，但没有发起添加标签的 API 请求，那么该博客文章就留下了不一致的数据（当标签在应用上下文中是强制性时）。
本质上，这意味着 API 消费者需要在客户端理解并执行业务逻辑（例如确保标签已添加、确保 API 请求的正确顺序等）。

即使 API 消费者清楚理解这一责任，当出现故障时会发生什么？
例如，第一个 API 请求成功执行 —— 创建了博客文章，但第二个添加标签的请求失败了。
这会使数据处于不一致状态。
在这种情况下，必须对 API 消费者应该做什么有一个非常明确的约定？
API 消费者可以重试吗？如果不能，谁来清理数据？等等。
这种责任并不总是被很好地理解，并且很难强制执行。
鉴于业务逻辑可能会发生变化，这种方法会增加维护工作量 —— 尤其是在存在不同类型的 API 消费者（原生移动端、Web 等）且 API 消费者可能未知或数量众多（对于公共 API）的情况下。

<ins>本质上，面向底层 CRUD 的方法将业务逻辑放入客户端代码中，在客户端（API 消费者）和它不应该关心的服务（API）之间创建了紧耦合，并且通过在客户端分解用户意图而丢失了用户意图。
每当业务逻辑发生变化时，所有 API 消费者都必须更改代码并重新部署系统。</ins>
在某些情况下（如原生移动应用）这是不可能做到的，因为客户不会有兴趣频繁更新他们的移动应用。
此外，提供支持频繁交互的底层服务意味着，当服务升级时，API 提供者将被迫支持所有这些底层服务，以保持对 API 消费者的向后兼容性。

<ins>在粗粒度 API 的情况下，业务逻辑保留在 API 提供者端，从而减少了前面讨论的数据不一致问题。
API 消费者甚至可能不知道服务器端应用的业务逻辑，并且在许多情况下也不需要知道。</ins>

注意：当我们谈论防止业务逻辑迁移时，我们谈论的是控制流业务逻辑（例如，按正确顺序发起所有必需的 API 请求），而不是功能性业务逻辑（例如，税款计算）。

## 面向业务流程的粗粒度聚合资源

我们如何将描述业务能力的粗粒度接口与针对命名资源的 HTTP 动词相协调？
如果没有足够的名词怎么办？
如果我的服务涉及多个（两个或更多）资源且这些资源上存在大量操作怎么办？
我们如何确保在众多名词和少量动词下实现粗粒度交互？
我们如何避免低层次、类似 CRUD 的服务交互本质，并使用更贴合业务术语的语言？

让我们重新审视 Roy Fielding 的论文中关于资源的论述：“……任何可能成为作者超文本引用目标的概念，都必须符合资源的定义……”。
<ins>业务能力/流程可以很好地符合资源的定义。
换句话说，对于跨越多个资源的复杂业务流程，我们可以将业务流程本身视为一个资源。</ins>
例如，在银行领域中开设新客户的过程可以建模为一个资源。
<ins>CRUD 只是几乎适用于任何资源的最小业务流程。
这使我们能够将业务流程建模为真正的资源，这些资源本身可以被追踪。</ins>

<ins>区分 REST API 中的资源和领域驱动设计中的领域实体非常重要。
领域驱动设计适用于实现层面（包括 API 实现），而 REST API 中的资源驱动 API 设计和契约。
API 资源的选择不应依赖于底层的领域实现细节。</ins>

### 摆脱 CRUD

<ins>摆脱低层次 CRUD 的方法是创建业务操作或业务流程资源，或者我们可以称之为 “意图” 资源，
  它表达业务/领域层面的 “想要某物的状态” 或 “达成最终结果的过程状态”。
但要做到这一点，你需要确保识别出所有状态的真正所有者。</ins>
在一个四动词（AtomPub 风格）CRUD 的世界里，就好像你允许随机的外部方通过 PUT 和 DELETE 来随意摆弄你的资源状态，仿佛服务只是一个低层数据库。
PUT 将过多的内部领域知识放入客户端。
客户端不应该操作内部表示；它应该是用户意图的来源。
为了更好地理解这一点，让我们考虑一个例子：银行领域中的一位客户想要更改她的地址。这可以通过两种方式完成：

1. <ins>在第一种方法中，围绕 “Customer” 资源构建的 CRUD API 可用于直接更新客户的地址。</ins>
也就是说，要更新现有客户的地址，可以向 “Customer” 资源（或 “Address” 资源，如果存在的话）发起 HTTP PUT 请求。
如果我们采用这种 CRUD API 设计，那么具有业务意义的事件数据，例如地址何时被更改、谁更改的（由客户还是银行工作人员更改）、更改了什么、变更历史等，将会丢失。
换句话说，我们将丢失可能在后期有用的业务相关事件数据。
此外，使用这种方法，客户端代码需要具备 “Customer” 领域的知识（包括 Customer 的属性等）。
如果 “Customer” 的领域定义发生变化，即使客户端不使用受影响的属性，客户端代码也可能需要立即更新。
这使得客户端代码更加脆弱。

2. <ins>另一种解决 CRUD 问题的方法是将 API 设计为围绕基于业务流程和领域事件的资源。</ins>
例如，要更新现有银行客户的地址，可以向 “ChangeOfAddress” 资源发起 POST 请求。
这个 “ChangeOfAddress” 资源可以捕获完整的地址变更事件数据（例如谁更改的、更改了什么等）。
这种方法在以下情况下特别有用：具有业务意义的事件数据要么对即时业务需求有用
（例如作为后台批处理的一部分执行地址变更的长时间运行异步进程），要么从长期角度来看有用（例如用于审计目的的分析或展示历史变更）。
即使当前没有即时或可预见的业务需求来保留事件数据，
仍然可以考虑（在成本效益分析之后）向 “意图” 资源 “ChangeOfAddress” 发起 POST 请求，以避免客户端了解内部领域知识。
这使客户端代码较少受到 “Customer” 领域定义变更的影响。
当业务不需要事件数据时，可以选择不持久化 “ChangeOfResource” 事件数据。
我们可以选择直接应用地址变更，而不存储 “ChangeOfResource” 事件数据。

摆脱 CRUD 意味着确保托管资源的服务是唯一能够直接更改其状态的代理。这可能意味着根据谁真正拥有特定状态位，将资源拆分为更多资源。然后每个人都只 POST 他们的“意图”，或发布他们自己拥有的资源状态（也许用于轮询）。

### 名词 vs. 动词

关于 [名词和动词的争论永无止境](http://opinionator.blogs.nytimes.com/2013/03/30/those-irritating-verbs-as-nouns/?_php=true&_type=blogs&_r=0) 。
让我们考虑一个例子 —— 在银行中开设一个新客户。
这个业务流程可以被称为 EnrollCustomer，或者 CustomerEnrollment。
在这种情况下，CustomerEnrollment 这个术语听起来更好，因为它更像名词。
它的可读性也更好：“客户 xxxx 的 CustomerEnrollment 编号 2543”。
它还具有保持业务相关、可独立查询和可演化状态的额外好处。
这种资源在业务上的等价物是我们在业务中可能填写的典型表单，它会触发一个业务流程。
思考典型业务职能中纸质表单的类比，有助于我们以与技术无关的方式专注于业务需求，正如 Dan North 在他的文章 [A Classic Introduction to SOA](http://dannorth.net/classic-soa/) 中所讨论的那样。

典型的客户注册可能涉及向外部机构发送 KYC（了解你的客户）请求、注册客户、创建账户、打印借记卡、发送邮件等步骤。
这些步骤可能重叠，且该过程将是长时间运行的，并存在多个故障点。
这可能是一个更具体的例子，我们可以将流程建模为资源。
像这样的流程将导致创建/更新多个底层资源，如 Customer、Account、KYCRequest 等。
对此类流程发起 GET 请求是有意义的，因为我们会返回流程当前的状态。

如果我们没有将客户注册流程建模为资源，API 消费者就必须 “知道” 客户注册所涉及的业务逻辑 —— 一个请求用于创建客户资源，一个请求用于 KYC 请求，一个请求用于打印卡请求，等等。
本质上，所有 API 消费者都必须在其代码中理解和执行业务逻辑。
如果 API 消费者遗漏了某个步骤，如 “打印卡请求”，那么注册就不完整，客户也会因为未收到卡而感到不满。
这显然是容易出错的。

<ins>也许这可以作为一个经验法则：该流程是否需要自身状态？
业务方是否会询问有关此流程的问题，例如 —— 流程的状态是什么？
如果失败了，为什么？谁发起的，从哪里发起的？发生了多少次？
流程失败的最常见原因是什么，发生在哪一步？
平均、最小、最大耗时是多少？
对于大多数非平凡的流程，业务方都想要这些问题的答案。
而这样的流程应该被建模为独立的资源。</ins>

这就是基于名词的方法开始变得受限的地方。
业务流程当然是行为，业务语言通常侧重于动词。
但它们对业务来说也是 “事物”。
鉴于我们可以将大多数动词转换为名词，这种区别开始变得模糊。
实际上，这取决于你如何看待它 —— 任何名词都可以动词化，反之亦然。
问题在于你想用它做什么。
你可能会说 “enroll Sue” 而不是 “make an enrollment for Sue”，但当谈论一个长时间运行的流程时，“Sue 的 enrollment 进行得怎么样了？”
这种说法更有意义。
<ins>这就是为什么对于任何持续时间足够长、以至于我们想知道其进展的流程，使用名词看起来更好的原因。</ins>

### 抽象概念的具体化（Reification）

Reification 的词典含义是 “使（某抽象事物）更具体或更真实”。
换句话说，具体化使某抽象事物（例如一个概念）变得更加具体/真实。

<ins>采用专注于业务能力的粗粒度方法时，我们将更多具体化的抽象概念建模为资源。
具体化资源的一个好例子是我们之前讨论的 CustomerEnrollment。
我们不使用 Customer 资源，而是使用一个相当于 “注册客户请求” 的资源。</ins>
让我们考虑来自同一银行领域的另外两个例子：

1. **银行账户现金存款：**
客户将钱存入其账户。
这涉及执行业务规则（例如：检查存款金额是否在允许限额内）、更新客户账户余额、添加交易记录、向客户手机或邮箱发送通知等操作。
虽然从技术上讲我们可以使用 Account 资源，但更好的选择是将业务能力/抽象概念 ——称为交易（Transaction）或存款（Money Deposit）—— 具体化，并创建一个新的资源 “Transaction”。

2. **两个银行账户之间的转账：**
客户将资金从一个银行账户转移到另一个银行账户。
这涉及更新两个底层资源（ “from” 账户和 “to” 账户），还涉及业务验证、创建交易记录、发送通知等。
如果 “to” 账户在另一家银行，转账可能需要通过中央银行或外部机构进行。
这里的抽象概念是 “转账” 交易。
要进行转账，我们可以向 `/transactions` 或 `/accounts/343/transactions` 发起 POST 请求，创建一个新的 “Transaction”（或 “MoneyTransfer” ）资源。
需要注意的是，创建新的 “Transaction” 资源并不自动意味着为 “Transaction” 创建数据库表。
API 设计应独立于 API 实现和数据持久化方面的底层设计考量。

在这两种情况下，我们使用的不是 Account 资源，而是一个相当于存款或转账命令的资源 —— Transaction 资源（类似于前面提到的 CustomerEnrollment）。
这是一个好主意，特别是当这可能是一个长时间运行的流程时（例如：转账可能在完成之前涉及多个阶段）。
当然，这并不排除你同时拥有 Account 资源 —— 它可能作为 “Transaction” 被处理的结果而更新。
此外，也可能存在向 “Account” 资源发起 API 请求的合理用例。
例如，要获取账户摘要/余额信息，API 请求应该向 “Account” 资源发起。

<ins>思维方式的一个关键转变是理解存在一个无限的 URI 空间可供你利用。
同时，最好避免资源过度膨胀，以免给 API 设计带来混淆。
只要资源存在真正的需求，且具有清晰的用户/消费者 “意图”，并适合整体 API 设计，URI 空间就可以扩展。
具体化资源可以用作你服务的事务边界。</ins>

<ins>还有另一个方面 —— 你组织服务器行为的方式与 API 的工作方式是分开的。</ins>
我们已经讨论了为存款设置 “Transaction” 资源，并且这样做有很多充分的理由。
但存款由对 Account 资源的 POST 请求处理也完全有效。
处理 Account 的服务随后负责协调变更并创建 Transaction 资源、Notification 资源等（这些可能在同一个服务中，也可能在不同的服务中）。
客户端没有理由必须自己完成所有这些工作。
API 提供者需要选择一个服务来处理协调责任。
在我们的例子中，如果选择那条路径，这个责任就交给处理 Transaction 资源的服务。
这与内存中对象设计是一样的。
<ins>当客户端需要协调一组对象的变更时，一种常见的方法是选择一个对象来处理协调。</ins>

## 无 PUT 的 REST 与 CQRS

HTTP 动词 [PUT](http://tools.ietf.org/html/rfc2616#section-9.6) 可被 API 消费者用于幂等的资源更新（或在某些情况下用于资源创建）。
然而，将 PUT 用于复杂的状态转换可能会导致同步的、低层次的 CRUD 操作。
它通常还会丢弃大量在更新触发时可用的信息 —— 触发此次更新的真正业务领域事件是什么？
<ins>采用 [无 PUT 的 REST](http://www.thoughtworks.com/radar/#/techniques/rest-without-put) 方法，其理念是强制消费者 POST 新的 “名词化” 请求资源。
如前所述，更改客户的邮寄地址是向新的 “ChangeOfAddress” 资源发起 POST 请求，而不是对具有不同邮寄地址字段值的 “Customer” 资源进行 PUT 操作。</ins>
后者意味着我们可以降低 API 消费者对原子一致性的期望 —— 如果我们 POST 了一个 “ChangeOfAddress”，然后 GET 引用的 Customer，会更清楚地表明更新可能尚未处理完成，旧状态可能仍然存在（异步 API）。
GET 以 “201” 响应创建的 “ChangeOfAddress” 资源将返回与事件相关的详细信息，以及指向已更新或将要更新资源的链接。

<ins>其理念是我们不再 PUT 实体的 “新” 状态，而是将我们的变更提升为头等公民名词（而非动词），并对它们进行 POST。</ins>
这也可以很好地与事件溯源 [Event Sourcing](http://martinfowler.com/eaaDev/EventSourcing.html) 配合 ——事件是头等公民名词的典型示例，并帮助我们摆脱将它们视为 “变更器” 的思维定势—— 它们是领域相关的事件，而不仅仅是对某些对象状态的更改。

<ins>无 PUT 的 REST 还有一个附带好处，即分离命令和查询接口（ [CQRS](http://martinfowler.com/bliki/CQRS.html) ），并迫使消费者允许最终一致性。</ins>
我们将命令实体 POST 到一个端点（CQRS 中的 “C” ），并从另一个端点 GET 一个模型实体（ “Q” ）。
进一步扩展，设想一个管理 Customer 的 API。
当我们想要查看 Customer 的当前状态时，我们 GET Customer。
当我们想要更改 Customer 时，我们实际上 POST 一个 “CustomerChange” 资源。
当我们通过 GET 查看客户时，这可能只是从与该 Customer 相关的一系列变更事件构建出的当前状态投影。
或者，也可能是 “CustomerChange” 资源实际改变了 DB 中 Customer 的状态，在这种情况下 GET 就是直接检索 DB。
在后一种情况下，我们可能会销毁一些数据（与变更事件关联的），并可能丢失变更背后的意图（取决于我们是否选择持久化事件数据）。
因此，无 PUT 的 REST 并不意味着我们 *会* 自动获得 CQRS，但如果我们想要的话，它确实让实现变得非常容易。

<ins>总而言之，如前所述，PUT 将过多的内部领域知识放入客户端。
客户端不应该操作内部表示；它应该是用户意图的来源。
另一方面，PUT 在许多简单情况下更容易实现，并且在库中有良好的支持。
因此，决策需要在使用 PUT 的简单性与事件数据对业务的相关性之间取得平衡。</ins>

## 来自公共 GitHub API 的示例

[GitHub API](https://developer.github.com/v3) 是公共领域中设计合理、资源粒度得当的 API 的一个很好的例子。
例如，[创建 fork](https://developer.github.com/v3/repos/forks/#create-a-fork) 是一个异步操作。
GitHub 支持具体化的 "Forks" 子集合资源，可用于列出现有 fork 或创建新 fork。
使用 [merges](https://developer.github.com/v3/repos/merging/) 子集合资源执行代码 "merge" 是 "merge" 概念及其底层合并操作具体化的另一个例子。
另一方面，GitHub 也支持许多底层资源，如 Tag。
<ins>大多数现实世界的 API 都需要同时具备粗粒度聚合资源和底层 "领域中的名词" 资源。</ins>

## **结语**

与所有其他事物一样，没有一种方法适用于所有情况。
如前所述，有些情况下，围绕底层资源构建的 API 可能就足够了。
例如，要获取银行账户余额信息，围绕 “Account” 资源构建的 API 就足够好了。
另一方面，如果需求是进行转账或获取银行对账单，则 API 需要围绕粗粒度的 “Transactions” 资源来构建。
同样，在许多情况下，对底层领域资源使用 HTTP PUT 可能是合适且简单的。
还有一些情况，状态转换复杂且长时间运行，或者事件数据具有业务相关性，值得通过向用户/消费者 “意图” 资源发起 HTTP POST 来捕获。
资源建模需要基于业务需求、技术考量（清晰的设计、可维护性等）以及前面讨论的各种方法的成本效益分析进行仔细权衡，以便 API 设计能够带来最佳的 API 消费者交互体验。
