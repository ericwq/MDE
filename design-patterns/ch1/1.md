# 1.1 什么是设计模式？

Christopher Alexander 说：“每个模式都描述了一个在我们的环境中反复出现的问题，然后描述了该问题解决方案的核心，使你能够一次又一次地使用这个解决方案，而不必以同样的方式做两次” [AIS+77, 第 x 页](../biblio.md#ais77)。
尽管 Alexander 谈论的是建筑和城镇中的模式，他所说的对于面向对象设计模式同样成立。
我们的解决方案用对象和接口来表达，而不是墙和门，但两类模式的核心都是特定语境中问题的解决方案。

一般来说，一个模式有四个基本要素：

1. 模式名称是一个手柄，我们可以用一两个词来描述一个设计问题、它的解决方案和结果。
给模式命名立即增加了我们的设计词汇。
它让我们在更高的抽象层次上设计。
拥有模式的词汇让我们能与同事、在文档中，甚至对自己谈论它们。
它让思考设计、交流设计及其取舍变得更容易。
找到好名称一直是开发我们目录最难的部分之一。

2. 问题描述何时应用该模式。
它解释问题和它的语境。
它可能描述特定的设计问题，例如如何把算法表示为对象。
它可能描述那些表明设计不灵活的类或对象结构。
有时问题会包括一份在应用该模式有意义之前必须满足的条件列表。

3. 解决方案描述构成设计的元素、它们的关系、职责和协作。
解决方案不描述某个特定的具体设计或实现，因为模式就像一个可以应用于许多不同情况的模板。
相反，模式提供对设计问题的抽象描述，以及元素的某种一般安排（在我们的情况中是类和对象）如何解决它。

4. 结果是应用该模式的结果和取舍。
尽管我们在描述设计决策时常常不提及结果，但它们对于评估设计替代方案以及理解应用模式的成本和收益至关重要。

软件的结果通常涉及空间和时间的取舍。
它们也可能涉及语言和实现问题。
由于复用往往是面向对象设计中的一个因素，模式的结果包括它对系统灵活性、可扩展性或可移植性的影响。
明确列出这些结果有助于你理解和评估它们。

视角会影响一个人对什么是模式、什么不是模式的解释。
一个人的模式可以是另一个人的原始构建块。
在本书中，我们聚焦于某一抽象层次上的模式。
设计模式不是关于诸如链表和哈希表这样可以在类中编码并原样复用的设计。
它们也不是针对整个应用程序或子系统的复杂的、领域特定的设计。
本书中的设计模式是 *对相互通信的对象和类的描述，这些对象和类经过定制，以在特定语境中解决一般设计问题。*

设计模式命名、抽象并识别一个常见设计结构的关键方面，这些方面使它有助于创建可复用的面向对象设计。
设计模式识别参与的类和实例、它们的角色和协作，以及职责的分配。
每个设计模式都聚焦于一个特定的面向对象设计问题或议题。
它描述何时适用、在其他设计约束下是否可以应用，以及使用它的结果和取舍。
由于我们最终必须实现我们的设计，设计模式还提供示例 C++ 和（有时）Smalltalk 代码来说明实现。

尽管设计模式描述的是面向对象设计，它们基于的是已经在像 Smalltalk 和 C++ 这样的主流面向对象编程语言中实现过的实用解决方案，
而不是过程式语言（Pascal、C、Ada）或更动态的面向对象语言（CLOS、Dylan、Self）。
我们选择 Smalltalk 和 C++ 是出于务实的原因：我们的日常经验在这些语言中，而且它们越来越流行。

编程语言的选择很重要，因为它影响一个人的视角。
我们的模式假设 Smalltalk/C++ 级别的语言特性，而这个选择决定了什么可以容易地实现、什么不能。
如果我们假设过程式语言，我们可能会收录名为 “继承”、“封装” 和 “多态” 的设计模式。
同样，我们的一些模式由不太常见的面向对象语言直接支持。
例如，CLOS 有多方法，这减少了对 [Visitor (331)](../ch5/11.md) 这类模式的需求。
事实上，Smalltalk 和 C++ 之间的差异足够大，意味着有些模式在一种语言中比在另一种语言中更容易表达。
（例子见 [Iterator (257)](../ch5/4.md)。）
