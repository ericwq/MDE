# 创建型模式讨论

有两种常见方式可以按照系统创建的对象类来参数化系统。
一种方式是子类化创建对象的类；这对应于使用 [Factory Method (107)](3.md) 模式。
这种方法的主要缺点是，它可能要求仅仅为了改变产品类而创建一个新的子类。
这类变化可能级联发生。
例如，当产品创建者本身也是由工厂方法创建时，那么你还必须重写它的创建者。

另一种参数化系统的方式更依赖对象组合：定义一个负责知道产品对象类的对象，并把它作为系统的一个参数。
这是 [Abstract Factory (87)](1.md)、[Builder (97)](2.md) 和 [Prototype (117)](4.md) 模式的一个关键方面。
这三者都涉及创建一个新的 “工厂对象”，其职责是创建产品对象。
Abstract Factory 让工厂对象生产多个类的对象。
Builder 让工厂对象使用相应复杂的协议逐步构建一个复杂产品。
Prototype 让工厂对象通过复制一个原型对象来构建产品。
在这种情况下，工厂对象和原型是同一个对象，因为原型负责返回产品。

考虑 Prototype 模式中描述的绘图编辑器框架。
有几种方式可以按照产品类来参数化 `GraphicTool`：

- 通过应用 Factory Method 模式，将为面板中每个 `Graphic` 子类创建一个 `GraphicTool` 子类。
`GraphicTool` 将有一个 `NewGraphic` 操作，由每个 `GraphicTool` 子类重定义。

- 通过应用 Abstract Factory 模式，将有一个 `GraphicsFactory` 类层次结构，每个 `Graphic` 子类对应一个。
在这种情况下，每个工厂只创建一个产品：`CircleFactory` 将创建 `Circle`，`LineFactory` 将创建 `Line`，依此类推。
`GraphicTool` 将用一个用于创建适当种类 `Graphic` 的工厂来参数化。

- 通过应用 Prototype 模式，每个 `Graphic` 子类将实现 `Clone` 操作，而 `GraphicTool` 将用它创建的 `Graphic` 的原型来参数化。

哪种模式最好取决于许多因素。
在我们的绘图编辑器框架中，Factory Method 模式起初最容易使用。
定义一个 `GraphicTool` 的新子类很容易，而且 `GraphicTool` 的实例只在定义面板时被创建。
这里的主要缺点是 `GraphicTool` 子类会激增，而且它们没有一个做很多事。

Abstract Factory 没有提供多大改进，因为它需要一个同样庞大的 `GraphicsFactory` 类层次结构。
只有当已经存在一个 `GraphicsFactory` 类层次结构时 ——要么因为编译器自动提供它（如 Smalltalk 或 Objective C 中那样），要么因为系统的另一部分需要它—— Abstract Factory 才会比 Factory Method 更可取。

总体而言，Prototype 模式对于绘图编辑器框架来说可能是最好的，因为它只要求在每一个 `Graphic` 类上实现一个 `Clone` 操作。
这减少了类的数量，而且 `Clone` 可以用于纯粹实例化之外的目的（例如，一个 Duplicate 菜单操作）。

Factory Method 让设计更可定制，而且只是稍微复杂一点。
其他设计模式需要新类，而 Factory Method 只需要一个新操作。
人们常常把 Factory Method 用作创建对象的标准方式，但当被实例化的类从不改变时，
或者当实例化发生在一个子类可以轻松重写的操作中时（例如一个初始化操作），就没有必要使用它。

使用 Abstract Factory、Prototype 或 Builder 的设计，比使用 Factory Method 的设计更灵活，但它们也更复杂。
<ins>通常，设计一开始使用 Factory Method，随着设计者发现哪里需要更多灵活性，会朝着其他创建型模式演化。
了解许多设计模式，能让你在权衡一个设计标准与另一个设计标准时有更多选择。</ins>
