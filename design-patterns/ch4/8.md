# 结构型模式讨论

你可能已经注意到结构型模式之间存在相似之处，尤其是在参与者与协作方式上。
出现这种情况，大概率是因为结构型模式依赖同一小部分语言机制来组织代码与对象：
基于类的模式使用单继承与多继承，基于对象的模式使用对象组合。
但这些相似表象掩盖了各模式之间不同的设计意图。
本节将对比多组结构型模式，帮助理解它们各自的优势。

## Adapter 与 Bridge

[Adapter (139)](1.md) 和 [Bridge (151)](2.md) 模式具备一些共同特征。
二者都通过引入对另一个对象的间接引用提升灵活性，都通过非目标对象自身的接口向该对象转发请求。

两种模式的核心区别在于设计意图。
[Adapter (139)](1.md) 侧重于解决两个已有接口之间的不兼容问题。
它不关注这些接口的实现方式，也不考虑接口如何独立演化。
它用于让两个独立设计的类协同工作，而无需重新实现任意一方。
而 [Bridge (151)](2.md) 用于连接抽象层及其（可能数量众多的）实现层。
它向 Client 提供稳定接口，同时允许变更实现该抽象的类。
它还能在系统演进时支持新增实现。

由于上述差异，[Adapter (139)](1.md) 和 [Bridge (151)](2.md) 通常在软件生命周期的不同阶段使用。
当你发现两个不兼容的类需要协同工作时，往往就需要适配器，目的一般是避免代码重复。
这种耦合是预先未预料到的。
与之相反，桥接模式的使用者在一开始就清楚，一个抽象需要多种实现，并且抽象与实现二者可以独立演化。
[Adapter (139)](1.md) 模式是在设计完成后让已有组件协同工作；
而 [Bridge (151)](2.md) 则是在设计阶段就为组件的协同工作做好准备。
这并不代表 [Adapter (139)](1.md) 不如 [Bridge (151)](2.md)；两种模式只是解决不同的问题。

你可以把 facade（参见 [Facade (185)](5.md) ）看作一组对象的适配器。
但这种理解忽略了一个关键点：facade 会定义全新接口，而适配器复用已有旧接口。
记住，适配器的作用是让两个已存在的接口协同工作，而不是定义一套全新接口。

## Composite 与 Decorator 与 Proxy

[Composite (163)](3.md) 与 [Decorator (175)](4.md) 的结构图十分相似，这反映出二者都依靠递归组合来组织数量可无限扩展的对象。
这种共性可能会让你误以为 decorator 对象是一种退化的 composite，但这误解了 [Decorator (175)](4.md) 模式的核心。
二者的相似仅停留在递归组合层面，根源依然是设计意图不同。

[Decorator (175)](4.md) 的设计目标是在不创建子类的前提下为对象新增职责。
它可以避免为静态覆盖所有职责组合而产生的子类爆炸问题。
[Composite (163)](3.md) 的设计意图则有所不同。
它侧重于对类进行结构化，使得大量相关对象能够被统一处理，多个对象可以被当作单个对象看待。
它关注的不是功能装饰，而是对象的层级表达。

这些设计意图各不相同，但能够互补。
因此，[Composite (163)](3.md) 与 [Decorator (175)](4.md) 模式经常搭配使用。
二者所形成的设计风格，都允许仅通过组装对象来构建应用，无需定义任何新类。
系统中会存在一个抽象类，它的部分子类是 composites，部分是 decorators，还有一部分用于实现系统的基础构建单元。
在这种场景下，composites 和 decorators 会拥有同一个接口。
站在 [Decorator (175)](4.md) 模式的视角，一个 composite 就是一个 `ConcreteComponent`。
站在 [Composite (163)](3.md) 模式的视角，一个 decorator 就是一个 `Leaf`。
当然，二者并非必须一起使用；正如前面所述，它们的设计意图差异很大。

另一个和 [Decorator (175)](4.md) 结构相似的模式是 [Proxy (207)](7.md)。
两种模式都描述了如何为对象引入一层间接访问，
并且 proxy 对象与 decorator 对象的实现中，都会保存另一个对象的引用，并将请求转发给该对象。
但二者的设计目的依然不同。

和 [Decorator (175)](4.md) 一样，[Proxy (207)](7.md) 模式组合一个对象，并向 Client 提供完全相同的接口。
但与 [Decorator (175)](4.md) 不同，[Proxy (207)](7.md) 模式并不负责动态增加或移除属性，也不是为递归组合而设计。
它的意图是：当直接访问主体对象并不方便或不适合时（例如主体运行在远程机器、访问受限或者具备持久化特性），为主体提供一个替身。

在 [Proxy (207)](7.md) 模式中，主体 (subject) 定义核心功能，proxy 负责提供（或拒绝）对主体的访问。
而在 [Decorator (175)](4.md) 中，component 只提供一部分功能，剩余功能由一个或多个 decorator 补充。[Decorator (175)](4.md) 解决的场景是：对象的全部功能无法在编译期确定，或者很难在编译期确定。
这种可无限扩展的特性，使得递归组合成为 [Decorator (175)](4.md) 的核心组成。
[Proxy (207)](7.md) 则并非如此，它只关注一种关系 —— proxy 和它的主体之间的关系，这种关系可以静态定义。

这些差异十分关键，因为它们对应面向对象设计里反复出现的特定问题的解决方案。
但这不代表这些模式不能组合。
你可以设想一个 proxy-decorator，用来为 proxy 附加功能；或是一个 decorator-proxy，用来装饰远程对象。
虽然这类混合模式可能有用（我们手边暂无真实案例），但它们都可以拆解为已知的独立有效模式。
